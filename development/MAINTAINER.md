# Cost Guard — maintainer rules

## Authority and change model

The exact Cost Guard filesystem at the start of an implementation request is authoritative, including intentional uncommitted work. Git/index/history are diagnostics and reference, never an automatic restore oracle. User-supplied checkpoint/package handoffs are source of truth when explicitly supplied. Do not reset, reconstruct or overwrite package-owned files from Git unless the user explicitly requests it.

Implement the requested semantic change with the smallest safe mechanism. Do not silently broaden scope. For non-trivial work, establish an affected-file baseline or isolated scratch copy when practical; verify the authoritative files still match that baseline before applying a completed delta. If they changed concurrently, stop and reconcile.

`development/MAINTAINER.md` is user-governed. Do not edit this file as a side effect of an ordinary feature, fix, refactor, documentation or packaging request. Change it only when the user explicitly requests a maintainer-rule change. If a task appears to require a maintainer-rule update but the user did not request one, ask the user before editing this file.

## Product invariants

- Cost Guard v78 is Python 3.11+ and standard-library-first. A third-party runtime dependency requires a demonstrated blocker and explicit architectural approval.
- `cost-guard.py` is the stable thin executable entry point. Business logic belongs below `src/` in bounded modules.
- Retained presentation behavior is contractual: ordinary prompt labels use `#N`, completed compactions use `/compact`, prompt/monthly totals retain the separator-before-Total shape, Watch keeps its fixed dashboard geometry/cadence, and prompt metric/mix colors remain independently meaningful rather than being collapsed into one whole-cell severity.
- Monetary table cells never use `~` to encode pricing-fallback provenance. Show one short report warning only when fallback actually occurred; README owns the generic explanation. `~` remains valid for inherently approximate diagnostics such as Ictx/model-repricing labels.
- Zero-config is a product principle for standard supported OpenCode installations. `config/user-config.jsonc` is optional and never shipped.
- OpenCode data is read-only. Cost Guard must never repair or mutate OpenCode persistence/migrations.
- Runtime state belongs under disposable `cache/`; no user-owned history may exist only there.
- Cache schema generations use new SQLite filenames rather than in-place migration of a live prior generation.
- Watch and one-shot reports share one analysis truth. Performance optimizations must not create a second billing/causal implementation.
- Usage, cost/valuation and quota/limits are independent semantic concepts. Do not collapse them into one scalar merely because a current provider permits conversion.
- Source/provider-specific data is normalized before analysis. Core logic must not branch on raw OpenCode generation for ordinary semantics.
- Configuration is validated before OpenCode/provider/cache runtime work. Omitted user settings inherit defaults; explicit JSON nulls remain overrides; arbitrary config/secret values must not be echoed in errors.
- `config/user-config.jsonc` is optional and MUST NOT be auto-created. Legacy compatibility normalization must happen before strict shape validation.

## Architecture ownership

`development/ARCHITECTURE.md` is the architecture authority. In short:

- `src/domain/` owns provider-neutral domain/capability contracts and imports no concrete integration/presentation layer.
- `src/sources/` owns OpenCode/session acquisition and normalization. OpenCode V1 schema/path/SQLite details stay inside the V1 source boundary; V1 reads are process-free, read-only/query-only, and its cheap tree-revision probe must not hydrate/parse message/part JSON merely to decide whether a tree changed.
- Canonical messages/parts are allowed because later source-independent compaction/tool/context semantics require that structure; core must still never consume raw V1 SQLite rows/JSON.
- `src/accounts/` owns account/quota acquisition.
- `src/pricing/` owns pricing/model metadata acquisition.
- `src/analysis/` owns source-independent billing/causal/context/comparison logic and must not import concrete source/provider implementations.
- `src/cache/` owns disposable persisted state and cross-process cache coordination.
- `src/reports/` owns one-shot use-case orchestration and source/provider-neutral report projections; it may depend on abstract integration contracts but never concrete OpenCode/GitHub implementations or presentation.
- Cache connections are short-lived and explicitly closed; do not rely on Python garbage collection for SQLite handle cleanup. Breaking cache schema changes create a new generation filename rather than in-place migration.
- `src/watch/` owns Watch lifecycle/orchestration, not source-specific storage semantics. It may use abstract source/report contracts but never concrete OpenCode/GitHub implementations. V1 change-gating stays payload-free/process-free; V2 events are hints and any stream uncertainty requires authoritative resync. Source changes must not cause unbounded account-provider refreshes.
- `src/presentation/` owns user-visible terminal rendering/progress of already-derived projections and must not query concrete sources/providers or recompute analysis/provider semantics.
- `src/bootstrap.py` is the composition root and may wire concrete implementations together.

Do not create generic dumping grounds such as `helpers.py` or `utils.py` for unrelated concepts. Split by responsibility when a module approaches its design budget; never split solely into meaningless `part2.py` files to satisfy a cap.

## File budgets and anti-bloat policy

`development/tools/validate_package.py` is release-blocking. `development/file-budgets.json` is the machine-readable authority for design warnings and hard caps. Every packaged file receives at least a universal cap; important classes have stricter limits. Never raise a hard cap merely to make validation pass. Refactor/consolidate first; a cap change requires an explicit architectural decision.

The entry point has the strictest budget because it must remain a bootstrap. README, version history and maintainer/architecture prose are bounded so AI-driven append-only maintenance cannot grow them indefinitely.

## Implementation workflow

For non-trivial changes:

1. Read the task/FR, this file and relevant architecture/current code/tests.
2. Establish the current filesystem baseline for affected files.
3. Identify requested behavior and protected neighboring behavior before editing.
4. Add/strengthen focused characterization/regression tests where practical.
5. Work in bounded todos: one clear question/change, expected scope, observable completion condition and focused verification.
6. Gate meaningful stages with focused tests/static checks; do not defer all verification to the end.
7. Review the complete change against the FR-start filesystem baseline and architecture boundaries.
8. Run the appropriate verification tier: Quick + distributable-view validator in a constrained hosted harness; Full + validator/Diagnostics on an unrestricted local machine.
9. Update current docs/version history only for behavior that actually exists.
10. Package only after the available tier is green; never claim a Full/local gate that did not run and never commit/push automatically.

Unexpected findings do not silently expand scope. Close the current todo, record evidence, then add/replan follow-up work. Repeated patch failures or long-running unfocused todos are planning failures: reread current files and decompose instead of retrying by inertia.

## Testing policy

Tests under `development/tests/` are deterministic, local and standard-library-only unless an explicit dependency decision changes that rule. Prefer real production logic with synthetic inputs over extensive mocks. Never require personal OpenCode databases, auth files, credentials, network access or long sleeps for either automated test tier. Source adapters use synthetic V1 SQLite and a local fake V2 HTTP/event service.

There are deliberately two verification tiers:

- **Quick / constrained AI:** `python development/tools/run_tests.py --suite quick`. This is the default. Test files run as isolated subprocesses with hard per-file timeouts and bounded concurrency. It covers source normalization, analysis, report/Watch presentation and current regressions while excluding expensive package-mutation, builder and large benchmark checks. Use it in hosted ChatGPT/Anthropic/Google-style sandboxes or any environment with uncertain command wall-time. Pair it with `python development/tools/validate_package.py --working-tree`.
- **Full / local unrestricted:** `python development/tools/run_tests.py --suite full`. This adds performance/parity, public diagnostics, release hardening, validator-negative and release-builder regression work. Prefer running the normal Diagnostics launcher on a real workstation because Diagnostics runs this Full tier plus distributable-view validation before collecting environment evidence, shows an interactive progress bar, and still creates a bundle when validation fails. `--skip-validation` exists only for recursive tests/emergency collection.

Use focused `--profile`/`--pattern` runs while iterating. A hosted model should not start Full merely to appear thorough; bounded relevant tests plus Quick are the intended contract. A local coding agent working directly in an extracted package should run Full (or Diagnostics) before handing off when time/resources allow. Before removing a release-candidate label or declaring a final release, Full/local validation evidence is required in addition to real-environment smokes.

## Secrets, runtime artifacts and packaging

Never package or log credentials, OpenCode auth files, personal session exports, `config/user-config.jsonc`, runtime `cache/`, runtime `diagnostics/`, local `releases/`, `.git/`, `__pycache__`, `.pyc`, historical checkpoint artifacts or generated test/release debris. Tests/maintainer/architecture/source and root `AGENTS.md` are distributable and remain in the release ZIP so future maintainers receive the same contracts.

`development/tools/build_release.py` always gates package validation plus a clean-extraction verification. In a command-time-limited harness, `--quick-already-run` may skip only the duplicate source Quick invocation after the same unchanged tree has just passed Quick; clean-extract Quick still runs. Its default behavior gate is the bounded Quick suite so RC artifacts can be produced safely in constrained AI harnesses; `--full-verification` upgrades both source and clean-extract gates to Full on an unrestricted machine. Builder calls nested inside tests may bypass only the duplicate outer behavior gate so packaging regression tests do not recurse. A final release must additionally have Full/local Diagnostics evidence; a Quick-gated RC must never be described as Full-verified.

## Versioning and history

Product versions are exactly `vMAJOR.MINOR`; no patch segment. Ordinary released work increments MINOR sequentially. A major is created only on explicit user decision. v78.0 is the final Python-rewrite baseline; subsequent feature/fix releases increment the v78 minor sequentially. A release candidate is not a completed release: its required verification must be completed or explicitly accepted before removing the candidate label.

`VERSION_HISTORY.md` records net product state rather than every implementation attempt. Major entries contain at most 10 bullets. Keep at most the latest five explicit majors; older history collapses into a bounded `Earlier versions` summary. During an unreleased implementation checkpoint, history must not claim behavior that does not yet exist. The file has a hard size cap enforced by the validator.

## Release procedure

For a release candidate or final release:

1. In a constrained hosted environment, run Quick + distributable-view validation. On an unrestricted/local machine run Full, preferably through Diagnostics so environment evidence and validation travel together.
2. Full includes the large-month/performance gate; rerun focused benchmark work separately when report/cache/source-selection hot paths need diagnosis.
3. Build with `python development/tools/build_release.py`. By default it writes `releases/cost-guard-vMAJOR.MINOR.zip`; for an explicitly requested release candidate, pass an explicit `--output releases/cost-guard-vMAJOR.MINOR-release-candidate-N.zip`. The builder uses Quick by default and repeats that gate plus validation from a clean extraction; pass `--full-verification` only where the unrestricted Full tier is appropriate.
4. Record the produced ZIP SHA-256 and only report checks that actually ran.
5. Never package runtime `cache/`, runtime `diagnostics/`, local `releases/`, `config/user-config.jsonc`, credentials, bytecode, `.git/`, historical checkpoint artifacts or local/generated debris.
6. Before removing a release-candidate label, complete the release's identified real-environment checks that deterministic fixtures cannot establish.
7. Never commit or push automatically.

## AI/session handoff contract

Root `AGENTS.md` is the entry point for a fresh coding model. A model working on an extracted package should infer the workflow from the user's request, read the referenced maintainer/FR/architecture files, and edit the authoritative extracted tree directly rather than creating a shadow rewrite. Brainstorm/FR work remains non-implementing until the user explicitly transitions to implementation.

Historical checkpoint files, prior release ZIPs and conversation artifacts supplied for context are **external references only**. They are never copied into a new release. Generated versioned ZIPs belong under the git-ignored `releases/` directory and that directory is excluded from package inventory. A final release uses `cost-guard-vMAJOR.MINOR.zip`; an explicitly requested release candidate may use `cost-guard-vMAJOR.MINOR-release-candidate-N.zip` while keeping the same unreleased product version.

## Public/open-source hygiene

Cost Guard is distributed under the root `LICENSE` using SPDX license `0BSD`. Production/docs/tests must remain organization-neutral: do not add employer/customer-specific branding, internal URLs, credentials, paths or assumptions. In particular, avoid environment- or application-specific service URLs/endpoints for Ictx enrichment; if canonical/local data cannot separate such context robustly, keep it in the aggregate/Other context instead. Hygiene checks must themselves remain generic; never encode a named real organization as a banned token. Real-environment diagnostics must be privacy-conscious and omit prompt text, session titles, auth tokens, raw auth files and raw OpenCode payloads.

All package-owned **directory names are lowercase**. This is a release-blocking validator invariant (`config/`, `development/`, `src/`, `windows/`, `macos/`, and runtime directories such as `cache/`/`diagnostics/`). File names may retain platform-friendly display casing, for example `windows/Cost Guard.cmd`.
