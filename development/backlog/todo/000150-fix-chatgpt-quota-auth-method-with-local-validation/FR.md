# FR 0150 — Restore OpenAI subscription quotas using the active OpenCode V2 auth method

## Problem and user-visible outcome

Meanwhile **the same computer can successfully invoke OpenAI GPT models in OpenCode Desktop V2**, so a successful model connection coexists with a **failed separate quota request**. The desired outcome is real current subscription quota data from the correctly authorized account when a supported read-only quota source exists—not another instruction to re-login by default, a cosmetic 401 rewording, an invented Pro tier or a guessed quota.

The user expressly confirms that the implementation workflow runs **on the Windows machine where this defect actually occurs**. Investigation and acceptance must use carefully bounded, privacy-safe *real installed OpenCode V2 evidence* in addition to synthetic tests. Don't ship a speculative fix from mocks alone if the active local method and the real failing quota request can be verified. Do not expose personal credentials or contact another machine/account.

## Important upstream/source-based hypothesis, not a confirmed root cause

OpenCode V2 has **different** OpenAI/ChatGPT OAuth flows sharing integration `openai`:

1. Current `Sign in with ChatGPT` uses method `chatgpt-token-sharing`, grants `chatgpt.tokens.use.direct` and `resource.invoke` scopes against resource `https://api.openai.com/v1`. Its credential metadata includes client/scopes and **need not contain a ChatGPT account ID**. Implementation reference: [OpenCode V2 ChatGPT token-sharing source](https://github.com/anomalyco/opencode/blob/1743d1a24e2356b3f631d3d384f44cb9d8359add/packages/core/src/plugin/provider/chatgpt.ts).
2. Legacy `Codex browser` / device-code OAuth uses `chatgpt-browser` or `chatgpt-headless`, routes generation to `https://chatgpt.com/backend-api/codex` and carries a ChatGPT account identity. Implementation reference: [OpenCode V2 legacy Codex OAuth source](https://github.com/anomalyco/opencode/blob/1743d1a24e2356b3f631d3d384f44cb9d8359add/packages/core/src/plugin/provider/openai.ts).
3. Official Codex still supports authenticated `/wham/` quota and sends `ChatGPT-Account-Id` where available, including Pro/Pro Lite variants. That proves a real supported *Codex client path*, **not** that every newer token-sharing token is accepted by `wham/usage`: [OpenAI Codex client reference](https://github.com/openai/codex/blob/970111f6cb62cc02fe36a82ea7d71b37a2889c97/codex-rs/backend-client/src/client.rs).

**Primary hypothesis:** Cost Guard indiscriminately sends a valid, currently active **token-sharing** OAuth token to the **legacy ChatGPT WHAM quota** surface. The token could legitimately work for OpenCode model inference while yielding 401 at that different resource. Alternatively Cost Guard may select an old/inactive record, wrong account/header, expired access generation, or an endpoint-specific policy/entitlement. The subscription's displayed name or price is not sufficient proof of any of these. **Inspect the user's installed OpenCode version and selected active method before attributing the failure.** Upstream sources are moving; compare them against the installed local contract rather than assuming a development-branch snapshot is exactly what runs.

## Required implementation: prove and repair the causal contract

1. **Inspect actual active credential selection on the affected computer (read-only).** Use the existing configured account/source and supported local V2 interfaces, or a bounded purpose-built local read-only inspector. Check selected integration, active credential *methodID*, expires/refresh generation, whether a compatible ChatGPT account identity exists, token audience/scope *classification* where safely available, and the distinction between token-sharing and legacy Codex. Check that the selected credential corresponds to the actual OpenCode model route; mere presence in V2 SQLite is not sufficient. If account authentication was just renewed, use a fresh current read-back. Do **not** print/copy/hash token bytes into model output or diagnostics; do not read unrelated credentials or hidden/private work data.
2. **Explain the 401 with local evidence, not guesswork.** Compare Cost Guard's actual request construction and account-header presence (only metadata-safe booleans or non-identifying classifications in output) with the *working model's* active method/route. If a **bounded actual read-only quota HTTP probe** is allowed by the installed account permissions, run it only with the eligible current identity, in a trusted local process where bearer material never enters model prompts, arguments, shell history, logs, diagnostics, artifacts or source control. Record only HTTP status, chosen method class, endpoint family, expiry status and safe parser shape; never raw request/response bodies, cookies or headers. Do not submit paid inference requests merely to test quota. No automatic sign-in, token refresh, identity switching or credential edits.
3. **Fix the real selection/compatibility bug.** Distinguish `chatgpt-token-sharing`, legacy `chatgpt-browser` / `chatgpt-headless`, API credentials and unfamiliar future OAuth methods. Use current supported/authorized read-only quota mechanisms appropriate to each actual credential type; investigate whether the installed V2 service exposes a supported, read-only usage/limit source before inventing a new network route. Never send a token to an unrelated host, mismatched resource or undocumented fallback just to obtain a 200. If token-sharing has **no permitted, reliable quota lookup**, show a specific `quota unavailable for this sign-in method` explanation while maintaining authenticated-model status, **not** the misleading `sign-in rejected`. This is a truthful fallback, **not** acceptable as a substitute for implementing available authorized quota retrieval.
4. **Use current evidence, not stale credentials or arbitrary accounts.** Prefer the genuinely active V2 connection used by the selected model; preserve FR0120's deduplication, generation pinning, removal and distinct-account behavior. A working account must not be labeled unauthenticated because a *different* endpoint or inactive legacy record returned 401. Handle missing `ChatGPT-Account-ID` correctly without guessing an ID, importing an unrelated org/workspace or merging different accounts. Separate 401 (wrong audience/credential vs verified failed login), 403 endpoint policy, expiry, 429 quota/throttling, transport and unsupported payload.
5. **Render actual authoritative quota, never synthetic plan data.** For a successful compatible response, preserve rate-limit windows, resets, plan/extra-credit fields as genuinely returned, including newer tier names. Keep Watch, one-shot reports and Diagnostics consistent; failed accounts clear stale native quota. Do not conflate local CCost, inference success, subscription billing and quota remaining.
6. **Avoid extra checks/permission prompts.** The user has already requested investigation on their own machine. Ordinary authorized read-only source analysis, safe local metadata inspection and applicable tests should proceed without routine confirmation loops. Existing OpenCode profile permissions, privacy/secret boundaries and explicit approvals for genuinely sensitive operations remain authoritative. No service/Desktop restart, global credential write, other-account probing, paid-model fanout, direct database mutation or workaround to bypass a denied permission.
7. **Real-machine acceptance is mandatory when safely available.** After implementing a candidate, rerun a bounded local live quota check using the same real OpenCode V2 installation and current eligible account, plus one-shot and Watch read-back, to show **either** a supported authenticated response with genuine quota values **or** independently demonstrated lack of a compatible quota surface. Never claim the quota is fixed from synthetic mocks alone. If an actual success cannot be proven, report the precise outstanding external constraint and tested evidence, and leave the functional gap explicit instead of labeling it PASS.
