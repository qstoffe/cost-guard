# FR 0115 — Adopt Toolkit's version-free FR writing and approval contract

## Problem and dependency
Cost Guard and Toolkit currently maintain parallel FR writing guides. A recently authored Cost Guard feature request included a **suggested implementation release number** even though autonomous prioritization and merges can change the actual version before delivery. Central Toolkit FR 0185 must own that rule, built on FR 0180's directory-bundle format, FR 0175's release contract and the installed /repo-init/portable structure. This request executes after Cost Guard FR 0100 and FR 0110; missing central features block it rather than permitting another local copy.

## Required behavior
- Retire the generic **duplicate authoring procedure** in Cost Guard's `development/FR_GUIDE.md`, `MAINTAINER.md` (if it still exists) and development/readme routing. Preserve a short discoverable Cost Guard-specific addendum about architecture ownership, Python/source-read-only boundaries, Watch/report/account/quotas, privacy-safe fixture requirements and current tests, while **actual drafting/numbering/approval/Git publishing rules** come from the installed Toolkit's one shared authoring skill/reference.
- For new Cost Guard FRs: **no future release/version numbers whatsoever** in FR title, text, filename, metadata or acceptance criteria, no `targetVersion`, guessed MINOR or numeric MAJOR. A major is only an explicit user-authorized **'new major' flag expressed without any target number**. A normal FR has no release number. Implementation selects the actual release at merge from latest default branch using the Toolkit-owned version contract; an FR's priority number is unrelated to versioning. Existing historical product evidence may remain in safely preserved records but never become a proposed future target.
- Preserve `development/backlog/todo` / `complete` bundle content, numbering and attachments after FR 0110. Apply central priority collision/append/explicit-order rules without moving completed history. Ensure an external client such as ChatGPT can discover the authoritative Toolkit instructions via a compact local pointer and GitHub/installed-resource route; do not rely on a third documentation repo, copy giant skills into the Cost Guard tree or require runtime to fetch live GitHub docs on every invocation.
- Review the most recently created **pending** Cost Guard FR for any hardcoded target release and remove just that speculative target if present while retaining its behavior/evidence; do not rewrite completed FRs or strip a version that is necessary to describe previously observed product output. Keep original priority and preserve attachments. Do not implement that FR as part of this migration.
- Continue to distinguish authorization to brainstorm, author/publish and autonomously implement. Git/PR/merge safety and privacy are unchanged.

## Verification and acceptance
- A fresh chat outside OpenCode and a Toolkit-powered `/repo-backlog` authoring route produce the same independently usable, version-free Cost Guard FR bundle with safe priority, approval boundary and correct local architecture constraints.
- Reject a proposed release number, a major target numeral, duplicate priority or unsafe attachment; allow explicitly requested 'new major' without assigning a number. Ordinary requests omit version claims. An already-authored speculative target is removed once, with no unrelated FR rewrites.
- Existing flat/bundle transition, Cost Guard FR-guide tests and both toolchains' authorized release gates still work. No duplicate long procedure and no third repo.
