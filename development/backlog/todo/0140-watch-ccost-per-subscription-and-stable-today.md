# FR 0140 — Clarify Watch CCost and show provider/subscription CCost by quota period

## Problem and user-observed behavior

Cost Guard Watch currently prints a long explanatory suffix on its overall CCost line, and renders `Today: Pending` whenever day-history enrichment runs. After a real Today value has already been published, subsequent refreshes temporarily replace it with Pending for seconds. That visual regression is distracting and implies the previous value disappeared.

The user also wants CCost alongside the existing subscription quotas, in a compact Watch layout, with clearer explanations in the normal account report. OpenCode request models carry canonical provider IDs, which provide a useful basis for grouping observed reference valuation even when a historical request lacks a proven account reference. However **provider, account identity, actual billing and native quota utilization are distinct**: a provider alone must not falsely prove which of several accounts served a request.

## Required Watch presentation

1. Replace the overall line with `CCost · Watch: <run> · Total today: <amount>`. Remove the entire `Deleted sessions before Watch start ...` suffix and its wrapped/continuation variant from Watch. Retain and, if necessary, improve the explanation in README / `docs/usage-and-cost.md`: available local-day history plus usage observed and retained by this Watch; requests deleted before Watch could see them cannot be reconstructed. Preserve existing Watch run/Today counting, local-midnight and 00:00–03:00 date-label semantics, and CCost rounding/unknown markers.
2. A **first** current-day accounting load can display `Pending` while no complete value for that day has ever been published. Once a complete value has appeared, keep it visible throughout every later refresh/enrichment attempt **for the same day**; atomically substitute the newly completed value without an intermediate Pending/blank/zero frame. Source polling, quota refreshes, redraws, reconnection and re-enrichment must not discard the published display value. Day rollover is a new accounting scope: never mislabel yesterday's amount as today's; handle that transition explicitly and truthfully. Do not enforce an artificial monotonic total when authoritative corrections, pricing updates or legitimate rollover change its value.
3. Add **CCost for the current local day** to a monthly Copilot-style account line immediately before Remaining: `Month ... 35% · 2483/7000 · Today: 1467 · Remaining: 275/day · 413/workday`. This is a *daily CCost* beside a *monthly native quota*, not month-to-date CCost or credits consumed. Keep original quota bars, native units, resetting, Remaining/day/workday, colors and account order.
4. For providers with multiple short/reset windows, insert a compact **CCost number in parentheses directly after the corresponding quota percentage**, independently per window: `5h ... 100% (651) · not started | Week ... 57% (25407) · Reset@Sunday 06:59`. The parenthesized number is **CCost in that period**, not an additional utilization percentage or native consumed quota. Requests may legitimately contribute to overlapping 5h and Week windows; never add these figures as though periods were disjoint.
5. Preserve existing responsive compact/split/vertical account rendering and terminal-width behavior. Do not sacrifice essential quota/status/error/warning information for CCost. When a percentage is genuinely unavailable, provide a readable, non-fabricated CCost presentation in the existing account block instead of creating a fake bar. Preserve numeric `?`/`N/A` behavior for incomplete/unpriceable usage.

Illustrative Watch output (values are examples, not test fixtures for actual billing):

```text
Token Mix % · 209 prompts · Input: 4.6% (566)   Cache: 93.9% (709)   Write: 1% (10)   Output: 0.5% (260)
CCost · Watch: 1543 · Total today: 2118
GitHub Copilot Pro+   Month  ████░░░░░░  35% · 2483/7000 · Today: 1467 · Remaining: 275/day · 413/workday
Claude Code Pro       5h     ██████████ 100% (651) · not started | Week ██████░░░░  57% (25407) · Reset@Sunday 06:59
```

Keep the existing configured-local overnight date exception if the overall Today label changes to a date; the intent is clear distinction between overall Total today and per-account Today, not removal of date context.

## Period accounting and provenance

- Reuse the **same canonical deduplicated model-request and reference-valuation logic** used by existing CCost; partition by the **request's canonical provider**, not by the model publisher/name (a GPT model used through Copilot must stay with Copilot, not OpenAI). Preserve verified request account references where available; normalize supported provider aliases at the appropriate boundary without conflating `claude-code` subscription with direct Anthropic API or other incompatible sources. No actual payment, subscription allowance or quota consumption may be inferred from CCost.
- For daily/monthly-plan displays, use the configured local calendar day's 00:00–now scope. For 5h, Week or other duration-bearing reset windows, calculate CCost from request timestamps within each current window, using a trustworthy native window boundary/reset and duration where supplied. If a quota says `not started` and no usable reset anchor is supplied, a duration-based trailing lookback (e.g. last 5 hours) may provide the user's desired illustrative CCost, but **label and explain** its observed trailing-window basis in the report; never imply this reconstructed window is the provider's certified quota accounting interval. Inability to establish a meaningful period must remain unknown rather than inventing a start/reset.
- **Account ambiguity:** a proven `account_ref` may support account-specific figures. If account identity is absent but there is exactly one compatible detected account for the canonical provider, allow a useful **provider-attributed CCost** on its Watch row, explicitly documented as *not verified account/billing attribution*. If several possible accounts share that provider, do **not** duplicate provider CCost on each or silently assign it to an arbitrary account. Show account-unknown/not-attributable state where necessary, with any safely computed provider total explained once in the report. Do not confuse a configured API key with a subscription entitlement. Keep multi-account accounts separate.
- Use existing incomplete-pricing markers and privacy/read-only guarantees. Dates/window refreshes, old-day and older-week requests, background/subagent causal usage, session deletion/reconciliation, fork deduplication, Watch restarts and local timezones/DST must follow existing source truth. Provider period totals can differ from overall Today because their scopes and attribution differ. Do not add a persistent billing ledger, mutate OpenCode, or couple native quota fetch cadence to expensive historical scans.

## Normal report

Expose the **same period-scoped CCost** in the ordinary `Accounts Overview` / account quota report, but prefer clarity to Watch density: clearly named distinct lines such as `CCost today: 1467`, `CCost in 5h window: 651`, `CCost in Week window: 25407` placed with their respective account/quota sections. Spell out scope and provenance (verified account versus provider-attributed estimate, and native reset window versus trailing lookback) and the relationship to native percentages, remaining quota and billed spend. Users must be able to run the normal report to understand the terse Watch parentheses. Do not require an exact report layout beyond readable separate scope labels and preserved existing report information. Do not turn unrelated `--sessions`, date details, `--token-mix` or model comparison output into a different mode.

## Ownership, non-goals and verification

- The existing `src/watch/today_ccost.py`, Watch projection and `src/presentation/token_mix.py` own stable daily publication/overall text; provider-neutral period grouping/valuation belongs in shared analysis/report projection rather than in presentation or native quota adapters; `src/presentation/accounts.py` owns the compact Watch and explanatory report layouts. Inspect the **then-current** ownership in `development/ARCHITECTURE.md` and `development/CODE_MAP.md` before implementation. Existing `src/reports/accounts.py` has an account-proven `ccost_scopes` projection that currently omits unproven provider history and suppresses history in Watch; extend this safely rather than adding a second valuation path.
- Keep Watch's first meaningful dashboard nonblocking and account acquisition independent; bounded incremental history reuse/projection should avoid repeatedly scanning an entire month/week on every redraw. Keep transient quota states and recent-event/Watch Total invariants intact. Do not implement the unrelated account-switch/401 bug tracked by FR 0120.
- Deterministic regressions: first Pending → first value → multiple slow refreshes holding old value → atomic new value; refresh failure/recovery; local midnight/overnight label; removed-before-observation vs removed-after-observation history; width/ANSI/plain rendering; exact placement and no deletion disclaimer in Watch while docs retain it; Copilot daily versus monthly native quota; Claude 5h and Week overlap and resets/not-started; source provider vs model publisher, direct API vs Claude subscription; one proven account, one provider-only account, two ambiguous accounts, partial/unknown pricing, deduplication and DST. Validate that report and Watch agree for an equivalent scope without false billing claims.
- Update README and usage/cost reference for the *implemented* behavior; include normal release/test gates at implementation time. This FR creation itself changes no runtime behavior and assigns no implementation version.

## Acceptance criteria

1. The overall Watch line displays `Total today` and no deleted-session explanation; README/reference retain the caveat.
2. After Today first publishes for a day, refresh never flashes Pending or hides it before the next valid whole-day total is ready; midnight is handled correctly.
3. Monthly account Watch rows display `Today: <CCost>` before Remaining, and 5h/Week quota rows place their respective CCost immediately after the percentage in parentheses, retaining compact and responsive output.
4. Report account sections explain the same CCost figures on distinguishable period lines, including provider/account provenance and any trailing-window fallback.
5. No fabricated subscription/account allocation, false quota/billing equivalence, double counting, regression to existing Watch/report contents, or unbounded startup/refresh work. Focused tests and repository validation pass before implementation delivery.
