# FR 000532 — Eliminate false Web Live reconnections and make connected status unobtrusive

## Owner-observed regression (2026-10-28)

While the Cost Guard Web Beta host is apparently still running and the page is in use, the top connection/status area repeatedly switches from **Live connected** to **RECONNECTING** and back, reportedly roughly every 30 seconds. The prominent full-width/sticky status banner is also much too tall and distracting. The owner wants normal connected operation to be visually quiet; a prominent status notice should appear **only when there is a genuine disconnected/degraded/actionable condition**, never periodically during an otherwise healthy live session.

Completed FR000500 intentionally introduced stronger stopped/offline/stale visibility, and its evidence covered controlled connection faults, not an extended idle/live soak on the owner's running server. This FR is a regression/stability and UX follow-up, not a rollback of FR000500's safety guarantees. Potential investigation points in current sources include `LiveConnection`'s 10-second authenticated probe, `EventSource.onopen/onerror` behavior and resync, SSE idle/heartbeat/disconnect behavior, 5-second fetch deadlines, tab visibility, cookie/auth/host identity, and the always-visible `.host-state` banner; **none is a confirmed root cause**.

## Required result

- Reproduce and instrument the periodic **connected → reconnecting → connected** transition with the real Web Beta host, actual browser and existing running OpenCode V2 source. Correlate browser EventSource open/error/close, authenticated `/api/live` and health checks, server SSE/HTTP logs, timestamps, stream identity, source health, page visibility, event loop/workload and retry timing. Determine whether the stream actually drops, the watchdog/API produces a false status, or a browser/proxy/host timer closes an otherwise healthy connection. Repair the causal failure without relying on a mere visual delay to conceal continuous transport failures.
- During a healthy authorized host+SSE/source session, **do not oscillate into RECONNECTING on a timer**. Avoid duplicate EventSource streams, unnecessary reopens/resync loops, busy polling, false terminal identity changes and reconnection work that adds pressure to the shared host. SSE errors with still-healthy authenticated HTTP should be classified accurately, with bounded recovery; do not equate a transient transport event with stopped/absent source data, and do not label a proven outage healthy.
- Make the **healthy connected state compact and unobtrusive**: ideally no persistent sticky full-width banner when connected, at most a small status indicator in the header/navigation with an accessible label/tooltip. Do not repeat the entire long host/source/snapshot explanation in two separate top bars. Show a clear, appropriately sized and accessible **notice only for actual starting/unavailable/degraded/reconnecting/offline/expired/identity-changed/stopped states**, with enough diagnostic context when actionable; preserve distinct source-unavailable vs transport-offline and frozen/stale report meanings. If relevant, move last-check/observation timestamps into an expandable detail rather than always consuming page height. Preserve legibility in light/dark and narrow widths.
- Never suppress true stopped/offline/authentication/identity/source failure simply because the host process is alive. Preserve FR000500's prompt truthful detection, last-known/frozen data, terminal stop semantics, authorized same-instance reconnect and disabled controls on genuine loss. No new secrets in browser storage/URL, unauthenticated endpoint, host restart/port scan, extra acquisition engine, or changes to CLI Watch/report semantics.

## Verification and acceptance

1. Actual local Windows Web Beta launcher/host + real browser + running OpenCode V2: remain on Overview and Watch for **at least 10 continuous minutes each**, including periods without new source activity. Observe and log connection-state transitions. A healthy server/stream must remain continuously connected without periodic `RECONNECTING`; browser UI must not show a bulky connected banner. Reproduce the owner's ~30-second pattern before the fix if possible and record the causal evidence, not an inferred cause.
2. Repeat with real finite report Refresh and Watch publications, tab switch/background-return, idle browser, multiple tabs, reconnect after a controlled *owned test-connection* interruption, and source temporarily unavailable while HTTP stays alive. Verify one stream per tab, bounded resource use, readable table retention and accurate state differentiation. Don't stop or alter the owner's shared OpenCode instance to produce a test condition.
3. Recheck FR000500 cases using isolated owned fixture/host where destructive actions are safe: server stop/crash, lost SSE, authorization expiry, host-identity replacement, source outage and restart. Genuine degraded/offline states must become apparent within existing reasonable bounded detection, **not** be hidden for 10 minutes in the name of status stability.
4. Deterministic tests cover transport error/open/resync/probe races and repeated healthy heartbeat/probes without false transitions; browser layout checks prove compact connected status and meaningful offline/frozen notification at desktop and 360px, including accessible text (not color only). Clearly identify any real-OS suspend/headless/physical limitations instead of claiming them tested.
