# FR 000410 — Cross-platform GitHub Actions revalidation of delivered Web Beta

## Problem and objective

Cost Guard's Web Beta migration is **already delivered**: FR 000290 through FR 000380 are in `development/backlog/complete/`, with v80.89 and a reported 105-file full local suite. Windows 11 native probes have been exercised on the owner's computer, but the macOS launcher/status menu/Finder experience was implemented best-effort **without any real macOS execution**. Synthetic cross-platform tests are not equivalent to native platform proof. The repository currently has no GitHub Actions workflow.

Add **new, reproducible, isolated Windows and macOS verification of the existing delivered implementation**, not just CI for the next change. Prefer free standard GitHub-hosted runners for this public repository so testing does not open windows, create tray icons or require repeated native-UI approvals on the owner's daily Windows workstation. A real Windows desktop remains an optional, separately approved last-mile check; no owner-owned Mac is assumed.

## Requested behavior

1. **Host-isolated, cost-conscious CI.** Add a modest GitHub Actions workflow under `.github/workflows/` with manual dispatch plus suitable pull-request/main-branch triggers. Use only standard GitHub-hosted runners available free for public repositories, not larger/paid, self-hosted or owner-workstation runners. Start with Windows x64 and macOS Apple Silicon; include a standard Intel macOS runner when available to exercise both supported architectures. Linux may provide an additional portable baseline if useful. Record actual runner image, OS build, architecture, Python and relevant system-tool versions, rather than interpreting `-latest` as a fixed OS. Revisit cost/permissions before running if the repository becomes private or GitHub's free-tier terms change; do not silently incur charges. Keep timeouts, concurrency and artifact retention bounded to avoid wasted capacity/storage.

2. **Run real existing regression coverage on every viable platform.** Reuse `development/tools/run_tests.py` and run its registered `full` suite against a clean checkout with CI-installed Python 3.11+; inspect/report failures and skipped tests per platform. Do not replace the per-file isolation, loosen deadlines or treat mock tests as native tests. Run the working-tree package validator where applicable. Account for the existing optional Node VM test harness explicitly: arrange runner-side developer tooling when useful and distinguish executed from silently skipped cases. CI provisioning may use ordinary GitHub runner/setup actions; no new end-user product install, package, compiler/SDK download or shipped binary is authorized. Existing CLI, Watch and Diagnostics behavior remains unchanged.

3. **Exercise the actual native Windows implementation as far as the hosted Windows session permits.** Reuse/refactor the already supplied `development/tests/integration/probe_windows_web.py` into bounded, CI-safe native smoke checks for Win32 tray/menu/message dispatch, lifecycle ownership, detached launcher, Open/Exit, host/browser failure, restart/source change, cleanup, and source paths with spaces/Unicode. The full historical approval-only probe includes local real-source/CLI behavior; split or adapt its platform-independent/native portions to synthetic isolated fixtures rather than requiring OpenCode, personal accounts, real quota requests or real user activity on the runner. Do not run the approval-gated workstation probe indiscriminately. Document which checks actually used Windows native APIs versus mocks, and that a hosted Windows image/session does not prove physical desktop mouse interaction or ordinary consumer Windows 11 behavior.

4. **Prioritize actual macOS verification missing from FR 000330/000380.** Exercise `development/tests/integration/probe_macos_web.py` or a scoped CI-safe derivative on a real macOS hosted runner. Attempt genuine AppKit/Objective-C loading, typed callbacks, main-thread event loop, status-menu Open/Exit, HTTP-owner lifecycle and failure cleanup. Separately test available native shell/launch mechanisms: `.command` execution, built-in `/usr/bin/osacompile` preparation and fingerprinted cache reuse/rebuild, executable mode, path/Unicode handling, clean first launch without *product* package/tool downloads, and Apple Silicon/Intel differences. Use safe temporary checkout/user-state isolation with teardown, not the owner's machine. Headless/locked GUI sessions may prevent NSStatusItem visibility, Finder, Gatekeeper, browser selection or physical double-click verification; attempt what is viable and report those limitations **as NOT VERIFIED**, never as PASS or as a synthetic substitute. No quarantine removal, security bypass, persistent login item, service or system-wide permission change.

5. **Add useful real-browser smoke where feasible.** The existing Node VM/DOM fixtures are not a rendered browser. On a clean CI runner, use an available headless browser or narrowly scoped CI-only test tooling (never a product dependency) to exercise the shipped local Web Beta shell with deterministic fixtures: bootstrap/auth session, navigation/Back/Forward, report table and session detail, live/reconnect state, safe hostile text, basic responsive/keyboard interactions and clean server stop. Favor a few trustworthy smoke flows over a new framework or exhaustive screenshot suite. If browser/GUI facilities prevent execution, surface an explicit blocked/skipped outcome and reason.

6. **Safety and faithful evidence.** All automated smoke uses synthetic, offline/read-only fixtures and disposable user-local state. No user credentials, private sessions, provider calls, model inference, billable API requests, credential mutation, or changes to the shared OpenCode installation. Limit workflow token permissions (read-only checkout), avoid secrets and unsafe untrusted-PR execution, do not upload raw private paths/prompts/tokens/session dumps, and sanitize/retain only bounded test logs or summaries. Tests must not install or ask permission on the owner's Windows machine. Separate `PASS`, `FAIL`, `SKIPPED`, `BLOCKED` and `NOT RUN` with reasons and platform/architecture, without disguising skipped native tests behind a green overall suite.

7. **Revalidate the whole already-completed Beta.** The first successful workflow must run against the actual delivered Web Beta after FR 000380, covering both core regressions and whatever native/browser evidence the hosted OS permits. Record a concise Windows/macOS/architecture coverage matrix and outstanding manual acceptance steps in existing product/development documentation (for example `docs/web-beta.md` and an appropriate development verification note). Re-run after fixes. Investigate CI-discovered regressions causally; make narrow repairs in implementation if this FR permits, or record a separate follow-up for larger unrelated defects. Never retroactively rewrite completed immutable FR files or assert that previous Windows-local PASS implies Mac PASS.

## Acceptance / constraints

- A committed, manually runnable workflow has produced retrievable Windows and macOS job results from the delivered codebase; supported standard runners and cost behavior are documented. Include both Apple Silicon and Intel macOS when standard runners are actually available, otherwise state the missing architecture explicitly.
- Existing full tests and relevant validation have real per-OS execution evidence, including counts of passed/failed/skipped and any OS-specific failures. CI-native Win32 and macOS/AppKit checks execute where environment capabilities allow, and unresolved limitations remain clearly visible.
- A small actual-browser test executes where feasible, or a concrete runner/browser limitation is reported honestly. An explicit remaining manual GUI checklist covers tray/status-bar appearance, Finder/Gatekeeper, physical clicks, accessibility and full desktop behavior that hosted headless runners cannot prove.
- No changes to normal Cost Guard installation requirements, no billable GitHub runner upgrades, no user-local UI prompts, no real account/model use, and no hidden CI status/release claims. Do **not** introduce branch protection, mandatory all-project release checks, release/version bumps solely for FR authoring or an automatic Beta promotion/Legacy removal. This is an additive verification capability and one-time retroactive re-test, not a new blanket release gate.
- Implementation owns its normal delivery and truthful evidence; **publishing this FR alone does not implement it or start a job**.
