# FR 000521 — Model-/publisher-aware Relative CCost and publisher Token Mix

## Owner observation and intended outcome

Cost Guard's Normal report and All Models report currently compute every model's **Relative CCost** using the same I/C/W/O distribution from the latest 100 eligible completed priced prompts. This is a useful generic personal-workload comparison, but it can be less representative of actual use of an individual model. The owner observes that token mixes can be relatively similar within a model **publisher** (e.g. OpenAI or Anthropic) while differing across publishers.

Replace the shared comparison mix with a **model-specific, evidence-weighted effective mix** which gains confidence as that model's own completed prompts accumulate. Use the publisher's other models as the preferred fallback, then the existing generic personal mix. The goal is that, once a model has 100 qualifying prompts, its relative price uses **only that model's observed token mix**. Preserve reference pricing rather than interpreting this as billed money or an experimentally controlled same-task comparison.

Separately, preserve the existing historical **Token Mix by model** table and add a second **Token Mix by publisher** table that lets the owner inspect how usage mixes vary among publishers. This feature must land in **both the CLI and the in-progress Web Beta**, via their shared Python/report/application boundary, not as two independent calculations.

## Relative CCost — 100-prompt evidence weighting

1. **Observation unit and eligibility.** Count **distinct user prompts**, not individual model requests/calls. A prompt with 100 tool-loop/model requests is still one prompt of evidence. Preserve Normal comparison's current completed, non-aborted, priceable eligibility: at least one physical request with real usage, complete I/C/W/O telemetry and resolvable reference pricing. Only eligible requests contribute their category tokens. Include attributed child/subagent/model-switch work under the initiating prompt, without cloning requests. Keep reasoning folded into Output. For a model/publisher sample, include **only requests attributable to that model/publisher** within an eligible prompt; do not contaminate one model's mix with another model's requests.
2. **Model evidence (first preference).** For each compared reference model M, collect its most recent up to **100** distinct eligible completed contributing prompts across **available history**, under existing exact/verified model identity semantics. Let nM be this count and let MixM be the I/C/W/O shares of their pooled eligible token volumes. The model receives weight nM/100. This is per model, not merely the subset of model prompts that happen to lie inside the current latest-100 *global* sample.
3. **Publisher evidence (second preference).** Resolve a model's **publisher** from trustworthy catalog/manufacturer metadata (e.g. OpenAI, Anthropic), not the OpenCode request/provider/account route (GitHub Copilot, Claude Code, etc.). For the remaining 100−nM weight units, collect the latest up to that many distinct eligible completed prompts from **other models of the same verified publisher**, excluding prompts already counted for M, and include only this publisher's eligible requests. Let nP be the number and MixP their pooled-volume I/C/W/O shares. Weight nP/100. Match publisher aliases/casing conservatively; ambiguous or absent manufacturer identity must not silently become a provider-wide group.
4. **Generic fallback (last preference).** Allocate any remaining weight 100−nM−nP to MixG, the current generic personal completed-priceable-prompt reference mix (up to the latest 100 eligible prompts across models/publishers). This is a **prior**, not a claim that additional distinct prompts were observed. If less than 100 total real prompts exist, use the observed MixG with the residual **statistical weight** and expose the actual evidence counts; never fabricate 100 real calls/prompts. If there is no eligible global evidence, keep Relative CCost blank and retain the existing hidden sorting-only fallback (2/96/1/1). If publisher cannot be resolved, use zero publisher weight and global fallback.
5. **Exact calculation.** Normalize each **nonempty group's pooled token volumes** to exact I/C/W/O share fractions and then blend these fractions by prompt-count weights: EffectiveMix(M) = (nM/100)×MixM + (nP/100)×MixP + ((100−nM−nP)/100)×MixG. This is **equal weight per evidence slot at the blend level**, not raw-token concatenation of the model/publisher/global pools and not rounding percentages before pricing. Apply the same EffectiveMix(M) to every published rate/context tier of M. Category shares must sum to 100% before display rounding. Missing group evidence has zero weight; no zero-vector substitution for unknown telemetry.
6. **Worked cases.** (a) 10 M prompts + at least 90 eligible other prompts of M's publisher → 10% MixM / 90% MixP / 0% MixG. (b) 100 M prompts → 100% MixM, regardless of publisher/global history. (c) 10 M + only 40 other-publisher-family prompts → 10% MixM / 40% MixP / 50% MixG. (d) No M prompts, but 100 eligible prompts of its publisher's other models → 100% MixP. (e) No model or verified-publisher evidence → existing generic MixG. (f) No completed priceable prompts anywhere → blank comparisons, never synthetic multipliers.
7. **Comparable ratios and ordering.** Price each displayed model's **own** EffectiveMix against its exact published I/C/W/O rates; preserve tier boundaries, promotions, priceability, availability/full-catalog membership and decimal precision. Define the single 1.0x denominator as the **lowest positive comparable base-tier price after applying each model's effective mix**; every model and higher tier uses that **same** denominator. Use unrounded estimated prices for default sorting/tie-breaking and one-decimal ratios only for display. Unknown/incomparable rates stay unknown, not zero. Document that ratios are **personalized workload-profile estimates** (models may have different observed workload mixes), not a same-task benchmark or billing.
8. **Related warning consistency.** Price-threshold/context warnings that currently derive a Relative CCost multiplier must use the **same effective mix for the relevant target model and observation** rather than silently retaining a global mix. Preserve existing correct threshold semantics and avoid repeated full history I/O or expensive recomputation for Watch/warning refreshes. The existing dashboard Token Mix % concept remains its **separate** latest-100 usage sample (including currently running/interrupted usage); do not change it to match the new per-model cost mixes.
9. **Transparent provenance.** Keep the actual model prompt count, other-same-publisher count, generic-prior weight and effective sample coverage as compact trusted report data, and explain the new semantics in CLI help/definitions and the relevant Web concept/help text. Do not describe 100 effective weight units as 100 actually observed prompts. Avoid unnecessary permanent visible columns or walls of provenance text; users should be able to understand why an untried model uses publisher/global behavior.

## Historical Token Mix — additional publisher table

- **Keep the existing report.** Both CLI `--token-mix` and Web `#/token-mix` continue to show the canonical Total Token Mix % and the current per-model table, with per-model Prompts, Calls, Input/Cache/Write/Output shares (including category CCost), total CCost, partial-price markers and existing history/availability caveats.
- **Add a second table grouped by verified publisher**, with `Publisher | Prompts | Calls | Input | Cache | Write | Output | CCost`. Aggregate from the **same underlying deduplicated, available historical requests included in the displayed model table** and under its existing availability filtering/fail-open rules, so publisher and model views reconcile to the same shown Total. Combine all shown models of one publisher and compute its own category shares from **raw pooled category token volume**; CCost remains the sum of each request priced at its original model and context tier (not reconstructed by repricing aggregate publisher tokens).
- Publisher `Prompts` counts distinct contributing user prompts **within that publisher**; `Calls` counts attributed physical model requests. A mixed-model prompt can appear once in multiple model/publisher groups but must not be duplicated within a publisher. Hence prompt row counts are not generally additive; explain that explicitly. Preserve partial pricing and unknown-telemetry behavior; a missing/ambiguous publisher must be visibly classified as unknown/unverified rather than incorrectly grouped by service provider. Publishers use stable, deterministic naming/order (e.g. descending known CCost then Calls/name); clear labels distinguish this historical table from the 100-slot price-estimation prior.
- Keep deep history **explicitly requested** in Web, including progress/cancel/retained frozen result. Adding the publisher table must not auto-trigger a full-history Token Mix scan merely by opening a page or changing navigation.

## Shared architecture, performance and safety

- Put model/publisher sampling, eligibility, identity resolution, blended Decimal price calculations, and historical publisher aggregation in the existing canonical Python **analysis/reports** layers. Pass immutable, minimal calculated projections through `src/reports/models.py`, `src/application/projection.py` and shared `src/application/display.py`. Both CLI rendering and Web Beta's Overview/Models (including All Models) and Token Mix view consume those same derived results. Do **not** calculate token mixes, prices or reference ratios in JavaScript. Preserve stable numeric Web sort keys and user-restorable canonical CLI order.
- Per-model latest-100 history may extend much further back than the existing global latest-100 sample. Design **efficient revision-aware reuse/targeted acquisition** rather than a second analyzer, private history ledger, excessive memory growth or a silent only-latest-global-100 shortcut. Profile warm/cold Normal and All Models performance on realistically large available histories; use truthful progress and documented missing/deleted-history limits. Avoid an uncontrolled deep scan on every regular report, Web refresh, tier warning or Watch update; never claim complete 100-per-model coverage when it was not actually collected.
- Preserve OpenCode source read-only behavior, V1/V2 canonical attribution, pricing identity/tier resolution, no invented prices, no account/billing/quota changes, Web loopback/auth/DTO constraints and current finite-job/8 MiB bounds. No new external dependencies, provider API calls, browser data persistence, background service or automatic Web/CLI migrations. This FR does **not** promote/retire Web Beta and does not implement the separately pending native launcher FR000520.
- Update `README.md`, `docs/usage-and-cost.md` and Web help/labels when implementing, so older wording about a single shared 100-prompt mix is no longer misleading. This FR-only backlog publication itself changes no runtime or version.

## Acceptance / regression evidence

- Deterministic synthetic data proves model weights at **0, 1, 10, 99, 100 and >100** qualifying prompts; publisher coverage at **0, 40, 90 and 100**, including 10/90 and 10/40/50 examples, no-history blank fallback and untried new model with verified publisher evidence. One prompt with many requests must not count as many model prompts.
- A model whose last 100 eligible prompts sit **outside the latest 100 global prompts** still reaches its true model-only mix. Fixtures include running/aborted, unpriceable/missing fields, reasoning/output, child/subagent and compaction requests, duplicate request evidence, a prompt using two models/publishers, stale/deleted history, unavailable/ambiguous publisher and publisher-name aliases. Confirm no double counting of requests, correct unique-prompt denominators and no producer-agnostic provider fallback.
- Independent manual/synthetic expected Decimal I/C/W/O blended shares and tier costs agree with implementation, including a changed cheapest base-model reference, multi-tier boundaries, null rates, 0 published rate versus missing rate, exact-value sorting, one-decimal display and warning multipliers. Global Token Mix % and actual CCost/account calculations retain their prior semantics.
- For the **same frozen source/catalog/time** CLI Normal/All Models and Web Overview/Models show identical comparable model list, exact model-specific underlying ratios, tier order and contextual explanations; CLI and Web historical Token Mix show identical model and publisher rows, counts, I/C/W/O shares, per-request priced CCost/partial markers and totals. Include empty/partial/unknown and narrow-screen/mobile Web presentation, explicit-history cancellation, preserved filtering/sorting and 8 MiB finite-result behavior.
- Run relevant existing `test_priced_token_mix.py`, `test_report_sampling.py`, `test_model_comparison_tiers.py`, `test_token_mix.py`, `test_token_mix_economics.py`, report/application/CLI parity and Web Overview/Models/remaining-view tests, plus new focused multi-publisher and older-history coverage. Collect representative cold/warm and refresh timings without inventing a universal latency target; any material degradation must be investigated and reported before implementation delivery.
