# FR 000320 — Windows Web Beta launcher and tray Open/Exit

## Outcome and dependency

After FR000310, add `windows/Beta/Cost Guard Web.cmd` as an opt-in way to launch the detached Web application. Keep `windows/Cost Guard.cmd`, `windows/Cost Guard Watch.cmd`, Diagnostics and their current console behavior working unchanged. Follow FR000290/PLAN.md and reuse the shared lifecycle, not a Windows-specific second server manager.

## Required behavior

- Resolve repository paths relative to the launcher, independent of the working directory, including spaces, Unicode and source ZIP extraction. Reuse the intent of existing Python 3.11+ discovery without altering the stable PowerShell/CLI launchers. The launcher is a plain-text `.cmd`/PowerShell script (or equally simple native script entry) that works by double-click, with **zero new downloads, package installs, virtual environments, Node, administrator access, compiled binaries or global execution-policy modifications**. Validate Python and native prerequisites before stopping an existing healthy server; startup failure should preserve the old instance where feasible.
- Double-click performs FR000310's verified restart, starts the host detached from its transient console and waits for shell readiness, then opens the default registered browser at the instance's authenticated bootstrap route. Exit the launcher automatically on success; do not inherit the stable launcher's `-NoExit` behavior. When invoked inside an existing user terminal, return control rather than closing that terminal. Do not bind the background process to the transient console's Ctrl+C or standard handles.
- The same application instance owns a Windows notification-area icon with exactly two initial actions: **Open Cost Guard** and **Exit Cost Guard**. Open opens the existing server without restarting or creating another one. Exit performs bounded clean shutdown of that instance and removes the icon; the browser is not forcibly closed. Tooltip can identify Beta/version/checkout when necessary without disclosing private session data. Use a bundled original icon with sensible light/dark readability.
- Implement the tray via already-installed Windows capabilities, preferentially PowerShell 5.1's in-box .NET Windows Forms `System.Windows.Forms.NotifyIcon` and its context menu, or a narrow Python `ctypes` wrapper around Win32 `Shell_NotifyIconW` if proven simpler/reliable. Do not install pystray, Pillow, WinForms via NuGet, the .NET SDK or third-party components. If source-only PowerShell/.NET calls are inadequate, a small committed C# helper may be compiled **locally with the already-installed Windows PowerShell 5.1 `Add-Type`**, with readable first-launch progress/errors and versioned generated output in protected per-user local application data outside Git. Reuse until helper source/target compatibility changes; never ship a compiled `.exe`/`.dll` in Git or download a compiler. First use must remain offline. The GUI loop must live as long as its matching host and report host loss, not spawn a second independently managed server. The cross-platform host must accommodate macOS's UI-main-thread requirement. Menu callbacks signal work without blocking on network/history operations.
- No persistent console window is required after a successful Explorer launch. Startup failure is not silently hidden: show a concise actionable error, preserve a privacy-safe diagnostic record and provide the existing Diagnostics route. Missing Python, native tray initialization failure, occupied/unverifiable instance, server startup timeout and browser-open failure must be distinguishable. Browser failure must leave a valid tray Open action when the server is healthy.
- Source-change shutdown from FR000310 removes the tray icon too. Server crash must not leave an independently running icon claiming that it is healthy. Do not register an OS service, startup task, scheduled task, login auto-launch or firewall exception.

## Acceptance

Exercise first-run launch with **no package setup or download**, offline startup, existing-instance restart, rapid double-click, Open without restart, Exit, failed browser open, in-box tray API failure and code-change exit. Verify a detached process survives launcher-window closure and the original CLI Watch still runs independently, including when Web exits or restarts. Test command invocation from an existing console, Explorer launch, paths with spaces/Unicode, supported Python discovery and stale state.

Native Windows evidence is required to claim the shell/tray interaction works; synthetic tests cover failure/ownership logic but cannot prove visual native behavior. Record untested environments honestly, without new permanent release gates. This FR can ship with the minimal Beta/status page from FR000300; it does not wait for a polished UI and does not move anything to Legacy.

Implementation pointers: `src/windows_launcher.ps1`, `windows/` and `src/launcher_feedback.py` describe existing protected behavior. Put new host/launcher code in a narrow Beta-owned seam rather than widening the stable launcher unnecessarily. Primary API references: https://docs.python.org/3/library/webbrowser.html and https://learn.microsoft.com/en-us/dotnet/api/system.windows.forms.notifyicon . Native support must be verified on actual supported Windows systems, not assumed from API availability alone.
