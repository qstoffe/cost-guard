# FR 000380 — Stabilize Web Beta without weakening CLI or calculation integrity

## Outcome and dependencies

After FR000320 through FR000370 are delivered, reconcile the complete Beta experience, repair integration regressions and provide truthful evidence for owner testing. This is a scoped migration milestone, not a new permanent all-project release/approval gate. Follow FR000290/PLAN.md. Completion does not authorize promotion or Legacy removal.

## Required behavior

- Finish the mode-to-view parity inventory begun in FR000290. Validate shared numerical results against CLI for the same normalized records, catalog, configuration, clock and scope. Cover costs/billing, running provisional metrics, request/token/cache mixes, children/clones, compaction, model effort, duration, context and account periods. Explain legitimate observation-window differences; never change a formula merely to make independently timed live screens match.
- Exercise stable CLI reports/Watch alongside Web, including absence/failure of optional packages, Web restart, source-change exit, multiple checkouts and concurrent cache access. Shared SQLite WAL does not by itself prove cross-version schema or account-state safety. Keep compatible generation-named disposable cache behavior; isolate incompatible Web state without deleting legacy caches, user configuration or historical logs. Do not globally serialize independent CLI processes through a Web-only lock.
- Validate native Windows and macOS lifecycle: first setup consent, offline installed startup, expected default browser, transient launcher exit, repeat restart, Open versus Exit, source unavailable, crash, stale PID/state, occupied port, paths with spaces/Unicode and source ZIP/executable handling. Distinguish real native smoke evidence from mocks; record OS/Python/architecture actually tested and remaining limitations.
- Stress a long session, several tabs, a slow client, reconnect/replay gaps, system suspend/resume and a deep history job beside live work. Use bounded operation counts, memory/DOM sizes and representative timings rather than unsupported universal latency promises. Verify that account refresh/source discovery are not multiplied per tab and control/shutdown remain responsive.
- Audit local security from FR000300: authentication and cross-checkout isolation, Host/Origin/CSRF, bootstrap expiry/replay, safe cookie/path scope, traversal, untrusted session text, stale clients after instance replacement and no browser-side secrets. Cookies are not port-isolated by browsers; instance/route scoping must not authenticate a different local checkout by accident. Do not expose a reusable stop token through the UI or a plain unauthenticated health endpoint.
- Integrate Web lifecycle/source/API failure facts into existing privacy-safe Diagnostics: fixed error codes, version/instance schema, bounded counters/timings and actionable startup status. Exclude prompts, titles, raw session IDs/paths, cookies, tokens, provider responses and uncontrolled exception messages. Preserve useful failure evidence before automatic cleanup. Update documentation for Beta startup, setup downloads, missing source, best-effort code-change shutdown, manual restart and CLI fallback.
- Address concrete owner feedback and discoverability/accessibility issues without treating a perfect visual design as a release prerequisite. Clearly separate proven defects from proposed future refinements. Keep the existing CLI entry points in the OS-folder roots throughout this FR; do not rename them to Legacy yet.

## Acceptance and delivery evidence

A reproducible synthetic parity/integration run, native launcher/menu smoke results for the supported platforms, the completed feature inventory, and an honest list of unresolved Beta limitations accompany the implementation's normal completion report. Mark unavailable real-platform verification as unverified, not passed. No paid model calls or private account/session dumps are required for regression fixtures. Native read-only smoke tests must not be represented as exhaustive accounting proof.

The owner can now test a fully navigable Beta and request follow-up UI fixes while CLI remains usable. FR000390 stays blocked until the owner explicitly says Web is ready to become the default, even if this FR's tests pass. No production code changes are made merely by publishing this specification.
