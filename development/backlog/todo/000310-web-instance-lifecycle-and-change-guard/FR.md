# FR 000310 — Restart-safe Web lifecycle and simple shutdown on code changes

## Outcome and dependencies

After FR000300, implement the shared lifecycle used by both OS Beta launchers: one detached Web instance per OS user and canonical checkout, verified restart on launch, bounded cleanup, and a deliberately simple code-change exit guard. This is the owner's chosen alternative to an updater or hot-reload system. Follow FR000290/PLAN.md; CLI remains independent.

## Instance and restart contract

1. Serialize start/stop/restart with an OS-appropriate lock, not a PID file alone. Canonicalize installation identity consistently, including Windows path case and symlinks. Keep private state outside Git under the user's local application-data directory, keyed by checkout identity. Record instance nonce, PID plus start identity, bound loopback address/port, startup build/schema identity and protected control authentication. Use atomic state writes and restrictive permissions/ACLs.
2. A deliberate launcher invocation restarts the identified Web instance even when its product version has not changed. Request authenticated graceful shutdown, stop accepting work, cancel/drain owned jobs, close source/SSE/account workers, remove the tray/menu-bar icon, and wait for the process/port to be released. Define a bounded graceful deadline; forced termination is permitted only after revalidating the exact owned process, never from PID or port alone. If identity cannot be established, report the conflict and do not kill an unknown process or start a duplicate for that checkout.
3. Recover from stale state, PID reuse, crash and corrupt state without touching unrelated Python, OpenCode, browser or CLI processes. Different checkouts must not terminate each other. Use an available loopback port; an occupied preferred/previous port does not authorize killing its occupant. Concurrent double-clicks are serialized/coalesced so they cannot leave duplicate instances or accidentally kill the just-started winner.
4. Detach the application from launcher console, stdin/stdout/stderr and terminal lifetime using supported platform mechanisms. Redirect owned diagnostics to bounded privacy-safe logs outside tracked source, close inherited handles and use a working directory outside the checkout. The launcher waits only for verified shell readiness, not complete account/history loading, then opens the OS default browser and exits. Browser failure is distinguishable from server failure and can be retried via the icon. Closing a launching terminal or browser does not end the host.
5. Native GUI startup is supplied by FR000320/000330. Design a single lifecycle owner compatible with a tray event loop on the main thread, HTTP/event processing elsewhere and serialized analysis ownership. Stop is idempotent from menu, launcher, runtime fault and change guard. A dead server must not leave a healthy-looking orphan icon; an unavailable required GUI host must not silently leave an unmanaged background server. Developer foreground mode may be explicit and icon-free.

## Primitive source-change guard

- Establish an in-memory baseline before serving normal work. On a cheap periodic check, provisionally every five seconds, compare relative path membership, `mtime_ns` and file size for explicitly owned runtime Python files, runtime entry points, shipped HTML/CSS/JS/assets and dependency/build manifests. Include added, deleted and renamed files within that allowlisted runtime surface. Traverse no arbitrary repository symlinks or external directories. No native file-watcher dependency or hash of every file on every check is required.
- Exclude `.git`, `development/`, documentation-only changes, logs, cache/state, generated bytecode, virtual environments, dependency installation activity and user configuration. Guard initialization happens after environment setup. The application's own writes must not stop it. A transient stat/read error should be retried and reported honestly, not mistaken for proven file modification; a confirmed deletion/change is sufficient to stop.
- On a detected change, enter a terminal `source_changed` stopping state and initiate the same bounded shutdown immediately. If possible send a final UI status and a sanitized reason before disconnecting; do not make shutdown depend on browser acknowledgement. No automatic restart, hot imports, browser-triggered restart, `git pull`, Git hook, update script, background reloader or deployment copy. The owner restarts with the launcher after finishing the update.
- This is best-effort detection, not an atomic-update protocol. It can miss changes with indistinguishable metadata and cannot prevent a mixed-version interval before detection or every Windows file lock. Never label it a guarantee. Avoid long-lived handles to tracked files and unnecessary native binaries in the checkout. Do not automatically terminate CLI processes when Web detects source changes.

## Acceptance

Use temporary synthetic runtime trees and fake clocks to test modification/addition/removal, exclusion of caches/logs/development files, missed-metadata limitations, startup races and idempotent cleanup. Verify no reload/restart is attempted after detection, resources and locks are released, and a later manual start uses changed code. Test stale/reused PIDs, unresponsive owned server, unknown port occupant, two simultaneous launches, different checkouts, paths with spaces/Unicode, failed browser open and old browser clients after a new instance ID.

Add platform-real launcher/lifecycle verification in the following OS FRs; mocked detachment is not a claim of native success. Use existing error/privacy infrastructure and bounded timeouts. No service install, login autostart, updater or changes to existing CLI launchers in this FR.
