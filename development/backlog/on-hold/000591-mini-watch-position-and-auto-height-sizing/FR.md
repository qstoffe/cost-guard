# FR 000591 — Mini Watch: separate window position and sizing, compact Auto height

## Owner request and decision

**Owner-approved Ready Feature Request, 2026-11-05.** Replace the misleading single **Mini Watch placement** setting (which currently controls **both native position and size**) with two clearly distinguished preferences. Introduce **Auto height**, enabled by default, to keep the separate Document Picture-in-Picture (PiP) window as vertically compact as possible while fitting all current content, growing and shrinking with content where the browser supports it. Preserve an opt-in **Remember last size** mode for manual window geometry.

The owner's final preference is **650-pixel nominal start width**, **automatic vertical height only**, manual horizontal resizing permitted, and ideally no manual vertical resizing in Auto mode. Total **outer-window** height should never be requested above **1,000 screen-device-independent pixels (DIPs)** or the current display's available work area, whichever is smaller. The entire native frame/chrome counts against that cap, not merely the HTML content. If the window reaches its maximum, internal vertical scrolling is allowed.

**Important feasibility qualification:** this is a browser-owned Document PiP window, not a native window manager. As of the current browser APIs, programmatic `resizeBy()` / `resizeTo()` require **user activation inside PiP**; merely receiving a new Live session, account update or timer does **not** authorize resizing. Scripts cannot set PiP's window coordinates, nor reliably forbid native resizing along one axis while allowing the other; `preferInitialWindowPlacement` couples the browser's remembered **size and position**. The implementer **must first verify the actual Chrome/Edge behavior** and not promise unrestricted automatic Live resizing, precise bottom-right placement, a hard native height lock or independently restored position and size without proof. No permission bypass, browser automation, privileged window handle workaround or fake simulated resizing. See the technical fallback and delivery condition below.

**Authoring only now:** publish this independent new FR after existing pending Ready items; do not implement product code/tests/docs or change version/release metadata in this publication.

## 1. Settings: position and size are separate concepts

Proposed user-facing entries under **Settings → Web settings**:

| Setting | Choices | Shipped default |
| --- | --- | --- |
| **Mini Watch position** | Default (Remember last), Remember last, Standard position | **Remember last** |
| **Mini Watch size** | Default (Auto height), Auto height, Remember last size | **Auto height** |

- **Position / Remember last:** retain the browser's most recently user-chosen PiP **location** when reopening within the **same live opener and Web-host instance**, to the extent browser-native PiP behavior actually permits. It must not intentionally reuse the previously manually resized dimensions just because position is remembered.
- **Position / Standard position:** ask the browser for a fresh initial placement on each opening, ordinarily toward the **bottom-right corner** on the supported target setup. Actual monitor, OS taskbar/work area and browser placement take precedence; don't advertise exact hard-coded lower-right coordinates that scripts cannot control.
- **Size / Auto height (default):** each new opening requests the nominal **650-DIP outer-frame width** (as close as achievable through the browser's viewport-size request), regardless of the last manual width/height. While open, the user **may manually change the width**; that width should be respected without continually resetting it, including when content height changes. The current visible content determines the desired vertical height independently of the width. Reopening in Auto should restore the standard width rather than use a previous manual size.
- **Size / Remember last size:** allow manual resizing in both axes and let the browser restore the **last size** on subsequent opens within the **same live opener and host instance**, to the extent supported. Disable application-driven Auto-height adjustments in this mode; preserve the existing functional disclosure overflow and scrolling behavior. Don't persist window dimensions across reload, new browser document, host restart or another user/browser profile.
- Preserve the existing symbolic `Default` versus explicit-choice semantics: missing user override inherits the shipped default and can follow future default changes. Existing `miniWatchPlacement` choices/config are not discarded; preserve or safely migrate/alias the existing value and user intention, with an added allowlisted size setting. Use normal validated JSONC writes, Settings API, defaults and error rollback. Changes apply **on the next opening**, not by forcibly moving/replacing an already open PiP.
- Correct the UI copy: today **Mini Watch placement** describes remembering position *and size*; the new labels and descriptions must distinguish what each setting **intends** to control. No extra geometry persistence in config, storage, cache, cookies or URL.
- **Do not assume the position/size settings can be fully orthogonal in every Chromium version.** Test all four non-default combinations. Because native `preferInitialWindowPlacement` resets/reuses position and size together, document supported combinations and any unavoidable limitation. Prefer a predictable in-bounds window to silently breaking the user's selected position or sizing policy; never claim unsupported combinations are exact. If independence cannot be delivered, record an explicit feature limitation and request owner decision rather than quietly declaring the requirement fulfilled.

## 2. Auto-height: smallest content-fitting window, with bounded growth and shrink

**Desired behavior wherever permitted:**

1. On the first and later **Auto-height openings**, choose the smallest safe overall height that fits the existing Mini layout: header/return action, CCost Today, visible health/status messages, running prompts, collapsed or expanded **Earlier Sessions** (fresh openings normally start collapsed), and **all visible subscription/account rows and bars**. Include padding, borders, normal font metrics and browser chrome; no pointless empty vertical area.
2. When **Earlier Sessions** expands, grow the PiP height to fit the newly visible sessions; when collapsed, **shrink again immediately** toward the smallest fit. Existing explicit-user-action resize behavior in `mini.js::DisclosureSize` is a starting point, not a second competing geometry owner.
3. If new running prompts, ended rows, multiple simultaneous sessions, account rows, warnings or other visible sections change height, **recompute desired height** and grow/shrink accordingly **when the browser permits**. Pure Live/SSE publications must not trigger unauthorized/native-blocked resize attempts on a loop. Retained/partial data, stale host status and real row removals must be represented accurately.
4. In Auto mode, remove or adapt today's **CSS max-height limits** (`.mini-prompts`, `.mini-accounts`, etc.) that would otherwise introduce internal scrollbars **before** the outer window reaches its legitimate max height. The goal is **no vertical scrollbars anywhere when content actually fits below the cap**. Once capped, let the necessary content area scroll with accessible keyboard/touch input and preserved sticky table headings; never hide rows or silently drop history/subscriptions. Preserve existing necessary horizontal overflow for a genuinely too-narrow user width.
5. At each supported resize, preserve the actual **current width** (including user-chosen width while open) and do not snap it back to 650. Avoid fractional-DIP width drift from repeated `resizeTo` rounding, zoom, Windows 125%/150% scaling and monitor changes. Coalesce layout changes into a bounded, non-looping measurement, avoid jitter from subpixel/scrollbar thresholds, and don't make costly repeated resize requests per SSE frame.

**Cap and screen safety:**

- Target **1,000 DIPs maximum outer-window height**, reduced further by the current display's **available work-area height**, a small margin and the browser's own PiP maximum/clamp. This is not `1,000 CSS content pixels` or `1,000 physical display pixels`; `requestWindow({width,height})` sizes the viewport, whereas `outerHeight` includes the browser frame. Measure actual `outerHeight - innerHeight` when supported and clamp intended **outer** dimensions accordingly. Initial width's 650 target is likewise **outer-frame** intent; document native viewport-versus-frame adjustment and browser rounding.
- On small screens, taskbars/docks, high DPI, zoom, side/bottom OS UI, and external/secondary monitors, the window must remain **within its browser/OS work area as far as the available API can establish**, not expand below the taskbar or off-screen. If the PiP sits near the bottom, prefer browser-supported **upward/in-bounds growth**, preserving its user's chosen location where possible; never call blocked `moveTo`/`moveBy` to fake it.
- If the browser cannot guarantee upward growth/repositioning or the available display is smaller than the content, **cap the resize at what can actually remain visible** and allow inner scrollbars. The work area and browser clamp outrank the nominal 1,000 target. Avoid requesting new **Window Management** privileges merely to query all monitors; handle unavailable/multi-monitor geometry conservatively.

## 3. Browser-owned interaction boundaries: auto height vs manual size

- The requested **ideal** in Auto-height mode is: manual drag/move allowed; **horizontal-only manual resizing** allowed; **vertical manual resizing disabled**, so the Auto algorithm owns the height. However, Document PiP's native window frame is **not an HTML `resize` element**, and there is no proven web API that locks only the vertical resize handle or disables native sizing while retaining move behavior. Investigate feature support, but **do not claim CSS can disable native window resizing**, spoof a lock, or fight the user's native drag with a resize-event oscillation.
- Graceful fallback if the browser allows manual vertical resizing: **leave the native action available**. Keep Auto as a content-fit *intent* on future permitted user gestures/openings, not a forced snapback loop that battles the user's drag; preserve manual width. If this materially differs from the owner's desired locked-height UX, document it clearly.
- **Resize requires user activation** in Document PiP. Expansion/collapse via the existing **Earlier Sessions** click is eligible; ordinary Live row additions/removals, timer callbacks and remote account updates are not. Provide correct **content-fit measurements** on every change, but only perform native resize when genuinely allowed. On unsupported/non-user updates, prefer stable current geometry plus internal scroll instead of silent failure storms, hacked synthetic user gestures, re-opening PiP, unexpected focus stealing or unauthorized permission requests.
- Before claiming background Auto-height works, prove it with **real Chrome/Edge Document PiP behavior**. If a future supported browser provides native content auto-sizing or lawful background resize, use it behind feature detection and tests. Otherwise the delivery must explicitly distinguish **fully automatic size at open/eligible clicks** from **unavailable hands-free resize on Live updates**. Do **not** mark the latter as passed without browser evidence.
- Auto mode should not introduce a new required button, per-update popover or repeated prompts just to make expansion work. Existing Later/Earlier disclosure, owner-tab navigation and true status remain intact. If optional user-triggered “fit height” recovery is considered essential for a limited browser, keep it a documented implementation option rather than silently changing this UX request.

## 4. Implementation and regression scope

Likely current owners to inspect **after other queued FRs land**:

- `src/web/assets/mini.js`: `Controller.toggle()` currently uses `requestWindow({width:560,height:250,preferInitialWindowPlacement:...})`; `DisclosureSize.toggle()` currently performs one bounded height resize from a **PiP click**, and does not resize on Live publication. Refactor toward one size policy and one safe bounds/measurement owner, not multiple observers racing.
- `src/web/assets/mini.css`: the flex layout, `.mini-prompts` `max-height:10.8rem`, `.mini-accounts` `max-height:8.4rem`, internal scrolls, sticky tables and container padding require a design for content-first Auto mode vs saved manual size.
- `src/web/assets/settings.js`, `src/web/settings.py`, `src/config.py`, `config/default-config.jsonc`, settings API allowlist, exposed values/defaults/choices and the existing mini placement subscription. Preserve settings atomic-write security and DOM isolation. Do not alter other Web/CLI settings or account acquisition.
- Existing `docs/web-mini-watch.md`, `docs/web-beta.md`, `development/architecture/modules/web.md`, Mini journal and focused unit/integration/real PiP browser regression fixtures. Coordinate with FR000589/FR000590's pending header/tooltip changes; the sizing work must not reintroduce help icons, regress accurate tooltip hitboxes or obscure content.

## Acceptance / truthful verification

1. Settings show **Mini Watch position** and **Mini Watch size** independently, with `Default (Remember last)` and `Default (Auto height)` respectively; existing user placement config still resolves correctly. Settings persist choices only, not geometry; next-opening semantics and source-default inheritance work.
2. Fresh Auto window targets **~650 DIPs total outer width**, uses the smallest content-fitting height, and is capped at **min(1,000 outer DIPs, actual usable screen/work-area/browser maximum)**. Native PiP rounding/clamping is measured and reported rather than invented.
3. **Auto + Earlier Sessions**: expansion grows and collapse shrinks when browser click activation permits. Visible prompts, expanded history, subscriptions and warning/status are included in the fit, with no premature vertical scrollbars below the effective cap. Above cap, scrolling remains readable/accessible; tables, quotas and titles are not lost.
4. When a user changes width while Auto PiP remains open, any legitimate vertical adjustment preserves that width. Manual native vertical resizing is prevented **only if a real browser-supported mechanism is proven**; otherwise user control is not fought with loops and the limitation is disclosed.
5. New/removed concurrent prompts and account/history/state transitions recalculate desired height; **only resize natively where permitted**. A purely background Live update **must not be claimed to have auto-resized** if Chrome/Edge blocks it. Show correct fallback scroll and retained content instead. No recurring polling, per-event native resize spam, unexpected window reopening or focus stealing.
6. Remember-last-size preserves browser-owned manual size within the current opener/host, disables Auto adjustments and tolerates any PiP clamp. Position modes preserve remembered vs browser-initial position **to the extent actually supported**, without pretending that the browser permits script-level positioning or independent restoration of both properties where it does not.
7. Real-browser test matrix covers all position × size combinations, first open/reopen/reload/host restart, manual width and height changes, prompt additions/removals, Earlier expansion/collapse, zero/many subscriptions, body/header content, Classic/Web themes, narrow displays, Windows display scaling, browser clamp, taskbar work area, multi-monitor moves where feasible, native PiP close and layout stability. Separate **measured browser PASS**, **unsupported platform/permission**, and **unverified physical behavior** truthfully.
8. The principal product goal remains **hands-free vertically resizing on any Live content change**. If the current Document PiP platform blocks this, record the precise blocker and **do not claim full delivery** merely because open-time fit/explicit-click resize and scrolling work. Return that product limitation for an owner decision about a later alternative; preserve the partial safe improvements separately as appropriate.
