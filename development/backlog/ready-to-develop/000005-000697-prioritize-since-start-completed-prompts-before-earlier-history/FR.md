# FR 000697 — Watch and Mini Watch: show newly completed prompts immediately while cold Earlier history is still loading

**Owner-approved Ready to Develop — 2026-11-13.** Permanent ID **000697**, priority **000005** (immediately after FR000696 at 000004). **Feature request only:** create a reviewed implementation task in the Cost Guard backlog, not a direct product-code change, native database access, version bump, new worker, live model call or installed service change during authoring.

## Owner-observed reproduction and desired behavior

On a fresh Cost Guard start with a large OpenCode history, **Earlier Sessions** in Web Watch and **the five-session activity list** in Mini Watch take noticeable time to finish loading. While that backlog is still loading:

1. The owner started an AI request that stayed running long enough. It **appeared promptly** as a Running prompt in Watch/Mini. This existing live path works.
2. The owner then ran another prompt that completed **extremely quickly, reportedly under one second**. It apparently **never appeared as Running** (normal if the live poll missed that very short window), **but also did not appear as a recently finished/Earlier prompt** until the entire older history had finished loading.
3. The owner wants **new prompts created or completed since this Cost Guard/Live Watch startup** to be prioritized and visible soon after they are confirmed, even when several thousand older sessions remain unverified. Several rapid prompts should update the relevant latest-prompt representatives promptly rather than wait for minutes of startup-historical scanning.

**Do not assert this owner's incident was reproduced by the FR author.** The observations above are owner-reported; the source paths below establish a plausible and actionable causal mechanism.

### Expected user experience

- **A long-running prompt:** still appears in Running promptly; a real observed running→finished transition becomes a brief completed success/error/abort highlight and then a recent finished candidate as today. The prompt is not lost when the 30-second or other finite running grace ends while Earlier remains loading.
- **A fast prompt that was never seen Running:** after the source confirms its saved final/terminal state, it **appears as a finished recent prompt/session even though Earlier's legacy global proof is still pending**. It does **not** need to have been previously observed running.
- **Several rapid prompts:** a newly completed prompt in a previously unknown root or in an existing root advances that session's latest representative; multiple different recent sessions occupy the most recent available Mini slots. Same session normally remains **one latest representative row** in Mini / one most-recent history card in Full Watch, matching current session-card semantics rather than showing duplicate rows for every prompt in one session.
- **The older Earlier baseline is still loading:** display a clear truthful `Loading earlier sessions…`/verification status for the still-unverified older population, **alongside already verified newly finished cards**. Do not freeze or suppress new results just because older roots are still being checked.
- **Once historical verification finishes:** reconcile into the existing source-verified canonical newest-five Full Watch result and Mini's latest five session activity slots, without duplicates, phantom reordering, lost focus, wrong completion time, wiped scroll, or an endless loading notice.

A session created days earlier can produce a new prompt today; it qualifies by its **new confirmed prompt finish/activity**, not its session creation date. Conversely, a session's catalog `updated_at` changing after Cost Guard started does **not** by itself prove that a new prompt finished.

## Verified code-level findings (repository main, not live private reproduction)

### 1. The current strict global proof blocks all new finished-card membership

- `src/watch/history_publication.py::HistoryPublication.project()` currently computes `ready = (checked == total) AND all(candidate captures exist)` across **every root in the selected historical catalog**. Only once this is true does the producer issue the definitive `observed` five-card list. This is the intentional FR000623 safety contract against displaying a *partial historic scan* as a verified global top-five.
- While not ready and with no previously certified epoch, `HistoryPublication.cards` remains empty and `history_state` is `loading`. Neither Watch nor Mini can see a newly finished card solely from this ordinary history channel.
- `src/web/assets/watch.js::View.update()` treats the producer's `history_cards` as usable only when `history_state === observed` or an existing `history_epoch > 0`, and shows a loading message otherwise. `src/web/assets/mini.js::sessions()` similarly uses `history_cards` only when history is observed/retained, then selects one representative per session and fills up to five total rows.
- **Important previous FR:** completed FR000623 and FR000624 deliberately strengthened trustworthy global historical winner verification. **Do not revert their anti-provisional behavior** to make new prompts appear; instead create an independently qualified **post-start source-verified recent lane/overlay** whose existence does not falsely certify the unread historical population.

### 2. The active/recent channel can miss a prompt completed between observations

- `src/watch/cards.py::WatchCards._focals()` selects rows that are *currently running / execution-unverified* or were seen in an actual **observed running→terminal** transition and remain in the short `terminals` grace window. A request that started and ended completely **between polls** can enter the first captured snapshot as *already finished*, never entering `terminals` and therefore never appearing in the active/recent channel.
- After the grace ends, even a correctly captured finished prompt must ordinarily be selected through the separate `HistoryPublication` global proof, currently held by the old backlog.
- `src/watch/cards.py::WatchCards.tick()` admits `busy` candidates with priority and reserves bounded historical workers; a newly completed root not recognized as active can fall into the **historical queue**, sorted primarily by its existing `admission_order` and then its root metadata timestamp. It can be delayed behind many previous historical reads even though its newest saved request is precisely what the owner wants to see.
- `src/watch/card_workers.py::CardWorkers` already provides a **bounded four-worker source-qualified capture lane**, per-session generations and completion wake-up. `src/watch/web_coordinator.py::WebWatchCoordinator.service_completed()` drains finished capture results without requiring another full source poll. Prefer **prioritizing recent changed roots within this existing lane** rather than launching an unbounded second reader/scheduler.

### 3. A source change is an acquisition hint, not a finish certificate

- `src/watch/coordinator.py::WatchCoordinator.poll_once()` uses event hints, native catalog/revision changes, active candidates and recent source activity to select relevant changed roots. `src/watch/acquisition.py::LiveAcquisition.tick()` receives bounded `LiveEventPump` hints and schedules an authenticated source refresh; hints alone do **not** prove that an AI request was executed or completed.
- `src/watch/cards.py::WatchCards.accept()` already checks session generation and source snapshot revision and stores per-row `at_ms` / `completed_at_ms` and actual terminal status. `HistoryPublication.project` retains revision-keyed verification. Use **the exact root/canonical prompt source record + finish and source generation/revision** to qualify a new post-start candidate, not wall-clock arrival, untrusted titles or latest catalog metadata.
- `WatchCoordinator.started_at_ms` (also exported as Live `started_at_ms` with `run_origin='Web live engine start'`) is already an available process-lifetime anchor. Prefer this **single authoritative Live-engine start/first-source-baseline scope** over Mini PiP creation time, Web tab navigation, render start, observer polling timestamp or a browser-local clock. In particular, a prompt already running at process start but **confirmed to finish afterward** should be eligible.

**No documented current evidence proves the owner's specific quick prompt had one of these exact loss paths**; an implementing worker must validate its own initial source-shaped before/after case rather than assert the test models reproduce the private incident.

## 1. Required design: recent new-prompt lane independent of global historical readiness

**High-level invariant:** a source-verified prompt/session whose **canonical finish** is reliably on or after this Watch engine's start must **not wait for all pre-existing historical roots** before becoming available as a recent finished card. The **final global top-five** still requires FR000623's complete historical proof.

A suitable implementation may use one small **bounded recent-since-start collection/overlay** in `WatchCards` or a revised `HistoryPublication` contract, backed by the existing per-root capture/revision data; the implementation worker should select the smallest safe design.

1. **Detect the right roots early.** Mark bounded, source-qualified **new or changed roots since the initial catalog baseline** as higher-priority Watch candidates when live events, root revision changes or a new root become visible — even if no poll observed `in_progress=true` and a root's previous capture did not exist. Use root-to-parent mapping to include subagent/child execution under the correct root. A mere metadata timestamp change qualifies a root **for inspection only**, not publication.
2. **Do not require a Running sighting.** A single authoritative per-root snapshot may show one prompt created/completed entirely between observations; capture it, verify exact session/provider source identity/revision and terminal/canonical completion, then publish it in the recent finished lane. Never invent an intermediate Running card or a completion transition.
3. **Qualify by prompt evidence, not history-scan position.** Prefer a concrete canonical representative prompt/finish event at or after `watch_started_at_ms`. Do not infer from a late historical read, a cache write, root `updated_at_ms`, source poll time, age since observation or the fact that the root was processed later. If a pre-existing active prompt finishes after startup, include its **actual verified finish** even if `at_ms` predates startup. If source timestamp trust/clock skew or a missing terminal boundary makes qualification uncertain, retain an honest pending/unverified state rather than fabricate recency.
4. **Prove correct identity.** Bind each candidate to source generation/instance, root revision, actual prompt event ID, finish time and supported completion/failure/abort outcome; reject late old-generation workers, unverified or partial snapshots and wrong-root replay. Preserve privacy/sanitized read-only source access and existing bounded persistence/caches.
5. **Bound and rank separately.** Rank recent finished candidates using canonical supported **finish time**, stable root/prompt tie breaks and the existing eligible five-slot rules (not the order a worker happened to return). Retain just the small visible/relevant evidence + enough revision data to recheck it. Protect currently running / short finished-grace cards against replacement by historical fillers. Newer actual finished prompts displace older verified recent candidates; do not make one root generate multiple Mini rows.
6. **Truthful partial provenance.** While `history_checked < history_total` or global history proof is otherwise not complete, do **not** change the global `history_state` to `observed` or fabricate a certified `history_epoch` just because a new candidate exists. Export a clear **recent verified, global-history-pending** distinction in the immutable Live projection (e.g. an additional `recent_finished_cards`/scope marker), or an equivalently strict approved producer contract. Both Full Watch and Mini must consume the **same single server-qualified** recent candidate set; no browser-side guesses or independent latest-ranking of unverified source data.
7. **Visible during historical Loading.** Full Watch's **Earlier Sessions** region may show the qualified recent finished cards **alongside an accurate loading status** for older history. Mini Watch's five-row session activity should fill its non-running slots with qualified newest finished candidates **even though the global Older/Earlier baseline is still pending**. Respect existing headings, session links, "Finished"/"Activity" timestamp text, tooltip, context/cost semantics and accessibility. Empty recent candidates still show the previous `Loading earlier sessions…` behavior, not fake `No earlier sessions`.
8. **Keep recent cards until reconciliation, not just the grace timer.** A completed recent prompt must **not disappear at 30 seconds** only because global Earlier proof is still unresolved. Preserve the newest bounded verified candidates across ordinary poll, warm refresh, Mini reopening/route changes and transient source delays (truthful retained/refreshing state when appropriate); retire them only when invalidated by actual source evidence, displaced by truly newer verified candidates, or atomically superseded by the final certified historical population.
9. **Atomic convergence.** When the background history sweep finally proves every relevant root/revision, publish the definitive global five from existing `HistoryPublication`, and reconcile any recent subset exactly once. Deduplicate by source-qualified root and prompt ID; do not produce two competing "Earlier" rows or momentarily clear just-completed prompts. If an old session still has a prompt that ended *after* Watch start, its verified finish participates correctly. If baseline proof becomes stale, maintain/revalidate recent qualified cards without presenting stale global winners as newly certified.
10. **Keep the current resource/safety contract.** No new unbounded scanner, non-owner process, per-prompt background worker, provider inference call, price reload, shared database mutation or raw session-export publication. Reuse bounded Watch capture workers, live hints, source revisions and existing event/completion wakes. Protect responsiveness of active Running prompts, daily CCost, quota, Watch/Mini reconnect, canonical cost pricing and other finite report sources. Recently changed roots get **reasonable bounded priority** over cold archive work without starving older candidates forever or exhausting source API. A 4,000-root history does not need to complete before one new root can publish.

## 2. Fast discovery and controlled latency: improve the real critical path

- **Measure distinct clocks:** user prompt's source-backed start and finish; native source event/catalog visibility; coordinator hint acceptance; root capture admitted, completed and revision-verified; Live publication produced/SSE delivered; Full Watch DOM and Mini PiP DOM painted. Never claim that a timestamp from a different clock domain proves sub-second end-to-end latency.
- **Source acquisition:** ensure a new terminal source event/change gets an early bounded read even when there were **no active prompts on the previous polling cycle** and the Watch engine is on its idle cadence. `LiveAcquisition.tick()` currently coalesces hints into a deadline (up to five seconds) before a new source read; investigate whether safe event-driven promotion or a tightly bounded expedited candidate check materially improves fast-prompt visibility. An API hint remains a hint until validated by a source read. Support V1's lower-information polling path as a best effort; do not claim V1 has native events it lacks.
- **Card acquisition:** when a source-backed changed root has a just-finished candidate, ensure it is not trapped behind thousands of prior-queued historical entries or long-running low-priority chunks. A single fast source snapshot should be admitted with bounded foreground priority while using existing four-worker/source-capacity limits and historical fairness. Incremental historical capture continues in parallel.
- **Publication:** once the per-root authoritative finished result exists, publish via the next existing Watch Live/SSE + UI frame, independently of global `HistoryPublication` readiness and without waiting for a costly daily CCost or full-session cost-enrichment scan. Display qualified known prompt/model/CCost/CTX fields as they become available; don't invent unknown prices or context. Do not wait for contextual help enrichment just to show an already verified prompt identity and finish.
- **Target:** in controlled healthy fixtures, the newly completed prompt should be visible within **one bounded source-detection + prioritized card-capture + normal Live-publication cycle**, usually within seconds and **before** the deliberately delayed old history finishes. Report measured p50/p95 latency split at each stage and whether existing idle polling/batching is the dominant delay. Do **not** promise below-one-second detection in an installation whose chosen source only polls every five seconds; do not make a fake "instant" placeholder as a substitute for actually detected prompt evidence.

## Completion criteria

With **Earlier Sessions still Loading** on a large cold history, **a prompt that was created and finished too fast for the Running state to be sampled** must be displayed promptly in **both Watch and Mini Watch** after its **actual source-backed finished state** is read. Additional fast prompts update the appropriate recent session representatives immediately on verification, not after unrelated historical roots finish. If a prompt was already Running, it remains visible through completion/terminal grace and, when relevant, as a recent source-verified candidate while baseline history continues. Once old history is certified, both views converge to the **correct global latest sessions** without duplicates or fictitious prior-state proofs.

**Not accepted:** treating root `updated_at_ms` or EventSource hints as confirmed completion; marking global history `observed` early; showing randomly scanned old roots as globally newest; dropping fast prompts after 30 seconds; implementing only a loading spinner, cosmetic reorder or historical-scan speed improvement; keeping the new candidate behind a huge old-worker queue; requiring an earlier Running sighting; displaying different source-derived winners in Full Watch and Mini; claiming subsecond end-to-end certainty when the source has not yet reported the prompt; or changing installed native session history.
