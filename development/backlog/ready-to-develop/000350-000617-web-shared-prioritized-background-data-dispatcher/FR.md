# FR 000617 — Web Beta: host-owned prioritized data dispatcher, shared warm cache and intelligent background refresh

**Owner-approved Ready Feature Request, 2026-11-06.** Permanent identity **000617**, Ready queue priority **000350**, after existing FR000616 (000340). This is a substantial **cross-page runtime architecture overhaul**, but **this transaction is FR-only backlog publication**. Do not modify product code, tests, settings, user documentation, versions, releases or unrelated backlog entries while creating the FR.

## Problem, intent and success experience

Today a user may leave Cost Guard running on **Watch**, **Mini Watch** or a browser tab for several hours, then visit **AI Stats**, **Token Mix**, **Comparisons**, **Models** or **Sessions** for the first time and wait for a separate expensive history acquisition. Even after useful source data has been read for other views, this is not coordinated as one demand-aware, reusable system. Historical refresh also depends on keeping the relevant browser route active and visible.

The owner wants **all useful top-level views to warm in the background without visiting them**, at very low priority, with the following user-observable behavior:

- Opening the app starts the **current visible route first**. It is the highest-priority *non-Watch* user demand until its necessary view data is ready. Other routes should be registered for low-priority prewarming and may make opportunistic progress in idle capacity, but **may not delay completion of the selected foreground route**. It is acceptable for the first, cold background warm-up to consume some additional resources *after* foreground readiness or otherwise demonstrably without slowing it.
- **Watch is special: always live, highest protected service priority**, regardless of which Web page is selected or whether the owning browser is backgrounded, minimized, or displaying Mini Watch. Preserve existing Live source, accounts and running-prompt correctness. No report warm-up can starve or queue behind Watch.
- Navigating to any other route should **immediately raise that route's existing task priority**; already-completed useful work is reused, and remaining work advances ahead of inactive reports. Navigating away lowers its priority but does **not** throw away its results or safe partial progress. Newly selected content should appear quickly if already warm; otherwise show the existing centered 0–100% progress UI with actual scope/stage/counts.
- When a requested report's **last valid observation is no more than one hour old**, show it **immediately** on route entry, then quietly revalidate/refresh as appropriate. When it is **older than one hour, missing or proven invalid**, present a progress/loading state rather than treating stale content as current. Preserve the last result internally for possible clearly marked failure recovery. **Never represent cached age, partial source coverage or a stale successful job as freshly acquired data.**
- Inactive views continue to be warmed and refreshed by **the local host** at a low, staggered cadence — approximately every **15–60 minutes by cost/type**, not a synchronized all-pages stampede. Foreground views generally refresh more often, based on data value and cost; **Models** is exceptionally slow-changing and can refresh at most hourly once its sample has stabilized. There is no user-facing Refresh requirement for routine report freshness.
- Use one **dispatcher/coordinator for data demand and shared reusable evidence**, not multiple tab-owned source scans. When two pages need the same session revisions/analysis, acquire the canonical inputs once when safely possible, then produce each page's distinct and truthful projection. **Do not eagerly load every Sessions pagination page or every session's full detail**, because only the current requested page/detail is useful.

The result should feel “already there” when switching tabs after idle time, without maintaining sustained high CPU or repeated duplicate acquisitions. This FR defines the architecture and externally testable scheduling contracts; the implementing team may refine exact component boundaries and cadence from measured evidence rather than hardcoding an unverified thread count.

## Research: what is already present versus what is missing

**Current source inspection, not a performance claim for the owner's exact installation:**

1. **Watch/Accounts Live is host-owned already.** `src/web/host.py::WebHost` owns the lifetime of `src/application/live.py::LiveRuntime` independently of tabs. `src/watch/web_coordinator.py::WebWatchCoordinator` has existing bounded workers for cards, account history, Sessions catalog and session details, and a single canonical source/Watch owner. Full Watch, Accounts and Mini Watch consume prepared Live publications; **Accounts must not receive a redundant second quota-provider scheduler** from the new dispatcher. Mini shares the owning tab's authenticated Live stream and server, not a second acquisition engine.
2. **Finite historical reports are not prioritized by active route.** `src/web/assets/app.js` initiates eligible Models/Token Mix/AI Stats/Comparisons jobs on **visible** entry; `scheduleCachedReport()/enterCachedReport()` refresh only the currently selected, visible historical view. Browser-local `views` is a bounded memory map, not a server-wide warm result registry. `src/web/jobs.py::ReportJobs` coalesces identical running/recent jobs and allows four queued/running entries with **one active spawned report process**, an ordinary 120-second per-job deadline and an 8 MiB result bound. Its kind-based order prioritizes Normal over historical jobs, **not whichever historical page a user just chose**. A single long uninterruptible background job would block a new foreground request.
3. **Historical freshness is partially implemented.** `src/web/assets/cached-reports.js` currently uses **5 minutes for Token Mix/Comparisons, 15 minutes for AI Stats**, and withholds views older than **60 minutes** on reentry. It does **not** schedule inactive background refresh or cover Models, Sessions and other view contracts. Source-result observation time matters; navigating to a route is not a successful acquisition.
4. **Overlapping evidence is already cached, but not globally dispatched.** `src/web/composition.py::application()` creates a fresh source selection, report service, pricing provider and disposable SQLite cache per finite child. `src/analysis/cache.py` has revision-/dependency-checked derived analysis; `src/reports/token_mix_cache.py`, `src/reports/ai_stats.py`, `src/reports/matched_inputs.py` and `src/reports/session_summary.py` maintain **different, compatible-but-not-interchangeable** compact caches. All can depend on some of the same root catalog/revisions, request usage, prompt attribution and price catalog. Reusing raw/derived canonical work is sensible; **combining their final cost/match/statistical outputs indiscriminately would be incorrect**.
5. **Models is not just a static price file.** `src/reports/sampling.py` uses a **100-sample target of eligible/priceable prompts** for model cost comparison and token-mix evidence, with real chronological/tie eligibility. It may require more than 100 raw prompts to fill that sample. `ModelsPriceRefresh` is a separate explicit **Refresh price list** action and does not mean normal report revalidation should make fresh remote pricing calls on every background timer. Model availability, source, price age and sample versions are distinct dependencies.
6. **Sessions is a live, paged catalog, not another historical finite report.** `src/application/session_catalog.py` owns a full root metadata index, bounded per-root scalar indexing, **50-row pages**, stable older-page epochs and active viewer leases; `src/web/assets/sessions.js` polls the selected catalog page about every five seconds while attached. A deep `/#/sessions/<id>` detail is separately acquired on demand in `src/application/session_detail.py`. On returning by clicking the **Sessions main-nav link**, `app.js::navigate()` passes fresh default parameters to `SessionsCatalog.configure()`, so a previously selected **page 10 normally resets to page 1**; browser Back to the precise old URL is different. This FR includes the owner's desired same-app last-page restoration where its epoch is still valid.
7. **The browser cannot own reliable minimized scheduling.** Background/hidden pages may have JavaScript timers throttled and animation frames paused (see MDN Page Visibility API). The central due-time queue and heavy work admission must be **host-owned** with browser tabs sending at most lightweight active-route/visibility *interest* signals, not issuing deep report jobs every quarter-hour.
8. **Existing limits and pending FRs matter.** The shipped FR000609 shared loader must be reused. Ready **FR000614** requests resumable, progressively prioritized AI Stats beyond one 120-second *logical* report; Ready **FR000615** removes report Cancel buttons without disabling safe internal teardown; Ready **FR000616** improves the active Sessions rows and model help. This dispatcher must coordinate their results and scheduling, **not overwrite their requirements or invent new UI cancellation**. Other report kinds retain their legitimate finite watchdogs until safe incremental execution is implemented.

## Proposed architectural contract: one demand-aware host dispatcher

Introduce **one central host-owned data demand / scheduling layer** in the existing Web host lifecycle. It may be a coordinator over current specialized owners rather than one gigantic mutable data object. Keep canonical analysis in Python and the existing independent Watch/Accounts, Sessions and finite-report owners, with a **shared task registry, revision-aware evidence reuse and effective priority arbitration**.

A task/subscription should describe: **view or data-product kind; canonical source identity/generation; actual dependency signature (root catalog/tree revision, pricing/algorithm/timezone as relevant); requested scope/period or selected page; last successfully observed/validated time; current status; progress/counters; interest/priority; and bounded checkpoint/retry ownership**. The host deduplicates equivalent work across tabs/views and may coalesce shared prerequisites without confusing distinct report semantics. No browser tab independently owns or executes one global background scanner.

Recommended execution model (design latitude retained):

- **Protected Live lane — absolute priority:** existing Watch source/card/account/Today cadence and Mini's data. Work remains active at the existing source-safe rate even with no browser tab in front. Reserved IO/CPU responsiveness means extra report workers cannot starve Watch.
- **Foreground lane — next priority:** the currently selected visible route and its selected scope/page, including an ordinary user navigation or explicit user action (e.g. a session-page change or Models' actual price-list refresh). New foreground interest must take effect **within one bounded scheduling quantum** rather than waiting for an entire 120-second historical child. Foreground scope may reuse a partially warmed dependency instead of starting a duplicate job.
- **Requested in-progress lane:** unfinished work already requested by a human and not currently foreground, including AI Stats 30 days while 7 days is selected. Its checkpoints survive priority reduction; safe internal pausing/preemption is *not* a user-facing cancellation. Resume without resetting valid work.
- **Background first-load warm-up and periodic refresh:** opportunistic lowest-priority work for the other relevant top-level routes, paced and staggered. No full-history scan should start if it would measurably delay an incomplete foreground view or exceed reserved Live capacity. A small available IO-only prerequisite may be fetched concurrently **only when proven harmless**.
- **Failure/backoff lane:** unavailable/terminal dependencies back off with typed status and bounded retries. One broken report/source must not fill every queue slot, spin forever or block unrelated cached pages.

Use **one source of scheduling truth** per host: avoid both browser timers and a second periodic host loop independently submitting the same job. Retain authenticated local API/session/CSRF protections and exact instance identity; a tab may report its *interest*, never arbitrarily grant itself unbounded worker capacity or request cross-source objects.

### Task priority changes, multi-tab and lifecycle

On authenticated entry, focus/visibility change, internal route/scope change and navigation Back/Forward, the browser reports a **bounded interest lease** for its visible route. The host computes effective foreground demand across multiple authenticated tabs; if several windows are genuinely visible/active, coalesce identical scopes and fairly serve distinct selected scopes without starving any. Expired/closed/disconnected leases lose foreground priority. A minimized/hidden page does **not** become a high-priority foreground requester, but host-owned background warming can continue at its **low idle budget** even when all browser windows are hidden.

**Start order:** initialize/prove the single existing source owner; give the initial selected page (often Models, but a direct Watch/AI Stats link may be first) the first foreground opportunity. Queue all other *relevant default top-level data products* as low-priority interests. They need not finish or even execute a heavy chunk before the first foreground result; once foreground is ready, warm them opportunistically without simultaneous saturation. **Do not start all expensive full scans on host launch before an authenticated Web interest exists** if doing so would waste resources. After an authenticated session has initialized interests, preserve modest host-owned work through tab hiding/minimization while that host stays alive; stop all owned work on host shutdown/source-identity invalidation.

Changing the active page must promptly **promote/reorder outstanding work**, not merely repaint its progress while another monolithic low-priority scan remains uninterruptible. Break expensive multi-root historical jobs into bounded source-safe stages/checkpoints, yield between slices, and use safe internal preemption; a running source operation may finish its short bounded quantum before yielding. **Avoid abort/restart of all already-completed roots** and avoid duplicate hydration for one source revision. Preserve FR000614's logical AI Stats continuation and FR000615's no-user-Cancel promise. Do not disable technical timeouts, parent-loss process sentinels or host shutdown cleanup.

## Background data set: warm useful views, not every possible row

The default low-priority initial warm set is intentionally **bounded**:

| Web surface | Initial and inactive work | Active behavior / exclusions |
| --- | --- | --- |
| **Watch and Mini Watch** | Existing always-on Live owner, highest priority | Continuous canonical Live cadence, including background/minimized; no report-style one-hour stale allowance |
| **Accounts** | Reuse the **same** Watch/account/quota publications and period costs; no independent second provider refresh | Display most recent valid observation, promptly detect source/account errors; refresh via protected Live owner |
| **Models** | Prewarm **one normal Models report** with catalog/model availability and latest eligible sample; reuse pricing/derived evidence | Slow cadence once sample is full; explicit **Refresh price list** stays separate and higher-priority when invoked |
| **Token Mix** | Prewarm its one default summary/report through shared historical evidence, at low priority | Higher priority upon visit; retain independent table sort/filter/scroll; no parallel duplicate full-history scan |
| **AI Stats** | Prewarm **default 30 days**, including independently valid Today and 7 days when supportable; bounded/reusable work | Selected month/All time scope becomes higher priority only when requested. Previously requested broader work may continue low-priority/resume, but do **not** eagerly scan all lifetime history for every possible period by default |
| **Comparisons** | Warm the all-root match *index* and the **first visible ten-group page only** (as its current report contract requires) | Requested page/offset is foreground. Keep exact-first-input matching, revision and paging semantics. Never prefetch previews for every group |
| **Sessions catalog** | Reuse Live root catalog/index; warm useful **first-page metadata/scalars** or the last remembered viewed page within a bounded cache | Only the requested **50-row page** and any global **sort-key index genuinely required** by the chosen sort. No eager content acquisition of pages 2…N |
| **Session detail** | **No speculative prefetch** for every session; optionally retain one/few explicitly visited details under bounded leases | Requested detail has priority on entry, preserves original per-root revision/25-row chunk semantics and live updates; large histories remain on-demand |
| **Settings** | Use existing settings cache/config as part of host/browser bootstrap; no expensive history work | Read/revalidate on actual entry/apply as today, no artificial periodic page job |

A report can share its **source catalog, root revision, normalized derived analysis or immutable compact source facts** with a second report, but output is still projected using the recipient report's distinct cost basis, first-prompt identity, duration union, time window and completeness rules. Never claim that a complete Models sample proves entire Token Mix history was scanned, or that 30-day AI Stats proves complete All time.

### Sessions page/sort restoration

Remember the **last selected Sessions list offset, sort/direction and valid page epoch/lease** during a single app/browser session. If the user is on **page 10**, navigates to another tab, then returns through the Sessions main navigation, immediately reuse that requested page's in-memory/host-cache view if still valid and at most 60 minutes old. Do not reenter at page 1 merely because the navigation link contains no query parameters. Normal browser Back/Forward and direct links with explicit pagination parameters continue to work.

If the underlying epoch/lease has expired or source changes invalidate membership, show a truthful, minimal **“Page position changed; return to latest sessions”** recovery (or safely re-anchor to the same stable page where provable). **Never silently substitute unrelated rows for page 10.** While inactive, do not scan or hydrate every list page; only the last actually visited page (or one bounded page cache) may be maintained. Page 1 may need new-arrival maintenance; older pages keep stable membership/order until the user changes page/sort. **Next/Previous** can fetch on demand at high priority; keep normal 50-row pagination, global sort keys and bounded server leases.

## Freshness contract and cadences

Define **last valid data observation/validation** separate from: browser navigation time, scheduled refresh time, unsuccessful job completion, cached write time and source startup time. Associate each result with real source generation/provenance/revision, report parameters and relevant pricing/config/time-window signature. After successful source-aware validation of unchanged dependencies the host may renew *proof of freshness* without duplicating heavyweight analysis, but **must not pretend a moving “Today” / rolling 7- or 30-day window was recomputed when only the source catalog was checked**.

**Universal non-Watch display rule when returning to a data-bearing report/list/detail:**

- **Fresh/usable (age <= 60 minutes, valid dependencies):** paint the retained, clearly attributable result **immediately**, without a foreground blocking loader; if it is due for a check, refresh in the background *for this visible page* and retain stable DOM, selection, focus and scroll.
- **Old/missing/invalid (age > 60 minutes or no coherent result):** show the **shared FR000609 centered determinate loading/progress** for the requested scope/page. A genuinely missing progress denominator must be described honestly with stage counts/qualifiers, never fake a percentage or ETA. Keep old data only as explicitly marked last-known evidence for failures; do not silently render it as current.
- **Recoverable error while refreshing:** preserve any still-valid retained result; show accurate Waiting/Delayed/partial/source-unavailable status without a blink or new endless retry loop. **Terminal failure/offline/permission problem** is an actionable error, not an eternally moving bar; when older data is displayed for diagnostics, mark its age/staleness conspicuously.
- **Watch:** the only exempt view, continuously prioritized with existing Live status and truthfulness rules. A real source outage is still shown as an outage, not invented real-time values. Accounts may reuse those Live publications without pretending stale upstream quotas are fresh.

**Indicative policy to benchmark and tune, not an extra user settings screen:**

| Work class | Active/visible check target | Inactive low-priority target |
| --- | --- | --- |
| Watch / Mini / shared Accounts Live | Existing true Live/account cadence | **Same protected Live ownership**, never demoted to report cadence |
| Sessions catalog visible 50 rows / selected detail | Approximately existing **5-second** view updates while healthy | Roughly **15–30 minutes** for cached last-view metadata when useful; no mass page/detail scan |
| Token Mix and Comparisons | Retain approximately **5-minute** quiet checks | Approximately **15–30 minutes**, staggered and coalesced |
| AI Stats (requested/default scope) | Approximately **10–15 minutes** | Approximately **15–30 minutes** for default/recently requested scope, with history-size-aware throttling |
| Models with **fewer than 100 eligible priceable completed sample prompts** | Approximately **15–30 minutes** if updates matter | Roughly **30–60 minutes** |
| Models with **>= 100 eligible priceable completed sample prompts** | **No more frequently than hourly** absent explicit action/invalidation | About **hourly**, not more frequently |
| Config/Settings | On demand | No periodic heavy work |

The 100 threshold must come from the **actual qualified Models sample** (not 100 raw messages or arbitrary UI-row count). React to price/catalog/source invalidation and time-window boundaries when justified, but keep genuine explicit price refresh distinct. Do not trigger needless external pricing re-fetches from report warm-up. Avoid an unachievable promise of exact refresh at a wall-clock second: **due times** must be coordinated per dependency, with stable stagger/jitter, source-aware `not-before` floors, missed-period coalescing, cooldown/backoff and a one-hour presentation gate on return. Inactive expensive tasks can be temporarily postponed by foreground/Watch pressure rather than consuming CPU to meet a timer; their cached age is then accurately visible on next entry.

Schedule **independent due times**, not one `setInterval(900000)` for all pages. If many reports become due simultaneously after hours of minimization or a laptop sleep/resume, spread them out, prioritize the active page and retain valid cached data. Day/month rollover and configured timezone/DST must invalidate relevant AI Stats/Today projections as appropriate even with unchanged session revisions.

## Shared evidence, cache coherency and result publication

The dispatcher should maintain **bounded dependency-level cache/coalescing**, not an unbounded all-session in-memory ledger:

1. **Shared read work:** authoritative source selection/revision catalog work and already-available root snapshots/derived evidence should be reusable across Models' 100-eligible sample, Token Mix, AI Stats, Comparisons, Watch/Sessions summaries when *truly compatible*. Design an explicit source-generation + root-revision + valuation/algorithm/config dependency signature. Two consumers for the same prerequisites should attach to one already-admitted task rather than make identical heavy source requests.
2. **Distinct projections:** each target view still computes its own required whole-history completeness, window-clipped time, cost numerator/denominator, grouping/fingerprints, status and privacy-filtered DTO. Avoid cross-using source-unsafe raw cached text, token data whose price signature differs, or a partial interval as a complete value. Confirm source before/after revision brackets and recheck active roots, deleted/archived sessions and pricing changes.
3. **Memory and persistence:** keep only bounded *currently useful* final page projections and compact canonical derived evidence, using existing SQLite namespaces/validation where possible. Key cache entries by source instance/algorithm/config/prices/timezone/period/page as required; LRU/TTL and bounded payload sizes prevent growth from many sessions/tabs. Do not add browser LocalStorage/IndexedDB, persistent raw prompt text, attachment data, secrets, or a second user ledger. A host restart may have to revalidate from disposable caches; do not promise result freshness survived without proof.
4. **Atomic publication:** present only coherently verified page/scope results. Partial verified evidence may be offered with explicit limitations where existing product semantics permit, never pretend full-source coverage or exact maximum/total based on incomplete scanning. All data exposed to Web remains allowlisted; progress/events contain safe status, completed/total counts and opaque job IDs, not raw session content.
5. **Multi-document sharing:** every authenticated tab of the same running host sees the same valid completed underlying evidence; each tab retains its own UI state (current page, sort, selected AI Stats period, scroll, help and focus). Tab changes do not move or invalidate another tab's view. Results must never cross host instance/source identity or authorization boundaries.

## Priority, performance and hard resource boundaries

- The active report must **not sit behind a deep background Token Mix/Comparisons/AI Stats scan for up to 120 seconds**. Implement measurable **bounded scheduling quanta** with safe checkpoints/preemption or equivalent priority-aware execution. If a worker is blocked in one authorized source operation, retain per-operation deadlines and explain wait, rather than starting unlimited parallel workers. Reprioritization should be observable promptly under normal source latency (target one bounded slice; instrument realistic switch latency).
- Prefer **shared scans and cache reuse** over “one thread per tab.” Separate **IO-bound source reads** from **CPU-bound canonical analysis** only where profiling warrants. The V2 source already limits some batch reads to **four concurrent source reads**, and Watch has its own workers; adding threads must not multiply unbounded source connections, SQLite writers, re-pricing or context memory. A controlled worker/process pool with explicit source/CPU/IO budgets and strict ownership is appropriate; implement the smallest measured safe design.
- During the initial cold prewarm, some extra CPU is acceptable, but **foreground time-to-first-useful-data and Watch delivery must not materially regress** versus the same host with background warming disabled. Once warm, a minimized/Watch-only host should spend most of its time **idle**: no constant full-history scans, tight source polling, hourly synchronized CPU spikes or runaway rebuild after every revision change. Measure baseline and warmed idle CPU/memory/IO; choose and document sensible budgets from actual evidence, without claiming a universal hard percentage absent workstation profiling.
- Preserve current **MAX_PENDING/queue fairness, bounded request/progress IPC, 8 MiB result safety, source-read timeouts, parent-loss child teardown, host stop, cancellation for internal lifecycle**, and read-only OpenCode behavior unless a well-justified scoped replacement is proven at least as safe. In particular **FR000614** changes AI Stats' *logical* completion limit, not permission to run an immortal hanging child. **FR000615** removes user-visible Cancel, not internal resumption/stop safety. No queue starvation of active work, no indefinite retry on terminal source/auth failures, and no new paid model inference.
- The local host owns scheduling and cache identity. Do **not** use the browser's `scheduler.postTask()` or hidden-tab `setTimeout` as the central dispatcher: browser background policies and feature support vary; `document.visibilityState` is at most an *interest input*. Do not introduce an external daemon, cloud scheduler, new public network binding or permanent unrestricted background service.

## Suggested integration and rollout order (design guidance, not a new release gate)

1. **Measure the existing baseline**: fresh/warm source I/O, duplicate root hydration/catalog listings across the four reports, first-visit latency, active switching behind one long historical report, idle host CPU and memory, Watch/Accounts update latency, and Sessions page return behavior. Record disaggregated cold/partial/warm and observed source changes.
2. **Build the host registry/interest+priority policy first** behind the existing APIs and deterministic fake clock/source tests. Prove one active foreground request, Watch reservation, coalescing, expiry, background jitter and correct multi-tab leasing before enabling broad preload.
3. **Move finite route results/progress/freshness ownership to the host**, eliminating conflicting hidden-client timers. Extend existing `ReportJobs` safely for priority and bounded slices, integrating FR000614's resumable AI Stats work and keeping FR000615's UI. Expose an authenticated cached-result/status lookup, subscription or suitable existing-endpoint extension rather than racing multiple per-tab POSTs.
4. **Add shared source/derived dependency reuse** and narrow per-view prewarming. Use feature-specific adapters for Models/Token Mix/AI Stats/Comparisons, Sessions/Accounts Live consumers and on-demand detail. Prefer incremental compatibility with current source/cache APIs rather than replacing canonical reporting math.
5. **Tune and enable staggered refresh** with resource controls. Document operational observability and recovery, then update Web behavior/docs and focused regressions during implementation. Do not change the product's release policy or impose broad new recurring gates just because this FR is large.

## Acceptance criteria and required evidence when implemented

1. **Default first launch:** With a cold, healthy local host and a browser initially on Models (and separately deep-linked to Watch or AI Stats), the chosen visible route gets prompt foreground service. Other top-level routes have registered low-priority warm tasks; their heavy work does not delay foreground readiness. Without visiting them, the other eligible reports eventually acquire usable results under bounded idle capacity. Accounts uses Watch; Settings and unvisited session details do not run heavy jobs.
2. **Priority switch under real load:** Start a deliberately slow Comparisons/Token Mix background scan; switch to AI Stats or another uncached page. Within a bounded slice, that page's required work gains priority and makes measurable progress **before the unrelated background full scan finishes**. Switch back: original verified progress continues rather than starting at zero; no duplicate roots/jobs. Cover AI Stats 30 → 7 days → 30 from FR000614 and several rapidly changing tab/browser interests.
3. **Minimized/idle hours:** After an authorized session has started the dispatcher, leave the browser hidden/minimized or sit on Watch/Mini for a simulated long interval. Host-owned background work still progresses in small staggered tasks; Watch Live continues at its normal cadence. Show that no dependence on browser throttled timers blocks refresh, but no sustained busy CPU/repeated history rescans occur after warm-up. Simulate sleep/resume so five due tasks coalesce and stagger rather than stampede.
4. **One-hour data-age cases:** For **0, 15, 59, 60 and 61 minutes** since trustworthy observation, navigate to Models, Token Mix, AI Stats, Comparisons and a previously displayed Sessions page/detail (and Accounts where applicable). Fresh/valid <=60m paints immediately and quietly refreshes when due; missing/invalid/>60m uses shared progress and truthful stale recovery. Inspect real provenance stamps, no resetting age on a failed attempt, cached DOM retention, partial evidence and no false “up to date” after disconnect or source switch. Check Today/local midnight and 7/30-day window movement separately.
5. **Cadence and Models' 100-sample rule:** Confirm the active-versus-inactive intervals and bounded/coalesced background due times. With 99 versus 100 **qualifying priceable completed** prompts (and >100 raw but <100 eligible), Models uses the intended dynamic cadence. A model-price explicit user refresh is not silently triggered by generic background scheduling. Verify work invalidation and exact new source/config/pricing signatures.
6. **Sessions page 10 and paging:** Navigate to Sessions page **10**, change to Watch, then reenter Sessions via its **nav link**. Preserve the requested offset/sort/epoch and display only cached/verified **50 rows** when eligible; no page 1 reset and no prefetch of pages 2–N. Next/Previous fetch just their requested page with foreground priority; arrivals do not scramble older pinned membership. Expired epoch, changed catalog and out-of-range page recover honestly, preserving sorting where possible. Direct deep links/Back and active running-row updates still work.
7. **Shared evidence correctness and reuse:** Against a fixed synthetic source and eligible read-only installation, compare the full per-view totals/period scopes/fingerprints/pagination to existing canonical results. Prove reduced duplicate catalog/root reads for overlapping report requests with safe, immutable dependency versions. Tests cover changed active roots, archived/deleted roots, source generation/identity rotation, price revision, partial/unsupported data, cache corruption and concurrent tabs. One subreport's partial proof never becomes another subreport's complete evidence.
8. **Resource fairness, safety and fault behavior:** Test concurrent authenticated tabs, hidden/closed tab leases, Watch-only Mini, broken/slow source, source-startup waits, partial I/O timeout, auth/CSRF/instance mismatch, server stop/parent loss, full job queue and oversized result. Watch and normal HTTP remain responsive; scheduler cannot leak workers, starve Live or produce an unkillable process. No source mutation, credential leak, raw prompt persistence or paid model calls. Failure of a background report does not suppress unrelated foreground data or spin indefinitely.
9. **UI and accessibility:** On all four finite-report pages, the **same centered FR000609 progress bar** shows meaningful scope-specific percentages/stages when no current usable data exists. Reusing background progress does not jump backwards except legitimate source/scope invalidation, never claims 100% early, and does not flicker on route changes. Warm route entry uses immediate stable content; quiet refresh keeps scroll/focus/sorting/help. No reintroduced user-facing Cancel from FR000615. Sessions/Accounts retain their own appropriate Live/status presentation and accessibility.
10. **Benchmark and regression artifacts:** Use controlled Python source/cache/dispatcher tests, Node fake timers/host APIs, authenticated hidden-browser tabs and a safe read-only real host where available. Compare baseline versus dispatcher on **foreground first-usable latency**, priority-switch delay, Watch event latency, background cold/warm throughput, duplicate source calls, CPU time, memory high-water mark, serialized/parallel worker counts, idle 15–60m behavior and failure/backoff. Include a large synthetic history on the order of previously observed **~2,700 roots / ~54,000 requests** without claiming that historical observation is a reproducible absolute performance target. Report actual measurements, caveats and any unperformed OS/minimization proof; do not manufacture “PASS” for a throttled-browser simulation.
