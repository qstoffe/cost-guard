# FR 000632 — Full Web Watch: expandable running-tool invocation and consistent yellow Running statuses

**Owner-approved Ready Feature Request, 2026-11-07.** Permanent identity **000632**; Ready priority **000550** (after FR000631 at 000540 and before FR000628 at 000560). The owner explicitly requests **both** the running-command disclosure and the inconsistent-Running-color correction **in this one FR**. This publication is backlog documentation only: do not implement product code, launch/stop OpenCode, run paid prompts, change product version, or alter other queued work.

## User need and observed behavior

In **Cost Guard Web Beta → Full Watch → Running Prompts**, a long-running tool currently appears as a short status such as `Running: grep 24s` or `Running: shell 1m`. It does not disclose **what the tool was actually instructed to do**. There is now room in the full Web interface for a collapsible disclosure, like the existing **Tool Calls** and **Skills** rows. The owner wants to expand the *currently running invocation* and inspect the **actual available command and all its arguments**, instead of only the tool name and elapsed time.

The owner also observes that some `Running: ...` rows appear **yellow**, while others (particularly `Running: shell`) are **gold/brown**, even within running prompts. Both should use the same yellow semantic foreground as the running prompt, whatever the underlying running-work category.

These examples describe the observed UI pattern; they are not a captured live session or proof of a specific running process.

## Feasibility findings from current main (static source inspection)

- **The inputs already exist upstream.** Both `src/sources/opencode_v1.py::_part_semantic_data` and `src/sources/opencode_v2_normalization.py::_part_semantic_data` retain normalized tool-part semantic data, including native `state.input` when provided. `src/watch/tool_contracts.py::tool_input` already reads `state.input` with legacy `input` fallback.
- **The detail is discarded at projection, not at source.** `src/watch/tools.py::observe_tools` deduplicates physical calls by `callID` / part identity and selects the longest visible `state.status == running` call after the existing 10-second threshold. It exposes only `running_tool` and `running_ms` in `ToolObservation`. `src/application/live_projection.py::card_row` exports those scalars to Web. `src/web/assets/watch.js::Card.drawActivity` draws a plain `<p>`, despite the file already having reusable native `<details>/<summary>` disclosure handling. No new OpenCode API, command execution, or generic source adapter is inherently required.
- **The color discrepancy has a concrete source.** `watch.js` builds two `Running:` elements: `this.running`, tagged `watch-running-tool`, and `this.background`, a plain paragraph. In `src/web/assets/app.css`, only `.watch-running-tool` uses `--watch-running`; the background row inherits `--watch-activity` (gold/brown). `src/sources/opencode_v2_background.py` independently tracks source-confirmed background jobs whose kind can be `shell`. This difference was explicitly allowed by the older FR000584 but conflicts with the owner's new preference. Treat the color as a presentation inconsistency, not proof that background and foreground have identical lifecycle semantics.
- Background jobs are a **different state** from an actively running native tool call: a backgrounded shell tool can have returned while its associated job continues. Its invocation should be shown only when the original tool part can be **reliably matched to that job**; a generic job kind alone is not a command.

**Conclusion: feasible.** The implementation must extend the bounded Watch observation/Web projection to carry specific, source-proven *invocation input*, rather than sending an arbitrary raw session or guessing the command from `shell` / `grep`.

## Required Full Web Watch interaction

1. Replace the currently plain **active running-tool** `Running: <tool> <duration>` row with an **initially collapsed, keyboard/touch-accessible disclosure**, retaining its existing short label, live elapsed duration and visual hierarchy. The disclosure arrow and expansion interaction should match the existing Tool Calls / Skills rows. It appears at the same existing **10-second** running-tool threshold; do not show a fabricated call before that threshold or change its measurement.
2. Expanding displays the **real observed invocation inputs, including the complete command string and its available arguments**. For shell/bash/execute-like tools, show the actual shell command as recorded (with line breaks, quoting and arguments preserved) plus relevant accompanying invocation options/parameters (e.g. workdir, description, background flag, timeout) **when present**. For grep/read/other tools, display the real named input fields in a readable key/value or pretty-printed JSON layout; do not invent a shell command for non-shell tools. The display must distinguish exact source input from derived presentation and never present a human summary as the complete command.
3. Preserve long commands' readability in a selectable, monospaced, wrapped/multiline detail area. Keep full-size/narrow/mobile document layouts usable, avoiding horizontal page overflow or a permanently expanded wall of text. Render all untrusted content as **text**, never executable HTML/markup; merely inspecting a call must never execute it.
4. Keep disclosure identity tied to the **specific canonical physical tool call and source generation/revision**, not just the tool name. Periodic Live/SSE duration updates must **not close an already expanded disclosure**, discard the user's text selection/focus, jump scroll, or replace its contents unnecessarily. When a *different* call becomes the current running item, do not show the previous command under the new label: reset/reconcile the detail and expansion correctly. A terminal/failed/cancelled tool, ended prompt, newer prompt, source switch or supersession must clear live detail according to existing lifecycle rules. Retained or unverified source state must not assert a freshly running command.
5. **Background shell/other jobs:** retain the separate background-job meaning and existing runtime evidence. If a single running background job can be unambiguously linked to the original tool invocation through canonical source tool/job identity, allow the same disclosure for its original command and arguments. Where only a job kind/aggregate (`2× shell` / `N jobs`) exists, do **not** invent or borrow a command from a foreground or unrelated tool. Show an honest input-unavailable state, or withhold the detail disclosure until a safe match is available; if several distinct verified jobs can be represented, keep identities/details separate rather than claiming one command represents all of them. This is especially important for the reported `Running: shell` case.
6. When a running call is verified but its input is genuinely absent, unavailable or intentionally redacted, label that state plainly (e.g. *Invocation details unavailable from the current source*). A tool name is **not** its argument list. A disclosure must not imply that all arguments are known when only a subset is recoverable.

## Color correction — all genuine Running-status lines

- Apply **`--watch-running`** to the **entire currently visible `Running: ...` status line**, including both `this.running` and `this.background`, independently of whether an invocation disclosure is possible. In Classic this is the bright yellow running role, not the gold/brown `--watch-activity`; keep existing theme-aware readable roles in Web light/dark, without introducing a hardcoded universal yellow or new badges/background highlights.
- This intentionally **supersedes only FR000584's decision to leave the separate background/subagent Running line gold/brown**. It does not change whether a job is running, when either status appears/disappears, the background-job threshold/cadence, or how independent activity rows are counted.
- Tool Calls and Skills summaries, completed/non-running activity and counts keep their established gold/brown styling; verified failures and cancellations remain red. No running status should become gold simply because its source is classified as a background `shell` rather than foreground `grep`.

## Data safety, correctness and performance boundaries

- Use the **existing canonical prompt scope**, child/subagent attribution, deduplicated physical-call identity and already-acquired Watch snapshots. Derive a small typed, allowlisted detail model in Python; the browser must not parse whole native sessions, infer call arguments from prose or execute OpenCode/OS commands.
- Invocations can contain **secrets, credentials, environment variables, tokens, private file content, sensitive paths or arbitrary prompt text**. Do **not** forward raw `part.data`, tool outputs, response bodies, traces, entire `state.metadata` or raw environment to Web. Make a privacy-aware distinction between ordinary invocation parameters, potentially sensitive/freeform fields and known secrets. Redact/omit proven sensitive elements, label redaction clearly, and never claim redacted or limited text is fully verbatim. Where the desired exact content cannot safely be exposed, say so rather than silently exposing a credential or inventing data. Do not persist invocation details in Cost Guard caches, diagnostics, logs or telemetry.
- **Respect Web Live publication and replay budgets** (current 2 MiB event limit / 8 MiB replay bound) and the existing bounded 100-card case. An invocation may be enormous (e.g. content-bearing tool arguments). Do not insert unbounded inputs in every Live/SSE tick or repeatedly recalculate them when only duration changes. Small safe detail may travel in the bounded existing DTO; if full safe input cannot fit, consider an **authenticated, call-identity/revision-pinned, on-demand local disclosure path** using already-owned observed evidence instead of streaming it to every subscriber. Whichever strategy is chosen, show when details are truncated/unavailable; do not present truncation as the complete command. No new high-frequency provider reads, scans, parallel Web services, command execution, global persistence or source-side write is authorized.
- Continue to use already-authorized loopback/same-origin Web security; never make private tool input publicly addressable or use it in URLs. No change to token usage, pricing, accounting, original OpenCode state, CLI Watch or Mini Watch is requested.
- This feature is **observation**, not execution control. A pending/scheduled tool does not become `Running` merely because its input was recorded; a background job must not be confused with a direct `state.status == running` call.

## Acceptance / verification

1. An authoritative active foreground `grep` tool crossing the existing 10s threshold shows a **yellow** `Running: grep <duration>` disclosure. Opening it reveals the exact available `pattern`, `path` and other recorded input fields (illustrative keys); it does not fabricate a command or reveal raw output.
2. A running foreground `shell` tool reveals its actual recorded command with quoting/newlines/arguments and all safe accompanying invocation options. A verified **background** `shell` job also has a **yellow** Running line and reveals the correctly matched original invocation when the job↔tool link is demonstrable. Test missing link and aggregated multiple jobs explicitly: never display a wrong, unrelated or guessed command.
3. Classic, Web light and Web dark rendered checks establish that both foreground and background `Running:` lines use the same `--watch-running` semantic color; Tool Calls/Skills summaries stay in the ordinary activity color and failure/cancellation subsets stay red.
4. Disclosure stays expanded and readable through repeated duration-only Live/SSE updates, route/card DOM reconciliation, focus/text selection, mouse, keyboard, touch, mobile width and scrolling. It resets accurately on different call identity, completion, cancellation, error, prompt supersession, source unavailability/revision or removal. No stale command is shown under a new Running label.
5. Deterministic fixtures cover V1/V2 input shapes, missing/partial inputs, source corrections, duplicated call IDs, multiple simultaneous calls, linked subagents, proper foreground/background distinction, and terminal-grace/history behavior. Verify that the original Tool Calls/Skills metrics and 10-second foreground threshold are unchanged.
6. Verify privacy against representative password/token/environment fields and freeform command injection, plus long/unbounded arguments and the 100-card Live payload/replay budget. Text is never interpreted as HTML or run. Any allowed redaction/truncation is **explicit**, and expansion does not add an unintended source/API fetch or repeated heavy serialization.
7. Update `docs/watch-activity.md` and applicable Web-specific help only during implementation to document command detail availability, sensitive data qualifications and uniform Running colors. Keep targeted existing tests and rendered checks; no live paid model run or unrelated broad gate is required to author this FR.
