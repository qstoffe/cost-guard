# FR 000637 — Mini Watch: tiny one-click Fit Height button, without changing width

**Owner-approved Ready Feature Request, 2026-11-09.** Permanent identity **000637**, Ready priority **000817** — **after** FR000635 (000815, cohesive Mini Watch header/toggle), **before** FR000636 (000818, account links) and FR000629 (000820). FR-only authoring in this publication: create this document and advance the identity watermark from 636 to 637. No product implementation, tests, releases, installed settings, running window or unrelated backlog modification now.

## Request and desired behavior

Add a **very small icon-only button to the top/header row of the Mini Watch Picture-in-Picture window**. Its one job is to **fit the current Mini Watch window's HEIGHT to all content that is actually visible at the moment the user clicks**. It may **grow or shrink** the window vertically as needed to eliminate unnecessary vertical document scrolling, while **never intentionally changing the width**. This is a deliberate, **one-shot user action**, not a continual automatic-resizing feature.

Owner concept: a visually centered **vertical up/down resize icon**, for example **`↕`** (or a comparably recognizable icon). The control should be discreet, roughly the visual width of a couple of characters, aligned with the redesigned header rather than a large labeled button. Its tooltip explains the action. Pressing the button does not open/close Earlier Sessions, refresh a source, recalculate usage or change any settings.

Owner-important companion requirement: **the new icon must participate in the existing Default/Fit-on-open header width calculation**. Do not create a new horizontal scrollbar or an awkward wrapping/reflow regression merely because the extra button was inserted in an already tight header.

## A. Exact button behavior and appearance

1. **Header placement:** add exactly **one** compact icon button in Mini Watch's own upper header, visually grouped naturally with the Existing Earlier Sessions control (for example immediately adjacent to it) while preserving the left **Cost Guard · Watch** return action and the right **CCost Today <amount> · <N> prompts** readout. Let FR000635's final designed header determine the precise DOM grouping. The four visible pieces should share one intentional baseline/vertical center, font/stroke/spacing rhythm and balanced alignment; no orphaned fourth item or button pushing Today offscreen.
2. **Icon and footprint:** a recognizable **vertical fit/resize** symbol such as `↕`, centered horizontally and vertically, with no always-visible text, arrow-label suffix, status badge or question-mark button. Aim for a very compact footprint approximately a **two-character-wide** small control, not another full-size header button. Keep a practically usable pointer/touch target and clear keyboard focus; a somewhat larger invisible/low-impact hit area is acceptable if needed for accessibility, but do not take unnecessary layout width.
3. **Tooltip:** using the existing standard help mechanism, on hover, keyboard focus and touch as appropriate, explain in brief clear terms, e.g. **“Fit Mini Watch height — shrink or grow the window to show all currently visible content. Width stays unchanged.”** The icon needs an accessible name such as `Fit Mini Watch height` and must work with Tab, Enter, Space and pointer/touch. No separate persistent help text or newly added UI status line.
4. **One click, one action:** each click/Enter/Space recomputes the currently needed height and makes **at most one deliberate native resize request** (with no redundant request if the size already fits). No reload, source acquisition, toggling Earlier Sessions, display-unit change, window reposition request, new window, extra worker, new observer/periodic check or changes to data. It must work whether Mini is set to **Default/Fit on open** or **Remember last size**, regardless of how the user manually resized the window.
5. **Both directions:** if content exceeds the current vertical viewport, the button **grows** the window enough to fit; if the window is excessively tall after sessions/accounts disappear or Earlier Sessions is collapsed, it **shrinks** it to a snug content-sized height. Re-click after content changes must be useful. A large current window must not remain large because previous disclosure sizing was grow-only or because `remember-last` captured old bounds.
6. **Visible content means genuinely rendered content:** include full current header, optional visible health/other existing messages, **Earlier Sessions rows only when expanded**, current prompt table including actual shown rows and empty states, account/quota entries, row separators, padding, borders and bottom breathing room. Exclude `display:none` / `hidden` Earlier table, inactive/detached help panels, inert measuring clones, historical offscreen copies, speculative unseen future rows and the artificial **two-row opening reserve**. No text truncation or hidden content merely to claim the fit succeeded. Preserve original table and quota data.
7. **Responsive to state at click:** clicking in collapsed mode fits the collapsed content; clicking in expanded mode fits the full expanded content; expanding/collapsing via the separate Earlier button still follows FR000635's disclosure behavior. The fit icon should not change disclosure state. If a source publication updates the content after fit, the window **must not autonomously resize**. Another fit button click then recalculates with the fresh content.

## B. Correct height measurement and real native PiP constraints

1. **Height-only:** use the user's **current actual inner/content width** as the measurement input, not the original opening request width or an invented target. Preserve existing window width, horizontal placement and chosen manual width to the extent native PiP permits. Do not call a width-fitting algorithm or re-open the PiP window. Prefer `resizeBy(0, Δheight)` where supported; any `resizeTo(currentWidth, targetHeight)` fallback should use actual current native width, never a newly measured header width. Native browsers may round or clamp by a pixel; observe and accurately distinguish that from an intentional width resize.
2. **Avoid circular scrollbars/measurement distortion:** measure style-resolved natural content at the **current width**, including width-dependent wrapping, actual content rather than synthetic placeholders, document padding, safe bottom margin, native browser frame/zoom/DPR and scrollbar-gutter effects. Use an inert offscreen measurement or an equivalent nonmutating measurement that does not briefly expand/collapse real content, steal focus, alter scroll position or trigger a scrollbar-width feedback loop. The tooltip itself is an overlay and must **not** inflate the calculated height.
3. **Snug, not undersized:** when current content genuinely fits within the allowed native window height, the resulting achieved viewport should show the full content **without vertical scrolling** and without a conspicuous unused blank area. Allow only a small practical rounding/line-height safety margin, not a fixed large padding or two-row reserve. Do not repeatedly overshoot/undershoot on identical clicks, and do not use the presence of a scrollbar to force a horizontal enlargement.
4. **Respect real limits:** bounded PiP/native maximum height (currently `heightCap` uses `min(1000, screen.availHeight)`), monitor work area, browser/native minimum dimensions, screen placement, OS refusals and zoom may make a scroll-free height physically impossible. In that case **stop at the safely achieved size, leave normal vertical scrolling accessible, never clip/hide rows, and do not lie about the result**. No warning banner is needed for a normal native clamp; the existing browser behavior can stand. Never simulate a success with a CSS `overflow:hidden` hack.
5. **User activation and lifecycle:** a resize should happen synchronously enough in the direct user-activation handler to satisfy the browser, not after an asynchronous source fetch. Preserve existing bounded native resize ownership/race handling, single user-click adjustment and observed-achieved bounds. Repeated clicks, user manual resizing, Earlier toggle, native resize refused, window closed/disconnected, hover help, live update and source reconnection must not leave stale geometry writes or an endless retry. No focus theft, hidden desktop manipulation or resize loop.
6. **No inconsistent default behavior:** Default/Fit-on-open remains the existing **initial sizing mode**, with its small width reserve and initial two-row-height reserve. Fit Height is an **additional manual correction** based on **current** content. Do not silently change the user's saved default/remember-last configuration or force a new minimum height every time data arrive.

## C. Default/Fit-on-open header must not acquire scrollbars from the new button

1. Measure the real **four-component header** in both collapsed/expanded states when opening a Default/Fit-on-open Mini Watch. Preserve existing reference `CCost Today 90 000 · 999 prompts` and any longer actual displayed value, real native text/fonts/theme/zoom, the existing scrollbar gutter and ~8 CSS-px allowance. Include the fit-height icon's full control width and the spacing it introduces in the measured intrinsic width.
2. When browser screen dimensions allow the existing contracted Fit-on-open width, the title, Earlier button, fit-height button and complete Today amount/prompt count **must fit in the intended top-line design** without clipping, wrapping, document-level horizontal scrolling or a width-induced vertical scrollbar. Explicitly test expanding/collapsing Earlier, focus and hover after opening: they must not unexpectedly shift the header or cause scrollbar emergence. Preserve FR000635's coherent typography and pressed toggle styling.
3. Do not enlarge the initial PiP window to accommodate tables that already legitimately pan horizontally; **the header still owns the default width**. On a manually narrowed or screen-clamped width, use FR000635's intentional responsive reflow so all header controls remain usable without document horizontal overflow. A manual **height-only** fit cannot cure horizontal overflow; leave the established table-horizontal-scroll fallback functional.
4. Do not make the new button's tooltip/hint part of the intrinsic width calculation, and do not reserve permanent space for an open tooltip, additional label or badge.
