# FR 000689 — AI Stats: never show "Counting paused"; show only Loading until real stats are ready, with automatic recovery

**Owner-approved urgent Ready to Develop, 2026-11-12.** Permanent identity **000689**, Ready priority **001020**, before the other open Ready requests because the owner reports the newly installed AI Stats page is unusable. **FR publication only:** no code implementation, programmatic tests, version/release edits, or model calls in this backlog commit.

## User-observed, currently shipped regression

On first launching the **latest Cost Guard** and visiting **Web → AI Stats**, **all twelve statistical cards** show **"Counting paused."** (described by the owner as "Counting Post") rather than the mandated **"Loading…"** while the page is trying to populate.

The owner has repeatedly demanded this exact simple behavior:

- **No prior ready data for the selected period:** every card shell's **entire interior** is just **`Loading…`**, from the moment the page opens **until the genuine server-backed values for that period are ready**, regardless of source startup, lower scheduling priority, foreground Watch work, host backoff, paused/parked checkpoint processing or transient failures. No title, emoji, trait, fake number, root count, "counting", "post", "paused", N/A, Unavailable, stopped copy or alternate status appears **inside a pending card**.
- **Ready data:** atomically replace the pending interior with the real complete card (all current metrics, including the Top 3 provider TPS podium), using AI Stats' normal playful Best Effort policy. On a quiet refresh or transient error, **retain the last valid same-period, same-source ready cards** without blinking, clearing or replacing them with placeholders.
- **No "Pause" semantics in this UI:** the user has no Pause/Stop button or intention to pause acquisition. Internal host work may *cooperatively defer* or park to protect foreground work; that does not make AI Stats user-visible "paused". Navigating to the tab should promote its existing pending demand, not require the user to toggle routes, click Retry or restart the app.
- **Real terminal operation failure is not successful loading:** do not create fictitious results, mark a failed job ready, pretend a source disconnection, or show endless Loading while doing nothing. Report a genuine persistent authorization/worker/cache/source failure **separately outside the cards** in one concise actionable, accessible page-level/connection notice, while every unready card still has only `Loading…`. Recover automatically when the blocker clears; keep a valid last-good snapshot if one exists.

The source of the phrase **is already confirmed in code**; the underlying reason the owner's particular first load failed or was interrupted **is NOT yet established without its local runtime/job diagnostics**. This FR must fix **both** the copy/state invariant **and** the actual acquisition/recovery problem; a one-line replacement of the string without causal diagnostics is incomplete.

## Verified current implementation and previous attempted fixes

1. **Direct trigger.** `src/web/assets/ai-stats.js::AIStatsView.View.update(state)`:
   ```js
   const ready = state.result?.view?.ai_stats_work?.scopes?.[state.period]?.ready === true;
   const row = ready && valid(state.result) && state.result.view.ai_stats.find(item => item.period === state.period);
   if (!row) {
     const message = state.failed || state.interrupted ? 'Counting paused.' : 'Loading…';
     for (const item of this.cards.values()) item.card.replaceChildren(message);
     ...
   }
   ```
   This is **an explicit presentation branch**, not a text produced by OpenCode, GPT/Claude, the number of prompts, a literal scheduler phase called `post`, or an intentional user action. It hides all 12 card bodies whenever `failed/interrupted` and no ready row exist.
2. **Flag origin.** `src/web/assets/app.js::show()` sets `state.interrupted` whenever the **host** is in `offline`, `stopped`, `identity_changed`, or `authorization_required` status. `acquire() catch/finally` sets `state.failed = true` for a request, worker, cached-result validation, publication or API failure. The flag alone **does not prove the scheduled AI Stats calculation intentionally paused**. A transient failed attempt, a disconnected browser or even a result rejected by `AIStatsView.valid()` can all produce the same twelve "Counting paused" shells.
3. **Cold failures are poorly explained.** In `app.js::show()`, the automatic-history page-level notice is populated only under `if (state.result && state.failed)`. **When the first load has `state.result == null` and `state.failed == true`, the card text hides the error while the page-level notice stays blank.** A user cannot tell if the workers are queued, retrying or genuinely blocked. Fix this with the shell-only Loading rule and separate operational feedback.
4. **Automatic work already exists and must remain:** `src/web/assets/data-demand.js` sends visible interest/30-second leases; `src/web/dispatch.py::DataDispatcher` owns foreground prioritization, resumable jobs, due/backoff and source/worker-failure classification; `app.js` polls finite jobs, uses roughly **500ms in-flight status polling** and **5-second pending-publication lookups** on the managed dispatcher. `CachedReports.cadences['ai-stats']` is a **900-second freshness cadence**, not permission to delay cold demand for fifteen minutes or to call a foreground job paused. A genuine host status or terminal error can prevent automatic resubmission until the source becomes healthy or the terminal gate is cleared; diagnose rather than silently assuming retries exist.
5. **Versioned schema risk, to investigate rather than assume:** the newly shipped FR000685 changed the AI Stats accepted result contract to `ai_stats_policy === 'fun-3-responses'`, requires twelve metric DTOs and a bounded token-rate `podium`. `AIStatsView.valid()` rejects old or inconsistent projections, and `app.js::acquire()` throws `report_invalid_result` on a complete response that fails validation. A still-persisted prior `fun-2-tokens` cache/result, stale worker publication, partial schema, source revision, result/period identity, or root-level compact checkpoint version may be relevant **hypotheses** after upgrading. Verify which one actually occurred in the owner's installation before choosing a fix. Do not weaken correct schema checks or relabel invalid old data as current.
6. **The contradiction was codified in tests/docs.** `development/tests/integration/probe_ai_stats_loading.cjs` explicitly asserts that `state.failed=true` makes all cards contain `Counting paused.`. `development/architecture/modules/reports.md` under **"AI Stats = best effort / never Unavailable"** explicitly approves **"paused shells if no last-good result"**. Both violate the owner's clarified binding design rule and must be corrected **permanently**; update matching test snapshots/fixtures, `development/journal/web/ai-stats.md`, `docs/web-beta.md` and appropriate developer-facing comments. The earlier FR000633 fun-first rule and FR000682 Loading-only shells should take precedence over the later paused-shell exception.
7. **Previous recovery:** FR000678 fixed artificial all-zero error cards, manual Retry buttons and stalled Token Mix/AI Stats acquisition. Preserve that distinction: *failed or interrupted acquisition is not a true empty day*, so no bogus 0-stat "success" just to make the UI prettier. But `Counting paused.` is not a valid substitute for Loading.

## Product requirements

### A. One, unambiguous AI Stats card lifecycle

- **Pending**: one stable grid of **twelve** normal-sized card shells. Each unready shell has **exactly one text node, precisely `Loading…`**; no title/heading, help button, image/emoji, progress percentage, trait, reason, hidden/accessible technical status, internal error code, "Paused", "Counting", "Post", "Unavailable" or `N/A` inside those cards. Use the established `.ai-stat` geometry and `role=status` / non-spammy live-region semantics, including screen readers.
- **Ready**: only `ai_stats_work.scopes[selectedPeriod].ready === true` **and** a validated selected-period projection may commit card contents. All data for the selected period appear in one synchronous update, with the original six Overview/six Fun Facts, optional matched fact, title help, friendly traits and current `Token Consumption Rate` podium. Internally approximated best-effort figures are accepted by the stats calculation rules; browser readiness must not be held hostage by statistical confidence or missing/partial old records.
- **Stale refresh**: never replace a previously ready same-source/same-period view with loading/paused/failure content. Only a proven changed source identity/observation invalidates last-good. Other periods cannot leak into this one. `Today`, `7 days`, `30 days`, `This month`, `All time` must each behave consistently.
- **Failed/interrupted without any ready result**: **cards still say only Loading** as specified; a **separate, unobtrusive-but-visible page-level notice** may explain a *confirmed real blocker* with an actionable recovery hint. A temporary queuing/backoff state can be quiet or have a nontechnical status **outside the cards**. Do not label a known permanent failure merely "still loading" without any accompanying operational signal. Do not provide a user-facing Pause/Cancel/Retry/Refresh control on AI Stats.
- **Attempt changes**: state.failed/interrupted must be scoped to the actual active attempt, cleared on a new healthy acquisition and never inherited from an unrelated route, old source generation, another tab or last failed job when the new job is running. Prevent old catch/finally and late SSE job hints from flipping a new healthy Loading view into paused/failure text.

### B. Establish that a visible AI Stats page actually completes automatically

- **Diagnose the owner's report:** on the actual latest product build, inspect a bounded, sanitized chain: route entry/visible lease → current host connection/source status → `/api/interest` → `/api/data` admission (including `id`, `refresh`, `terminal`, `error`) → job state/error/progress and exact selected-scope readiness → `AIStatsView.valid()`/retention decision → browser state flags and rendered 12 cards. Collect reason **codes, counts, timings, schema/policy ID, revision and job/source generation only**. Never publish private prompts, cost histories, raw model sessions, credentials, database paths or full RPC payloads.
- Reproduce **each distinguishable failure class** with real source-shaped fixtures: source not yet healthy, retryable worker interruption, checkpoint BUSY/LOCKED, exhausted/stopped job, schema/policy mismatch after upgrade, stale old generated result, job source invalidation, cold cache miss, invalid complete DTO, and terminal source authorization/permission/unsupported version. Confirm that `Counting paused` previously appeared; then prove it cannot render after the fix.
- **Do not just rename a frozen error state to Loading:** `DataDispatcher` and the browser should keep the **same logical foreground demand**, bounded checkpoint progress and **automatic rediscovery/readmission** after transients. If an older invalid cached result cannot be used, invalidate/repair only the affected AI Stats derived schema/version/checkpoint and regenerate it without manual cache deletion or changing native OpenCode history. Truly terminal blockers should remain error-classified until their real prerequisite changes; do not spin an infinite retry loop.
- When the user navigates to AI Stats after visiting another tab or while Watch/Mini/Sessions work is prioritized, an existing AI Stats worker is **allowed to be queued or internally parked**, but the visible page must (a) display Loading, (b) register/retain foreground priority/demand, (c) actually make progress and eventually render ready values once resources become available, **without user intervention**. Internal priority/delay must not be presented as user cancellation/pausing. Bounded source/worker safety and cooperation with the Live host are retained.
- For truly empty selected-period source data, the usual **ready** best-effort zeros/fun facts may display *only after a real successful acquisition*, not as fallback on failure. Fix the cause of stuck cold load, not simply the visible word.

### C. Automatic success and diagnostics without regressing other routes

- Keep the normal host-owned `ai_stats_work` checkpoint/slices, five-period scope prioritization, source revision, memory limits and 256-root slice/64-root batch constraints, cooperative cancellation, genuine source identity/authorization security, credits/USD math and other report ownership. Never add costly independent polling, extra source hydration, paid model inference or a browser-only fake progress timer.
- Repair any cold-error automatic-lookup blind spot: `app.js::scheduleCachedReport()` currently explicitly schedules automatic-history failure lookups, but check `demand`, `document.hidden`, writable/host reconnect, the 5-second lookup versus 15/30-minute freshness cadence, `state.attempted`, concurrent route changes and `DataDispatcher` terminal flags. Ensure healthy source recovery resumes without manual Retry or an app restart and does not starve under active Live status updates. Preserve last-ready snapshot and focus while retrying.
- Show real infrastructure/authorization errors **outside** the stat cards and outside the fun copy, clearly distinct from ordinary scheduling/worker backoff. Do not suppress the existence of a fatal issue simply to maintain 12 Loading shells indefinitely.
- **Centralize the standing rule in a prominent source comment** by `AIStatsView.View.update` and in the owning architecture contract: "AI Stats: pending means exactly Loading in every card, including queued, deferred, failed and interrupted attempts. A genuine blocker is page-level, never a card label. Ready values are atomic and last-good retained." Remove any contradictory active test or guide prose.

1. **Plain Loading across ALL states:** in a real DOM/Node/browser test set `state.result=null` and iterate `failed` false/true, `interrupted` false/true (including simultaneous), `loading` false/true, queued/deferred/parked/backoff, source starting, result partial `ready=false`, and incomplete/invalid publication. Assert a string search over every AI Stats card/help/accessible pending surface finds no `Counting paused`, `Post`, `Unavailable`, `N/A` or similar alternate status.
2. **Cold error visibility:** a confirmed terminal **report/cache/source failure before any ready snapshot** creates a clear separate page-level operational notice (or existing connection notice with sufficient specificity) with no error copied into any stat card. A retryable transient error keeps the page loading automatically, without a new Retry button and without a perpetual unadmitted job. Visible pending snapshots don't masquerade as ready.
3. **Healthy vs waiting priority:** exercise authentic managed `/api/interest` and `/api/data` workflow with AI Stats opened while Models/Watch worker is busy, source warming then ready, lower priority work internally parked, real checkpoint resume and foreground promotion. Assert initial Loading → actual finite progress → complete correct 12-card results, with no user action; no technical "pause" wording at any time. A previously valid result stays displayed through background refresh and a paused *worker*, with no visible card changes.
4. **Upgrade/schema compatibility:** start from legacy AI Stats `fun-2-tokens`/old `podium`/pre-FR000685 or stale compact cache and verify clean source-correct regeneration to `fun-3-responses`; version mismatches trigger proper dependent invalidation and recovery, not `report_invalid_result` terminal dead ends. Keep strict validation for real malformed data; don't accept a bogus metric merely to satisfy the visual test.
5. **Actual failure to recovery:** simulate source offline/authorization required → recovered, source revision change, invalid/missing checkpoint, SQLite contention → unlocked, failed child → supervised restart, disposed job/old tab lease and all five period switches. All surviving eligible cases eventually show ready metric values; permanent blockers keep safe diagnostic alerts without tight polling or user-facing paused cards.
6. **No regression of fun stats:** nonempty/empty/partial estimated histories still produce the **current twelve actual stats**, correct selected period, token counts and TPS podium, optional matched fact and session links after readiness. Keep same-source last-good results, dimensions, user unit/theme choice, title help/keyboard/hover/touch, focus/selection and stable DOM across 360–1920px and zoom.
7. **Real installed verification:** replay the owner-reported **latest-host first entry into AI Stats** using bounded read-only local observation; capture observed `failure` reason and after-fix successful admission/readiness/DOM. If workstation access is absent, write **NOT VERIFIED**, never call a synthetic green test a reproduction of the specific report. This is a requirement to *investigate* the root cause, not to run new model calls.
