# FR 000695 — Models: make Price List and Benchmark refresh truly section-local; fix intermittent sticky Refresh-button glow

**Owner-approved Ready to Develop — 2026-11-13.** Permanent ID **000695**, priority **000003**, immediately after existing FR000693 (000001) and FR000694 (000002) in the Ready queue. **Documentation-only FR publication:** do not implement product code, change installed source/cache, run paid inference, modify tests, alter version/release metadata or start an implementation branch during authoring. All implementation and testing belongs to the eventual selected Repo Backlog worker/PR.

## 1. Owner's observed issues, without overstating reproduction

On **Cost Guard Web → Models**, the owner reports two separate, potentially related UX regressions:

1. Clicking **Refresh price list** (the button above **GitHub Reference Pricing**) appeared to reload **both the pricing table and the Coding Benchmark table** beneath it. The owner is **not certain this happens on every click** or whether another fetch really occurred; the definite symptom is **unwanted visible refreshing/redrawing of unrelated table content**, not necessarily an extra upstream download. The matching **Refresh benchmark** button should likewise affect only its own table. One table's control must not act as a page-wide refresh.
2. Clicking the price-list or benchmark Refresh button sometimes leaves a conspicuous **outer accent/glow/focus-like border** around the button **after the click and refresh have finished**. Sometimes it disappears and sometimes not, making the bug intermittent. The owner wants the action to have a clean, predictable resting state without a lingering mouse-click halo, while retaining legitimate keyboard accessibility/focus cues.

**Desired UI contract:**

```text
Models page
  GitHub Reference Pricing
    [Refresh price list]  → ONLY pricing fetch / data / rows / last-fetched /
                           feedback for this section
  Coding Benchmark – Cost per Task (Terminal-Bench 4.0 · Harbor Hub)
    [Refresh benchmark]   → ONLY Harbor benchmark fetch / data / rows /
                           last-fetched / feedback for this section
  More Coding Benchmarks
    Artificial Analysis link (passive, unchanged)
```

If a **genuine independent** automatic background refresh is due at the same time, it can proceed according to its existing source freshness rules; the manual click must **not cause, forcibly reset, unnecessarily redraw, or falsely visually mark** the other section as refreshing. Keep failure/success/retry evidence attributable to the correct button/source only.

Do not accidentally interpret the **More Coding Benchmarks external link** or the **parked Artificial Analysis suggestion (000680)** as an existing third live table. At publication the live Models UI contains **two data tables** and one link-only section. Future additional static tables should follow the same section-isolation principle without changing the parked suggestion here.

## 2. Verified code-level investigation leads (static review of current GitHub main)

These are **actual source findings**, not an instrumented replay of the owner's particular desktop incident:

### A. Price-list result replaces the entire Models DOM

- `src/web/assets/render.js::ReportView.render(parent, result, state)` begins with **`parent.replaceChildren()`** and, on the Models route, calls `overviewModels(parent, view, state)` to create the price heading, toolbar, filters, table and link section again.
- `overviewModels` builds a **new GitHub pricing table and refresh button** on each call; it also does `state.benchmark ||= new BenchmarkView.View(); state.benchmark.attach(parent)`. The benchmark **View object/root is retained**, but after the containing parent has been emptied, its root is **detached and then reinserted** alongside the rebuilt price DOM. That transient detachment/reflow can appear to the owner as the *benchmark also reloading*, even when Harbor rows/date have not changed and no Harbor network request occurred.
- `src/web/assets/app.js::show()` skips `ReportView.render` only if the current **whole `state.result` object identity** (and search/output reference) is unchanged. A successful price-list refresh sets **`state.result = job.result`** in `acquire(state, ..., prices=true)`, so the whole Models render path is reached even if the underlying benchmark result is independent.
- Every eligible `show()` on Models also calls **`state.benchmark?.load(api)`**. Its own 5-second check in `BenchmarkView.load` usually suppresses frequent calls, but after time has elapsed this can trigger a **separate normal `GET /api/models/benchmark`** around a price refresh even though the user did not click the benchmark button. Instrument and separate automatic polling/due checks from an incorrectly coupled manual action; simply testing that `POST /api/models/benchmark/refresh` was not called would miss a secondary GET or a DOM flash.

**Candidate root of visual bug:** the broad Models DOM teardown plus reattachment and optional benchmark status read. Do not assert a Harbor upstream forced refresh without request trace evidence. Fix visual/DOM ownership rather than papering over the symptom with an artificial loading delay.

### B. Benchmark button already owns a different endpoint but its repaint lifecycle needs verification

- `src/web/assets/benchmark.js::View.refreshSource()` posts **`/api/models/benchmark/refresh`** then calls `load(api, true)` to read **`/api/models/benchmark`**; it does **not directly** call the price-list endpoint.
- `src/web/benchmark.py::BenchmarkLane` owns Harbor fetch/cache and manual force independently of `src/web/jobs.py::ModelsPriceRefresh` and `/api/models/refresh` in `src/web/assets/app.js`. Existing architecture already intends separate lanes. Preserve those HTTP/security/worker semantics rather than merging or changing them.
- `BenchmarkView.load()` computes `JSON.stringify(data)` as a whole-data signature; when the status-only fields differ (`refreshing`, `unavailable`, etc.), `BenchmarkView.draw()` can be invoked even if benchmark **rows themselves** have not changed. `draw()` executes **`this.body.replaceChildren()`**, recreating all benchmark table rows. Audit whether normal refresh progress/status polls or another section's price action are causing gratuitous full-body rebuilds. Distinguish **necessary data-row updates** from just changing local progress/date/status controls.
- Currently independent *sort/filter state* is persisted in `state.models` and `state.benchmark.choice/sort`. Those objects surviving a redraw does **not** guarantee DOM-row identity, scroll position, selection, open help, keyboard focus, or absence of visible flicker.

### C. Intermittent outline/glow is plausibly a focus-lifecycle issue, not an indefinite loading state

- `src/web/assets/app.css` sets **global `:focus-visible { outline: 3px solid var(--accent); outline-offset: 3px; }`** and also gives active buttons an accent border/inset shadow via `button:not(:disabled):active`. The observed “outer glow” could be one of these or a related browser-native focus style. Inspect computed `outline`, `box-shadow`, `border`, `:focus-visible`, `:focus`, `:active`, focused element and input modality *after* actual click, success/error, delayed response and DOM replacement.
- `app.js::acquire` has **special price-button focus recovery**: `priceFocus` records whether the old refresh button was active; `show()` snapshots `data-model-control` and calls `.focus({preventScroll: true})` on the newly built button after rerender; `acquire().finally` can again refocus the new refresh control when `document.activeElement === document.body`. This was introduced to protect legitimate keyboard-focus behavior when disabling/replacing the control. It may also create or preserve a `:focus-visible` accent halo after pointer activation, depending on browser focus heuristics and how the original button was disabled/detached.
- Benchmark `View.controls` disables and re-enables its `this.refresh` button; unlike the pricing flow it retains a stable refresh node in the retained benchmark View. Test that the two distinct focus lifecycles work for pointer, keyboard and touch. Do **not** remove all `:focus-visible` outlines just to silence the symptom: that would regress Tab/Enter/Space accessibility.

**Important:** A visible outline *while the user deliberately leaves keyboard focus on a button* is expected and necessary. The bug to fix is a **sticky/inconsistently restored pointer/touch halo**, a stale active/focus state after the interaction ends, or a focus ring that is reintroduced by an artificial refocus despite keyboard focus having moved elsewhere. Evidence must distinguish these.

### D. Existing tests do not establish cross-table repaint isolation

- `development/tests/integration/probe_models_refresh.cjs` covers price fetch and old table retention **during a pending or failed price refresh**, duplicate coalescing, native Enter/Space, and focus recovery; it also makes legitimate snapshots of button/toolbars. Those tests do **not** establish that the **benchmark DOM rows and state remain exactly untouched** when a new valid price result completes.
- `development/tests/integration/web_models.cjs` checks that **sorting** the benchmark table cannot reorder the pricing table and validates separate control endpoints; a sort-independent test is not a manual-refresh isolation test.
- `development/journal/web/models-pricing.md` records earlier fixes to the price-button focus reattachment. Treat them as history/constraints, not proof the current owner's sticky-outline report cannot happen.
- Historical backend tests established independent forced price and Harbor retrieval lanes; new **real browser/DOM** assertions need to cover visual continuity and focus modality, not just two distinct endpoint names.

**Do not claim** the owner's observed reload/focus is reproduced or permanently fixed until a source-shaped real-browser run actually shows the bad/before and good/after behavior. The FR author has not run the owner's installed Cost Guard, visual desktop, new browser replay or backend tests.

## 3. Product behavior — independent refresh controls, independent DOM ownership

1. **Price list click affects its own section only.** A manual `Refresh price list` requests and applies a validated new GitHub Copilot pricing snapshot as today. The reference table may update its true rows/prices, ratio, local last-fetched date, local loading/success/error text, and eligible model notices. Its own changed subset may rerender, but **the Harbor benchmark heading, toolbar, table, rows, date, filters, sort, selected effort subset, horizontal scroll, focused cell and open help remain physically and visually stable** for unchanged Harbor data. **Do not detach/reinsert the benchmark root or replace unchanged benchmark row DOM just because `state.result` changed.**
2. **Benchmark click affects its own section only.** `Refresh benchmark` uses the existing Harbor force-demand/lookup lane. On actual new benchmark results, redraw only the benchmark's changed records, controls/date and notice. While Harbor runs, retain the last-good benchmark table without a blank/disappearing body. The GitHub reference heading/button/date, table DOM and current sorting/filtering/scroll/focus/selection remain untouched; neither a forced price-list POST nor an unnecessary price report rebuild is caused by the benchmark click.
3. **Status != data change.** Separate source/data revision/row identity from `refreshing`, failure/success indicator, a polled status date, global connection notice, unit/theme/focus state and unchanged endpoint response. Show progress inside the **correct section's** toolbar only. For same complete dataset (including unchanged rates with a newer official successful observation timestamp), update its factual date/status without destroying rows that have not changed.
4. **Retain last good & local failures.** Offline, invalid, stale, interrupted, delayed, queued, failed and retry responses retain the previous valid table and date **for both sections**, with the relevant local error in the initiating section only. The other table must not display a placeholder, turn grey, become disabled, change sort order or announce a refresh merely because its sibling fails.
5. **Keep each refresh independently available.** A manually triggered price request must not disable `Refresh benchmark` just because `state.loading` is true for price. Vice versa, benchmark work must not disable `Refresh price list` unless a **genuine shared host/CSRF/source** restriction prevents it. Coalesce repeated clicks **on the same source**; if both buttons are activated close together, both rightful jobs may proceed under existing finite priorities without overwriting each other's progress or receipt.
6. **Preserve existing backend boundaries.** Never merge GitHub pricing and Harbor into one forced fetch; do not start network work on hover, drag, sort, filter, data unit change, quiet Live health, or reopening a retained view. Honor the host-managed queued/refresh lifecycle and normal truly independent source freshness/5s polling checks, but do **not** make them repaint sibling sections or appear to be the user's manual action.
7. **Incremental presentation.** Favor stable section-owned DOM roots with targeted source-qualified update methods rather than `parent.replaceChildren()` on every Models price publication. No double listeners, duplicate price buttons, lost `ContextHelp` ownership, repeated benchmark instance creation, text selection/focus loss, document scroll jump or wiped sort/filter state across cycles. Keep parent layout, source headings, table semantics, More Coding Benchmarks link, responsive horizontal scrolling and Classic/Web visual parity unchanged.
8. **Future sections.** If another static/benchmark table is later added by a separate approved FR, the same isolation applies to its content; **do not implement or move parked Suggestion000680** as part of this bugfix.

## 4. Focus/outline: no sticky halo from mouse or touch, preserve keyboard focus

1. **Reproduce and classify, do not blindly suppress.** For both buttons sample `activeElement`, `:focus`, `:focus-visible`, `:active`, computed outline width/style/color, `box-shadow`, `border`, and DOM identity before click, while pending, after completion and after moving mouse away. Test **pointer click, touch activation, Tab→Enter, Tab→Space**, delayed response, fast completion, double click, failed refresh and a second retry.
2. **Mouse/touch:** after the press ends, when a pointer-initiated action completes, the button returns to its normal **resting/hover** style. A newly created or refocused button must **not** retain a conspicuous keyboard-like `:focus-visible` outline solely because the pointer clicked Refresh. A legitimate transient `:active` pressed style must end with release; no lingering 3px outer border/halo after completing the operation or subsequent mouse move. Do not arbitrarily `blur()` other inputs or fight the browser's focus transitions.
3. **Keyboard:** on Tab navigation a clear accessible focus-visible outline **must remain** on the active button, including across successful/failed refresh and disabled→enabled transitions when the user has not intentionally moved focus. Enter and Space must still activate one request each. Focus restoration should preserve keyboard navigation order and not scroll the page unexpectedly. If focus intentionally moves to a filter, tab header or anywhere else while pending, completion must not steal it back.
4. **Both implementations:** test the price button's special `priceFocus` and new DOM creation **and** the benchmark button's retained-node disabled/enabled lifecycle. Use input-modality-aware focus retention (browser-native heuristics / supported semantics), not a blanket CSS `:focus-visible {outline:none}` or global `button:focus {outline:none}`. Avoid new bespoke focus timers, arbitrary blur after every click, an extra click to clear the ring or a fake disabled state to hide it.
5. **Accessibility:** visible keyboard focus, accessible button names, correct `disabled`/`aria-disabled`, status/live region, contrast and normal hover/touch are preserved at 360px and desktop, Classic/Web light/dark, zoom and reduced motion/forced colors where available. A lingering ring that is genuinely **keyboard focus still present** is **not a defect**; the wrong persistent pointer glow is.

## 6. Completion acceptance

The **clicking of either Refresh button** updates, reloads or displays progress **only for its own source/table**. The other existing table remains visibly and structurally steady for unchanged data, regardless of a full new price report object, 5-second polling, own background activity or a sibling button's disabled-to-enabled transition. **Neither refresh action leaves an intermittent artificial outer focus/glow after ordinary pointer/touch activation**, while legitimate Tab/Enter/Space focus cues remain accessible. Negative/failure/concurrency cases pass, and an actual before/after browser trace confirms **separate HTTP source operations, stable unaffected DOM and correct focus modality**.

**Not done:** merely showing separate button labels, swapping the refresh URLs, disabling focus outlines globally, adding a sleep/debounce, suppressing CSS glow without preserving keyboard accessibility, checking only independent sorting, declaring both tables independent without testing DOM identity, or reporting the owner's particular defect reproduced without evidence.
