# FR 000642 — Mini Watch: one Activity session table, five-row history fill, and new default fit dimensions

**Owner-approved Ready Feature Request, 2026-11-09.** Permanent identity **000642**, tentative Ready priority **000830**, after FR000641 (000820, guesstimate display rounding). **Backlog publication only:** add this FR and advance the permanent identity watermark **641 → 642**. This authoring task does not change executable code, tests, user docs, settings, releases or active windows.

## Requested redesign

Replace Mini Watch's **two separate Running/Recently-ended prompts and Earlier Sessions tables** with **one always-visible, chronological session table**, and **remove the Earlier Sessions button completely**. The button is no longer useful: eligible previous sessions automatically fill unused space beneath active sessions. Keep the existing compact header **Cost Guard · Watch** return action, the small **↕ Fit Mini Watch height** button and the non-clickable **CCost Today** readout. Do not add a replacement disclosure, divider, fifth column or persistent “Earlier” heading.

The new table has **exactly four columns**, in this order:

**`Activity | Session | CCost (Total) | Ctx`**

Start from the current **Earlier Sessions table's compact four-column presentation**, but change its `Finished` heading to `Activity` and display both live and completed sessions there. Remove the old running table's **Duration** column completely. Prompt duration remains available in the **existing CCost cell's focus/hover/touch details**, which already include model/effort/duration/calls; no separate duration column, tooltip button or always-visible duration label is needed.

## A. Four-column semantics and timestamp help

1. **Activity** is the represented session's relevant current prompt activity time:
   - A genuinely **running/in-progress** (or conservatively execution-unverified unfinished) representative uses **that prompt's actual start time**.
   - An **ended/recently-finished** representative and an **Earlier Session** use **the supported finish time of the latest canonical finished representative prompt**, not its start, source refresh time, browser clock, session metadata update, last text change or an inferred end.
   - Show the existing compact configured-local **HH:mm** (24-hour, no seconds) in both cases. The **Activity column heading tooltip explicitly explains: “Start time for a running prompt; finish time for a completed prompt/session.”** The actual time value also retains its focus/hover/touch **full local date, time and UTC offset**, including daylight-saving repeated hours. If the finish is genuinely unverified or unknown, show the existing honest **— / Unknown finish time** rather than manufacturing it. If the current start-time token lacks the full offset, prepare it on the server, not by browser-local reformatting.
2. **Session** is the existing flexible, left-aligned session title (canonical session ID when unnamed), with ellipsis where necessary. Preserve selection, full title and the represented **Prompt #** in its existing contextual help; no extra prompt-number column. Session identity is the **canonical root/session ID**, not display-name equality.
3. **CCost (Total)** preserves existing semantics and independent accessible help: first the **representative prompt's own reference CCost**, then the **full canonical session/root total in parentheses**, including supported linked subagent work. Keep Credits/USD, `N/A`, unknown/loading, partially priced `?`, cost provenance and model/effort/calls/outcome detail. **Duration of the represented prompt remains in the existing CCost tooltip** for active and finished rows, including a frozen final duration when completed. Never substitute the total for missing prompt cost or vice versa.
4. **Ctx** keeps its source-specific existing value: for a running/recent prompt, the current representative prompt's supported next-incoming context estimate; for historical-only sessions, the last valid session-level next-request context. Do not show a historical prompt's stale local Ctx in place of the session summary. Preserve context warnings, unknowns, help and token-unit display.
5. **Row colors are unchanged:** actively running rows remain yellow, successfully ended rows green, aborted/error rows red (and established unverified/unknown states remain honest). Preserve accessibility beyond color, hover/focus treatment and existing theme semantics in Classic and Web light/dark.

## B. Exactly one row per session; unbounded active rows, fill to five

**Distinct-session uniqueness takes precedence over distinct-prompt multiplicity.** Although a session can contain several sequential or concurrent prompts, the new Mini table represents **a session only once**.

1. **Select active sessions first:** group all authoritative `active_cards` by canonical `session_id`. If the session has **any genuinely running prompt**, it contributes **exactly one active session row**. If several prompts in the same session are concurrently running, select the **most recently started genuinely running focal prompt** as that row's representative (stable `at_ms`, then stable event-ID tie break). Preserve the *whole-session total*, which can reflect multiple concurrent prompts; do not double-count, fabricate a merged prompt cost or claim its CCost cell totals all simultaneous focal prompts. Existing detailed/full Watch can continue showing separate prompts. Treat `execution_unverified` conservatively as an unfinished active candidate, without inventing a completed timestamp or healthy outcome.
2. **No cap on unique active sessions.** If there are 5, 6, 10 or more **distinct simultaneously running sessions**, show every one of them once. The “show all running prompts” intent is interpreted with the explicit one-row-per-session requirement: **ten running prompts in ten different sessions = ten visible session rows (scrollable); ten concurrent running prompts in one session = one Mini row**. Do not silently drop a distinct active session to enforce a five-row data limit.
3. Let **R = the number of distinct currently active/running sessions** selected above. Choose up to **`max(0, 5 − R)`** **distinct non-running sessions** as a filler. Candidates include the existing short **recently ended/terminal-grace** active-card state and verified **Earlier Sessions**; if both refer to one root, keep one latest coherent representation. Pick the **most recently finished eligible** sessions first using the existing canonical finished-time/history ranking and deterministic tie/unknown-time fallback, excluding every active session ID **before** applying the historical count. Do not let a less-recent grace row displace a more-recent valid finished history item simply because it came from a different list.
4. Examples: **0 running → up to 5 finished**, **1 → up to 4**, **3 → up to 2**, **4 → up to 1**, **5 or more → 0 finished**. If only 1–2 verified historical sessions exist, show only those, without duplicating them or inventing rows. A genuinely empty/initially loading history must retain its established truthful status, not be silently presented as an authoritative “five most recent” list.
5. **One ID, one row across all states.** If session A appears in finished history and a new prompt starts in A, the old A row is **replaced/promoted** to the current running representative; it cannot remain both above and below. If that session has five sequential completed prompts, it still gets **one** row, representing the relevant latest canonical prompt and updated entire-session cost. When it ends, it returns to the non-running pool under existing terminal/history eligibility. Concurrent prompt changes must not create flickering duplicates or temporary double counting.
6. **Order the selected rows by Activity ascending:** oldest activity at the top, **most recently started/finished at the bottom**. A resumed session with a new start naturally moves down to the newest position, using the real prompt start, with stable session-ID/event-ID ties. Do not split the table into an “Earlier” section and a separate Running section or pin all running rows above the history regardless of timestamps. Never use source publication time as a sorting shortcut. Unknown/unverified finish times have a deterministic conservative fallback and must not masquerade as newest.
7. Use **one keyed DOM row per session ID** and one `<table>`/`<tbody>` with the single header. Reconcile rows in place when activity, source status, cost, or display units change; retain proper focus, scrolling, help targets and canonical session identity. Terminal grace, resumed activity, source corrections, disconnect retention and certified empty publications must retain their existing truthful lifecycle behavior. No new source/valuation/identity computation belongs in the browser.
8. Preserve the existing **verified historical winner** contract (FR000623): while the history top-k is unverified, do not substitute a provisional set of old candidates as the latest five. Active rows, Today and account quotas remain usable while history is pending. The existing server **five-session historical population** should provide the required top-five eligible candidates after excluding active/grace IDs; Mini must no longer truncate it to three. Verify the returned candidate pool actually supplies enough correct eligible fillers for the five-slot rule, without a new scanner or unrelated expansion of full Watch's own historical presentation.

## C. Opening size: five-row session viewport + visible subscriptions

1. **Fit-on-open / Default Mini Watch size** must measure and request the **smallest practical outer window height** that fits its full current header, existing genuine health/messages (if any), **the table header and a viewport for five normal session body rows**, and **all currently displayed subscription/account rows**, plus only necessary natural gaps, borders, body padding, browser frame and any scrollbar gutter. The previous artificial **two-running-row opening reserve** is replaced by **a measured five-row table-viewport reserve**. This is *space*, not five fake session data rows.
2. If there are **0–5 selected actual session rows**, the **table viewport has capacity for five rows** in default Fit-on-open mode; no table vertical scrollbar should appear solely from those rows. Empty space for a currently missing history row is acceptable as reserved capacity, not a fake visible session. For truly empty/loading content, an existing compact loading/empty message can occupy the table area without destroying the five-row opening capacity.
3. With **6 or more unique running sessions**, render them **all** in the same unified table but cap the **table's vertical viewport at approximately five ordinary body rows (plus its header)** and make **the session-table area scroll vertically**. The **subscription list and window header remain outside that internal scrolling region and visible**. A sixth row must **not automatically grow the entire PiP window**, move accounts offscreen, induce a document scrollbar when table-only scrolling suffices or trigger a passive native resize. Keep the column header readable (sticky if needed) and all running rows keyboard/pointer accessible through the table's own scrolling region.
4. Five-row sizing must derive from real styles/row metrics at current CSS zoom/font/DPR, including borders/padding and legitimate row height variations; avoid rounding that cuts a fifth row or creates a gratuitous scrollbar. Handle any internal **horizontal table panning** correctly without losing a row to scrollbar feedback. If native PiP work-area/min/max constraints prevent the requested height, preserve reachability by normal scrolling and do not hide/clamp data to simulate success.
5. **Remember last size** must still respect the user's remembered/manual dimensions rather than silently overriding them with the default opening fit. Manual resize remains usable; a too-short remembered window can scroll as necessary. **Keep ↕ Fit Mini Watch height** with the same one-shot, user-activated, height-only behavior and immediate tooltip dismissal. Under the new unified layout its target is **the current visible bounded table viewport (up to five rows) plus real header/messages/accounts**, not all offscreen sixth+ running rows. An explicit Fit can correct a manually resized window without toggling hidden history, fetching data or creating periodic autosizing.
6. Default opening measurement may use the existing inert offscreen layout in `OpeningMeasure.read()`, updating once the CSS and font measurements are available before the initial PiP request. Do not modify width/height on every Live/SSE publication; no new resize loop, timer, popup, persistence or second EventSource. A fresh user opening performs one normal request and native clamp handling as before.

## D. Default width: compact other columns, generous Session area

The owner wants a **deliberate ballpark default width based on the unified table**, not the old “just fit the four-item header” width, and does **not** require an exact pixel constant. Design-time browser measurement with a robust responsive minimum is acceptable, or use a measured runtime target.

1. At typical actual font/theme/zoom, measure the compact **intrinsic usable widths** (headings plus representative nontruncatable values, normal paddings/borders) of the three **non-Session** columns: **Activity, CCost (Total), Ctx**. Keep each of those columns **as narrow as practical without clipping its important clock/cost/context contents**; the CCost column should not expand to consume flexible whitespace.
2. If their combined measured table-column width is **N**, reserve a **Session** title column of approximately **1.6 × N**. The resulting intended table content width is approximately **2.6 × N**, before distinct scrollbar/body/window allowances (Session consequently gets ~61.5% of intended table width). For illustration only: compact columns totaling 180 CSS px suggest Session ~288 CSS px, table ~468 CSS px; these are **not** mandatory values.
3. Add a **stable session-table vertical scrollbar gutter** (including six-plus active cases), necessary horizontal padding, borders, frames and only a small appropriate zoom/focus/rounding allowance. Ensure the real **header** still fits: Cost Guard · Watch, **↕ Fit Height** and the complete actual/reference **CCost Today** value and prompt count. The reference `CCost Today 90 000 · 999 prompts` and true longer current text remain relevant. The default outer width is the **larger of the table-derived need and the complete header's intrinsic need**. If the header needs more width, put most additional table width into Session; do not fatten compact metric columns.
4. Both a measured runtime implementation and an empirically chosen, documented design-time approximation are acceptable **provided real browser tests demonstrate a sensible ~1.6 Session-to-other-columns-total ratio under ordinary desktop conditions** and no clipping/wrapping regression. This is a visual design target, not a hard pixel-perfect runtime invariant. When fonts, text, theme, zoom or narrow screen constraints prevent the ideal ratio, prioritize legible complete metrics, usable header controls and correct responsive behavior over forcing 1.6 exactly.
5. Preserve **manual width resize** and **Remember last size**. At genuinely narrow/clamped widths, the Session title may ellipsize, prompt-table content can pan horizontally, and the header can intentionally reflow; no document-level horizontal clipping of controls and no automatic native-width correction. Do not size opening based on the longest unbounded session title or every row's text, or add a new width-fitting setting.
