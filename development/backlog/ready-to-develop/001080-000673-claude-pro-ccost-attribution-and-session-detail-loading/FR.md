## Reported observations and desired result

This request now contains **three independently testable problems** under one FR: (A1) Claude Agent model/reference price coverage beyond Sonnet, (A2) qualified Claude Pro account-period attribution, and (B) Sessions detail loading. A1 and A2 are separate potential causes of missing CCost: fixing model pricing is not proof of correct account attribution, or vice versa.

### A1. Claude Agent models beyond Sonnet: Opus prompt CCost shows Not Applicable (owner update 2026-11-11)

The owner reports using a **Claude Agent / OpenCode Opus 5.5** model and seeing **Not Applicable** for the prompt's Cost Guard CCost, while OpenCode's own dollar-denominated display increases. This is an investigation clue, **not yet proof that OpenCode's displayed dollars equal Cost Guard's canonical reference valuation or actual billed spend**.

The owner wants **all currently selectable Claude Agent models**, and future models exposed using the same upstream structure, to be recognized and priced generically when supported. The reported examples span **Opus, Sonnet, Haiku and Fable** families and selected releases/aliases around 4.5, 5, 5.2 and 5.5. These are **user-reported names, not a verified inventory or permission to invent models/prices**. Enumerate the actual current `providerID=claude-agent` catalog at implementation time rather than hardcode this list.

**Desired result:** a request with a source-qualified model identity, real token usage and a supported reference price produces a correct canonical prompt/session/Watch/**global Today** CCost, rather than N/A because a non-Sonnet family or moving alias falls through the model/price mapping. Genuinely missing or ambiguous model/pricing evidence must remain truthfully unavailable, not quietly converted to $0 or a guessed Sonnet/Opus price.

### A2. Claude Code Pro subscription: observed 1% but parenthesized $0.00

The owner has used a **Claude Code Pro subscription** for several OpenCode/Claude Agent sessions. During the active **five-hour** quota window, the native account quota displays about **1% used**. At least one session in that same window has a positive **reference CCost of approximately USD $0.06**, yet every corresponding Claude Pro account-card reference CCost display, including parenthesized period values, shows **USD $0.00**.

This seems especially suspicious following **completed FR000651** (Claude Agent moving alias `claude-agent/sonnet` etc. mapped through the exact OpenCode Desktop/current-location model catalog for display/reference valuation). The model's reference valuation may now work at the session level while the **subscription-provider/account attribution still fails to recognize that request route**.

**Expected:** Qualified, uniquely counted Claude Agent requests that can safely be associated with the Claude Code subscription contribute their **same canonical priced reference CCost** to the correct native five-hour/weekly account windows and same-day account summary as applicable. A synthetic in-window **$0.06** request should **not** show $0.00 solely because it is labeled `claude-agent` rather than `claude-code`. Show an honest known subtotal/estimated attribution or unavailable state when account ownership or pricing is not provable; never assign API-billed traffic to Pro because it uses a Claude-branded model.

**Important:** Native **`1% used` is independent provider quota telemetry**. It is **not** converted to dollars, and the parenthesized amount is **reference CCost (estimated token valuation), not actual Pro billing**. A subscription can have quota consumption that is not fully represented in locally available OpenCode history; do not force percentages and dollar amounts to reconcile numerically.

### B. Sessions detail: frozen "Waiting for session source" at 0%

When opening a session from **Web → Sessions**, the centered determinate progress sometimes shows **`Waiting for session source…` and 0% for roughly five seconds**, then suddenly the full table appears. The owner expects honest **useful progress feedback and prompt arrival of the completed view**, not an apparently stuck meter that skips directly to done.

**Expected:** Identify why this visible 0% plateau lasts until the next response, eliminate avoidable client polling latency, surface meaningful source-backed phases/readiness and real available counts, and retain the existing centered consistent progress design. If the source is genuinely in an opaque operation and no percent can be measured yet, explain the waiting phase clearly rather than fabricate gradual numeric progress. The first usable session should appear promptly when the host has qualified it, not after an unnecessary full five-second browser sleep.

- `src/analysis/period_ccost.py::quota_window()` only admits supported native reset/duration boundaries. `AccountPeriodHistory` and Watch account projection reuse bounded history/index evidence; account cards `src/web/assets/account-cards.js` render server-prepared CCost values. A zero can also come from a genuinely empty qualified window, history gaps, window mismatch or per-unit formatting. Investigate all of those before concluding that a provider alias is the only cause.
- Existing `development/tests/test_account_period_ccost.py` tests `claude-code` usage and direct `anthropic` API separation, but its standard request fixture **defaults to `claude-code`**, so it does not exercise the concrete **`claude-agent` with current-catalog model fallback → Pro quota CCost** path.

### Session-detail status

- `src/web/assets/session.js::SessionDetail.View` initially displays `Opening session…` / `Waiting for session source…` with a fixed **0%**. `historyProgress(completed,total)` only starts after `/api/detail begin` has returned an acquired revision and verified rows, then maps transferred rows to **0–95%**, with **100% only on DOM apply**. A pending `begin` reply contains no totals to drive these percentages.
- `View.poll()` currently schedules the next visible-page read after **5,000ms** (30,000ms when hidden), including the **initial pending-without-result case**. Thus even a completed backend capture can go undiscovered for up to another five seconds on the browser. **Measure this latency before changing cadence**; source acquisition time may also contribute.
- `src/application/session_detail.py::SessionDetails.open()` enqueues due work; `SessionDetails.tick()` acquires it on an existing owned Live/detail lane, normally marking its next due in five seconds. While acquisition has not produced a qualified report, `page(begin=True)` exports `state/pending/result=None` without source-phase/count telemetry. The HTTP path only reads detached state and must not become a new arbitrary source-acquisition owner.
- Completed **FR000662** deliberately implemented a centered numeric determinate progress bar, real chunk counts and no fabricated timer percentage. **Preserve that contract**, improving the missing *pre-first-result* feedback/response latency rather than replacing correctness with a decorative animation.
