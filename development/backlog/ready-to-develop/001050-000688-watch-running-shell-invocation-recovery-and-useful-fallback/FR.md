# FR 000688 — Full Watch: recover real running-shell commands and replace generic unavailable invocation details

**Owner-approved Ready to Develop, 2026-11-12.** Permanent ID **000688**, queue priority **001050**. Scope: **Full Web Watch → Running Prompts → expandable Running tool/background lines**. Improve the underlying source correlation and meaningful fallback, not merely the wording. Preserve all existing Watch accounting, running duration and privacy guarantees.

## Owner-reported recurring symptom

An active Web Watch prompt reports roughly **two shell calls/jobs** and a **Running shell** time of about **2 minutes 6 seconds**, yet expanding Running shows:

`Invocation details unavailable from the current source.`

The owner can sometimes expand a shell call inside OpenCode and see what it did, but at other times OpenCode's own UI provides no obvious command. The owner wants to understand **why a shell can be running while Cost Guard cannot show how it was invoked**, and to see **some genuinely useful identifying/execution information for every running item**. Ideally a shell invocation reveals the actual command/script and relevant options, without ever attributing an unrelated command or exposing secrets.

This repeats concerns raised in **FR000632** (expand running tool inputs) and **FR000648** (preserve real commands and correct timeout units). Those requests were completed; their success on a single foreground shell and synthetic source examples did **not** prove coverage for multiple concurrent background shells, registry-recovered shells, absent native tool input or retained/unverified generations. This is a new **source-correlation + multi-job** request, not a repeat of their already-completed CSS/string changes.

**Do not assume the reported exact 2m06s running instance was diagnosed by repository inspection.** No particular local session/call ID or live OpenCode database was available during FR drafting. A later implementation worker should inspect a small **owner-authorized, read-only** active example if available; its source version and actual failing branch must be recorded separately from synthetic findings.

## Important source-level findings (verified at FR authoring)

### A. Current Cost Guard can know the tool is running while suppressing its input

- `src/watch/tools.py::observe_tools` gathers **all canonical physical tool calls** under a prompt, groups count by tool name and identifies the longest active tool after a 10-second threshold. When `include_invocations=True`, its `running_invocation` is derived from the actual running `NormalizedPart`; the `running_tool` label and timer can be available independently of input text.
- `src/watch/invocation.py::invocation` derives bounded/redacted text **only from the canonical part's `state.input` or legacy `input`**, via `src/watch/tool_contracts.py::tool_input`. When a part exists but has no input, this function still returns a `ToolInvocation` with a specific `No source input available.` qualification. The **exact generic unavailable sentence** in `src/web/assets/watch.js::drawInvocation` is displayed when there is **no detail object at all**, not simply when the `command` field is absent.
- `src/watch/cards.py` **deliberately clears `running_invocation` and `background_invocation`** when the card is not `observed`, its generation is not verified, the capture is retained, or the prompt is execution-unverified; `src/application/live_projection.py` and `watch.js::drawActivity` apply additional state/ownership gates. A stale/uncertain Running heading can thus coexist with intentionally absent command detail. Preserve that safety rule unless fresh request-qualified evidence really repairs it.
- `2 × shell` under **Tool Calls** means two observed physical shell *calls*, not necessarily two simultaneous running processes. `Running: 2× shell` from `background_kinds` is a different signal: two outstanding *background* shell activities. **Disambiguate which the owner observed** before assuming a concurrency bug.

### B. Multi-background-shell suppression is deterministic and currently by design

- `src/watch/invocation.py::background_invocation` returns details only when **exactly ONE running background job** belongs to the prompt; if `len(jobs) != 1`, it immediately returns `None`. It then demands exactly one source part linked by the same session+assistant message and `callID` or `part_id`.
- `src/watch/cards.py` independently exports only a single `background_invocation` when `len(row.background_kinds) == 1`; `src/web/assets/watch.js` also passes **null** when `kinds.length != 1`.
- **Therefore a verified, correctly loaded prompt with TWO actually running background shell jobs WILL show `Running: 2× shell` with no expandable individual commands, even when both original parts contain valid inputs.** This is a proven design limitation and a very plausible explanation of the reported symptom. **Do not “fix” it by choosing whichever shell ran last, the longest, or one with a matching tool name.** Make per-job details possible, with stable scoped identities and correct ownership.

### C. OpenCode itself exposes additional command information that Cost Guard discards today

Current public OpenCode `dev` source:
- [Shell schema](https://github.com/anomalyco/opencode/blob/dev/packages/schema/src/shell.ts) defines `Shell.Info` with **id, status, command, cwd, shell, metadata, start/completion time** (plus other potentially sensitive details).
- [Shell API](https://github.com/anomalyco/opencode/blob/dev/packages/protocol/src/groups/shell.ts) exposes location-qualified read-only `GET /api/shell` to list **running shell jobs**, plus `GET /api/shell/:id`. It is not restricted to one user's prompt by itself.
- [ShellTool source](https://github.com/anomalyco/opencode/blob/dev/packages/core/src/tool/plugin/shell.ts) creates the shell with `metadata: { sessionID: context.sessionID }` and a separate internal `toolCall: { sessionID, assistantMessageID, callID }`. It registers an actual `command` and job/session association in the task registry.
- [Background Job schema](https://github.com/anomalyco/opencode/blob/dev/packages/schema/src/job.ts) has a shell job with **sessionID, shellID, command, status, start/completion**. [Experimental job API](https://github.com/anomalyco/opencode/blob/dev/packages/protocol/src/groups/job.ts) supports read-only `GET /api/experimental/job`, optional **sessionID, kind, status and descendants** filters. This may help if original native tool part details were lost. It is explicitly experimental: capability-check the exact installed OpenCode version before depending on it.
- `src/sources/opencode_v2_background.py::running_jobs` **already calls `GET /api/shell`** but extracts only a `frozenset` of currently running **IDs**, throwing away the source-provided **command, session association, time and safe identity metadata**. It also currently drops part/call links when registry status is unobservable.
- `src/sources/opencode_v2_background.py::_starts` recognizes only native background starts with `state.input.background == true` and native `jobID`/`shellID`. The source may know running shell processes without having a complete canonical tool-input part in the currently acquired session tree.

**Important limitation:** An OpenCode **UI** that lacks a command does not prove `/api/shell` or `/api/experimental/job` lacks it. Conversely, a raw registry command **does not establish which prompt or tool call** owns it merely from the same name or current location. Check exact identifiers; never broadcast an unrelated session's process command.

The upstream `dev` code is **not proof that the owner's installed OpenCode server has these endpoint/metadata contracts**. Compare to its actual version and supported source generation; V1 and older V2 may differ. No real local shell API was queried during FR authoring.

## Desired behavior and implementation guidance

### 1. List the actual running invocations separately, including **2+** shells

- Retain the established `Running: shell 2m06s` or `Running: 2× shell 2m06s` compact line and existing tool-outcome counts. On expand, show a **short per-invocation list of the currently attributable live jobs**, not a single ambiguous `background_invocation` object. For two running shells, show two separate real command/detail entries, each independently correlated and updated. Do not mistake one completed earlier shell for a concurrently running one.
- Bound the number of displayed jobs/commands to a small sensible limit (e.g. first 5, stable order and honest `+N more`), without dropping the correct total. Distinguish **foreground tool currently running** from **background shell job(s)**. When 1 background job is present, preserve prior FR000632/648 behavior and exact existing fields.
- Display the actual command/script path, arguments, workdir/cwd, shell, requested timeout and/or started time **only where independently source-observed and privacy-safe**. Example, not a real user command:

```text
Running: 2× shell 2m06s
  Shell 1 — background, running
    command:
    python scripts/test_one.py --short
    cwd: (source-recorded safe path)
  Shell 2 — background, running
    command:
    python scripts/test_two.py --check
```

- Use stable **source/instance/session/physical-call-or-shell-job identity** and revision for each entry. Preserve expanded state, text selection, focus and scroll on duration-only ticks; clear/replace only the specific changed/ended job, source revision or identity. Avoid repeated closing/reopening of the entire disclosure when only seconds tick.

### 2. Use OpenCode's real shell/job information as a **targeted fallback**, not guessed commands

- **First choice:** existing canonical tool `NormalizedPart.state.input`/`input`, already linked to the exact prompt/tool ID and filtered by `invocation.py`. Verify no current V2/legacy union adapter accidentally drops the input under an alternate supported shape (tool state, `callID`, `shellID`, `jobID`, context/code-mode continuation, nested child).
- **Second choice:** existing **same-source, location-scoped running `/api/shell`** observations, **only when** provider-owned metadata or same physical `shellID`/`jobID` unambiguously matches the intended session + call/prompt/child. Reuse the existing background registry observation in the source reader where possible; do not add a second global location shell poll or call the registry on every tooltip expansion.
- **Third choice if supported:** `/api/experimental/job` with **kind=shell, status=running, exact owning session/descendant filter**, and its `sessionID`/`shellID` plus command. Gate by API capability/version and avoid separate expensive scans. When only **session-level** ownership is provable, show a truthful session-scoped job list if useful, but **do not state a specific prompt launched that command** without a prompt-qualified join.
- If the registry and original tool part both expose a command, prefer the original invocation's source input and independently verify that any supplemental registry identity is consistent. If conflicting IDs/commands, withhold the conflicting command and present safe status/correlation information, not an invented or last-write-wins attribution.
- Don't assume background jobs can only have one shell per prompt. Correctly handle nested/child sessions, a child that has already returned but has a still-running job, self-resuming background commands, multiple shells from one code-mode tool call, duplicate parts and daemon takeover after OpenCode restarts. Keep canonical session/part/call identity and source generation, and reject other unrelated concurrent sessions in the same directory.

### 3. Always show the **most useful honest facts available**, never generic dead-end prose

- **Remove the generic literal** `Invocation details unavailable from the current source.` from this expanded Running UI. This is a user-facing usefulness guarantee, **not a guarantee that every external source always retains an executable command**.
- If an exact command cannot be attributed, show the **known tool/job kind, observed live status, current elapsed duration (when evidenced), per-job distinction/count, and source-supported context such as background/foreground, start time or session scope**, plus one concise specific reason (e.g. **`Command not recorded in the current tool event`**, **`Two shell jobs; original call links missing`**, **`Only the running process is observable`**, **`Command intentionally withheld (sensitive input)`**, **`Awaiting verified live source`**). Do not use a blanket `Unavailable` paragraph without context.
- Never invent a shell command, script path, PID, workdir, tool input, a specific job-to-prompt link or completion solely from a timer, title, model-generated prose, native output or approximate timestamp. Even when raw command is truly lost, an accurate **`Shell running • 2 jobs • 2m06s • command not recorded`** is more informative than an empty disclosure.
- **When the source becomes verified later**, update the matching job's details without requiring manual page refresh or losing unrelated job rows. For complete failure/no active evidence, avoid displaying an old command as if still running. Distinguish no command from no source and intentional privacy withholding.

### 4. Do not weaken FR000632/648 privacy or lifecycle boundaries

- Reuse the **same `watch/invocation.py` allowlist, 4096-character ASCII-escaped text budget, credential/redaction/withholding policy, source text preservation, safe multiline quoting and labeled shell `timeout` milliseconds** for *every* new source of command text. `GET /api/shell` `command` and experimental background job `command` are **not safe merely because they came from a server**, and should never bypass `invocation_redaction.py`.
- Never show raw environment blocks, API keys, authorization headers, private-key values, arbitrary opaque metadata, tool output/stdout/stderr, shell capture files or unbounded full OS process argv. Don't fetch `/api/shell/:id/output` for invocation details. Do not execute shell commands or call OpenCode's shell creation, stop, remove, wait or background mutation endpoints.
- Details remain **Web Live-only, in memory**, delivered only over authenticated, same-user, loopback channels; no durable command cache, browser storage, public diagnostics, tracking, telemetry, raw-log dumps or secret-bearing error exceptions. Maintain existing event/replay size caps; smaller per-job budgets or bounded omission notes are acceptable when many jobs overlap.
- **Source safety:** no wrong-session command even when two sessions share a project, shell names/cwd/timestamps coincide, a process daemon carries jobs over a restart, call IDs repeat across sessions or registry data are stale/partial. A failure to establish identity must not expose another user's invocation. Preserve source epoch/session/parent/canonical scope, verified-generation gating, retained-history suppression, terminal/unverified cleanup, 10-second threshold, existing polling/retry and workers' ownership.
- Prefer extending the existing one bounded per-source observation through `src/sources/opencode_v2_background.py` and the already owned Card worker. No new always-running timers or independent browser fetch on expand; no full-history rescan, extra worker/daemon or OpenCode restart.

## Mandatory regression and acceptance proof

1. **Reproduce the actual predictable missing-detail path:** a verified prompt with **two running background shell jobs and two complete original tool parts** currently gets `background_invocation=None` by both `len(jobs) != 1` and `len(background_kinds) != 1`. Demonstrate that baseline failure *before* the patch, then assert after the patch the expanded Watch line shows the **two correct, separate commands** with identities, not one arbitrary shell or generic unavailable.
2. **Registry-only recovery:** construct V2 API-shaped **`/api/shell`** response with one running shell `Shell.Info.command`, metadata.sessionID and shellID; canonical tool part is missing/retained or has missing input. Reconcile to the correct session/call where supported. Assert readable redacted command and options appear only after the appropriate verification; use a second wrong-session command in the **same location** to prove no leak. Explicitly test a contradictory command/ID and lack of a call-join.
3. **Experimental job support:** if the installed source supports `/api/experimental/job`, test session+descendant-filtered shell records, two jobs, recovered daemon state, mismatch and absent endpoint (404/compatibility) without failing normal Watch. **Do not ship a mandatory dependency on an experimental endpoint** merely because upstream `dev` contains it.
4. **Multiple meanings of `2× shell`:** separate `Tool Calls: 2× shell` with only one currently running foreground call from **`Running: 2× shell`** with two actual outstanding jobs. Never show two simultaneously running commands on the basis of tool-call counts alone. Also test a foreground shell plus background jobs, two prompts/subagents in the same session, several active foreground calls, and a child background shell after the child finishes.
5. **Unavailable-source matrix:** one correctly scoped part with ordinary missing `state.input`, missing `command`, unsupported input, too-large command, known redacted credentials, unknown registry, source unavailable, retained capture, revision churn, execution-unverified prompt, elapsed-time-only Live updates and a truly shell-less prompt. Every *visible expanded Running* state offers the safe facts and specific cause that exist; no generic `Invocation details unavailable from the current source`. When a complete command exists and is safe, **show it, not a vague fallback**.
6. **Privacy and source identity:** synthetic commands with `--token`, `--api-key`, `curl -u`, URI credentials, PowerShell env assignments, private-key material and giant fields must not leak into DTO, DOM, SSE/replay, errors, public fixtures or logs. Exact matching and revision/generation/retirement checks protect same-directory peers, nested sessions and source reconnect. Never infer via executable name or substring equality.
7. **Real browser/host:** authenticated shipped Full Watch + real Chromium/Edge interaction in Classic/Web and narrow/wide layouts; verify two job rows, open/close, keyboard/hover/touch, wrapping, selectable multiline command, focus/scroll retention, correction/reversion, 10-second running threshold, unchanged tool counts/colors, stale cleanup and source-ready transitions. Test one **isolated controlled non-secret shell execution** against a supported OpenCode V2 server with a bounded harmless local command (no paid model call) if feasible; this is different from merely rendering static fixtures. Read-only bounded observation of the owner's naturally running session is desirable if available, with session IDs/commands excluded from public evidence; if unavailable mark that actual incident **NOT VERIFIED**, not PASS.
8. **Measure overhead:** count added API reads and Live bytes for 0/1/2/5/many jobs, active vs quiet Watch, V1 vs V2; no extra expensive source rehydration or refresh on disclosure expand. Keep terminal/outage/shutdown semantics and ordinary CLI/Mini Watch behavior unchanged. Tests `development/tests/test_watch_invocation.py`, `test_watch_cards.py`, `test_web_live.py`, integration `web_watch_summary.cjs` / `probe_watch_invocation.cjs` and source-specific V2 fixtures must be updated to assert new multi-job behavior rather than treating the old missing-details fallback as accepted.

**Non-goals:** redesign the entire Watch page, change CLI/Mini Watch tool summaries, show arbitrary command output or env, read every OS process command line, start or modify the user's shell, per-hover network calls, unsandboxed paid inference, invent missing historical commands, weaken source identity/auth/redaction, replace elapsed Running with a completion guarantee, or claim full live proof from synthetic fixtures alone.

**Done means:** a **verified two-shell background case shows both actual commands when source evidence exists**; a single source-known shell uses real safe command/script inputs whether they came from canonical tool state or an exactly linked native shell/job record; every expanded running item has **meaningful truthful facts** instead of the old generic unavailable string; and missing provenance/secret redaction never leads to another session's command being shown.
