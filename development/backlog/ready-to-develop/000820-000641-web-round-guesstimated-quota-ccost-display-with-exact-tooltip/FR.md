# FR 000641 — Web: round guesstimated quota CCost to sensible significant digits, preserve raw estimate in help

**Owner-approved Ready Feature Request, 2026-11-09.** Permanent ID **000641**; temporary Ready priority **000820**, after FR000639 (000800, Mini Watch interaction) and FR000640 (000810, provider-authoritative quota amounts). **FR-only publication now:** add this document and update the backlog identity watermark 640 → 641. No product implementation, tests, release, Settings change or unrelated backlog modification in this transaction.

## Owner request / intended user experience

Cost Guard Web's **usage-subscription quota guesstimates** currently display implausibly precise figures, such as **613** or **52 343 CCost Credits** and **$6.13** or **$523.43**. These are *estimates derived from observed reference CCost and a provider-reported percentage*, not measured entitlement balances. Displaying every final digit suggests an accuracy the inputs do not justify.

**Desired result:** display these specifically estimated values with **as few significant digits as possible**, allowing **up to and including 10% relative rounding difference** from the *original unrounded computed estimate*. Round **in canonical CCost Credits first**, then convert that rounded display amount to the currently selected **Credits / reference USD** unit. Retain the original computed value at full available precision internally and make it available in a concise, accessible tooltip. **Keep normal USD formatting with the dollar prefix and exactly two decimals**, even when the rounded value is an integer number of dollars.

This is a **presentation-only precision policy for quota guesstimates**, not permission to change source evidence, calculations, quota percentages, native balances, reported entitlements or provider-confirmed values. It must work in full **Watch**, **Accounts** and **Mini Watch** wherever the same applicable estimate is rendered.

## Deterministic rounding policy

1. Compute each eligible estimated number **normally and at full raw Decimal precision** in **reference CCost Credits**. The numerical estimate is never overwritten.
2. For a **positive** raw estimate, first round to the **nearest one significant decimal digit** (a single nonzero leading digit at the relevant power of ten). Use decimal **round half up** for exact halfway values, not floating-point artifacts. Compare the rounded candidate with the raw estimate via **absolute relative error = |candidate − raw| / raw**.
3. **Accept the one-significant-digit candidate only if error ≤ 10%.** Otherwise round to the **nearest two significant digits**. Two significant digits normally give substantially less than 10% error; check the bound and preserve additional necessary precision for edge cases rather than ever violating the declared tolerance. Do **not** round every value by a fixed 10% step or use a fixed tens/hundreds increment independent of magnitude.
4. **Choose the coarsest of the accepted 1- or 2-digit candidates**; do not keep an unnecessary trailing digit when an approximately round number already satisfies the error rule. The result must be deterministic across calls, OS/theme/zoom, display modes and source updates. Do not round a positive value to numerical zero merely to simplify it; treat an actual zero as zero. Missing/unknown/nonfinite/invalid values retain their current appropriate **N/A / ? / omission** semantics, not a fabricated estimate.
5. **Apply the rounding exactly once per displayed estimated quantity, before unit conversion**: the raw reference-Credit number is the invariant input for both units. For **Credits**, use the project's locale grouping convention, without redundant trailing zeros or false fractional precision at ordinary magnitudes. For **USD**, divide the rounded Credits by 100 and then apply the existing **`$N.NN`** format. Keep **two USD decimals**, even when they are `.00`. Small values may legitimately retain cents, such as **250 Credits → 250 Credits / $2.50**, because rounding to 300 Credits would change the estimate by 20%. Do **not** promise all USD estimates end in `.00`.
6. **Small-value handling:** no coarse integer display, positive-to-`0` collapse, rounding-ceiling or two-decimal currency quantization should be claimed to satisfy the **≤10% Credit-space tolerance** when it cannot. Where a sub-Credit/near-cent estimate cannot truthfully be represented at that tolerance using existing display precision, retain necessary fractional Credit precision or the existing honest small-value notation and explain the display limit in help. Do not silently turn nonzero into zero or break the user's requirement that ordinary USD formatting remains two decimals.

### Illustrative exact examples

These are **synthetic unrounded reference-Credit estimates**, not observed usage:

| Original estimate (Credits) | Rounded display (Credits) | Rounded display (USD) | Explanation |
| ---: | ---: | ---: | --- |
| 613 | 600 | $6.00 | One significant digit; ~2.1% lower |
| 2 343 | 2 300 | $23.00 | 2 000 would be ~14.6% lower, so use two significant digits |
| 49 000 | 50 000 | $500.00 | One significant digit; ~2.0% higher |
| 51 000 | 50 000 | $500.00 | One significant digit; ~2.0% lower |
| 52 343 | 50 000 | $500.00 | One significant digit; ~4.5% lower |
| 250 | 250 | $2.50 | 300 would be 20% higher; preserve two significant digits |
| 149 | 150 | $1.50 | One significant digit would become 100, over the tolerance |
| 0 | 0 | $0.00 | True known zero, not a missing estimate |

An estimated raw **613 Credits** becomes a visible **600 Credits / $6.00**. The tooltip exposes the **original computed 613 Credits / $6.13**, clearly described as **unrounded estimate, not verified provider usage**. If the raw value includes fractional Credits, keep that computed precision available in the tooltip; do not present the rounded display as the raw calculation.

## Precisely what is and is not a guesstimate

- **In scope: `capacity_basis="ratio"` derived estimates** from percentage-based/rolling quota windows (where the calculation uses known observed same-window CCost divided by the native percentage consumed). **Estimated Capacity** and **estimated Remaining** should display rounded; their source values, provider fraction and cost observations remain raw. These are the types of estimates described in completed FR000585.
- **In scope: derived `Monthly Capacity` guesstimates**, even when their underlying current-period Capacity was source-confirmed, because extrapolating a period to a hypothetical 30-day equivalent is itself an estimate. Round only the *computed monthly-equivalent result*; never pre-round the actual period capacity before multiplying by the duration ratio. Preserve its existing **`(guesstimate)`** annotation and assumptions.
- **In scope when applicable: estimated Web Remaining/day and Remaining/workday reference CCost pace** from the same `ratio` / inferred-guesstimate basis. Calculate the daily rate from **unrounded remaining** and actual day/workday counts, then round **each displayed rate** by the same policy. Never divide a rounded parenthetical value; this applies only to genuinely estimated pace, not provider-authoritative balances.
- **Out of scope: measured/observed period `CCost Used`** for percentage-only subscriptions; it is a value calculated from actual observed requests and is not itself the ratio-derived quota guesstimate. Keep its existing normal precision. The raw known Used value remains the correct input to estimating Capacity.
- **Out of scope: source-verified finite provider allowances** (including Copilot AI-credit Used/Remaining/Capacity and their remaining/day/workday pace after FR000640), as well as other verified reference-capacity values before theoretical monthly extrapolation. These must keep normal numeric precision and consistent provider facts; do not round a real reported quota Used or Remaining just because it is shown next to an estimated row.
- **Out of scope: `CCost Today`, prompt/session/token costs, actual billing/native money, native percentages, raw quota limits, native progress bar fractions, native pace/CLI output, external unaccounted usage figures, pricing and general reference CCost formatting.** Do not globally alter `ccost_amount()` or make all account spending look approximate. Provenance and field-level classification, **not a mere substring in display text**, determine whether this policy applies.

## Tooltip / accessible help

1. On every **visible guesstimated quota amount** subject to this rounding (the **Remaining** number in parentheses, **Capacity**, **Monthly Capacity** and applicable estimated **Remaining/day** or **/workday**), provide concise existing-style **`ContextHelp` hover/focus/touch information** showing the **original raw calculated estimate** *before this presentation rounding*, in reference Credits, and optionally its normal-precision USD representation in the selected mode. Example: **`Guesstimate before display rounding: 613 Credits ($6.13).`** Append or integrate the existing estimate-basis caveat; never suggest this is the provider's exact balance.
2. Keep the current visible **`(guesstimate)`** suffix where it already exists, but do not invent a large extra explanatory label, precision badge or new `≈` on every quota line. Keep compact layouts intact. Existing Capacity help in full Watch/Accounts and the Mini Watch line's help can be extended; attach help to the **value itself** where the currently visible parenthetical/pace estimate lacks a focusable target, without making the whole card a tooltip.
3. A tooltip must track the selected **Credits/USD**, current Used/Remaining mode, account/quota identity and latest relevant raw estimate. Never show a stale raw number when display tokens have changed, and do not expose unrelated accounts. Provider-confirmed figures should keep their separate existing provenance help, not a misleading “before rounding” explanation. The tooltip must remain keyboard/touch accessible and follow the existing shared opening/dismissal rules.
4. This exposes the **exact value of the calculation (to its retained supported Decimal precision)**, **not an assertion of real-world accuracy**. It is still a guesstimate. If using a bounded human-readable precision to avoid unwieldy repeating decimals, retain the raw Decimal in the canonical payload and do not describe a trimmed tooltip number as exact.

## Verified code areas and coordination

- **`src/application/quota_ccost.py::quota_ccost_values()`** distinguishes **`basis="ratio"`** estimated reference Capacity/Remaining from **`basis="native"`** verified quotas, and **`monthly_tokens()`** independently emits a theoretical **`Monthly Capacity`** with **`(guesstimate)`**. **`quota_ccost_tokens()`** currently formats all these numbers with generic **`ccost_amount()`**, which is intentionally exact-looking: USD uses two decimals; Credits display full integer units. Reuse the existing raw values and make rounding an **estimate-specific presentation** step.
- **`src/application/quota_ccost.py::quota_ccost_pace()`** returns raw reference per-day/workday amounts, and **`src/application/display.py::amount_tokens()`** formats `ccost_per_day` and `ccost_per_workday`. Attach scoped provenance to these fields so genuinely ratio-derived pace gets the policy, while native/source-verified pace does not.
- **`src/numbers.py::ccost_amount()`** and existing `display_units.credits/usd` define the normal conversion and 2-decimal USD style. Do not change this global formatter; provide a pure decimal estimate-rounding helper at the projection/display boundary, or an equivalent narrowly scoped implementation. Compute estimates and raw tooltip tokens **once on the server**, not from parsing formatted `(guesstimate)` strings in JS.
- **`src/web/assets/account-cards.js`** has separate parenthesized `ccost_...`, Capacity, Monthly Capacity and pace presentation. **`src/web/assets/mini.js::View.drawAccounts()`** uses the same quota amount display tokens for the primary subscription and has its own ContextHelp for account details. **`src/web/assets/render.js::overviewAccounts()`** covers Accounts pace and details. One source-prepared display/provenance contract should produce matching results across all three surfaces. Preserve existing layout and native quota help.
- Explicitly **build on FR000640**: that FR makes eligible provider-authenticated finite quota Used/Remaining authoritative, while percentage-only plans retain ratio estimates. This FR only changes the *cosmetic precision of those still-estimated values*. It must not undo FR000640's data-source selection, nor FR000638's proper Web reference-CCost pace basis.
