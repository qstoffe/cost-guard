# Recover Windows Web startup from stale instance state after reboot and PID reuse

## Problem and verified local evidence

The owner runs Cost Guard from a separate local installation and reports that the Windows Web Beta launcher fails with:

> Existing Web instance could not be verified. Do not delete its state; run Diagnostics.

Read-only investigation on the affected Windows workstation on 2026-11-02 established the following. The installed source reported **v80.121**, while the retained, schema-valid Web instance record and diagnostic snapshot belonged to **v80.119**. The relevant lifecycle/process/state implementation also exists on repository `main` at investigation revision `6d826beba5aa0e92ae375d40a8230f0f04e3b490`.

- The retained record identifies a `pythonw.exe` host born on **2026-11-01 at 22:58:50.556645 UTC**. Its private control material was not printed or copied.
- Windows reports its latest boot at **2026-11-02 16:03:09.500 UTC**. The recorded PID now identifies `svchost.exe` in Windows session 0, created at **16:03:22.185 UTC**, not the recorded Python host. This is confirmed PID reuse across a reboot, not evidence of an existing Cost Guard instance.
- `OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION)` for that recorded PID fails with **Win32 error 5, Access is denied**. The production `process_identity()` consequently raises `InstanceConflict("process_identity_unavailable")`.
- Calling the installed `stop_existing()` with the real record, a non-writing store substitute and mocked control/termination reproduced exactly `process_identity_unavailable`: **zero control requests, zero termination calls and zero state removals**. No real launcher, tray, browser or server was started by this investigation.
- The checkout's lifecycle log records three generic `instance_conflict` failures at **16:15:22, 16:15:47 and 16:15:55 UTC**. Its older `ready` snapshot is historical, not current readiness proof. The existing Diagnostics ZIP predates this incident and cannot establish its cause.
- A separate scratch-only private-store probe succeeded, as did querying the investigator process's own native identity. The observed failure is specifically the recorded PID's identity lookup, not demonstrated general Python/private-store failure.

The immediate causal chain is: stale record survives host loss/reboot; PID is reused by an inaccessible system process; `stop_existing()` calls `process_identity()` before its stale/mismatched-identity cleanup branch; the exception prevents recovery. `windows_launch.py` then collapses this specific reason into `instance_conflict`, losing the cause in both feedback and lifecycle diagnostics. Existing stale/reused-PID tests cover `None` and readable identity mismatches, but not this access-denied case.

The investigation left the installation, instance record, ACLs, processes and OpenCode service unchanged. Why the original host did not remove its record before reboot was not established and is not needed to explain this startup failure. Do not publish raw instance records, control/bootstrap secrets, user paths or unrelated process data as evidence.

## Desired behavior and safety invariants

1. **Recover safely from the demonstrated stale-state case as a normal, non-administrator user.** A retained record whose old host is conclusively gone must not permanently block Web startup just because its numeric PID is now an inaccessible unrelated process. No manual deletion of application state, reboot loop, elevation or permission/security changes should be required.
2. **Do not translate access denied into process absent.** An inaccessible PID may still belong to a legitimate host. Establish positive, race-safe evidence that the old managed instance is gone before retiring its record or admitting a replacement. Process name, PID alone, record age, old build number, an expired heartbeat or a failed TCP probe are not sufficient ownership/staleness proof.
3. Keep recovery in the existing checkout-private transition/lifetime-lock and native identity protocol. An OS boot identity, reliable native incarnation evidence and/or the existing lifetime lock may help establish safe retirement; the implementer must justify their exact semantics and race handling. Do not assume a wall-clock comparison alone is an authoritative boot boundary. Preserve serialization through retirement and replacement admission, and do not allow a second managed host or erase a newly published record during overlapping launches.
4. Handle **already existing schema-1 records without boot metadata**, including the affected installation, rather than fixing only newly written records. Any record/schema extension needs explicit safe compatibility behavior. If reliable proof is unavailable, preserve state and refuse safely with a precise reason; do not guess, silently discard evidence or bypass locks.
5. Never send the old control secret to an unrelated PID's reused port. Never terminate the system process, kill by name/port, broaden process rights, or stop OpenCode, another checkout, CLI/Watch or a user's browser. Graceful/forced stopping of a positively verified own host retains its existing exact-handle/birth safeguards.
6. **Preserve actionable, privacy-safe failure facts.** Distinguish process-identity access denied/unavailable, corrupt/unsafe state, busy lifetime/transition coordination and control/readiness failures using bounded allowlisted reasons at the correct stage. The console and existing failure dialog must not assert that an existing Web instance is present when that is unproven. Diagnostics should retain the specific startup cause even when there is no newly started host, without exposing tokens, raw errors, process command lines or user paths. A recovered stale-state case should be recognizable without being reported as an active conflict.
