# FR 000615 — Web finite reports: remove Cancel controls and preserve started acquisitions

**Owner-approved Ready Feature Request, 2026-11-06.** Permanent identity **000615**; Ready priority **000330**, after currently Ready FR000614 (000320). **Backlog authoring only**: publish this FR and advance the identity counter; do not implement code, run tests, change version/release files or modify unrelated backlog entries in this step.

## Owner request

When opening a heavy Web Beta report, particularly **Comparisons**, a **Cancel** button appears at the top-right during loading. The owner does **not** want the user to be offered a way to cancel a requested report: once a page is entered and an eligible acquisition begins, **it should keep processing until a usable result has been obtained or a genuine technical failure makes that impossible**. The owner asks to remove the same kind of report-cancellation control from other pages too, not merely hide the Comparisons instance.

**Desired UI:** No user-facing **Cancel**, **Stop loading** or equivalent action for finite-report acquisition on **Comparisons, AI Stats, Token Mix or Models**, during initial load, waiting, quiet refresh, retained-result states or failure. The standard progress indicator continues to explain ongoing work. Existing actionable **Retry** for genuine failures, and the separate **Refresh price list** on Models, are not cancellations and remain available where useful.

Do **not** interpret “no Cancel button” as permission to create an unkillable process, ignore actual auth/host shutdown, or claim all heavy jobs can finish no matter the source. This FR removes *user-initiated cancellation of normal report loading* while retaining necessary internal watchdogs, lifecycle termination and per-operation safety.

## Current code findings

- The page template `src/web/assets/index.html` declares one global `<button id="cancel" disabled>Cancel</button>` in the common `.toolbar` beside `#refresh`. The four finite routes are defined in `src/web/assets/reports.js`; they share this shell.
- `src/web/assets/app.js` keeps `const cancel = document.getElementById('cancel')`. `show()` sets its disabled/hidden status, including a visible loading-time Cancel on **Token Mix**, **AI Stats** and **Comparisons**, with common fallback for other routes. **Models** already hides its full common toolbar via CSS but still inherits the cancel implementation. Fix the **shared control**, not just the Comparisons-specific visibility flag.
- `app.js` also binds `cancel.addEventListener('click', ...)`, calling `state.attempt.cancel()` and `POST /api/jobs/<id>/cancel` if there is an active job. This is the direct user-click cancellation path to remove. A CSS-only `display:none` with a still-focusable/programmatically clickable global Cancel is an incomplete solution.
- The completed **FR000609** introduced `src/web/assets/report-loading.js::ReportLoading.Attempt` for bounded admission/retry and the shared 0–100% progress view. This `Attempt` also has *internal* cancellation/abort for e.g. suspended, interrupted or obsolete work. `app.js::navigate()` currently suspends an **unadmitted** previous attempt on route changes; `visibilitychange` similarly suspends unadmitted work when hidden. In contrast, an already-admitted `ReportJobs` job can keep processing across route changes. Distinguish an unwanted *user-exposed Cancel* from necessary protocol/ownership cleanup when changing this behavior.
- `src/web/http.py` and `src/web/jobs.py::ReportJobs.cancel()/close()` implement authenticated bounded-job cancellation required for host shutdown, watchdogs, old-worker cleanup and tests. **Do not remove or disable those lifecycle safety interfaces** merely because the button disappears.
- Existing rendered-browser/Node test fixtures sometimes click the global Cancel or assert its `hidden`/`disabled` state. In particular `development/tests/integration/probe_ai_stats.cjs` uses a click on `#cancel` to test a terminal failure path, while `web_views.cjs` models this button in the fake DOM. Update the affected UI tests to the new contract while retaining separate direct backend/process cancellation coverage.

## Required behavior

1. **No report Cancel control anywhere in the live Web UI.** Remove the shared `#cancel` markup and its direct event handler, plus stale CSS, DOM assumptions, focus/tab-order entries, ARIA references and programmatically invokable UI paths that exist solely to cancel a user's finite report. Do not replace it with a differently named Stop/Abort action elsewhere in the four report views. Verify on all four routes during initial loading, waiting-for-source/slot, in-flight refresh, retained successful display, failure and after completion. Don't touch Settings' native Escape/cancel-selection semantics, unrelated browser close controls, internal Watch/source cancellation, or other non-report UI actions.
2. **Started work continues after ordinary navigation.** Once an authenticated, eligible first visit has **requested/admitted a finite report**, moving to Watch, Settings or another report route, using browser Back/Forward, or temporarily hiding the tab must **not silently cancel that previously requested logical report**. Let the admitted job complete under its server-owned lifecycle; preserve its correct result/failure state in the existing bounded per-view memory and show the result (or a truthful terminal status) on return. Do not discard its state, overwrite it with another page's result, start a duplicate job, or reset its progress merely because it became inactive.
3. **Do not silently lose a user's intent during brief pre-admission waiting.** The completed FR000609 currently suspends unadmitted `ReportLoading.Attempt` on navigation/visibility changes. Reconcile this with the new owner choice: once a legitimate first-entry request is initiated, a temporary source/slot wait should not become a hidden “cancelled” report. Where technically safe, retain one bounded, server-/host-owned pending request or resumable admission intent so the request continues to admission or an honest terminal wait/error, without an unbounded hidden client retry loop. Retain retry/backoff ceilings, authentication/instance protection and scheduling fairness. Do not initiate *new* heavy history checks in inactive/hidden routes simply to satisfy this rule; existing visible-route refresh cadences remain unchanged.
4. **No promise to survive genuine faults or stopped hosts.** A user must never need Cancel to escape a stalled report. Preserve the report service's actual watchdogs, finite queue/result limits, child cleanup, authorization/CSRF, host shutdown/offline/identity protection and cancellation mechanisms for trusted internal owners. Persistent source errors, genuine report limits and abandoned host lifetime end with specific truthful errors, not perpetual Loading. Removing Cancel must not let a hung Comparisons worker monopolize the service beyond its existing technical bounds. If the heavy report times out rather than finishes, the user should see that actual failure; a separate correctness/performance fix is needed, not a fictional successful result.
5. **Coordinate with long-running AI Stats.** Pending **FR000614** introduces resumable, prioritized AI Stats work beyond one 120-second logical acquisition and has language about explicit user cancellation. This later FR **supersedes only its user-facing voluntary Cancel requirement**: AI Stats should continue its logical requested acquisition without a Cancel button, while preserving chunk watchdogs, host shutdown, resource safety, checkpoints, real errors and the user-requested **30 days → 7 days** priority switch. A safe internal pause/preemption to serve 7 days is not abandonment of the original 30-day request; resume its saved progress rather than cancelling its logical goal. Do not rewrite the historical approved FR now; implement the two in queue order and document this narrow override.
6. **Retain healthy UX.** Use the standard FR000609 progress with meaningful work stages and accurate selected scope, including long workloads and return navigation. Keep the current quiet active-visible refresh cadence for Token Mix, AI Stats and Comparisons; a background check may finish in flight, but leaving a route must not *start repeated new checks*. Keep successful retained data/scroll/focus, keyboard accessibility, theme/responsive toolbar geometry and other buttons' semantics. No accidental extra empty toolbar/spacing where Cancel was removed.
7. **Scope is the Web frontend and report-request lifetime semantics, not a general cancellation ban.** Keep CLI interruption, process teardown, server stop, internal timeouts, transport cancellation, test harness control and source-safety APIs. The user does not request background tasks that outlive the local server, an always-on scanner, new external services, priority starvation, or a change to all other reports' hard deadlines. If implementing “finish once entered” requires crossing the browser tab-close/host-stop boundary, treat that as unsupported; surface the actual remaining ownership limit rather than claiming impossible persistence.
