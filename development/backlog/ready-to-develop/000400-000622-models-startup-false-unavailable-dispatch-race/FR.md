# FR 000622 — Bugfix: Models must load automatically on Web startup, not fail before the dispatcher is ready

**Owner-approved Ready bugfix Feature Request, 2026-11-07.** Permanent identity **000622**, Ready queue priority **000400**, after currently Ready FR000621 (000390). Severity: **reproducible first-run/startup regression** after the recent Web background-loading dispatcher delivery. **Backlog publication only**: write this FR and increment the allocation watermark. Do not implement product code, run product tests, change version/release/docs, or edit other FRs while authoring.

## User-reported regression

After the recently merged feature to improve initial/background data loading (**FR000617**, v80.197), **every time** the owner restarts and opens Cost Guard Web Beta on its default **Models** route, the page **immediately** shows a red error close to:

> Source/report unavailable. Check the local source and retry Refresh.

It also offers **Retry Models**. Clicking **Retry Models** then makes the model data appear almost immediately. Restarting Web repeatedly reproduces the same initial failure. The owner expects Models to **begin loading automatically** on initial entry, show its regular determinate loading/progress/waiting UI if startup is not yet ready, and then display the report without any human intervention.

This is a **bugfix**, not a request to disable genuine source errors or remove the useful Retry control for a real terminal failure. It should be prioritized for correctness of fresh Web startup and verified against the actual prior dispatcher regression.

**Evidence boundary:** user reproduced the visible sequence multiple times on their own machine. The code investigation below establishes an executable-looking *race/error-classification path capable of producing the same symptom*, but we do **not** have the owner's private HTTP trace nor an independently reproduced failing startup yet. The implementation must prove the exact causal path with a controlled failing regression before applying a fix; if the owner's incident is different, investigate and correct that causal path instead. Do not label a hypothesis as a verified personal-source trace.

## Source analysis: strongly plausible new startup race

The new `src/web/dispatch.py::DataDispatcher` is initialized and fed by `src/web/host.py::WebHost._serve()`. It correctly gates expensive finite report work on a **first healthy Live observation**. However, several adjacent readiness protocols do not agree at the instant the browser first opens:

1. **Source selected is earlier than Live ready.** `src/web/source_startup.py::SourceStartup` sets `report_status()['ready']=True` once source selection succeeds / the Live driver is constructed. That **does not mean** `src/application/live.py::LiveRuntime.observed` has been set by the first real frame.
2. **Dispatcher in a legitimate waiting state.** `WebHost._serve()` computes source identity from the existing Live driver, but calls `dispatcher.tick(..., ready=driver is not None and driver.error is None and self.live.observed.is_set())`. Thus after driver/source identity is established but before `observed`, the dispatcher can have **a valid identity yet `ready=False`**. In `DataDispatcher.tick()`, `source_error = error or 'source_unavailable'` while not ready, even when there is **no underlying source error at all**. This is a transient *await-first-observation* case being represented with a generic unavailable code.
3. **The browser starts reports earlier than dispatcher readiness.** `src/web/assets/live.js::LiveConnection.report()` marks several statuses including `starting` as `writable` to permit regular authenticated operations. `src/web/assets/app.js::firstReport()` launches `acquire()` as soon as `hostState.writable` and the initial Models route exist; the auto-start path does not explicitly wait for **dispatcher logical readiness**. Initial `/api/interest` can register the route while the host is still waiting.
4. **HTTP explicitly describes a temporary state.** `src/web/dispatch_http.py::handle()` checks source startup status and nonempty dispatcher identity, then calls `dispatcher.lookup(request)`. In that no-job/no-result/nonterminal window, `lookup()` returns `id=None`, `error='source_unavailable'`, `terminal=False`; `dispatch_http` replies **HTTP 503** with **`{error:'source_unavailable', retryable:true}`**.
5. **The client can incorrectly make this terminal.** `src/web/assets/report-loading.js::retryable(error)` accepts `busy`, `source_starting`, or a **narrow whitelist of transport errors** with `error.retryable===true`. **`source_unavailable` is absent** from that list. Thus the 503 with explicit `retryable:true` becomes a thrown terminal error instead of “Waiting for source…”; `app.js::failure()` does not map that code and falls back to the owner's generic red **“Source/report unavailable...”**. `state.failed` remains true and `firstReport()` has already set `state.attempted`, so it does **not** automatically resume after a healthy Live publication. The explicit Retry button starts a new attempt when dispatcher readiness (and possibly the warmed result) has arrived.

This sequence explains the reported **immediate generic error followed by almost instant manual Retry success** without assuming a broken model catalog or pricing. Another possible pathway is a real background worker failure / early terminal cached error; diagnostics/tests must distinguish them. **Do not fix by only swapping the red text, hiding the Retry button forever, or silently clearing any terminal error.**

Additional risk in the new client/server bridge: `app.js::acquire()` assigns `state.dispatchError = admission.error || null`, later promoting it to a UI failure in `finally` even if a valid result is received on the same logical task. Verify that a **transient old dispatcher error** cannot outlive successful source readiness/result publication and create the same false startup failure. This is a secondary audit point, not asserted as the owner's root cause.

## Required behavior and implementation guidance

1. **Initial Models must be automatic and robust.** Opening a fresh Web host/browser on `/#/models` should begin the ordinary foreground Models demand. If source selection succeeds but the first healthy Live frame is pending, **stay in `Queued`/`Waiting for source`/normal centered 0–100% loader** (with truthful unchanged progress) and automatically continue when the dispatcher is ready. No red `Source/report unavailable`, no `Retry Models`, no need for a manual click during an ordinary healthy startup. A few seconds of genuine source startup delay are normal.
2. **Align readiness semantics at the correct ownership boundary.** Distinguish `source_starting` / `awaiting_first_live_observation` from genuinely `source_unavailable`. Do not set a generic terminal-ish source error simply because Live has not yet published its first observation. The host/demand endpoint should advertise a **typed temporary readiness state** with explicit recoverability, or the browser should safely handle the exact recoverable HTTP contract; prefer a consistent solution at **both** the host state and the UI admission boundary rather than ad hoc string matching. A valid source identity or `SourceStartup.report_status.ready` alone must never be mistaken for completed Live initialization.
3. **Preserve actual errors.** If OpenCode source registration/authentication is invalid, access is denied, schema/version unsupported, host identity changes or source truly becomes permanently unavailable, maintain prompt, specific, actionable failure. The user should still see **Retry Models** when an explicit retry can help, and never see invented report data. A genuine provider-pricing failure, managed-job failure, stale/corrupt evidence or bounded resource exhaustion must not be disguised as “Waiting for source” forever.
4. **Correct bounded recovery.** Automatic first-start waiting should not spend the entire normal finite-client budget in a tight retry loop, consume the `Retry Models` user-action flag, or poll rapidly. Reuse the existing source startup/dispatcher event and bounded backoff. A transient 503 with `retryable:true` must not be irreversibly labeled failed merely because the error string is not in a legacy transport whitelist; conversely **not every** `retryable:true` fault is safe for infinite retry. Keep a finite per-operation/admission retry/backoff policy, no timeout disabled globally, and avoid a background warm-up reintroducing the same error.
5. **Exactly one requested logical Models job.** During the startup wait, navigating, repeated status/Live events and multiple authenticated tabs must not duplicate source selection, launch a second OpenCode wake, saturate the four-job pending queue, corrupt cache/pricing or create repeated first-report attempts. Once ready, the foreground Models job wins before low-priority Token Mix/AI Stats/Comparisons warming per FR000617. If an already completing host job has a valid observation, reuse it without allocating another one. An explicit `Refresh price list` remains a separate user action and may not be triggered as startup recovery.
6. **Client state is monotonic across transition.** A transient dispatcher error code or result-less response must not stick in `state.dispatchError`, `state.failed`, `state.attempted`, `state.withheld` or `state.message` after successful automatic recovery. Ensure `Retry Models` is not visible after success, the red notice vanishes, and `report-loading` reaches 100% only after a coherent eligible Models result. If the browser reenters during a healthy in-progress job, preserve shared progress without flashing failure.
7. **Do not regress other entry routes.** Direct startup on Watch/Accounts/Sessions, Token Mix, AI Stats, Comparisons and deep links should retain their current eligibility/priority rules. A slow first Live observation, temporary source reconnect or hidden/minimized tab must not fabricate a failure nor start unintended expensive work before Watch. Source-failed/terminal cases keep accurate host health and security protections.
8. **Maintain security and lifecycle bounds.** The host remains authenticated loopback-only; HTTP admission respects session/CSRF/Origin/source identity. Never alter OpenCode source or user history, start paid model calls, stop a shared third-party OpenCode server, leak private diagnostic text or remove parent-loss worker teardown. Preserve FR000614's resumable AI Stats semantics and FR000615's no-user-Cancel behavior.
