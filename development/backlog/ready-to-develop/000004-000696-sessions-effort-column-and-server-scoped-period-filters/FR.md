# FR 000696 — Sessions: Effort column after Model; Today-first server-scoped period filtering, sorting and paging

**Owner-approved Ready to Develop — 2026-11-13.** Permanent FR identity **000696**. Queue priority **000004**, directly **after** FR000695 (000003), FR000694 (000002) and FR000693 (000001). **FR-only publication:** add the specification and advance the backlog watermark in the same documentation-only commit; no product code, source database, runtime configuration, tests, release/version changes, native model calls or implementation outside the normal selected worker/PR.

## Owner's problem and desired change

**Cost Guard Web → Sessions** currently displays a long, fully paginated catalog of all historical sessions. The owner estimates roughly **4,000–5,000 sessions** in the private installation. Sorting by an expensive numeric field, especially **CCost**, can require reading/indexing **all sessions**, so it feels very slow. Merely showing 50 rows at a time does **not** limit the full-catalog sort workload; reducing the page to 25 rows must not be mistaken for the requested server-side performance optimization.

The owner requests **TWO coordinated enhancements to the existing Sessions catalog, not Session Detail or AI Stats**:

1. Add **Effort** as a dedicated sortable table column **immediately AFTER Model**, before CCost. The voice-dictated “F4” refers to the existing **model reasoning Effort** concept. Preserve the existing Model column and remaining metrics, but reduce the Sessions table from **50 to 25 rows per page**. Desired order:

   ```text
   Last activity | Session name | Model | Effort | CCost | Prompts | Duration | CTX
   ```

2. Add a compact period selector **above the Sessions table**, exactly the familiar AI Stats choices **Today | 7 days | 30 days | This month | All time**, but with **Today as the default for Sessions** (AI Stats retains its independent **30 days** default). The selector controls **the population of the server-side Sessions catalog BEFORE every sort and page operation**. For example, when Today is selected and CCost sorting is clicked, **only today's qualifying sessions** are indexed/sorted, not all 5,000 historic roots. Seven-day sorting only considers the seven-day population. `All time` explicitly restores current complete-history behavior when selected, accepting its correspondingly higher work cost.

This must be a **real performance optimization**, not a client-side filter applied after an all-history scan, a hidden visible-page subset or an incorrect claim that all history was searched.

## 1. Confirmed source findings and why current sorting is expensive

These were verified by repository review; no live measurement of the owner's 4–5k sessions was performed:

- `src/web/assets/sessions.js::columns` currently lists **7 columns**: `activity | name | model | ccost | prompts | duration | ctx`. It has no Effort cell and no period selector. `destination(offset,epoch,sort,direction)` writes only sort/direction and optional paging/epoch to the `#/sessions?` hash. `View.load()` posts `token/offset/epoch/sort/direction` to `/api/sessions`, and `View.rows()` renders metric cells `model/ccost/prompts/duration/ctx`.
- `src/web/session_catalog.py::catalog_page` validates only `token,offset,sort,direction,epoch`; it currently rejects a new `period` field. `src/application/session_catalog.py::SORTS` lacks `effort`. Current `SessionCatalog._targets()` returns `set(self.roots)` whenever an interested visible lease requests a non-`activity`/`name` sort. `page()` likewise computes `indexed` and `pending` against **every root** for expensive sorts and orders `self._rows()` for the entire catalog. This is the demonstrated design-level reason that cost-sorting can scale with all historical sessions even when only the current 50-row page is visible.
- `SessionCatalog.observe()` already builds **`self.activity = root_activity(observation.sessions)`** from the native catalog, so the shared engine has a lightweight source-backed **per-root latest activity timestamp** that can select period-eligible IDs *before expensive per-root scalar history/CCost/CTX hydration*.
- `src/reports/models.py::SessionUsageRow` currently has `model, multiple_models, ccost, prompt_count,` etc., **no effort**. `src/reports/service.py::_session_rows()` chooses a representative model by highest observed cost (with fallback), and tracks whether multiple distinct models contributed. Effort is normally **request/prompt attributable**, not a single guaranteed session setting: `src/analysis/effort.py::interpret_effort/prompt_effort`, `src/reports/prompt_rows.py` and `src/analysis/comparisons.py::effort_model_parts` already own source-faithful per-request effort semantics. A new scalar Sessions effort needs a defined **mixed/unknown** aggregation, not a guessed session-wide value.
- `src/reports/session_summary.py::session_summary` uses strict dataclass-field parity, the disposable **`session-summary-4`** cache algorithm, source-qualified revisions and `MODEL_IDENTITY_SEMANTICS`. Adding Effort requires a **versioned/cache-safe migration**: old scalar rows may not have effort and must rebuild lazily, without silently painting `Default` or throwing away the previous CCost model evidence.
- AI Stats already has the desired period labels and IDs: `src/web/assets/ai-stats.js` uses `today,7-days,30-days,month,all`; `src/analysis/ai_stats.py::windows(zone,now)` defines **Today from local midnight, 7/30 days as trailing 7×/30×24 h, This month from first local-calendar-day midnight, All time unbounded**. Reuse semantics and shared timezone helpers; **do not reimplement AI Stats backend or couple its selected period to Sessions**.
- The Sessions catalog currently has **50 rows/page** (change to **25** in this FR), lease tokens, immutable older-page snapshots/epochs, live activity updates, source-revision/identity validation, sort progress, Retry/Cancel and last-good retention. A period must now be a **first-class part of that same request + lease + epoch scope**, otherwise pages and sort keys could belong to different populations.

The user reports a real slow experience, but no exact stopwatch/CPU/sample times are assumed here. Measure cold/warm behavior and root analysis counts, not fictional timings.

## 2. Period quick filter — identical choices to AI Stats, Sessions defaults to Today

**Required toolbar above the Sessions table:**

```text
Sessions                                      [Today] [7 days] [30 days] [This month] [All time]
Last activity | Session name | Model | Effort | CCost | Prompts | Duration | CTX
... up to 25 rows in the CHOSEN period ...
Previous                   Showing 1–25 of N sessions                   Next
```

**Sessions page size — additional owner requirement (2026-11-13):** Show a fixed maximum of **25 session rows per page, replacing the current 50**, in **every** period (Today, 7 days, 30 days, This month, All time) and for every sort. Keep the existing Previous/Next pagination when the filtered result contains **more than 25** sessions, with accurate page count, offsets and `Showing X–Y of N sessions` for the selected server-side population. Exactly 25 results fit on one page; 26 results require a second page. The last page shows only its remaining rows. No separate page-size selector is requested. This change applies **only to the Sessions catalog**, not Session Detail, AI Stats, Watch or other tables, and does not replace the period-scoped server-side indexing requirement.

- **Default = Today for a fresh Sessions page**, including `/#/sessions` with no period argument, browser launch and fresh navigation. Do not inherit AI Stats' `30-days` or use `all` merely because a previous older Sessions URL omitted scope. Each route should reflect its own selection independently.
- **Valid values/labels:** `today` / Today, `7-days` / 7 days, `30-days` / 30 days, `month` / This month, `all` / All time. Reuse AI Stats' visual/accessible segmented-button look (or a consistent compact existing Web period control), including visible selected state and keyboard/focus usability; preserve global button/anchor focus-glow fix from FR000695.
- **Membership is by source-backed LAST ACTIVITY of the entire root session tree**, including relevant child/subagent activity, consistent with the **Last activity** column and `root_activity`; not just creation time, the last prompt in a detail response, the browser's clock, or when the cache last refreshed. A session created last week but still active today belongs to Today. A session with genuinely missing/invalid activity must **not** be silently dated today; for finite periods exclude/mark it uncertain rather than synthesize timestamp (All time may still list it with N/A activity).
- **Period bounds** use the configured source/report timezone and a server-authoritative `now`: Today from current local midnight, rolling 7/30 days exactly as the AI Stats windows (not `calendar week` or seven local midnight boundaries), This month from current local month start, All time unbounded. Match DST midnight, month/year rollover and local timezone selection. Half-open timestamp boundary comparisons; current logical snapshot must not be contaminated by future/invalid timestamps. Do not ask the browser to guess local timezone.
- Switching period chooses a new **server query scope**, resets offset to **0**, keeps the desired sort key/direction where meaningful, cancels/obsoletes only its own pending page/sort intent (not globally shared source acquisition), and shows **an accurate filtered total** in the footer. It should not leave stale old-period rows under a new-period button highlight or falsely show Page 9 from another period.
- Filters apply identically to **all sorts**, all pages, search if present, and after navigation/Back/Forward. `CCost` on Today must compare all and only Today candidates (not just the 25 visible rows), with unknown/partial values handled per the current full-catalog contract. `All time` must still return all eligible roots and identical ordering/values to the previous implementation.
- **URL/deep-link ownership:** represent the period explicitly as e.g. `/#/sessions?period=today&sort=ccost&direction=-1` plus `offset/epoch` where applicable. Validate `period` on the server allowlist, default to `today` only for omitted scope from the new UI; do not silently change `today` to `all` on malformed input. An old URL `#/sessions?sort=...` receives the new default Today and the requested sort. Preserve period on header sort clicks, pagination destinations, Retry/Cancel, lease renewals, refresh and route revisits. Prevent cross-period reuse of a stale token/epoch/order.
- **Time passage:** Today and This month need a new epoch/membership at local midnight/month change, and rolling periods need date-driven eligibility refresh when cutoffs advance, without constant expensive full reanalysis. A stable older page retains a well-defined server-issued filter window and epoch; a new first page reflects the new period cutoff. On rollover, preserve honest source identity/order and reconcile cursors without mixed-period or duplicate/missing rows.
- Show **No sessions in Today** (or the selected period) with a useful selector still visible; do not pretend an empty Today subset proves no historical sessions. A simple link/button for All time is acceptable via the five primary buttons, but no extra auto-expansion.
- Filtering/paging is independent of AI Stats, Watch, Accounts, Models, Mini, and native session detail. Clicking a session name still opens its original full session history; returning to Sessions restores the selected period/sort/page where valid without searching every historic root.

## 3. Performance contract — the period MUST restrict expensive backend work

**Nonnegotiable:** apply scope to eligible **root IDs using cheap catalog timestamps BEFORE** hydrating per-root usage/model/effort/CCost/context data. Never compute every root's CCost and then filter the results in JS or from an all-history server sort.

- Extend `SessionCatalog.page`, server transport validation, leases, `_targets()`, `_candidate()`, `_progress()`, `_key_current()`, `ordered`, `_rows()` as needed so an interested lease sorting cost in Today triggers missing index/summary work **only for that lease's Today root subset** (plus other legitimate independent leases/host warm work, explicitly attributed). Period-filtered sorting must require indexed keys for all **eligible roots in the chosen period**, not globally. `progress.total/completed/revalidating` is the **filtered denominator**, and the pending state resolves when that subset is sufficiently qualified.
- Use the already observed inexpensive root-activity catalog to construct a candidate set (index/bucket/cache appropriately if beneficial, but don't invent another persistent all-history ledger). `All time` retains the current bounded full-catalog behavior; do not artificially read full old history merely to produce period membership. A 5k-root catalog with 30 Today roots should be able to sort Today CCost without invoking per-root history analysis for the other ~4,970 roots.
- Keep the existing **single bounded shared catalog worker, source API/transport budgets, cache signatures, request/response limits and per-root revision invalidation**. Do not introduce N workers per period, per-tab duplicate history crawlers, a second SQLite store, unbounded polling or a separately acquired source. Reuse existing qualified scalar keys across periods and across Today→7 days→All time when source/pricing/effort signatures still match. Narrow changes should not purge valid all-history caches.
- Preserve foreground priority: currently visible 25 eligible root summaries first; then remaining **period-eligible** scalar keys for the requested costly sort. If multiple visible leases have different periods, schedule a fair bounded **union of each lease's eligible work**, not global-index all roots because one Today lease sorts CCost. If an `All time` lease is truly active it may independently require all roots, but isolate/attribute its own scope.
- Keep deferred and retained source semantics: a row whose required metric key is stale or missing shows Loading/retained appropriately; never sort incomplete values as known, change the sort header to a requested-but-not-applied sort, report that `0/N` is complete because only the first page was read, or silently fall back from a scoped requested sort to all-time.
- Avoid repeated full-root `SessionUsageRow` materialization on each five-second poll for a narrow Today page when no relevant activity/revision/scope changed; maintain stable keys/rows/DOM and bounded CPU. Reconcile when a session receives activity crossing into/out of a period and when a child session updates. Existing pagination/epoch guarantees remain with the new 25-row page size.

## 4. New Effort column directly after Model

**Required table order:** `Last activity | Session name | Model | Effort | CCost | Prompts | Duration | CTX`. Effort is **sortable on the server** and has the same Loading/retained/unavailable behavior and keyboard/hover accessibility as the other metric columns.

**Semantics are deliberately source-faithful:** A session may contain multiple models, different effort settings across prompts, compactions and subagents. There is not necessarily one true session-level effort. Derive from the same **source-qualified, attributable per-request/prompt effort records** as Full Watch/Session Detail; preserve `default` as the recorded selection. Do not infer effort from model family, title or pricing, and do not replace the visibly selected `Default` with a documentation-based guessed concrete value.

- **One genuinely observed selected effort** across all attributable model requests in the session → show its familiar display name (`Default`, `Low`, `Medium`, `High`, `XHigh`, etc.).
- **Two or more distinct observed selections** across actual session contributors (for example `default` and explicit `high`, even if documentation thinks default equals high) → show **`Multiple efforts`** with a concise source-qualified tooltip breakdown. This applies regardless of whether Model says one model or `Multiple models`. Do not display a misleading most-expensive/last-prompt effort as if it covered the entire session.
- **Insufficient or conflicting attribution** → `N/A` / honest pending or retained state, not an invented `Default` and not zero. A zero-usage/failed-saved selection must not be asserted as executed usage; it may be distinguished as a recorded selection in help only when source-supported.
- Preserve exact **provider/model + selected-effort** identity for multiple contributors and safe grouping (bounded length/count); do not cross-join unrelated model routes, earlier prompts, subagents or response metadata. Follow existing `interpret_effort` semantics for request-bound default vs explicit. For a genuinely known selected `Default`, the Effort column's **value tooltip** must honor FR000694's specific `default (effective)*` plus its short, evidence-qualified disclaimer; **visible cell stays `Default`**, other Model/CCost tooltips remain without the asterisk.
- If a session has `Multiple efforts`, its tooltip lists each observed **selected** effort and attributed provider/model (and qualified frequency/count when safe). It may show separately resolved defaults through the existing FR000694 formatter but must not assert one common effective level for mixed contributors.
- New `effort` sort: define consistent source-backed grouping/order and stable tie-breaking, e.g. normalized explicit level / selected Default / Multiple efforts / unknown last; ascending and descending both work, deterministic raw selected identifiers, unknowns last. **Do not sort effort using guessed effective default**, nor compare it to token cost or reasoning intensity. Sorting may require efficient scalar indexing just like Model/CCost, **but only within the selected period**.

**Cache and integration:** extend `SessionUsageRow`, `src/reports/service.py::_session_rows`, `src/application/projection.py::project`, strict `session_summary.py` field/cache algorithm, `SessionCatalog.sort_value/SORTS` and metric_states, and the Sessions JS column array/row renderer. Upgrade/add only the versioned derived scalar cache fields; don't mutate native session history, priced token math, CCost cache or bill. Honor prior FR000687/000692 model identity boundaries and FR000694 tooltip effort semantics. Keep existing responsive table horizontal panning/column widths and accessible sorting after adding the eighth column; no unnecessary wrap, clipped values or lost current scroll.

## 5. Integration and test acceptance (must demonstrate actual speedup)

1. **Period selector visual/functionality:** five selectors in exact order `Today | 7 days | 30 days | This month | All time`, correct `aria-pressed` or equivalent selected state, keyboard/touch/mouse; fresh Sessions defaults Today, AI Stats still defaults 30 days. The selected period survives sort, pagination, page 2+ Back/Forward, Retry/Cancel and route return; changes reset page to 1 and update true total, not a client-side subset. Correct zero-session period.
2. **Server-first scope proof:** synthetic catalog with **5,000 roots** across two years and **only 20–60 Today**: instrument per-root `session_summary/_analyze`, catalog `_targets`, source reads and progress denominator. Cold Today CCost/Effort/CTX sort must **not hydrate thousands of non-Today roots**; filtered total and `index progress.total` equal eligible Today roots (not 5000), and order covers all Today roots not merely visible page. `7-days` can request more, `30-days` still more; `All time` deliberately restores baseline global work. Compare cold + warm + revised source, record measured CPU/elapsed/root reads with representative bounds rather than an invented percentage.
3. **Time semantics:** fixed clock and explicit `Europe/Stockholm` / UTC, Today/This month midnight DST shifts (23/25 hours), December–January and month boundary, rolling windows exactly `now - 7/30*24h`, sessions active today but created long ago, last child/subagent activity, missing activity and boundary timestamp ties, and rollover while paginating; no wrong membership or mixed periods.

No duplicate/missing rows, no false `pending_sort=false` and no stale old-period list shown under a new period label.
6. **End-to-end browser/host:** test authenticated `/api/sessions` new period allowlist, invalid input (no silent All time), original table DOM/AX, hover/focus/touch selector interaction, real page sort/navigation, 360px/1366px in Classic/Web light/dark, 100/150% zoom, keyboard and scroll retention. A real read-only owner installation with thousands of roots is desirable when available and authorized, but synthetic proof must still quantify root hydration counts. Never use paid AI inference or inspect another worker's scratch merely to test a session list.

Scope only Sessions catalog and its shared scalar DTO; avoid coupling AI Stats period selector or the Mini Watch's separate five-row representative list.

## Completion

When the user enters **Web → Sessions**, they immediately see **Today** selected above an eight-column table with **Model | Effort | CCost** in that order. Selecting 7 days/30 days/This month/All time **changes the real server-side eligible session population**; all sorting (including by CCost, Effort and CTX), 25-row pagination, page totals and progress operate **only inside the selected period**. On a 5,000-root fixture with 30 Today roots, sorting Today must analyze at most that period's eligible roots (plus separately justified independent work), not the entire lifetime catalog. Source-backed effort/mixed/unknown values remain truthful and prior security/refresh/UI contracts are preserved.
