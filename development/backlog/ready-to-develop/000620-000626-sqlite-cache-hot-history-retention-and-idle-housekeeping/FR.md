# FR 000626 — Keep recent and genuinely used history hot; prune stale SQLite cache during idle time

**Owner-approved Ready Feature Request, 2026-11-07.** Permanent ID **000626**, Ready priority **000620**; intentionally queued **after** the selected FR000624 (priority 000420) and the small FR000625 Web USD-default change (priority 000520). This is a future implementation, **not a request to stop, edit or reselect the currently running FR000624 worker**. Authoring-only publication changes this FR and the identity watermark; no product changes now.

## Why and desired behavior

Cost Guard has a reconstructible SQLite cache at `cache/cost-guard-cache-v2.sqlite3`, which the owner reports has grown to roughly **288 MB**. That size is not presently a problem: caching expensive derived information is desirable if it measurably speeds up cold and especially warm Web loads. The owner does not want an arbitrary small database cap or a cleanup pass that undermines FR000624's performance work.

However, a disposable cache should not accumulate **large unused historical per-session analyses forever**. The most valuable working set is sessions that have had actual prompt activity in the last **30 days**, together with older sessions whose cached information has been genuinely consulted in the last **30 days**. Older, unused, reconstructible entries may be removed; users who later inspect old sessions simply incur a cache miss and recompute/read from the authoritative supported OpenCode source.

## Retention rule — two clocks, either retains

For each **eligible, reconstructible, session-root-scoped** cache entry or associated root group, use two independently sourced UTC times, without confusing cache write time with use:

1. **Last actual session/prompt activity**, including relevant child-session activity for that root. An active/running root is protected. Get timing from real supported source/analysis evidence, not session creation or an unproven root `updated_at` interpreted as authoritative last prompt completion. Do not invent activity dates from missing telemetry.
2. **Last meaningful cache use / viewed-at**: the last occasion the cached information was needed by a user-requested Web/CLI report, a direct historical session inspection, or a genuine cache hit feeding that demand. A deliberate user view that had to rehydrate an old entry should count. Maintenance's own reads, audit/probe activity and automatic low-priority scans that opportunistically revisit the entire corpus **must not refresh every old root's viewed-at**; otherwise nothing will ever age out. Choose a narrowly defensible distinction between real demand and passive warming/housekeeping.

**Retain** when the root has confirmed activity within the last rolling 30 days **OR** meaningful use within the last rolling 30 days. **Eligible to prune only when both are older than 30 days**, with both ages established reliably and no active job, outstanding pending update, selected/visible root or other actual use requiring the entry. When either timestamp is missing/ambiguous, fail conservatively (keep or defer that entry until evidence is adequate), never delete source-authoritative records. A 30-day rule is for the *cache*, not a change to product history, report date ranges, source discovery or the completeness/accuracy of All time, Sessions, Token Mix, Watch Earlier, AI Stats or period reports.

The existing SQLite `cache_entries` schema includes namespace, opaque/digest keys, source revision, algorithm version and **`updated_at_utc` (last write)**, but no reliable read/use timestamp or general root association for all namespaces. Implement just the minimum explicit indexed lifecycle metadata that makes this policy sound. Don't assume an opaque cache key can be reversed to identify a root. Preserve valid revision/algorithm/pricing/config/source-identity gating and correct cross-session isolation. Avoid an SQLite write/lock **on every cache read**; coalesce or bucket low-frequency touch updates where possible. Minimize migration/startup overhead, especially on a large existing database.

## Housekeeping schedule and performance safety

- **Never launch a heavy prune at startup.** Earliest automatic attempt is after **at least 60 minutes of the current Cost Guard Web host's continuous uptime**, once initial foreground/Live/startup warming has had a chance to settle. Afterwards run infrequently (e.g. at most daily), only when the host observes genuinely spare capacity; defer during foreground requests, active expensive history acquisition, provider/Live pressure or source contention. An uptime threshold allows eligibility, **not a mandate to run exactly at minute 60**.
- Prefer an existing background/due scheduler and cache/DB owner over a new service, independent long-running daemon, dedicated timer-driven process, distributed ownership table or separate housekeeping framework. Never let maintenance delay user-visible first-use loading or compromise Live freshness/cadence.
- Delete only eligible cache rows in **small, bounded SQLite transactions**, with suitable indexes and safe busy/error/backoff behavior. Cooperate with concurrent readers/writers: no extended blocking locks, no repeated contention loops, no global read of thousands of source message trees solely to decide eviction. Cancel/pause safely on shutdown, source identity changes, foreground promotion and real request demand; no lost or partially published authoritative results.
- Pruning can reclaim reusable SQLite pages without immediately reducing the physical file size under SQLite's freelist/WAL behavior. If on-disk size reclamation is justified, do it with the smallest **safe, low-priority, bounded** native SQLite option and measure it; do not schedule blocking full `VACUUM` or aggressive WAL checkpoint during active Web/Live. No blanket DB-file deletion/rebuild.
- Optional cache outages/SQLite busy/corruption remain classified with existing fail-soft semantics. Maintenance errors must never make normal historical source work falsely `unavailable`, terminate the Web host or remove the user's data. The authoritative sessions are always read-only OpenCode data; maintenance must **never delete source sessions/messages**, account settings, source registrations, model-pricing authority or user files.

## Existing JSON state files — do not migrate them merely for tidiness

There are separate bounded operational state files such as `cache/state/model-metadata.json` (release-metadata health/retry schedule with legacy fallback) and `cache/state/watch-account-refresh.json` (latest sanitized quota-refresh diagnostics). They are **not the same thing as the large session-analysis cache**. Do not merge/migrate them into SQLite as an automatic prerequisite, particularly where operational recovery may need to survive SQLite unavailability. Examine duplication only if a **measurable concrete advantage** follows; this FR's default scope is SQLite historical-cache lifecycle, with lifecycle bookkeeping in SQLite rather than yet another JSON index/state file.

Preserve base `cache_metadata`, model-first-sighting records and other non-session operational namespaces that have different retention meaning. Classify session-scoped namespaces individually, including `derived-analysis`, Web Token Mix/AI Stats/coverage, session CCost and other actual reconstructible derived evidence; do not indiscriminately delete all old SQL rows. Future cache features should be able to opt into the same small lifecycle mechanism without new per-namespace cleanup services.

## Implementation scope and verification (proportionate)

- Inspect/cache-profile current table/namespace size and hit behavior using **safe aggregate metadata**, without reading/logging/publishing private prompt texts or full user sessions. Determine what actually accounts for large disk consumption, how many rows carry root metadata, and which entries have meaningful expensive warm reuse. The owner's ~288 MB observation is context, **not** a measured growth-rate or mandatory hard cap.
- Design a minimal schema update/indices and cleanup query preserving existing installations, opaque-key privacy and cache revision gates. Older unannotated entries must have conservative eligibility during migration; do not slow startup by eagerly hydrating all source history to backfill timestamps.
- One focused test path should show: recent session activity protects cache despite no recent view; an older session meaningfully viewed yesterday stays cached; one >30-day inactive/unviewed root is pruned; missing/unknown dates are not falsely pruned; passive background refresh cannot keep obsolete entries alive forever; an evicted old session is correctly rehydrated on user demand. Include any necessary active-child/changed-revision/source-restart isolation and no-source-deletion checks. Test idle startup/uptime gate, bounded SQLite contention, shutdown and cache-rebuild behavior using existing fixtures.
- Compare cache hit/miss and meaningful warm Web latency before/after on a representative recent-vs-old mix; ensure maintenance causes no significant Live/foreground delay and no pathological repeated SQLite writes. Report approximate rows/pages reclaimed and database/WAL observations without assuming file bytes shrink instantly. **No new generic validation gate, monthly data scan, service, compulsory benchmark suite or user-interrupting cleanup wizard.**
- Update only affected current technical/user documentation. Final implementation follows the normal Repo Backlog product delivery tests; the **FR authoring itself** runs no product tests, version bump or release.

## Acceptance

**A.** Recent activity **or** recent meaningful use preserves eligible cached history for at least 30 rolling days; old entries with neither become reclaimable, without changing their source data. **B.** Housekeeping does not start before 60 minutes of current host uptime, runs only opportunistically with bounded resource cost, and does not harm visible Web/Live. **C.** Real user navigation to pruned old history rebuilds it correctly without loss of source-backed meaning; background scans do not indefinitely postpone eviction. **D.** Normal SQLite warm-cache utility is retained or improved, rather than trading FR000624's performance for smaller files. **E.** JSON operational state is left intact unless there is independently justified benefit in changing it, and no overengineered new scheduler/registry or verification gate is introduced.
