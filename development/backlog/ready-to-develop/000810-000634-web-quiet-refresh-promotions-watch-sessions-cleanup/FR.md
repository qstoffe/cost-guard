# FR 000634 — Web-wide quiet-refresh UX cleanup, Models promotion tooltips, Watch and Sessions clutter removal

**Owner-approved Ready Feature Request, 2026-11-08.** Permanent identity **000634**, Ready queue priority **000810**, after FR000633 (000800) and before currently Ready FR000629 (000820). **FR-only publication** now: write this standalone specification and advance the backlog identity counter. No application implementation, testing, release/version change, restart, active-session interference, or unrelated backlog edits during publication.

## Owner's intent and non-negotiable UI rule

Cost Guard Web should display the data the user came to see, **not continuously tell the user that the data is a historical snapshot, being refreshed, not fully verified, or being rechecked**. The owner explicitly does not want implementation agents adding unsolicited technical caveats, banners, progress strips, counters or status messages while working on unrelated features. If the owner finds the information wrong, they will file a separate correctness bug.

**Universal presentation rule: once a view has useful content, ordinary background refresh must be visually and accessibly silent.** Keep showing the last usable content until the next usable coherent update arrives. Never insert short-lived "Loading…", "Updating…", "Checking…", "Historical snapshot as of…", retained-data, partial-refresh, catalog-verification, or other process-status prose in or under an already populated table/card group. Avoid reserved empty gutters and flashes. The same prohibition covers off-screen DOM, hover/focus tooltips, status live regions and aria descriptions where they merely repeat that passive refresh is underway.

**Initial load exception:** before that view has *ever* shown usable content for the selected source/scope, unobtrusive initial loading information or a loader is allowed. As soon as useful content arrives, that startup-only affordance disappears; refreshing/revalidating must not bring it back. An actually observed empty collection can display a stable friendly empty state. User-initiated operations can acknowledge their action inside the relevant control where necessary; do not append global diagnostic banners.

This is a **presentation/behavior decision**, not an order to stop fetching, skip freshness validation, misreport host connectivity, silently fabricate values, or disable actual security/authorization/error handling. Internal provenance, source revisions, reference valuation, cache validity, report schedules, recoverable errors, and diagnostics still work. An actionable terminal condition that prevents use (for example expired authorization, stopped host or an explicit failed save) may be communicated through the app's established single appropriate recovery surface, **not through repeated per-card/table refresh caveats**.

## A. Models — remove historical-snapshot disclaimer completely

1. **Remove the entire routine passive `Historical snapshot as of …` / `Updating…` / `Refresh scheduled` / `Update delayed` / `Checking refresh status` presentation** from Models, including the enclosing #report-updating strip and empty spacer. No replacement disclaimer, warning badge, time-since-refresh hint, tooltip, icon or hidden aria announcement. Its presence must not return after navigation, background refresh, manual price refresh, source resumption, tab visibility changes, Credits/USD switch or reloading cached data.
2. The same shared passive historical-report banner should not persist on **any** already populated Web report: cleanly remove/deactivate it for Models, Token Mix, AI Stats and Comparisons. Coordinate with FR000633's separate fun-first overhaul; do not change AI Stats' actual metric calculation in this FR. Retain quiet-refresh scheduling and backend freshness/provenance logic.
3. Do not remove the distinct, intentionally requested **Refresh price list** button, its actual price-cache fetch timestamp or useful price controls/model data. If a *user explicitly clicks* a control, a short control-local busy acknowledgment is acceptable; an unrelated automatic refresh must not create prose. Keep genuine source/authorization recovery accessible where operation cannot continue.

## B. Models — one unnumbered postfix promotion star and one good tooltip

1. When a visible model has an active price promotion, render its **Relative CCost** value in the existing promotion highlight color, followed by **one plain ` *` postfix** (with a single separating space). Example formatting, not a claim about a current model: `7.4x *`. **Never prefix the value with `*1`, `*2`, or `*`**, never number promotions, and never use multiple stars for a row. When the relative value has additional price tiers, put the one star **after the complete displayed relative-cost chain** so it clearly belongs to that row. A non-promoted model has no star.
2. Hover over the star/adjacent highlighted Relative CCost value to show an accessible **multi-line** Price Promotion tooltip. Use the existing ContextHelp interaction for pointer hover, keyboard focus and touch, with Escape/leave behavior; no native duplicate `title` pop-up. The tooltip must contain at least: **Price Promotion**, the applicable model, the actual available promotional discount/rate description (including percent off when known), the promotional end date and when normal prices resume if those data exist. Keep language clear and human; readable line breaks and sensible wrapping, without an overlong single paragraph.
3. The tooltip **must correspond to the actual displayed row and offer**. Promotions may be shared across models/tiers; filtering, sorting, switching all/latest, Copilot catalog refresh, supersession and simultaneous promotions cannot cross-link to the wrong note. Prefer per-model **structured, allowlisted** promotion data in the Web projection rather than parsing numbered footer strings in JavaScript. The underlying pricing semantics, source promotional dates, current discount calculations and price selection remain unchanged. Do not invent discounts, dates or an expired promotion.
4. **Remove the entire promotion-footnote block below the Models table** and its leftover spacing. No `*1 Price Promotion…` notes or duplicates anywhere below the table; don't put the old note into a hidden aria description. Retain the existing highlighted relative-cost style in Classic, Web light and Web dark. Don't change CLI's numbered notes unless independently needed; this request targets Web Models.

## C. Full Watch + Mini Watch — plain global CCost Today

1. Above the subscription/account cards, **CCost Today** must show its normal formatted daily CCost value and prompt count without a leading `?`, partial-price or incomplete-prompt suffix, `Partial CCost pricing`, `Prompt count incomplete`, `Partial pricing / token data`, warnings, replacement uncertainty symbols or explanatory extra line. Apply equally to Full Watch and Mini Watch, both CCost units, hot/cold publications and ordinary refresh. Do not make the user-facing result depend on complete pricing flags. Reuse FR000627's daily-only display semantics rather than undoing its existing working implementation.
2. **Remove every tooltip from this global CCost Today summary**, including label, CCost value and associated prompt count in Full Watch, and the corresponding daily amount tooltip in Mini. No focusable hidden question target, ContextHelp entry, native title, aria-describedby to old explanatory copy or new disclaimer elsewhere. Keep a semantic accessible label with the actual visible value and count, not an invisible breakdown lecture. The scope is the **global daily summary**, not every account's individual historical/daily cost tooltip or every Watch prompt.
3. Preserve raw daily CCost, prompt count, current period boundary, canonical source/completeness flags, underlying known-priced subtotal and original CCost display-unit conversion. Do not make an unpriced request look free or alter CLI/Token Mix/Watch individual prompt metrics. Genuine empty day, no priceable requests and no initial publication keep their own existing value semantics (including a true zero and no-number behavior where appropriate), but **no passive partial disclaimer** may be added to the displayed daily line.
4. When there already is a last usable global daily summary, refresh/retry must not insert `Updates delayed`, `Daily updates delayed`, source-state banners, a transient spinner or a help badge into that summary. Host-wide critical failure remains handled by the existing host connection surface.

## D. Earlier Sessions in Full Watch and Mini — never announce routine refresh below loaded rows

1. When Earlier Sessions is expanded and has ever received a usable displayed set for its current source/epoch, **do not render or announce** `Loading earlier sessions…`, checked-root counters, `Previously verified sessions; checking for changes`, temporary `Unable to verify latest sessions` or equivalent status/footer **below existing rows** on ordinary refresh. Remove the source of the extra status row in both Full Watch and Mini, not merely its CSS. No hidden live-region chatter or layout shifts.
2. Before a first usable Earlier Sessions population exists, `Loading earlier sessions…` is allowed; show it only in that genuinely empty initial state. After a verified empty result, a stable friendly `No earlier sessions` is also allowed, but a later routine refresh must not flip it back to loading. Preserve the first successful set (or clean observed-empty state) while revalidating in background; update the table in place when a coherent newer set is ready.
3. If the source/host identity **actually changes** and old rows are no longer valid, the initial-load rule can apply to the new source; do not misrepresent different-source cached history as live. Real terminal/access failure may use the existing single host-level actionable warning, but must not recreate per-table polling chatter.
4. Preserve canonical five Full/three Mini latest-eligible membership, ordering, finish times, session-link/CCost/context correctness, source revision/epoch safety, open disclosure state, scroll/focus, keyboard, PiP resizing and the shared history acquisition/verification pipeline. **Suppress only the unwanted transient presentation**, not the history work or the truth of returned session data.

## E. Sessions catalog — remove position banner and the bottom 0% loader

1. **No amber/golden `Page position changed` message/banner** or `return to latest sessions` notice below/above the populated Sessions table during routine automatic polling. On catalog lease/epoch expiry (`catalog_expired`) or an ordinary page-position change, **recover automatically and silently** using the safe Sessions catalog API: re-open/re-anchor the requested page when possible; if that cannot be proved, safely navigate to the latest page while preserving the chosen sort and direction, synchronizing URL, pager label, data, and epoch. Never leave a dead token, silently show rows from a different page under an incorrect pagination label, produce duplicates or hide/blank a previously populated table indefinitely.
2. **Remove the persistent bottom ReportLoading/0% element from the Sessions catalog altogether.** In particular `Waiting for a current session catalog observation` and a `0%` progress bar must never appear at the bottom after data have loaded, nor because an hourly observation age threshold passed. Sessions is a dynamic list; do not append a generic finite-report progress widget to it. A simple initial loading/empty-table placeholder is acceptable when no usable list has ever been received. Stop having `freshness()` hide the entire populated table/pager just because an old observation is being renewed.
3. Quiet routine `Waiting for shared session source`, `Global sort unavailable: indexed X of Y`, `last observed rows retained`, or catalog-check updates once the table has usable content. If a user requests a sort whose global index is genuinely not ready, keep existing rows, previous valid order/pager and the requested sort intent; change to the correct new order only once ready. Do not display an incorrectly sorted table as if it already meets the requested sort.
4. Ordinary five-second background polls must quietly update actual values and row order without unnecessary status/layout shifts, focus loss, selection breakage or resetting pagination on every refresh. Preserve real running indicators, source-driven value truth, stable 50-row pagination, session-detail navigation and source/epoch isolation. A true first-ever empty/loading state or an unrecoverable user-action error still needs a nondeceptive way forward, without the specified passive banners.

## F. Full Web audit — no post-load transient process chatter

Systematically inspect **Models, Watch, Mini Watch/PiP, Accounts, Sessions catalog and individual detail, Token Mix, AI Stats, Comparisons and Settings**, including shared header/status/notice/progress surfaces. Do not stop after fixing the explicitly reported strings.

For *each* view identify initial acquisition, first useful content, ordinary automatic refresh, delayed/failed refresh with retained content, visible/hidden tab, source reconnect, navigation away/back, manual user action and terminal host/authentication failure. Apply the same presentation rule:

- **First no-data load:** restrained loading indicator allowed where it helps.
- **Loaded / retained data and ordinary refresh:** no new/spontaneous progress bar, `Loading`, `Updating`, `Checking`, root counters, historical snapshot timestamp, passive stale/partial-refresh note, source-verification caveat, flashing status banner, duplicate warn/info line, or redundant post-table footer. Keep content visible and quietly replace only values/rows whose actual results changed. The rule applies to visible DOM, focus/hover/touch help about that refresh and live-region announcements.
- **Stable empty set:** show one useful empty message when applicable; don't flash "Loading" just because a new poll started.
- **Explicit action or genuine outage:** existing control-local feedback and a single actionable recovery mechanism are allowed when they genuinely affect operation; don't conflate normal partial/background work with an outage. Auth/security/source integrity still enforced, no fake "current" indication.
- **No unauthorized UI additions:** the implementation should not invent new warning strips, refresh badges, as-of labels, partial legends, retry counters or substitute tooltips under the guise of precision. If a new caveat would otherwise be necessary, record its technical cause internally or raise a follow-up FR rather than silently placing it on a populated UI.

Particular audit candidates: src/web/assets/cached-reports.js, app.js, report-loading.js, watch.js, mini.js, sessions.js, session.js, token-mix.js, comparisons.js, account-cards.js, live.js and index.html/app.css. Check whether shared freshness/status surfaces currently turn ordinary retained-data refresh into a warning; remove redundant output while retaining state internally. This task is **not** an authorization to strip unrelated intrinsic per-metric semantics, actual provider-quota restrictions, security notices or genuine requested Settings-save feedback.
