# FR 000643 — Bugfix: Mini Watch historical session rows return to neutral text after completion grace

**Owner-approved Ready bugfix Feature Request, 2026-11-09.** Permanent identity **000643**; temporary Ready priority **000800** (the Ready queue is currently empty). **FR-only publication now:** add this document and advance `development/backlog/identity-state.json` highWatermark **642 → 643**. No product code, tests, user docs, configuration, release or other backlog changes in the authoring transaction.

## User-observed regression

Since **FR000642** merged the Mini Watch Running and Earlier Sessions tables into the single always-visible **`Activity | Session | CCost (Total) | Ctx`** table, **historical/completed sessions appear in green text on initial Mini Watch startup** simply because the representative prompt finished successfully at some point in the past. The green success highlighting is intended as a **short-lived completion state**, not the permanent color of every successful historical session.

The desired coloring should match the established full **Web Watch** lifecycle:

- **Currently running:** the session row is **yellow** using the existing semantic `--watch-running`.
- **Just finished successfully, still inside the canonical recent-terminal/finished-prompt grace window:** **green** using `--watch-success`, temporarily emphasizing the completion.
- **Just aborted or failed, still within that same recent-terminal grace:** existing **red/error** styling applies; preserve the source-backed outcome.
- **Older completed/historical session, including those present on the first Mini opening:** **normal default/neutral foreground text**, not green and not persistently red solely because of an old terminal outcome. “White” means the ordinary foreground in the current theme (Classic dark may look white; Web light must use its normal dark text), not a hardcoded CSS `white`.
- **When a new prompt starts in a previously completed session**, the **same keyed row becomes yellow immediately** while genuinely running, then transitions to the appropriate transient finish state and subsequently neutral history. Do not leave a stale green historical copy.

A session's **status label and accessible outcome information may still truthfully report Completed/Aborted/Error** after the highlight expires; only the visual emphasis is temporary. The previous prompt's completion is a historical fact, but not evidence the current row should remain visually “just completed.”

## Verified source findings and likely cause

1. **`src/web/assets/mini.js::sessions(view)`** produces one row per canonical session and already distinguishes active-card candidates (`historical: false`) from `history_cards` candidates (`historical: true`). The current top-five history fill, stable selection and chronological order are part of FR000642 and should remain intact.
2. **`src/web/assets/mini.js::View.drawSessions()`** destructures `{card, item, running, historical}`, but its current CSS class assignment ignores **`historical`**:

   ```js
   row.className = prompt?.execution_unverified ? '' : prompt?.in_progress ? 'mini-running' : prompt?.aborted || prompt?.has_error ? 'mini-error' : prompt?.completed_successfully ? 'mini-success' : '';
   ```

   A verified historical representative normally has `completed_successfully=true`, so this expression assigns **`mini-success` even after terminal grace has expired and on cold opening**. This explains the reported symptom at source level; verify actual rendered behavior during implementation rather than asserting that a browser screenshot has already been captured.
3. **`src/web/assets/mini.css`** maps `.mini-running`, `.mini-success` and `.mini-error` to the shared semantic color variables. The CSS colors themselves are useful; the **eligibility/lifecycle for assigning those classes** is the suspected regression.
4. **`src/web/assets/watch.js::Card.update(value, historical)`** already gates focal row/title emphasis behind **`!historical`** and otherwise leaves historical prompt rows neutral. Follow the same underlying lifecycle distinction in Mini rather than inventing a second timeout.
5. **`src/watch/cards.py::WatchCards._focals()`** owns in-progress/execution-unverified focal prompts and the **bounded recent terminal-grace membership**; `src/watch/history_publication.py` owns verified Earlier membership. Keep that server-owned transition, not an arbitrary client-side “time since UI saw green” counter. `MiniWatch.Observations` may retain data across transient Live retry; retention is not a new completion event.
6. Current tests in **`development/tests/fixtures/mini_sessions.cjs`** and **`development/tests/integration/mini_watch.cjs`** assert that a recently ended active card gets `mini-success`, but do not explicitly prevent a successful `history_cards` entry from receiving `mini-success`. Extend those fixtures with the missing historical-versus-grace distinction.

## Requirements

1. **Define row appearance by canonical lifecycle category as well as prompt outcome.** A genuinely running active session has `mini-running`; a source-certified just-finished active/grace card can be `mini-success` or `mini-error` according to its terminal outcome; a verified historical-only row is **unconditionally neutral** with no `mini-success` or `mini-error` class. A historical row must not inherit a stale class from earlier states. Do not classify by non-null `completed_at_ms` or `completed_successfully` alone.
2. **Cold/open history:** on a fresh Mini window with zero running sessions and up to five already completed historical sessions, all genuinely historical rows use the current theme's default foreground text (no green), regardless of whether their historical representative completed successfully hours or days earlier. This holds when history is already verified before opening, when verification arrives afterward, and when the Mini window stays open through ordinary SSE/refreshes.
3. **Live completion:** when a running representative transitions to a genuine **successful terminal-grace** state, turn that same session row green for the existing source-owned grace interval. Failures/cancellations retain existing red styling during eligible grace; unknown or execution-unverified work must not falsely appear successful. When the grace expires and the row becomes eligible historical content, remove the terminal-highlight class and display it neutrally, even if the last prompt still says `completed_successfully`.
4. **Resume in same session:** when a historical session starts a new prompt, reuse the one existing row keyed by canonical `session_id`, update its Activity to the new start, set the running/yellow appearance immediately and remove historical neutral/old status styling. If that prompt finishes successfully, green during grace; after grace, neutral when historical again. The same session never appears twice, and ordinary history reordering follows Activity.
5. **No stale highlight due to retention:** on source retry, an old retained snapshot, history proof refresh, unit/theme change, PiP reopen or the handoff from `active_cards` to `history_cards`, do not reset/restart a finished highlight or leave a previously green DOM row permanently green. Distinguish a genuinely still-in-grace source card from historical membership; honor source/identity invalidation and source-backed actual resumption.
6. **Keep the presentation narrow:** apply the foreground color consistently across the whole Mini session row (Activity, Session, CCost (Total), Ctx) as before, preserve focus/hover accessibility, theme-semantic colors and readable contrast. No new background color, animation, badge, timeout, state setting, warning/status text, tooltip or transition artifact. Neutral uses inherited foreground, not literal `#fff`, `white` or a color that vanishes on the Web light theme.
7. **Do not change the unified table's other contracts:** exactly four columns, one row per canonical session, up to five slots filled with historical rows, unlimited active sessions with internal scrolling, ascending Activity sorting, correct prompt/session costs, Ctx, prompt duration in CCost help, Fit Height, initial width/height, account cards, provider quota data, and full Watch's separate tables. Do not change actual terminal eligibility, grace duration, data-source reads, pricing or historical ranking merely to fix styling.

## Acceptance scenarios

1. **Historical-only cold start:** synthetic authoritative `history_cards` of five successfully completed sessions (with `completed_successfully=true` and supported finish timestamps), no active cards. All five Mini rows are neutral; `getComputedStyle(row).color` matches the theme's ordinary inherited foreground, not `--watch-success`. Include old failed/aborted history as neutral while keeping outcome descriptions accurate.
2. **Running → success → history:** one source session runs (**yellow**); completes with a genuine active-card terminal-grace representation (**green**); after the producer's established terminal-grace handoff it is selected from verified history (**neutral**). Same row node and single session ID throughout, with no stale `mini-success`. Repeated identical Live updates do not recolor it green.
3. **Running → failed/aborted → history:** red only while in eligible recent terminal state; historical row returns to neutral. Unknown/unverified never becomes green from an inferred finish.
4. **Historical → resumed running:** one existing historical session gets a new genuinely running focal prompt; row turns yellow and moves to its updated Activity position; no duplicate history row. Later success follows green-in-grace → neutral-in-history. Cover consecutive prompts in one session and concurrent prompts represented as one session.
5. **Repeated rendering & presentation:** source reconnect/retained publication, history proof completion, sorting/filler changes, Credits/USD, Classic/Web light/dark, narrow widths and a new PiP opening preserve the proper state. Validate actual DOM class and computed foreground, not merely the status string. A row containing old `completed_successfully=true` from history must never receive `mini-success`.
6. **Regression:** full Web Watch history remains neutral and active/grace highlights unchanged; five-row selection, running overflow, historical fill count, row keys, Tooltip/Activity/CCost details, quota and Daily display remain untouched.
