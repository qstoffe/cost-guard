# FR 000703 — App-wide stable refresh: retain last-known values instead of flashing Loading

**Owner-approved Ready to Develop — 2026-11-13.** Permanent identity **000703**, Ready queue priority **000011**, immediately after FR000702 (000010). **FR authoring only:** publish this request and advance the permanent ID high-water mark in one documentation-only commit. Do not implement product code, change runtime/source records, run tests, update product version/release metadata or modify unrelated backlog states while creating the FR.

## Owner-observed problem and intended experience

In **Cost Guard Web → Sessions**, the table contains running sessions whose metrics continue to be updated. A session's **Ctx / context** cell can display an actual context value, then unexpectedly revert to **`Loading…`**, then reveal another value, and repeat this cycle. This destroys useful information while the owner is reading it: the previous number disappears even though it was already known. The owner wants this corrected **throughout the entire application**, not only the Sessions context column.

**Binding user rule:** `Loading…` is appropriate **only when the particular item/field/scope has never had usable data**, or for a genuinely new result explicitly requested by a direct user action such as changing a sort or pagination page. After a real value has been shown, subsequent ordinary refreshes must happen **in the background**. Keep showing the last known usable value until the next usable replacement is ready, then **swap directly** to that replacement. Never use an intervening `Loading…`, spinner, skeleton, blank, `N/A` or `Unavailable` merely to represent another pending request. This applies whether updates happen every few seconds, after a long delay, on a retry, or after navigating away and back when an eligible retained result still exists.

This is the familiar **stale-while-revalidate / last-good-value** presentation pattern, applied consistently at the correct semantic granularity.

### Additional owner-observed regression — Mini Watch adds a sixth `Loading earlier sessions…` row (2026-11-13)

The **Mini Watch sessions table has a five-session-row limit**. The owner has already loaded historical sessions and sees **five real session rows**. Nevertheless, an extra **sixth table row** periodically appears with **`Loading earlier sessions…`**. It then disappears, restoring five rows, only to reappear on another background refresh. This is a second explicit acceptance blocker for FR000703, **not a separate FR and not a relaxation of its application-wide scope**.

**Required Mini Watch behavior:**

- **Five actual session rows already visible:** show **exactly those five rows, never a sixth `Loading earlier sessions…` row**, regardless of history source `loading`/`pending`/`refreshing`/`retrying` transitions, a new poll, or recent-finished overlays. Historical revalidation may keep running invisibly; it must not make the table temporarily grow or blink.
- **Fewer than five actual session rows:** `Loading earlier sessions…` is acceptable **only while trying to fill genuinely missing session slots during an as-yet-uncompleted initial history search for that population**. Once the applicable historical scan has been completed/observed, do not show that placeholder again on ordinary rechecks—even if fewer than five real sessions exist. A verified empty/exhausted history is a completed state, not an endless loading state.
- **Real changes still work:** a newly discovered eligible older session may replace a provisional incomplete view or change the five real rows according to existing membership/ranking rules, but without interposing an extra phantom status row after prior completion. Truly new source/population identities require correct invalidation and may again have legitimate *initial* Loading when they lack any observed data.
- Keep *session row limit* separate from internal *background history-demand status*: whether history collection is worth requesting cannot alone authorize a visible Loading row. Preserve the current session membership, ordering, source qualification, PiP sizing and accessibility contract. No arbitrary timer/fixed cooldown used to merely mask the repeated placeholder.

**Specific static code lead (not a replay of the owner's exact instance):** `src/web/assets/mini.js::drawSessions()` computes `needsHistory` from **`values.filter(value => value.running).length < 5`**, not from the **total existing real visible rows**. It then sets `notice` using history readiness and `recent_finished_cards`; `reconcile(this.body, [...wanted, ...(!wanted.length || notice ? [this.emptyPrompts] : [])])` appends the placeholder as a physical table row **after all existing session rows**. In shared `src/web/assets/watch.js::historyNotice()`, a `recent_finished_cards` snapshot with `history_state !== 'observed'` can emit `Loading earlier sessions…` even when retained history rows are already present. Together these branches permit the **five real rows + one loading row** pattern. Confirm the real runtime transition and correct the ownership/presentation predicate rather than only replacing the text or hiding overflow with CSS.


### Additional owner-observed regression — Full Watch Earlier Sessions intermittently inserts `Loading earlier sessions…` (2026-11-13)

The owner reports the **full Web Watch page**, not only Mini Watch: after Earlier Sessions/Previously shown prompt cards have already been populated, a transient **`Loading earlier sessions…`** status line appears *inside/between the Earlier section's content*, disappears, and reappears on later automatic updates. This exact visible/accessible status flicker and its resulting layout shift are **explicit acceptance blockers for this existing FR000703**. Do not create another FR or treat the Mini-only sixth-row fix as covering the full Watch DOM.

**Required full Watch behavior:**

- **After the Earlier Sessions section has obtained usable historical rows for the current logical source/population**, ordinary automatic polling, history verification/revalidation, newly finished prompt overlays, SSE publication, source retry and partial/provisional `history_state` updates **must not reinsert `Loading earlier sessions…`, `Refreshing…` or equivalent transient acquisition prose anywhere in or around its previously populated content**. Retain the last qualified rows with their positions and expanded state until a genuinely coherent replacement population is ready. Reconciliation must not temporarily append a status paragraph/row or produce a vertical jump, including accessible live-region flicker.
- **Initial acquisition only:** a meaningful `Loading earlier sessions…` placeholder is permitted when that *specific* section/population is genuinely cold and has **no usable prior observation**. When the initial search has completed and verified that there are **no** Earlier sessions, show a stable `No earlier sessions` (or the established verified-empty equivalent), not recurring loading on subsequent background checks. If there are already visible real sessions, a temporary attempt to discover newer/older candidates is not a fresh initial load.
- **General application-wide distinction:** automatic background updates must be **silent after the affected content has first become usable**, whether they run continuously, periodically or on reconnect. Do not show new page/section/table-level `Loading`, `Refreshing`, `Retrying` or similar *operational status* solely due to another automatic refresh, even if the underlying worker reports pending. A **direct, deliberate user action** requiring a new data population—e.g. pressing **Next** for pagination, changing a sort/filter/period, or explicitly requesting a first load—**may** show a suitably scoped loading/progress state if the requested result is not yet available; this is not permission to flash loading for idle refreshes or for an already usable same-scope result. For an entirely new source/identity/never-seen field, retain the FR's truthful first-load rules; for a genuine action-required error, retain actionable feedback rather than a misleading Loading label.
- **Concrete code lead to verify and repair:** `src/web/assets/watch.js::historyNotice(view, retained)` checks `recent_finished_cards.length && history_state !== 'observed'` **before** it checks `retained`. That branch can return `Loading earlier sessions…` *even when the caller already has retained historical cards*. In `WatchView.View.update()`, the historical `wanted` list can already contain rendered cards, yet the resulting `notice` is appended as `this.historyNotice` and `reconcile(parent, wanted)` inserts/removes it on repeated transitions. Examine this actual full-Watch predicate and the source observation lifecycle, not just the Mini `drawSessions()` branch. This is a **static source explanation for the symptom, not a verified capture of the owner's browser**.
- Keep independently meaningful **confirmed source errors**, authorization failures, invalidation and verified empty state truthful in their appropriate established UI surface. A real new source/population may require initial Loading if the previous rows no longer apply; never retain unrelated history merely to silence text. Do not mask the problem by hiding the paragraph with CSS, delaying it for an arbitrary number of seconds, or globally replacing all Loading strings with blank text.

**Required focused regression test:** render **Full Watch** with at least one previously observed Earlier session/card and a nonempty `recent_finished_cards` snapshot; cycle `history_state: observed → loading/refreshing/retrying → observed`, with intermediate history epochs, retries, delayed publication and verified new-session promotion. At every post-first-observation DOM/ARIA frame, assert that **no `Loading earlier sessions…` status node is mounted or announced**, earlier cards persist without jump/remount, and a genuinely changed verified history set replaces them coherently. Separately test cold/no-history (initial Loading allowed), observed-empty (stable empty message), explicit user-triggered navigation (scoped loading permitted), and real source invalidation/error. Extend the same no-passive-loading-status audit to other populated Full Watch surfaces and other Web/Mini surfaces per this FR's existing app-wide scope.

## Required application-wide behavior

1. **Unknown → first result.** For a truly unobserved metric or item, retain the existing meaningful initial `Loading…` or initial progress UI. Do not invent, estimate or borrow a number just to suppress Loading. Real unknown, genuine zero, verified empty, pending and confirmed unavailable are distinct states.
2. **Known → background refresh → replacement.** Once a valid value is displayed, the same logical entity + metric + source/scope retains that value across `loading`, `pending`, `refreshing`, `retrying`, queued work, incomplete responses, brief disconnects and ordinary source reacquisition. A mere null/omitted field or pending state in a newer partial snapshot is **not proof that a previous valid value vanished**. Do not revert to a placeholder on each polling/SSE tick. Replace the old visible value in place **only** with a genuinely qualified newer observation. An actual value of `0` is a valid result, not missing data.
3. **Field-level, row-level and card-level stability.** One field refreshing must not wipe other valid fields in its row/card. Maintain stable row identity, table order, selection, sorting semantics, links, tooltips, expanded details, focus, scrolling and accessibility where existing behavior promises them. A legitimate updated number should update without flashing the whole row/page. Do not rebuild entire visible populated sections just to show progress.
   **Specifically, loading-status rows count as visible layout and must not be appended below an already full bounded table.** A table that has met its real row capacity remains visually fixed during background history refresh, including Mini Watch's five-session limit.
4. **All dynamic surfaces, not a shortlist.** Audit **every shipped place** that presents `Loading` or an equivalent pending placeholder while dynamically acquiring/refreshing data. At minimum inspect: **Sessions table (especially running session Ctx), session detail/history**, **Full Watch / Running Prompts / Earlier Sessions**, **Mini Watch and PiP**, **Accounts**, **Models / pricing / benchmark**, **Token Mix**, **AI Stats**, **Comparisons**, other dynamic Web tables/cards/metrics, and any analogous live terminal/CLI Watch rendering. Include shared data/cache/source projections and browser subscribers, not only string replacements. Document the audit so newly overlooked surfaces are not silently excluded.
5. **Correct scope and invalidation.** Retention is per **actual semantic identity**, not a global last number: session/prompt/call ID, metric meaning, provider/model/source generation, reporting period/timezone, account, filters and request population as applicable. It is legitimate to show initial Loading for a genuinely new item or unvisited scope. Clear or replace an old value when authoritative evidence shows it is **invalid, no longer applicable, removed, expired, unauthorized, or belongs to another scope**, but do not use a routine retry or transient missing payload as that evidence. Do not show another period's stats, another session's context, an old tool invocation, yesterday's daily amount or a prior provider's quota under the new label. For changed page/sort/period navigation, preserve existing safe previous-view behavior without presenting old rows as the new requested population.
6. **No misleading stale data propagation.** Last-good retention is a display/qualified projection rule, **not** permission to treat obsolete facts as newly computed or feed them into a fresh sort, total, cost, quota, export, security decision or authorization check. Keep data provenance, freshness and internal ready/retained/pending/invalidated states truthful. Align tooltips/ARIA with what the cell actually displays; do not mark a pending value as freshly observed. Existing quiet-refresh behavior means ordinary background refreshes should not add noisy indicators.
7. **Errors and terminal states.** During recoverable refresh failures, retain valid same-scope content. Show genuine actionable failure/authorization/disconnection feedback via the existing appropriate status surface, rather than erasing values or disguising a permanently blocked operation as successfully updated. Real terminal invalidation, explicit unsupported/unavailable results and verified empty datasets still require their correct states. Recovery must automatically resume last-good → new-value updates.
8. **Race and lifecycle safety.** Out-of-order results, abandoned requests, changing live prompts, source-generation changes, navigation and repeated retries must not overwrite a newer valid value with an older pending snapshot; must not leak data across scopes; and must not cause a rapid known → Loading → known flicker. Do not use a fixed timeout to erase a valid value solely because a refresh takes longer than usual. Bound retention/caches sensibly without requiring unbounded per-row history.

## Acceptance examples and implementation verification

- **Primary reproduction — Sessions Ctx:** an active session starts with no context → cell may say `Loading…`; an observed context `42,000` arrives → `42,000`; several refreshes provide `pending`/no context/new partial data → **still `42,000`**; valid new context `47,000` arrives → **directly `47,000`**. Repeat over multiple updates/retries and after ordinary route return: `Loading…` never reappears for that still-applicable observed cell.
- **Mandatory Mini Watch regression — no phantom sixth row:** with **five real sessions already shown** and history previously fully loaded, simulate repeated `history_state: observed → pending/refreshing → observed` transitions, nonempty `recent_finished_cards`, background polling, history epoch/revision updates, temporary source failure and recovery. At **every frame**, Mini Watch (including PiP) shows **at most five real session rows, no appended `Loading earlier sessions…` row, no brief sixth-row height jump or accessible ghost status**. Validate actual DOM `tbody` child count and text through several cycles. Also exercise **zero to four rows** on a genuinely cold search: the loading row may appear only while it is actually searching for missing rows; after legitimate completion, repeated checks do **not** resurrect it, even if fewer than five eligible sessions exist. Verify real new session insertion/ranking and genuine source-identity changes separately.
- **Mixed updates:** multiple simultaneously running sessions/prompts have independent retained Ctx/model/cost/token/duration/etc. One can refresh, error or finish while the others remain stable. A newly appearing session with no data still displays initial Loading. A verified terminal correction/invalidated context is handled truthfully, without retaining a context for an unrelated prompt/provider/scope.
- **Cross-surface matrix:** for every audited loading-capable surface, exercise at least `cold empty → initial loading → first ready → pending refresh → next ready`, repeated pending polls, recoverable failure → recovery, cancellation/navigation, out-of-order responses, certified empty/zero and a real scope/source change. Assert **no usable same-scope value changes to a transient pending placeholder**. Validate Web light/dark/narrow layouts, visible DOM and accessibility output, and Mini/PiP/terminal as applicable.
- **Scope switches:** selecting a genuinely new reporting period, session or other population must not display the previous population's data under the new label. Returning to a period with a still-valid cached result may display that result immediately and refresh quietly. Preserve existing Sessions pagination/sort/cancel/lease integrity.
- **Nonregression:** no extra source requests, expensive per-frame recomputations, growing cache leaks, incorrect accounting or detached-source retention; existing loading progress for genuinely absent content, FR000634 quiet refresh, FR000689 AI Stats loading-only shells, source-invalidation protections and real error feedback continue to work.

**Done means:** a documented complete inventory of dynamically refreshed Loading/pending sites, their correct retention or invalidation behavior, implemented fixes wherever actual previously known values can regress to Loading, and tests demonstrating all three explicit owner-observed regressions (**Sessions context reverts to Loading; Mini Watch intermittently adds a sixth Loading earlier sessions row; Full Watch intermittently inserts a Loading earlier sessions status within Earlier Sessions after it has already shown real data**) plus the cross-application matrix. The shipped UI retains each qualified old value **until a replacement is available**, without flashing, while never displaying wrong-scope or demonstrably invalid data.
