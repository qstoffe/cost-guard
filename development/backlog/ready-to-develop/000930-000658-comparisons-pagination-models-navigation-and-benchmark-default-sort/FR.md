# FR 000658 — Web polish: reliable Comparisons pagination, shared pagers, Models scroll and Solved default

**Owner-approved Ready Feature Request, 2026-11-09.** Permanent identity **000658**; Ready priority **000930** (after FR000657, leaving owner-prioritized FR000651 at 000001). **Backlog-only publication:** add this FR and advance `development/backlog/identity-state.json` highWatermark **657 → 658** in one docs-only commit on `main`. No product code changes or implementation verification claimed at publication.

## Owner observations and goals

The owner has **321 Comparisons groups, 33 pages**. The initial page 1 loads, but clicking **Next** can advance the loading UI to about **80%**, then switch to **"Waiting for source…"** and remain there for **multiple minutes** with no meaningful progress or outcome. This must be investigated as a potential server/source/report pagination bug, not treated as a cosmetic progress-indicator issue. When slow but legitimate, show **truthful, changing progress**; when retrying/stuck/failing, explain why and **terminate or recover cleanly** rather than presenting an indefinite 80%-done illusion.

The owner also wants (a) the same compact, consistent Previous/Next button layout and behavior on **Sessions** and **Comparisons**, with the **centered "Showing X–Y of N ..."** summary style currently used on Sessions; (b) switching into **Models** must not automatically scroll down to **GitHub Reference Pricing** or any lower heading; and (c) the **Coding Benchmark – Cost per Task** table should default to **Solved descending** instead of Relative Task Cost descending, without changing user-initiated sorting or benchmark math.

**Source inspection (hypotheses, not a reproduced production failure):**

- `src/web/assets/comparisons.js::View` shows the current **"Page N of M · T groups"** line inside a simple flex `.pager`, and invokes the page switch callback with **offset ± 10** and existing `revision`.
- `src/web/assets/app.js::show()` changes Comparisons `state.request` to `{kind:'comparisons', comparison_offset, comparison_revision}` and calls `acquire(state)`. `acquire()` admits/polls the full finite report, may re-admit after retryable errors and changes `ReportLoading.waiting()` to **"Waiting for source…"**. The user-visible progress percentage can remain at its last observed **80%** even while no source progress is being made. **An admission retry loop with bounded backoff is not necessarily a bounded overall wait**, and the precise observed root cause is currently unproven.
- `src/reports/matched_inputs.py::build_comparisons()` **rechecks all-history revisions and the matching index on page change**, updates changed roots, computes groups, then hydrates only ten displayed previews. It rejects changed pinned `comparison_revision` with `SessionCatalogChangedError`. A large catalog, changed source, snapshot churn, unavailable preview or stale revision may affect page 2. `src/web/dispatch.py` and host-owned job admission may further affect waiting/recovery. **Do not assume source I/O, cache, networking or front-end retry is to blame until instrumented.**
- `src/web/assets/sessions.js` already has a pleasing three-zone `.sessions-pager` with centered range+page summary, and `src/web/assets/app.css` defines its responsive grid. `src/web/assets/benchmark.js` currently initializes `this.sort = {index: 3, direction: -1}` for Relative Task Cost, while **Solved** is the fifth column, **index 4**, with raw numeric sort data available.
- Navigation into Models uses the general route renderer (`src/web/assets/app.js::navigate/show`) which hides the global toolbar heading on Models and replaces/reuses content. Exact reason for unexpected downward scrolling (e.g., browser scroll anchoring, focus, hash restoration, asynchronously inserted content or hidden toolbar) is **unverified**. The FR requires a reproduction and real fix rather than guessing.

## A. Fix Comparisons Next/Previous correctness and progress

1. Build a **deterministic large-catalog regression**, approximately **321 groups / 33 pages**, with non-sensitive synthetic first inputs, several roots per matched group, warm caches and optionally changed/new/removed roots. Reproduce route **Comparisons → Next → page 2 → Previous → other pages**, including browser navigation/tab switches, multiple Next clicks, resource pressure, no data/partial data, and long-running source work. Also offer an **owner-authorized, read-only, bounded real-source probe** if needed (no paid model calls, no raw prompt exports). Do not claim an actual root cause until a failing trace exists.
2. Trace the full **browser `acquire`/data-demand → report-job admission → source readiness/retry → `build_comparisons` all-history revision/index → page-preview hydration → publication** lifecycle. Identify whether a repeat source wait is genuine upstream unavailability, a repeated transient error, a pending report slot, lost job identity, invalid pinned revision, cache-acquisition wait, loop in progress/state transitions or legitimate expensive work. Record **numeric and stage-only** timings, attempts, root/cache counts, revision changes and a sanitized exact failure code; no personal titles/prompt text, credentials or session dumps.
3. **Fix the actual identified hang/stall** and ensure a valid page 2 is reachable. If paging can safely reuse an already validated, pinned match index/catalog and hydrate just page-specific previews, explore that targeted optimization without changing revision correctness, root membership, order or invalidation. Avoid re-evaluating entire unchanged history for every page solely due to offset where safe, but do not trade correctness for speed or invent caches without source qualification.
4. When real work is ongoing, expose **truthful stage/count progress**; e.g. Checking history index (X of Y), Updating changed roots (X of Y), Preparing groups, Reading page previews (X of up to 10). Counts must come from actual work/progress callbacks and remain monotonic per attempt, not a fake elapsed-time bar. If source/admission retries, change the stage to an explicit **waiting/retrying reason** and show attempt/recovery feedback rather than retaining 80% as if computation continued.
5. A page request **must not wait invisibly forever** on repeated retryable faults or stale/non-advancing source. Adopt an explicit, finite, source-appropriate recovery policy for a **user-requested page navigation**, distinguish recoverable and terminal outcomes, show a readable error/retry option after the budget is exceeded, and preserve the last successfully displayed page and summary. Avoid an unbounded retry loop or spinning every 500ms without new progress. Respect the existing host-owned job lifetime/navigation semantics: no uncontrolled duplicate jobs, auto-cancel of unrelated successful work, or false success. An owner can navigate away; the page must remain interactive and recoverable.
6. Keep **revision-pinned pagination** correct. If group membership/revision changed between pages, perform the existing deliberate one-time restart/rebase to page 1 with a clear explanation and stable summary, **not** silent wrong page data, duplicate rows, out-of-range offset, infinite re-admission or a stale 33-page count. Preserve matched-input privacy, deduplication, original group ordering and all request/usage/CCost attribution.

## B. Standardize Sessions and Comparisons pagers

Use the existing **Sessions pager's responsive three-zone layout** as the design baseline, harmonized with shared Web controls/button styling (including the site's Models controls where common). **Previous** left, descriptive page-range **summary centered**, **Next** right. Reuse the same shared CSS class/rules/spacing/disabled/focus/hover/touch semantics rather than separate diverging pager implementations. On narrow screens, put centered summary above two equally reachable edge buttons like Sessions currently does; do not clip, wrap text misleadingly or cause horizontal viewport overflow.

- **Sessions** retains its existing summary idea: `Showing 1–50 of 1,234 sessions · Page 1 of 25` (illustrative); preserve actual page size, server sort, epoch/URL navigation and catalog-expired behavior. The user specifically likes the current **Showing X–Y of N sessions** format.
- **Comparisons** instead reads, e.g., **`Showing 1–10 of 321 groups · Page 1 of 33`**, then **`Showing 11–20 of 321 groups · Page 2 of 33`** when Next succeeds; on last page, **`Showing 321–321 of 321 groups · Page 33 of 33`**. The unit is **groups**, not individual session runs. Preserve total count and page size (10 groups) even where run counts differ.
- Both pagers have coherent first/last disabled states, prevent repeated click while their page request is pending, support click/keyboard/touch, correct focus restoration and `aria-live` summary updates. Keep stable layout while loading, and do not silently retain clickable Next when admission cannot proceed. Error recovery must not jump pages without visible confirmation. No additional pagination UI or new full-page sort for Comparisons is requested.

## C. Models tab navigation must not scroll downward

When switching **into `/#/models`** from any other route, including when the previous page was scrolled, the browser must **not automatically scroll down** to GitHub Reference Pricing, benchmark, or another inserted heading. It is acceptable—and preferred for consistency—to start **at the top** of the new route. A same-route user-driven scroll and ordinary focus interactions must remain intact.

Trace browser scroll and focus at **navigation start, after `show`, after async report publication, after toolbar visibility changes and after model/benchmark DOM insertion**. Fix the owner-observed unexpected downward jump by preventing scroll anchoring/focus side effects or applying a deliberate new-route top policy; **do not repeatedly force scroll to top on subsequent data refresh, table sort, filter toggle or tooltip open**. Test route transitions from bottom of Comparisons/Sessions/Token Mix/Accounts/Watch, both preloaded and freshly loading Models, slow async content arrival, Desktop width/zoom, and normal keyboard focus. Avoid breaking browser Back/Forward and internal Session-detail scroll restoration.

## D. Coding Benchmark default sorting: Solved descending

In the **five-column Coding Benchmark – Cost per Task** table delivered by FR000656, initialize to **`Solved` column, descending numeric solved percentage** so the strongest published task performance appears first. With current column order Publisher, Model, Effort, Relative Task Cost, Solved, the new default key is **column index 4 / `solved`, direction -1**. Use existing **raw numeric solved** sort, not formatted strings or lexical ordering. Keep `N/A` / unknown scores last, stable deterministic ties, correctly displayed descending indicator/aria-sort, and exact model/effort/client row identity.

**Only change the initial/default sort**, not benchmark measurement, computed Relative Task Cost or the user's ability to click any of the five headers to sort differently. Preserve a user's chosen sort while filtering, refreshing or navigating within a retained Models view. The intuitive workflow is to browse higher Solved first, then compare Relative Task Cost for better value. Do not change GitHub Reference Pricing's sort, the effort multiselect, checkbox defaults or provider matching.

**Explicit non-goal:** the existing monospace/tabular alignment of **Relative Price List Cost** in the GitHub table is intentional and should remain unchanged. Do **not** restyle that font or apply it to the benchmark as part of this FR.

1. With the **321-group / 33-page** fixture, page 1 shows 1–10; Next **reliably finishes page 2 (11–20)** with correct revision/ordering and Previous returns 1–10. Test multiple later pages, final page (321–321), empty groups and one-group cases; no repeat/skip or stale summary.
2. A deliberately slow but progressing source/job shows **true phase/count progress**. Forced source starvation, retryable source error, transient source revision churn, unavailable page preview, job-slot exhaustion and stale pinned revision **never leave a frozen 80% + Waiting for source** for minutes with no outcome; display clear bounded recovery/failure and a working Retry path. Preserve last-good page and nonblocking UI.
3. A before/after **instrumented source trace** demonstrates the root cause of the reported Next symptom and verifies the correct fix. Record real and synthetic outcomes separately; don't claim the symptom reproduced on the owner's data without actual evidence.
4. Sessions and Comparisons share the same responsive pager CSS/interaction conventions and **centered "Showing X–Y of N ..."** summaries, with correct units, page sizes, disabled/focus/keyboard/touch behavior. Test wide and narrow views and all supported Web themes.
5. Changing tabs **into Models** never scrolls downward unexpectedly, whether Models data is cached or finishes loading later; preserve user scroll during same-route refresh/filter/sort and correct navigation focus.
6. Benchmark initially sorts **Solved descending** numerically; manual Relative Task Cost/Model/Publisher/Effort sorting still works and persists across ordinary updates. No underlying benchmark score/ratio/filter/source changes, and no font change to GitHub Relative Price List Cost.
7. Exercise targeted Python report/index/dispatch retry and job tests, JS Comparisons/Sessions/Models DOM tests, and a real browser route/paging/progress/scroll probe. Source inputs and fixtures stay synthetic or owner-authorized, no real AI inference calls required. No unrelated backend or provider changes.
