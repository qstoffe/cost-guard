# FR 000670 — Web: show a source-aware V1 compatibility notice and verify V1 Watch behavior

**Owner-approved Ready Feature Request, 2026-11-10.** Permanent identity **000670**, Ready priority **001050**, after the current Ready queue. Initial publication incremented `development/backlog/identity-state.json` highWatermark **669 → 670**. **This is an in-place clarification of FR000670 only:** preserve its existing ID, priority and Ready status; do not modify the identity counter, other backlog entries, product code, tests or version/release files in this documentation revision.

## Request and important correction from repository inspection

An issue has been reported with **Cost Guard Web → Watch** in an environment running **OpenCode Desktop version 1** and using numerous plugins. In the same environment, **Cost Guard CLI Watch is reported to work without major problems**, while Web Watch has issues. The exact Web symptoms, the **actual data-source generation selected by Cost Guard** in each mode, and any causal connection to plugins are **not yet established**. Investigate this **CLI-versus-Web discrepancy** rather than attributing the failure to V1 by assumption. Also provide a **clear, compact, sticky notice on Web pages when the running Cost Guard instance actually selects V1**, describing only confirmed compatibility limitations.

**Distinguish product and source versions:** an installed **OpenCode Desktop version 1** is not by itself proof that Cost Guard selected its **V1 SQLite session source**. The supported `auto|v1|v2` mode and the actual `SourceSelection.selected` result are separate facts to establish. Do not use Desktop's displayed version or the presence of plugins as a proxy for the selected source.

**Static analysis of current main does NOT support claiming that the entire Web requires V2.** The banner must be correct and proportionate, not a blanket disclaimer that all V1 Web Watch/report behavior is unsupported:

- `src/sources/selection.py::SourceSelector.select()` supports `auto|v1|v2`. Auto prefers healthy V2, but selects healthy V1 when V2 is absent/unhealthy; explicit V1 works. It never merges V1/V2 histories.
- `src/web/source_startup.py::SourceStartup.prepare()` uses that same selector and deliberately **reuses healthy auto V1** without launching a V2 service. `src/web/composition.py::live_acquisition()` constructs the Web Watch coordinator from the selected source; its V2-specific card readers are optional. Web finite reports also select a source via the shared selector. `src/sources/opencode_v1.py` normalizes read-only SQLite history; V1's `live_changes=False` lacks V2 native change hints, but Web Watch was explicitly designed for **V1 polling vs V2 buffered/event hints** (completed FR000542). Common V1/V2 report and lifecycle parity tests exist.
- **At least one genuine Web-only restriction is confirmed:** `docs/web-beta.md` states **Sessions → Export Sanitized JSON** requires a selected, compatible **OpenCode V2** source and native export API; V1/unsupported sources must show `Export unavailable` with the ordinary native CLI alternative. V2 also has native event hints not provided by V1; V1 Watch uses polling, which may make observed refresh latency different. These do **not** establish that V1 Watch is inherently broken.
- `src/web/http.py` currently exposes `/api/status` with `report_source` readiness/error flags. `SourceStartup.report_status()` currently returns `ready/error/retryable`, **not the authoritative selected generation**. `src/application/live_projection.py` has `source_label` in the Live view, but a robust global banner should use an explicit allowlisted source-selection state from the active host rather than infer it from the configured preference, installed executable version, or a formatted label in a stale report.
- **The reported Web Watch issue has not been reproduced here.** Unlike Web Watch, **CLI Watch reportedly works in the same installation**. Verify which source each mode actually selects and isolate their differences in startup, acquisition, polling/cadence, cache/projection, runtime lifecycle and browser presentation. Plugin activity is relevant test coverage, **not an established cause**. Separate legitimate capability differences from defects; do not use the banner as a substitute for fixing a real regression.

## Desired Web behavior

When the **actually selected, healthy source is V1**, show one lightweight, persistent **source compatibility banner directly below the main navigation**, outside page-specific content, visible when switching among Models, Watch, Sessions, Accounts, Token Mix, AI Stats, Comparisons and Settings. It should remain easy to notice when scrolling (sticky), but must not obscure content, cover navigation controls or dominate the viewport.

Suggested concise English copy (adjust to verified supported/unsupported features and established UI tone):

> **OpenCode V1 source selected.** Cost Guard Web supports V1, but some features are limited: Watch updates use polling and native session export requires V2. For the full Web feature set, use a compatible OpenCode V2 source. **Learn more**

Avoid wording such as `Web does not support OpenCode V1`, `Watch is broken on V1`, or `All reports require V2` without fresh supporting proof. The notice is about the **selected legacy data-source generation**, not a guess from the installed OpenCode application's displayed semantic version. It must be clear that some functionality still works. The optional details/help link can open a focused existing local guide section describing supported behavior, known restrictions, troubleshooting and CLI choices; no new external service or privacy-leaking diagnostics URL.

No banner is necessary when a **compatible V2 source is actually selected**, even if a V1 database also exists. Do not confuse V1 migration-gap inspection or `auto` configuration with selecting V1.

## Requirements

### A. Source-aware, correct, secure banner gating

1. Derive source generation **only from the active, established `SourceSelection.selected` / host-owned Live acquisition**, expressed as a small allowlisted **`v1`, `v2`, `unknown`** field in the existing authenticated host/status or Live publication contract. The actual wire field/API is an implementation detail; do not introduce a new periodic browser scanner or query native source endpoints from JavaScript. Reuse the existing `/api/status`, `/api/live`, SSE/reconnect and instance controls when appropriate. Avoid leaking storage paths, registration URLs, API credentials, process arguments, database locations or private session metadata.
2. Handle **start-before-selection** carefully: unknown/loading source should not be mislabeled V1 or V2. With explicit V1, or auto fallback selecting V1, show the banner promptly **once selection is authoritative**. With V2 selected, hide it. A failed/unavailable source gets its existing truthful connection/error notice, not an invented V1-compatibility diagnosis.
3. Keep the evidence tied to the **same host instance and selected source**. On a new instance, changed/invalidated source or reconnect, do not retain a stale previous source label as fact. If a genuine transient offline state retains the last verified source, clearly distinguish **last known** from currently verified, or withhold the compatibility banner until reliable evidence returns. Do not change source selection, force a switch to V2, wake/start OpenCode, or couple UI gating to a report job's completion.
4. Implement one **shared top-level banner** (not one per route) under `<nav>` in `src/web/assets/index.html` / `app.js`; use `app.css` theme roles and layout for a restrained, high-contrast, accessible announcement with a short text and optional learn-more link. Preserve header/main geometry, keyboard/tab order, reduced motion, Classic/Web light/dark, mobile widths and 100–150% zoom. Its sticky position must not cover the menu, content focus targets or internal help/popovers. No intrusive modal, animated marquee or unnecessary repeated live-region announcement.
5. If details are expanded or a guide link is used, let the user understand the supported CLI/Web distinction and current known V1 limitations. Avoid promising a user-setting toggle, automatic migration or a dismiss preference that could permanently hide important compatibility context without explicit design scope. Remove the banner automatically when the selected source is authoritatively V2 under a fresh legitimate host/source state.

### B. Audit actual V1 Web support, particularly Watch

6. Build a compact **feature support matrix from real source contracts and tests**, not assumptions: CLI Watch and reports, Web Models/finite reports, Full Watch/Mini Watch, Sessions catalog/detail, Accounts/quotas as applicable, and explicitly **native sanitized JSON export (V2-only)**. Differentiate `supported`, `supported with polling/other limitations`, `unavailable`, `not verified`. Do not relabel every Web page 'V2 only'. Include a clearly separated **OpenCode Desktop product version vs. Cost Guard selected data-source generation** distinction. Update `docs/web-beta.md` (and README only if appropriate) with a concise selected-V1 notice explanation and current restrictions.
7. **Investigate the reported CLI-versus-Web Watch discrepancy** using a realistic read-only **V1 SQLite fixture** and, where possible, identical normalized sessions passed through **CLI Watch and the genuine Web host/Live Watch/HTTP/browser path**, rather than just mocking the banner boolean. Verify which source generation CLI and Web *actually select*, including the same `openCode.source` setting under `auto` and forced `v1`, source health/fallback, host startup, separate CLI/Web acquisition owners, polling versus event hints, refresh timing, history/caching and Web-only rendering. Compare the same session's discovered activity, active/recent/earlier membership, prompt lifecycle/terminal transitions, context/CCost/Duration, child/compaction, accounts where applicable, and Mini Watch. Test both idle and actively updating V1 history while Web is open. Compare matched canonical V1/V2 evidence where valid and distinguish missing source telemetry, plugin effects and a broken Web projection. **Do not request private installation databases or credentials by default.**

   Include **plugin-rich cases** alongside a minimal baseline: repeated tool calls, custom tool names and metadata, tool/skill parts, subagent/child sessions, partial/in-flight tool state, errors/cancellations, and any legitimately supported plugin-generated records. Verify normalization, Watch aggregation, deduplication, long-running indicators and updates are not incorrectly filtered or duplicated on Web while CLI remains correct. Use safely synthesized fixtures and supported source evidence; avoid unsupported claims about a particular plugin or plugin count.
8. If the audit finds a **small, demonstrable Web Watch regression** (whether V1-specific, source-selection-dependent or triggered by supported plugin-shaped data) within this path, fix it at the correct source/normalization/Live/presentation owner and add a focused CLI-versus-Web parity regression. Do not silently switch to V2 or change the common CLI behavior to make the browser pass. If it is broader or unrelated, document the precise evidence and follow normal separate FR escalation instead of broadening this feature or claiming parity. Keep actual error/unknown state visible; never hide a real failure behind the banner.

### C. Acceptance and tests

9. With the selected source explicitly `v1` and with `auto` genuinely falling back to healthy V1, the banner appears after authoritative selection, stays visible and consistent across **all Web routes**, including during Watch Live updates, filtering/sorting, background refresh, Mini window open, and navigation back/forward. It should not be duplicated inside every report or open in the Mini PiP unless separately justified.
10. With selected `v2` **and V1 also present**, the banner does **not** appear. With source selection pending, failed V1/V2, unavailable registration, stale old-instance SSE or switched instance, the UI never invents or silently keeps an incorrect V1 claim. Existing actionable offline/source messages remain intact.
11. Verify every source-generation update uses only an allowlisted non-sensitive enum, existing authenticated transport and source/instance identity, with correct reconnect/replay order and no extra unbounded polling or report work. Existing V1 selection never unintentionally launches OpenCode. CLI selection, Watch, reports and source-generation preferences are unchanged by the warning feature.
12. Extend focused source-selection and host-status/Live tests (`development/tests/test_web_source_startup.py`, `test_web_live.py` / HTTP contract tests as applicable), V1 Watch/source-projection tests, and a real-browser full-navigation banner probe for source loading/V1/V2/offline/reconnect and themes/keyboard/narrow widths. Add a **paired CLI Watch vs. Web Watch** read-only fixture test under selected V1, with minimal and plugin-rich events, and both equal and intentionally differing source selection. Include auto fallback, CLI startup versus Web host startup, repeated V1 polling, plugin-shaped tool/skill events and the distinction between real unsupported data and dropped Web values. Run ordinary repository tests and validation **when implementing**, not while writing this FR. Record actual test evidence and any unresolved V1 gaps; do not assert the reported installation was reproduced without it.

**End state:** Cost Guard Web accurately indicates when it uses its **legacy V1 source**, plainly explains **verified limitations** without misrepresenting supported functionality, and a source-backed **CLI-versus-Web Watch comparison** establishes whether the reported difference comes from selected generation, Web-specific lifecycle/projection, plugin-shaped data or another proven cause. A demonstrable narrow bug is fixed; an unresolved broader issue is documented without speculation.
