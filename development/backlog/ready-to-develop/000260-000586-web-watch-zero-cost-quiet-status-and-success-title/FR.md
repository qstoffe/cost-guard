# FR 000586 — Full Web Watch: zero-cost prompt breakdown, quiet transient statuses, and successful session-title color

## Owner request and backlog decision

**Owner-approved executable Feature Request, 2026-11-04.** Permanent identity **000586**; Ready priority **000260**, after existing Ready FR000585 (000250). Scope: **Cost Guard Web Beta → full Watch**, covering both Running Prompts and Earlier Prompts where relevant, their per-prompt **CCost (I + E)** column, transient acquisition/refresh text, and the session heading over a recently completed prompt card.

The owner observes three small but distracting UX inconsistencies:

1. A prompt whose **displayed total CCost is `0`** may currently show **`0 (N/A + N/A)`** in the **CCost (I + E)** cell. The owner's explicit rule is **always show `0 (0 + 0)` whenever the displayed total CCost is zero, regardless of whether model calls exist, whether component costs were computed, or why the total currently displays zero**.
2. Temporary text such as **Refreshing**, **Retrying**, **Loading**, **Getting new prompts**, and status messages under session headings or inside/below the prompt tables can appear and vanish within seconds. This is distracting. A prior Ready **FR000583** already removes some flashing "refreshing; retained total" and "Retrying prompt refresh" text; the owner now explicitly requests a **complete audit and suppression of all similarly transient Watch status messages**, including the Earlier Prompts area, not just those two examples. It may be reasonable to show an operation that remains unfinished for **around 30 seconds or longer**.
3. When a prompt finishes successfully, its Prompt cell already turns **lime green**, but the **session title immediately above that prompt's table** returns to neutral. During the existing temporary successful-completion grace/highlight, the title should also turn the **same success green**, then revert naturally under Earlier Prompts' existing presentation rules.

Author the FR **only**. No source, tests, documentation, version or release change in this session.

## 1. Whenever the displayed total CCost is zero, show `0 (0 + 0)`

- **Owner clarification overriding any earlier zero-request-only proposal:** In **both Full Watch Running Prompts and Earlier Prompts**, if the **total CCost displayed in the cell is zero** in the currently selected unit (e.g. `0` in Credits or `$0.00` in USD), render the **I + E breakdown as two zeros**, e.g. **`0 (0 + 0)`** or **`$0.00 ($0.00 + $0.00)`** according to current formatting. This is mandatory **regardless of model-call count, missing first-request token data, partial component evidence, or whether the individual components would otherwise be `N/A`**.
- **Do not condition this display rule on `calls === 0`, presence of source requests, provenance, or completeness of the component calculation.** If the displayed total is zero, neither component is allowed to show `N/A` in this cell. The owner's desired display semantics treat the components as implicitly zero whenever the visible total is zero.
- Only when the **displayed total CCost is greater than zero** may one or both components show `N/A` if their own values are unknown, retaining the established genuine `?`/partial conventions for positive totals. A wholly missing/unknown total (`N/A` or Loading) is **not** numeric zero; do not turn it into a fictitious `0 (0 + 0)`. If the total carries an explicit unresolved/partial marker, preserve that marker rather than silently claiming a fully known total.
- This is a **presentation override**, not a change to source telemetry, the canonical unrounded total, accounting, attribution or I/E calculation. The three figures still represent total prompt CCost, incoming-context cost of its first model request (I) and other prompt-attributed costs (E), but the visible zero rule takes precedence over component availability in the Watch cell. Do not modify CLI or Sessions reports.
- Apply it whenever the displayed total is zero, including before the first request, after observations that have no displayed cost, after a refresh, and in Earlier Prompts. Do not reintroduce `N/A + N/A` on a displayed zero simply because the prompt has some observed tool/model calls. Switching Credits/USD follows the existing formatter; an amount shown as zero in the chosen display unit gets zero components in that same unit, without altering the underlying precise values.
- Current implementation sites: `src/web/assets/watch.js::promptCost()` concatenates `ccost`, `incoming_context_ccost` and `extra_ccost`; `src/application/display.py::amount_tokens()` maps unproven I/E components to `N/A`. The implementation should apply the zero-display override reliably at the presentation boundary, without guessing that missing total equals zero.

## 2. Remove *all* fleeting Watch acquisition/refresh-status prose, not only FR000583's two sites

**Owner's UX rule:** Full Watch is a live monitoring surface. An ordinary operation taking a few seconds should be silent: show the last coherent values and then replace them. Avoid a status line appearing briefly, pushing the table down, then disappearing. This applies to **running prompt cards, earlier cards/disclosure, the session summary, and analogous short-lived loading/refresh strings elsewhere on the Full Watch screen**.

### Audit every current Watch status entry point

Investigated current source, including these examples in `src/web/assets/watch.js`:

- `Card.update()` writes `this.message` under each session title: **`Retrying prompt refresh; retained contents are not current.`**, **`Partial / retained evidence`**, **`Loading prompts…`**, and genuine **`Source unavailable…`**.
- `Card.drawSummary()` writes session CCost **`(refreshing; retained total)`**, **`Loading…`**, and unavailable/partial notes.
- `View.update()` writes shared **`Retrying source read…`**, **`Loading active prompts…`**, **`Loading earlier prompts…`** and history unavailable/empty notices. Verify actual user-visible placements when Earlier Prompts is expanded or data refreshes in place.
- `daily()` may show **`Loading daily activity…`** or **`Retrying daily refresh…`**; inspect other full Watch account/quota or activity paths and generated help for equivalent blink-inducing operational notices.
- The inventory above is **not exhaustive**. Include all transient *retrieving / fetching / updating / recalculating / refreshing / loading / retrying* text at runtime, not just matching these exact words.

### Desired behavior

1. **Routine refresh with existing valid values:** silently retain stable last-known prompt, history, context, cost, daily and account values while reacquiring them. Do not insert/remove fleeting text, emit a spinner, replace numbers with Loading, cause vertical layout jumps or steal focus. Update only when the next coherent result arrives; do not use the UI to infer missing usage.
2. **Brief initial acquisition / newly encountered card:** don't show repetitive short-lived loading prose under headings or next to tables. Prefer an unobtrusive, non-jumping blank/reserved or neutral initial treatment while waiting for the first coherent result; if it genuinely lasts **~30 seconds** (proposed UX delay, not a backend timeout), show a **single** concise actionable "Still loading"/availability status in an appropriate stable place. Do not temporarily invent zero rows or pretend an empty table is a valid observed empty result. Keep **no running prompts** and **no earlier prompts** when truly observed empty, because those are meaningful *stable* states rather than refresh notices.
3. **Retained values and source problems:** a real sustained outage, expired authorization, host identity change, deliberate stop, lasting partial/unavailable evidence, priceability problem or other actionable failure must still be communicated truthfully, without suppressing critical issues for 30 seconds. Use the established global/source-health warning and relevant accessible freshness/help where possible. The optional ~30-second delay is **for ordinary progress/temporary retry copy**, never a policy to hide confirmed errors, missing permissions or genuine data-loss warnings.
4. **Consistent across both tables:** running and Earlier card headings and the Earlier disclosure must obey the same "no flash" policy. No transient "Refreshing" can reappear in another card when live updates, history selection, source corrections, CCost cache refresh or publication order changes.
5. Avoid large new timer/state machinery just to suppress labels; use stable observation/source timestamps or existing live UI wakeups where possible. A timer used for a delayed visible status must be bounded, lifecycle-owned and cleaned up. No extra source polling, SSE streams, history scan, provider calls or modification of the canonical acquisition state machine.

**Relationship to existing FR000583:** this FR **extends/supersedes only its narrow quiet-refresh acceptance** with the complete Watch-wide transient-status audit. Keep FR000583's Mini resizing and parenthesized session-cost changes untouched. Coordinate shared styling/tooltip copy with **FR000580**'s Session Context / CCost line, **FR000582**'s tooltip overhaul, **FR000584**'s Tool Calls/Skills status and other queued presentation updates. Don't remove meaningful **`Running: <tool>`** activity text: it describes genuinely ongoing work, not generic acquisition progress.

## 3. Successful prompt: session title shares lime-green completion highlight

- For an **active/recently-ended Running Prompts card**, when its **focal prompt has authoritative successful-completion evidence** and is still inside the existing terminal-grace highlight, color the **session title link directly above that table** using **exactly the existing `--watch-success` semantic color** already used for successful prompt-row text (lime in Classic). The current `--watch-running` yellow remains for a genuinely running focal prompt.
- Once the existing success grace expires and the session becomes eligible for **Earlier Prompts**, revert to its ordinary historical session-title color as that section currently works. Do not extend grace, change history eligibility/order, add a green badge, recolor unrelated rows or keep a stale green title on resumed sessions.
- **Failed/aborted/unknown outcomes are not successes.** Use the same **confirmed status** as the prompt row to decide title color, not merely `!in_progress`; preserve existing red/error treatment and neutral fallbacks, as well as visible status/ARIA labels. With multiple concurrent focal cards from one session, the title reflects **each card's focal state**, not an unowned global "session is complete" inference.
- Current `src/web/assets/watch.js::Card.update()` sets `this.title.className` **only for running** cards. Its individual prompt row has `watch-running`, `watch-error`, or `watch-success`; CSS `.watch-prompt-table .watch-success` uses `--watch-success`. Extend the title class and rule minimally, retaining keyboard focus, link navigation, contrast in Classic/Web light/dark and no hover regressions.

## 4. Acceptance and verification

1. **Every prompt whose displayed total CCost is exactly zero** (including a running prompt with one or more observed model calls, regardless of missing/unavailable component figures) displays **`0 (0 + 0)`**, or corresponding zero values in USD. This applies to both Running and Earlier; no `0 (N/A + N/A)` remains. Test zero requests, existing requests, unavailable component data, and repeated live updates.
2. When **displayed total CCost is positive** and one or both components cannot be calculated, keep `N/A`/appropriate partial indicators for those components. A truly unknown/missing total must not become zero. Test positive total with unknown I, unknown E, both unknown; total `N/A`; actual zero; unit switching and a tiny positive amount that displays as `$0.00`. No canonical pricing, source-accounting or attribution formula changes.
3. Repeated brief refreshes and transient retries (e.g. 1–10 seconds) across Running cards, Earlier cards, shared status, session CCost and daily/account Watch widgets produce **no visible Refreshing/Loading/Retrieving/Getting new prompts status flicker or layout shift**. Retained values remain readable and correct. When first loading lasts about 30 seconds, a concise delayed status can appear; when genuine outage/auth/partial/error evidence exists, appropriate actionable status must remain visible.
4. Prompt success transition: running title is yellow while active; on **confirmed successful completion**, both the prompt cell and title are lime/success-colored for the existing grace; when moved to Earlier, the historical title returns to normal. Test abort/error/no-success terminal, rapid resumption, concurrent focal prompts in same session and source revision races. No extra transient color flash caused solely by refresh.
5. Verify text/cost status by deterministic Python projection/formatter and JavaScript DOM tests, including `src/web/assets/watch.js`, `src/application/display.py`, `src/reports/prompt_rows.py`, `development/tests/integration/web_live.cjs`, `development/tests/integration/web_watch_summary.cjs`, and focused browser probes of actual live/mocked publication transitions. Check Classic, Web light/dark, narrow layouts, focus/copy selection and Earlier disclosure updates. Update current `docs/web-beta.md` and relevant current module help after implementation; preserve historical completed FR files.
6. Keep the existing Live connection, backend timing, account polling, canonical prompt/session costs and server-owned warnings unchanged. Suppressing short operational prose is **not** permission to hide lasting failures or turn missing evidence into valid zero.

**Out of scope:** Mini Watch's separate status display, CLI Watch, rewriting backend acquisition scheduling or pricing, changing success/terminal grace timing, making unseen model calls, adding a new global loading setting, and implementation/version/release work in this FR-authoring session.
