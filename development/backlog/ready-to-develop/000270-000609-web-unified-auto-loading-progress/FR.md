# FR 000609 — Web Beta: automatic loading and one stable 0–100% progress UX for four report pages

**Owner-approved Ready Feature Request, 2026-11-06.** Permanent identity **000609**; Ready queue priority **000270**, after current FR000608 (000260). This is **backlog publication only**: do not implement code, run product gates, alter product documentation, change versions, or move unrelated FRs while authoring this request.

## Owner observation and outcome

The four finite-report pages **Models, Token Mix, AI Stats and Comparisons** currently make a first-time visitor wait in inconsistent ways. The owner saw AI Stats fail shortly after launching the Web server when attempting Refresh/Retry, with a source/service-not-started or try-again message; temporary startup lag should normally remain a visible *loading/waiting* state rather than prematurely becoming a manual-retry dead end. Token Mix requires a **Load Token Mix** click and uses an indeterminate moving/marquee bar. Models automatically loads with a centered percentage bar, but prefixes the number with an unnecessary **≈**. Comparisons automatically loads, yet its moving status text/progress region appears to flicker, jump and offer poor visual continuity.

**Deliver a cohesive, shared, calm loading experience:** entering any of these four pages automatically starts the first eligible data acquisition; a centered, *determinate* horizontal progress bar shows **0–100%**, with an integer percentage and a short changing description of the actual current work directly **beneath** it. No first-load button, no indeterminate marquee, no approximation glyph, and no status-line jumping. This is a product UX correction plus reliable startup/retry handling, not a request to simulate progress or conceal hard failures.

## Current implementation and investigation leads (source inspection, not a proven incident trace)

- `src/web/assets/reports.js` marks **Token Mix** as `explicit`; `src/web/assets/app.js::navigate()` skips automatic first acquisition for it. `show()` exposes **Load Token Mix** until a result exists. Models, AI Stats and Comparisons already have conditional first-entry automatic acquisition.
- `app.js::overviewProgress()/showOverviewProgress()` implements Models' phase-/stage-weighted `0..99` estimate and `100` upon a usable fully acquired result, but its visible and ARIA text say `≈N%` / “Approximately N percent.” It is currently Models-specific.
- `ai-stats.js` and `comparisons.js` create `<progress>` **without `value`**, so browsers render an indeterminate animation. `app.js` also has a generic indeterminate initial-report and stale-withheld path. Comparisons puts mutable status text above the data/progress and `app.js::acquire()` can publish different `queued/running` + phase/count strings on ~500 ms polls, producing varying text height/position. Validate the actual source of visible jitter in a browser rather than assuming all flicker has one cause.
- **Likely early-startup race to reproduce:** `src/web/source_startup.py::SourceStartup.prepare()` owns an asynchronous OpenCode source wake/health check, but `src/web/assets/live.js` counts `source_starting` as `writable`; `app.js::acquire()` gates on `hostState.writable`, not on confirmed source readiness. Its separate spawned report process invokes `src/web/composition.py::application()`, selecting the source independently. A premature selection can fail before source wake finishes; `src/web/jobs.py::run_report()` collapses unhandled errors to `report_unavailable`, which `app.js::failure()` presents as a generic retry instruction. Separately, the finite-job admission limit (`MAX_PENDING=4`) can return HTTP **429 `busy`**, currently another manual-retry outcome. Neither hypothesis is proof of the precise owner incident; use a controlled just-started host/source and captured *sanitized* error codes to distinguish them.
- The existing bounded spawned-job lifecycle, progress events with phase/stage/completed/total/sequence, cache policies and revision checks are valuable; do **not** replace them with fake percentage timers, a new independent scanner, or another server wake path.

## Required interaction contract

1. **Automatic first visit — all four routes.** Models, Token Mix, AI Stats and Comparisons start the appropriate existing finite read-only acquisition on the first *visible* eligible entry, without a Load/Refresh button being required. Remove Token Mix's manual `explicit` first-load behavior and the redundant pre-result `Load Token Mix` action. AI Stats and Comparisons retain their current automatic behavior while adopting the shared UI. Use the existing authenticated/CSRF, route, view-result reuse and coalescing rules; entering a route repeatedly must not duplicate in-flight jobs or flood the four-slot queue. Do not preload expensive hidden pages merely to enable auto-loading. Keep any genuine **Refresh price list** action on Models as a separate explicit price-refresh feature; it is not the initial page loader.
2. **One consistent central progress component.** During an initial/no-usable-result acquisition, render a single stable block centered horizontally in the main page's available content area and comfortably centered vertically, without interfering with navigation/headers. Use a determinate bar with explicit `max=100` and `value` in **0..100**, a clear visible integer `N%` (no `≈`, `~`, “Approx.” or “Approximately” in the visible/accessible percentage), and a short, specific stage/status line **underneath** it. Prefer a reusable renderer/view + shared CSS, not four visually similar copies. A brief readable stage count such as “Checking history (240/2,757)” is useful when the backend truly supplies both numbers; use meaningful fallback labels when it does not.
3. **Truthful bounded progress.** Derive advancement from the report's actual ordered phases, stage ownership and observed counts (extend the existing safe `WorkProgress`/mapping where needed). Preserve monotonic percentages during one attempt, ignoring stale/out-of-order events; no advancing merely because time passes, cycling percentages or claiming a measured global denominator where none exists. The bar may hold at the current percentage during an opaque expensive stage while its status identifies that work. Do not fake 100% before a valid terminal response has been received/applied. On a *successful finite job with usable partial source data*, 100% may mean **this loading attempt finished**, while a clear separate **partial coverage / unavailable evidence** warning remains visible; never label partial history itself fully complete. Failure, cancellation and timeout never show successful 100% completion. Fast stages may legitimately jump forward; don't introduce artificial sleep to showcase every integer.
4. **Stable geometry and calm updates.** Keep the loader's DOM and dimensions stable across polls/phase changes (tabular numerals, reserved height for the stage line, predictable text wrapping, restrained paint frequency), not remove/reinsert bars or bounce headings/pagers. In particular, Comparisons' job status and paginator/group area must not jump or flicker on every poll or when a new coherent result arrives. Accessible status changes must be useful but not spam screen-reader announcements on each count update. Respect `prefers-reduced-motion`, keyboard/touch focus, light/dark themes, mobile/narrow widths and the existing shared visual language.
5. **Startup/waiting vs genuine errors.** If the host is authenticated but the read-only source or a finite-report slot is *temporarily* not ready, show **“Waiting for source…”** / **“Waiting for report slot…”** as meaningful progress stages and continue/automatically retry through a **bounded, cancelable, backoff-aware** readiness/retry path. A just-started server should not force a user to click Retry when ordinary startup recovers. Determine the cause from actual host/source readiness and typed errors; do not treat HTTP readiness or `writable` alone as proof that the source can be acquired. Do not retry forever, mask sustained source/auth/permission/instance failures or bypass the existing **120-second report-job deadline**, **8 MiB result limit**, **four pending jobs**, protected session/CSRF, lifecycle cancellation or host ownership. Terminal/offline/auth, unsupported source, real report failure/timeout and repeated startup failure must end in specific actionable visible error feedback with an accessible **Retry** option where retry can actually help. A recovery-only Retry is not a first-load Load button.
6. **Correct retained-result behavior.** Keep the existing historical-page freshness policies (`CachedReports`: Token Mix/Comparisons 5-minute, AI Stats 15-minute checks and >1-hour withheld re-entry), AI Stats periods, Comparisons paging/revision behavior, and Models snapshot/price semantics. If a successful retained result remains usable during a quiet refresh, **leave the data, scroll, sort, selection, links and keyboard focus intact**, with a small non-disruptive updating indicator instead of replacing the entire page with a large centered initial loader. If the result is legitimately withheld/stale or no usable result exists, display the shared central loader. Do not falsely show stale metrics as fresh or reset progress on every poll/navigation. Failed background checks retain existing provenance without flooding the page with changing text.
7. **Data can appear progressively only when coherent.** It is acceptable to reveal independent fully prepared sections once the backend can prove their integrity, but not by displaying partial computations as final, inventing tokens/prices/ratios, or flashing sections in/out. A simple atomic data reveal on completion is acceptable and preferable to unstable pseudo-streaming. This FR does not change the underlying reports, filters, stats, comparisons, provider services, billing, or any CLI/live Watch/Mini Watch workflow.

Models never displays `≈` or an accessible “Approximately.”
2.
