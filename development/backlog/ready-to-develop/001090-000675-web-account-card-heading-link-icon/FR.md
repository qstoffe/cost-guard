# FR 000675 — Web account cards: link icon and reliable CCost Today

**Owner-approved Ready Feature Request, 2026-11-10; expanded by owner 2026-11-11.** Permanent identity **000675**, Ready queue priority **001090**, after existing Ready FR000673 (001080), leaving higher-priority FR000674 (001065) untouched. **This in-place FR revision is documentation only:** no implementation, tests, product/release/version changes or changes to the running application. Both the original link-icon change and the additional CCost Today verification/repair are approved.

## Owner observation and desired outcome

In **Cost Guard Web**, the account/subscription card heading on **Full Watch** and **Accounts** is already a clickable provider usage/settings link (delivered by FR000636). However, because the account name looks like an ordinary card title until hover/focus, a user can easily miss that it is a hyperlink.

Show a **small, recognizable link/chain icon immediately before the account name** in each *linked* account-card heading. The icon must be visible even before hover, making the existing navigation affordance discoverable while keeping the header clean and attractive.

## Required presentation and behavior

1. Put the icon **to the left of the account name, inside the same existing `<a>`**. Icon and name together form **one link**, not two controls. The account name remains unchanged and fully readable. Do not turn the whole header background or card into a click target.
2. Use a restrained, familiar **outline chain/link symbol** (prefer a simple existing UI asset or lightweight inline SVG; avoid a large colorful emoji or new icon dependency). Size it proportionately to the heading text, align it neatly with the text, use a modest gap, and inherit appropriate heading color. Keep the combined icon + name centered in the existing colored heading region.
3. Display the icon **only when the account heading has a trusted destination URL**. Unknown/unmapped providers that retain a plain-text heading do **not** get a misleading icon, hover/pointer decoration, or fake action.
4. Preserve the existing link destinations, provider/plan selection, **new-tab** behavior, `target="_blank"`, `rel="noopener noreferrer"`, pointer cursor, hover underline, and keyboard `:focus-visible` treatment. The icon is a permanent visual cue; the original hover/focus feedback must still work.
5. The icon is **decorative** (`aria-hidden="true"`, not separately tabbable); the link's accessible name still identifies the account and provider usage/settings destination, including opening a new tab. Do not announce a duplicated “link” label or accidentally replace the accessible account name.
6. Preserve existing themes (Classic/Web light/Web dark), exhausted-state header colors, long/wrapping names, narrow screens, browser zoom, focus retention and quota-card grid alignment. Do not introduce unwanted header-height/row shifts or truncated names simply to fit the icon.
7. **The icon is a presentation-only change:** it must not alter account discovery, native quotas, CCost, polling, URLs, authentication, connection ownership or Mini Watch's unrelated UI. The **independent CCost Today fix below** may change the appropriate shared accounting/projection pipeline as necessary; do not couple accounting to icon rendering.

## Implementation seams and coordination

- `src/web/assets/render.js::accountHeading()` already creates the shared `<h4>` with an `<a class="account-provider-link">` for known providers, or a plain `<span>` when no trusted destination exists. It is used from `src/web/assets/account-cards.js::Subscription.draw()` and the legacy Accounts rendering path. Implement the icon once at this shared heading boundary so **Full Watch and Accounts** remain identical.
- `src/web/assets/app.css` owns `.account-provider-link` and the account-card heading styles; use minimal styling to keep the existing centered title and focus/hover affordances intact. Keep icon position before the text even through retained DOM updates and card redraws.
- **FR000636** intentionally asked for linked text with *no standalone icon*. This new owner decision **supersedes only that earlier no-icon preference** by adding a compact icon **inside the existing linked heading**; it does not authorize a separate button or changes to the provider links.

## Acceptance criteria

1. With a known linked provider on **Full Watch** and **Accounts**, a small link icon is visible **immediately before** the account name in the heading, at rest; both icon and name open the same existing provider URL in a new tab. No extra focus stop or nested button exists.
2. With an unknown/unmapped provider, the title remains plain text **without** a link icon or click behavior. Account names and their exact provider destination mapping remain unchanged.
3. Hover/focus, Tab navigation, touch activation and screen-reader naming remain correct; decorative SVG is hidden from assistive technology. Clicking empty header padding or the rest of the card still does not navigate.
4. Long account names, normal/exhausted cards, Classic/Web light/Web dark, mobile widths and zoom preserve legibility, centering, line wrapping and aligned card rows. Updates/redraws do not duplicate the icon or lose link focus.
5. Extend the existing focused Web account-link/card DOM/browser regression coverage (including `development/tests/integration/fixtures/account_links.cjs` and the suites that invoke it, as applicable) and run relevant checks **during implementation**, not as part of this FR publication.

## Additional owner request (2026-11-11): investigate and repair CCost Today

**Observation, with important midnight uncertainty:** the owner saw **CCost Today = 0** on the account cards for **GitHub Copilot Pro+** and **OpenAI Pro Light** despite substantial recent usage, and also worried about Claude Code Pro. The upper **overall Watch CCost Today** showed **Not Applicable** around the same moment while an Opus Claude Agent prompt was in progress or newly recorded. The owner then realized the clock had just passed **local midnight**, so the empty/zero today period **may be perfectly normal** even if there was heavy *yesterday* usage. Do **not** claim the entire daily-cost pipeline is broken without reproducing it on the correct side of the local date boundary. However, the owner explicitly asks to **verify and fix** any incorrect or stuck account/global Today values, rather than dismiss the report as midnight rollover.

### Diagnosis and required behavior

1. **Reproduce the exact midnight boundary**, with a configured **Europe/Stockholm** local timezone and a second timezone/DST control: an expensive/active previous-day session, snapshot just before midnight, rollover at 00:00, and genuinely new nonzero priced requests after midnight. A **zero for the new day before any eligible current-day request is valid**; continuing zero after an attributable, priceable completed request in that new local day is not. A truly unpriced new-day prompt can make an aggregate unavailable/partial, not evidence that midnight failed.
2. **Trace end-to-end for each provider:** source message completion time and local-day conversion; new-period history acquisition, revision and cache; token/reference-price resolution; deduplication; request provider/account identity; `src/analysis/period_ccost.py::PeriodCCostIndex`; `src/reports/accounts.py::_period_scopes()`; the Watch account projection; `src/web/assets/account-cards.js` `CCost Today` rendering. Audit `src/watch/today_ccost.py::WatchTodayCCost` separately for the **overall** daily total and its midnight refresh/retention. Do not assume an account's Today is identical to global Today or a native quota/actual billed amount.
3. **Correct all three reported accounts where evidence supports it:** GitHub Copilot **Pro+**, OpenAI **Pro Light**, and Claude Code **Pro**. When an eligible, correctly priced new-day request has a known matching account, the corresponding account card must show the appropriate positive **reference CCost Today**, with the correct existing USD/Credits presentation. For unknown/ambiguous multi-account routing, insufficient history, or unpriceable usage, prefer truthful unknown/known-subtotal semantics over fabricated $0. A single account's daily sum must not steal another account's usage.
4. **Separate the causes of zero/N/A:** an empty new local day; an account attribution mismatch; absent/late day-history evidence; real model reference-price N/A (especially the newly reported Claude Agent Opus case); delayed publication, stale UI/cache; and rounding of a small positive reference cost. Reconcile only comparable evidence. **FR000673 A1** owns generic Claude Agent model → canonical reference-price fixes, and **FR000673 A2** owns Claude Agent → Claude Pro subscription attribution. This FR owns a **cross-provider and post-midnight verification/regression fix**; reuse FR000673's results if it precedes this implementation, and do not duplicate competing provider-alias policies.
5. **Correct global Watch Today as well:** when supported priceable requests for the current local date exist, the overall value must reflect their canonical reference CCost, subject to the established partial/unknown semantics. Where a newly recorded Opus request truly cannot be priced, diagnose that separately under FR000673 rather than turn N/A into a fake positive amount. Preserve the existing intentional *previous-day date label* in overnight display hours where configured; distinguish label policy from the actual local-midnight accounting boundary.
6. **Preserve invariants:** account Today and overall Today are reference valuation, never native subscription percentage or actual provider bills. Preserve completed-request timestamp rules, deduplication across roots/subagents, historical/retained evidence, identity isolation, safe refresh costs, complete-vs-partial price provenance, focus/DOM preservation and no added paid provider inference or user source mutation.

### CCost Today acceptance and regression

1. Simulate 23:59:59 → 00:00:00 in Stockholm (including summer/winter offset and a DST-related control), with an old-day positive prompt and **no new-day usage**: account and overall Today must not incorrectly carry yesterday's cost. Then append a new priced request after midnight for Copilot Pro+, OpenAI Pro Light and independently Claude Pro, and show the correct daily value as soon as qualified evidence is published—not a stuck 0.
2. Verify **each account independently** alongside global Today, across account cards on **Full Watch and Accounts**, stale/unknown/partial/zero states, one versus multiple same-provider accounts, live refresh and source-history catch-up. An account sum need not equal global Today when unattributed requests exist; ensure this is explained and not hidden as zero.
3. Verify an **Opus Claude Agent** request with nonzero tokens and known supported reference pricing contributes to global Today, with correct account-day attribution only when the Claude subscription route is qualified. Include an unpriceable source request, unknown provider/account, zero-token control and subagent/dedup regression.
4. Extend existing account-period, Today/rollover, watch-projection, Web account-card and browser integration tests (for example `development/tests/test_account_period_ccost.py`, `development/tests/test_web_accounts.py`, and the owning `src/watch/today_ccost.py` tests) as appropriate. Test both immediate post-midnight values and later history completion. During implementation record **which observations were legitimate rollover** and **which were real accounting defects**; never claim a fix solely because a previously idle new day accumulated normal usage.
