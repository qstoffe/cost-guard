# FR 000624 — Web: restore Earlier Sessions availability and aggressively optimize foreground/cold-start loading

**Owner-approved Ready Feature Request / P0 regression + P1 performance overhaul, 2026-11-07.** Permanent identity **000624**; Ready queue priority **000420** (the queue is currently otherwise empty). This is **backlog-authoring only**: create this FR and advance the identity watermark on `main`. Do not implement product code, tests, version/release/docs or change other FRs in this authoring transaction. The future implementation is intentionally large, evidence-driven and allowed to invest substantial engineering/benchmark time, including ten hours or more when productive.

## Why this is urgent — owner-observed symptoms

The recent change to start/warm all useful Web views in the background (FR000617, v80.197) delivered the desired *concurrent loading intent*, but the owner now perceives the **initial loading of essentially every page to be much slower**, especially:

1. **Models:** on a fresh Web launch or first visit, the model list takes far too long to finish. When Models is visible, its initial data should get the fastest safe service; inactive views should not compete for the same critical path.
2. **Full Watch → Earlier Sessions and Mini Watch → Earlier Sessions:** opening/expanding historical sessions takes an extremely long time.
3. **New, blocking functional regression:** Mini Watch now shows **“Loading…” followed by “Unable to verify latest sessions”**, rather than the actual latest earlier sessions. This is not merely a cosmetic progress issue. Full Watch and Mini consume the same server history; investigate both, not just the Mini notice.
4. **General responsiveness:** navigating to a page that was warming in the background should immediately promote its existing work and make it usable as rapidly as possible. Inactive tabs can take much longer to finish, provided their work continues opportunistically and does not steal capacity from the foreground.

The owner explicitly distinguishes **fast first usable load and foreground promotion** from periodic refresh: once a view is usable, its passive refresh can be deliberately gentler and slower to avoid sustained CPU/IO saturation. **Never “fix” speed by ceasing all background warming**; keep the intended all-pages-warm behavior, but enforce real foreground-first scheduling and source-efficient acquisition.

The two problems belong in **one FR with an early P0 correctness/availability gate and a substantial P1 measured performance phase**. Do not close it as a successful performance improvement if Earlier remains unavailable on a healthy, readable real source, or merely because a synthetic fixture passes.

## Confirmed code/evidence (not a new reproduction of the owner's current installation)

- **FR000617:** `src/web/dispatch.py::DataDispatcher` owns foreground/browser route interests, warm results, low-priority due work and prioritization of finite reports. `src/web/jobs.py::ReportJobs` uses one active finite child at a time, cooperative `ManagedReport` yielding/parked children, priority ordering, and bounded queue/memory/deadline ownership. `src/web/assets/data-demand.js` sends a visible route lease on a timer. This is a sound architectural foundation; first establish whether its priority affects **end-to-end time-to-visible**, not just queue placement.
- **Separate Watch history lane:** `src/watch/cards.py::WatchCards.tick()` feeds `src/watch/card_workers.py::CardWorkers` (four concurrent card workers) independently of the finite dispatcher. Each card capture creates an isolated service and reads/analyzes a source tree. `src/watch/web_coordinator.py` also owns account-history and Sessions catalog/detail work. Promotion of finite Models/AI Stats work is therefore **not by itself proof that Watch Earlier has timely foreground service**.
- **Mini Watch demand gap to test:** `src/web/assets/mini.js` displays retained Live history and toggles Earlier locally; the toggle does not request a higher server-side history priority. `data-demand.js` reports a route as foreground only while the **opener's** `document.hidden` is false. A visible Mini document/PiP with a hidden opener must be treated as a genuine user-visible history demand, without creating another scanner/EventSource/provider owner or granting unlimited resource rights to browser messages.
- **FR000623, v80.203:** `src/watch/history_publication.py::HistoryPublication.project()` authorizes the initial newest-five list only when **all cataloged roots have revision-matched scalar verification** (and finalist captures exist). Mini shows the newest three from the same certified list. This deliberately eliminated falsely finalized older candidates; **do not regress that correctness**. A single failed/unverified root can prevent initial certification. `src/watch/source_status.py` converts confirmed source-read failures into unavailable states. The completed FR specifically acknowledged that large/churning real sources may never deliver a verified list.
- **Real-installation evidence from FR000623's engineering journal:** a supported, read-only `probe_web_live.py --watch-cards` run with **2,793 roots** reached only **20/2,793** verified roots within **90 seconds**, surfaced `concurrent_source_change` / unavailable, and observed one capture lasting **57.7292 s**. This is a prior engineering run, **not** a fresh verification of the owner's latest symptom. Critically, its real winner IDs and time-to-first-certified Earlier remained **INCONCLUSIVE** under an explicitly approved prior exception. This FR must address that remaining real-use gap rather than inheriting the exception as success.
- **Synthetic FR000623 evidence:** the 2,700-root test removed 674 provisional winner replacements, but time-to-first-visible history became **20.8717 s**, with **2,700 root reads / 8,100 revision checks**. These are synthetic serial-run measurements, not hardware latency guarantees. They expose the potential cost of requiring complete coverage.
- **V2 acquisition candidate:** `src/sources/opencode_v2_snapshot.py::load_snapshots()` brackets message hydration with catalog revisions; the after-bracket calls `_list_native_sessions(refresh=True)`. Per-root work can repeatedly enumerate and revise the whole V2 catalog. `src/sources/opencode_v2_catalog.py::V2CatalogIndex` memoizes within an instance, but separate per-card source/service lifetimes may defeat reuse. **Profile whether repeated full-catalog HTTP requests, unstable-root retries, tree loads, source worker contention or cache writes dominate**; do not assume the exact proportion until traced.
- **Models candidate:** `src/reports/service.py::_build_dashboard()` gathers a priceable **100-prompt** recent sample via `src/reports/sampling.py::recent_sample_roots()`, builds model comparison/availability and period data through the normal report path. Source catalog, price/cache validation, fresh spawned-process setup, message hydration, projections, serialization, scheduling and front-end paint all need separate timing. Never assume “Models = static price list” or make up a singular cause for the slowdown.
- **Prior finite real measurements (`development/journal/web/data-dispatch.md`):** Models was usable at **23.375 s** in one foreground-only run vs **13.621 s** in a different warmed run; those evolving-source/caches runs were **not controlled paired cold-start proof**. A warm-run foreground job showed progress ~0.714 s after navigation, which does **not** establish fast final readiness. Model end-to-end speed must be remeasured with matched workloads, not inferred from those numbers.

## Required UX and correctness contract — implement P0 first

1. **Healthy readable Earlier must become usable.** Reproduce the user's `Loading → Unable to verify latest sessions` path; identify the actual blocked root/stage/failure/retry pattern without leaking private payloads. On a stable, supported source with sufficient eligible earlier sessions, **Full Watch and Mini Watch must produce the correct newest five/three and remain usable** after a fresh launch, including a large real/simulated catalog. If the source truly cannot be read/verified, report a truthful typed unavailability and recovery action, not silently guessed newest sessions. A short transient `concurrent_source_change` must not permanently poison the whole collection.
2. **No provisional masquerading as final.** Retain source-backed global ordering, eligibility, canonical prompt finish semantics, tie-breaking, generations/revisions and coherent publication across Full/Mini. Never reintroduce old “plausible latest five” that get replaced by previously existing newer sessions. Do not use root `updated_at` as a proven last-prompt-finish upper bound unless the supported source API *guarantees* that fact. If introducing per-root compact certificates/summary indexes, prove that they are sufficient for a globally correct top-k, including negative/exclusion evidence; never equate cached model/account metrics with complete Earlier history.
3. **Avoid one-pathological-root hostage behavior where correctness permits.** Test continuously changing roots, source restarts, subagents, a slow historic tree and absent/unknown finish evidence. A qualified root may be excluded from the proof *only with authoritative source-backed grounds that it cannot displace the winners*. Otherwise preserve meaningful pending/error state and bounded retry; ask the **Decision Delegate** about fundamental source-contract limitations rather than silently weakening proof.
4. **Prioritize visible Earlier demand.** The protected Live/active prompt/Accounts service must remain responsive, while expanded **Full Watch** or an opened **Mini Watch** displaying Earlier receives a bounded, high-priority *history* demand. Mini must remain foreground-important even if the opener/browser tab is hidden. Collapsing or closing Mini downgrades demand without destroying reusable work. Active historical foreground may sprint within demonstrated safe resource limits; hidden refreshes remain quiet and low-budget.
5. **No fake completeness.** Preserve “Loading / verifying latest”, retained previous qualified cards with clear freshness, distinct transient vs terminal errors, no false zero/empty, no duplicate/flickering rows, no stale cross-host/source publication and accessibility/keyboard/PiP behavior. If the first full verified result is impossible due to a genuine source failure, communicate precisely what blocked it rather than replacing truth with an invented fast list.

## Required P1: substantial cross-Web speed work

**Primary design principle:** prioritize *time until the user's requested view is actually useful*, not only when its task starts or the progress bar moves. Background throughput is secondary. Retain low-cost staggered warming so routes visited later often render immediately.

- **Startup and priority arbitration:** trace auth/first Live, first foreground request, dispatcher admission, source/catalog/message IO, finite vs Watch worker contention, source/OS CPU pressure, result publication and actual DOM paint. Audit priority inversion across the finite worker, Watch card pool, Sessions/catalog indexing, Watch account-history lane and source HTTP transport. Optimize admission sequencing, adaptive bounded concurrency and preemption/checkpoint granularity, not merely badge order. Do not launch heavy speculative scans before the requested initial route if doing so hurts it.
- **V2 source cost:** benchmark pooled HTTP reuse, session-list pagination, catalog bracket frequency and scope, memoized revision index lifetime, batch reading multiple roots under one coherent before/after bracket where safe, immutable summary reuse, dirty-root detection and efficient retry of only changing roots. Compare multiple candidate designs. Verify semantic equivalence on concurrent catalog churn, source identity changes and current/legacy V2 wire shapes. **Never remove required revision validation simply to win a benchmark.**
- **Efficient Earlier proof:** explore cheap, *authoritative* incremental latest-finished summary/certificate (source-backed, bounded and version/revision-scoped), reusable verified scalar evidence and a conservative global-top-k proof. Prefer quickly checking likely winners with a sound way to exclude unread competitors, rather than requiring thousands of full prompt trees every startup *if the actual source contract permits*. If it does not, significantly reduce the cost of exhaustive verification through batching, shared catalog brackets, IO staging, safe concurrency, minimized per-root service startup and changed-root revalidation. Retain bounded memory, privacy and source-read safety.
- **Models cold path:** profile 100-eligible-prompt sampling, revision/catalog IO, derived cache hits/misses, model/pricing/availability lookup, account-period work actually performed on the managed route, child-process/IPC overhead, projection and JS table rendering. Test cheap early availability/catalog reuse, efficient sampling stop conditions, amortized process/service initialization, bounded parallel IO and first-use-oriented projection. Do not degrade eligibility, completeness, model ordering, pricing/provenance or explicit “Refresh price list” behavior.
- **Other views:** inspect first usable load/switching for Token Mix, AI Stats (30-day default and an explicitly requested scope), Comparisons, Sessions first 50 rows/sort and session details, and Accounts/Watch. Find actual shared bottlenecks and avoid a Models-only tuning exercise. Reuse valid compact derived inputs without conflating differing report scopes or exactness.
- **Adaptive first-load sprint vs quiet refresh:** foreground initial/missing-data acquisitions can temporarily receive more capacity **only if measurements show net benefit and Watch remains healthy**; inactive/hidden periodic refresh must remain staggered, deduplicated, low-priority and backoff-aware. After the first usable result, reduce churn/CPU/IO and avoid rerender/rehydrate loops. Fast reentry should reuse correctly scoped fresh observations immediately.
- **Browser/PiP responsiveness:** measure actual time to first meaningful content, stable completion, layout/repaint on Models and Watch/Mini; do not make a faster backend feel slower through repeated full DOM rebuilding or excessive progress updates. Respect authenticated browser-interest leases; no background browser-owned scanner or second Mini Live owner.

## Required research, tests and benchmark workflow

### 0. Baseline and diagnostics — before optimization

- Pin the exact starting commit/version and use comparable workload fixtures with cold, retained-cold, warm and invalidated caches; distinguish real source churn from app changes. Capture *before* results for all target routes, not just one report. Repeat measurements (at least three comparable runs when practical) and record **p50/p95**, variability and min/max, not a cherry-picked fastest run.
- Build a low-overhead, opt-in, sanitized stage timeline: host/auth → first healthy Live → interest/queue → worker start/park/resume → source list/revision reads → messages/parts → analysis/cache → projection/serialize → HTTP/SSE → render/first usable. For Earlier log **verified/total roots, time-to-first-certified top-k, per-root retry/failure buckets, long-tail blocking roots and true source-change count**, without logging session titles, prompts, credentials, raw IDs or personal paths. Clearly separate first displayed retained evidence from **fresh proof**.
- Re-run or extend `development/tests/integration/probe_web_live.py --watch-cards` and `benchmark_history_readiness.py`; extend `benchmark_data_dispatch.py` and `probe_data_dispatch.py` as needed. Existing synthetic fast/slow comparisons are *leads*, not today's real baseline.

### 1. RED: reproduce the P0 functional regression

- Create a deterministic owned-source regression using thousands of roots, one delayed candidate, one repeatedly changing root, source-revision changes, and Full + Mini rendering. Under the pre-fix implementation demonstrate why the correct first winner set fails to materialize or becomes unavailable; keep a real failing assertion before production modifications.
- Also capture a **safe read-only real-source** reproduction when permitted/available, matching the user's `Loading → Unable to verify latest sessions` with source-stage timings/failure codes. A test reporting `INCONCLUSIVE` or legitimately unable due to missing local data is not a PASS. Do not assume the installed source is healthy without verifying supported read-only endpoints.
- Cover stable source, transient churn, continuous churn, slow but valid root, restart/revision change, source temporarily offline and zero earlier sessions. All must reach the correct *observed/retained/pending/unavailable* state without provisional publication. Give source failure states honest finite backoff and recovery.
- Validate a visible PiP with opener hidden, Full Watch expanded, foreground Model route vs simultaneous speculative report warm-up, mid-work route switch, immediate reactivation and close/host teardown.

### 2. Profile → hypothesize → experiment → iterate

- Run representative CPU/wall/IO/HTTP-count/memory profiles. Identify the dominant critical path and compare **several real alternatives**: e.g. better batch brackets, proof/certificate indexing, source reuse, priority/quanta changes, cache-layout improvements or targeted UI rendering. Preserve useful experiments that failed, regressions and causal evidence in `development/journal/web/`.
- Implement the smallest correct candidate(s), rerun the same workload and compare **before/after**. For every optimization record source calls, roots hydrated, retries/revision checks, p50/p95 usable latency, Live publication gaps, foreground response time, CPU and RSS. Reject “improvements” that merely skip work, use provisional historical winners, starve Live or make high-tail latency worse.
- Be thorough rather than optimizing to a short timebox. The owner explicitly permits **roughly ten hours or more of meaningful investigative/benchmark effort** on the implementation thread. A worker may and **should consult the Decision Delegate** when source-contract changes, a major architecture tradeoff, a blocked real reproduction, verification cost, safety constraints or correctness/performance tension require a choice. Request a decision *with options, measurements and risks*. Do not silently claim a prior exception applies; any genuinely necessary exception must be explicit, scoped, attributed and truthfully reported.

### 3. Quantified targets (ambitious goals, not pre-established facts)

- **Hard correctness gate:** Latest Earlier is really verified and displayed on a stable supported large source (including a live read-only probe if available); Full/Mini agree; no false-final lists, no unexplained healthy-source “Unable to verify” terminal result; retries/recovery behave correctly. If the source is truly unverifiable, a typed accurate error is permissible, but it cannot be used to disguise the reported regression.
- **Substantial speedup:** Aim for **at least 2× faster p50 first-usable Models** and **at least 3× faster first-certified Earlier** versus *matched original baselines* on a large representative workload. Prefer improvement at p95 too. Aim to materially reduce redundant full-catalog reads/long-tail waits and increase verified-roots/s. These multipliers are engineering targets; report exact attained improvements and tradeoffs, never re-label misses as PASS.
- **Switch responsiveness:** active tab/Mini interest promotion should take effect within a bounded scheduling quantum, not after a whole background scan. Measure **navigation-to-real-usable content** separately from navigation-to-progress and from returning a stale cached result. Background views must yield/continue safely and retain progress.
- **Protection:** no meaningful regression in active Live correctness/cadence, source-read security, foreground CPU responsiveness, bounded process/queue/memory or idle refresh rate. Quantify the tradeoff and obtain a Decision Delegate decision if the safe upper bound prevents achieving a target; never silently raise resource limits.
- **Cross-view:** show baseline and final cold/warm/foreground-under-load metrics for Models, Watch/Mini Earlier and at least Token Mix, AI Stats, Comparisons and Sessions. Report real-source vs synthetic evidence separately.
