# FR 000572 — Replace Watch Context with ECTX and a session summary, with incremental SQLite CCost cache

## Owner request and scope

**Owner-approved executable feature request, 2026-11-04.** Permanent identity **000572**, Ready priority **000120**, following current Ready FR000570 (000100) and FR000571 (000110).

Refine **CostGuard Web Beta → full Watch**, in **both the running/active prompt cards and Earlier Prompts**:

- Replace the per-prompt **Context** column with **ECTX**, directly before **Δ Ctx**.
- Under each prompt table, show the **session's current/next context size first**, then its **total full-session CCost**, on one compact summary line.
- **Integrate the context-price warning into that same line**; do not render a separate warning row below it.
- Persist and incrementally update the **full-session CCost** in CostGuard's reconstructible **SQLite cache**, so long histories are not repeatedly revalued and the cache can also support a future Sessions-page improvement.

This is a full **Watch page** change, not a Mini Watch change, a Sessions-page UI change, a CLI Watch change, or a change to global daily/account accounting.

## 1. Prompt tables: remove Context, add ECTX

1. Remove the present **Context** column (the per-row estimated **next** incoming context) from **both** Watch prompt tables.
2. Add the heading **ECTX** **immediately before Δ Ctx**. ECTX is the **effective incoming context size at the start of that particular prompt** (the established first-request/start-of-prompt incoming-context concept). It is **not** the estimated context for the session's next model call, a per-call/token-volume sum, or the Δ Ctx value.
3. Reuse the canonical prompt/source field and analysis already representing this concept (e.g. `incoming_context_tokens` / source `input_context_tokens`) with the existing compact context number formatting. Do not construct a separate estimate in browser JavaScript. If the first-request evidence is missing, display the supported unknown/N/A state; do not substitute a later call, a zero, or an unrelated continuation.
4. **No visible approximation/estimate decoration** in ECTX cells: no `~`, “estimated”, badge, extra estimate column or fabricated precision. Retain a **column-header tooltip/help explanation** on mouse, keyboard focus and touch/click that incoming context may be **estimated/approximate**, identifies what the value measures, and explains missing/N/A.
5. Keep every other existing per-prompt metric and its meaning, especially **Δ Ctx**, prompt-local CCost, Token Mix %, Calls, Started/Finished, Duration, model/effort and one-line behavior.

**Final shared table order:** **Started** (active) / **Finished** (Earlier), **Duration**, **Prompt**, **Model**, **Effort**, **CCost**, **Calls**, **Token Mix %**, **ECTX**, **Δ Ctx**. Still ten columns. Preserve prompt-only ellipsis, numeric column sizing and narrow-viewport horizontal pan. Update the shared CSS subgrid and any positional cell-index/event references; remove the obsolete Context-cell warning icon/update path rather than leaving dead branches.

## 2. One session line below each table, including inline warning

Immediately **below the prompt table**, before the existing active activity/tool/skill area, show **one logical summary line** for that card, with **session context first and total session cost second**. Example with no warning (numbers are illustrative only):

`Session Context: 123K · Session CCost: 4 582`

- **Session Context** means the existing canonical Watch **current/next incoming context estimate for the session's latest valid continuation**, honoring canonical context epochs, compaction, causal ownership and unknown/unavailable semantics. It is a *current session-level context estimate*, not the row ECTX value, not a sum over prompts, and not a generic last displayed row's old context. Keep the plain formatted number without an added approximation prefix. Expose its estimated-next-incoming meaning in accessible help/tooltip.
- **Session CCost** means **all cost attributed to the whole canonical root/session tree**: all historical and current prompt requests, requests before Watch/browser/server startup, compaction, supported child/subagent contributions and provisional running usage, without double counting. It must **not** be the single visible prompt, retained/earlier rows, Watch-run subtotal, daily total or provider billing. Preserve full-session canonical cost coverage: partial/unpriced/unknown are distinct from true zero, and the existing CCost unit configuration (Credits/USD), formatting and applicable partial-cost markers remain authoritative.
- When multiple live cards belong to the same session, show the **same session-scoped summary state** in each; never attribute one concurrent focal prompt's context warning to another. Share the aggregate calculation, not duplicate it.
- Prefer one physical line when space allows; wrap naturally on genuinely narrow screens or with a long canonical warning. Do not ellipsize warning details or numeric totals.

### Context price warning: integrated into the session line (latest owner refinement)

The existing full context-price warning **must be moved into the Session Context summary line itself**; there must be **no separate warning text row below the table**. Retain the existing canonical threshold/severity, relevant text and supported cost/multiplier impact; do not reduce a rich warning to an unexplained triangle.

1. **Normal:** show `Session Context: <value> · Session CCost: <value>` with ordinary colors, no triangle or warning text.
2. **Approaching threshold:** show a **gold/orange warning triangle immediately before the Session Context label or its value**, and insert the **canonical approaching-price-threshold explanation in parentheses immediately after the context number**, before the `· Session CCost` segment. For example: `⚠ Session Context: 123K (Approaching price threshold …) · Session CCost: 4 582`. Preserve any canonical impact details and the distinction between approaching and exceeded. Keep ordinary legible text color for the summary line at approaching severity; the triangle uses the existing warning color.
3. **Price threshold exceeded/crossed:** same inline structure, but say explicitly that the **price threshold has been exceeded** (with the canonical relative-price/cost details within the parenthetical explanation), and **color-highlight the entire summary line in the existing context-price-warning gold/orange role** — including the Session Context figure, parenthetical warning and Session CCost label/value. Use theme-appropriate legible warning foreground, not a distracting full-width colored background and not error/red coloring. For example: `⚠ Session Context: 201K (Price threshold exceeded …) · Session CCost: 4 582`. This is **context-price guidance**, not a claim that the session's already accumulated CCost is itself over a limit.
4. The warning/triangle is derived from the **valid session continuation**, with the same canonical approaching-percent setting, exact threshold crossing, model/tier and current owner/epoch rules as before. No warning is invented for unknown context; a compaction, newer prompt, changed model, corrected usage or invalidated continuation must update/downgrade/remove the warning atomically with Session Context. Never show a prior prompt's warning on the wrong session/card.
5. Keep tooltip/keyboard/screen-reader meaning, readable wrapping and semantic warning severity. Preserve canonical details previously shown below the table in the **inline parentheses or an equally accessible non-truncating continuation on the same logical line**, rather than silently dropping cost multiplier information. No duplicate warning footer remains.

The **active tool/skill/background activity** continues after the summary as before; historical cards have their usual compact presentation. Do not reintroduce the previous Session Total Duration metric.

## 3. Full-session CCost: incremental, persisted, reusable SQLite cache

The owner wants the whole-session total to be cheap on subsequent updates and when a session disappears from/reappears in Earlier Prompts. Implementation choices are delegated, but **persistent incremental reuse** is a requirement, not an optional optimization.

- **Canonical source of truth:** reuse CostGuard's shared reference-price valuation, causal prompt/root/child attribution and `ComparisonCost` completeness/provenance rules. The cache is **derived and reconstructible**; it is not a new accounting engine, billing ledger, data source or browser-side sum. Cache raw unrounded amounts/necessary partial-pricing metadata rather than a formatted UI string; the active CCost display unit is applied at render time.
- **Incremental updates:** after the initial build of a session, process **new and genuinely changed contributions** rather than re-analyzing/revaluing every old prompt for every new prompt, history reorder, card refresh or page tick. Corrections, late linked-child requests, aborted or resumed attempts, compaction and partial-to-complete transitions must amend/reconcile the right previously counted contributions instead of double-adding. Duplicate/replayed observations are idempotent; deletion/reclassification and changed historical data must invalidate or reconcile correctly. A revision change is an invalidation/checkpoint signal, **not** permission to assume the old total is always correct.
- **SQLite reuse:** use CostGuard's existing disposable generation-named SQLite infrastructure (`src/cache/database.py`, `src/cache/repository.py`). Prefer a versioned cache namespace if sufficient, or a narrowly justified new schema. Key/fingerprint data with the **source instance/root/session identity, canonical attribution/algorithm version and pricing/valuation identity**, together with source revisions or per-request checkpoints. Prevent cross-session, cross-source and stale-catalog mixing. Rebuild on cache miss, incompatible version or actual invalidation; preserve supported existing schema/generation behavior. Avoid persisting private content unnecessarily; only the minimal aggregate/contribution identity data needed.
- **Retention and reappearance:** once computed, a complete session total remains reusable if a session leaves the **five Earlier Prompts slots**, moves to Running, returns to Earlier after more activity, the disclosure is collapsed/expanded, a browser reload/reconnect occurs, or Web host restarts. A new prompt in an old session should update the existing total by the supported delta. Multiple cards for one session and multiple tabs share a single logical aggregate/source work owner.
- **Responsiveness:** build/reconcile totals in bounded, deduplicated **background work**, independently of the card's promptly available row/context and of live lifecycle, account/daily data and existing SSE cadence. First load may show a localized truthful `Loading…`; stable known values should not flash back to Loading during normal refresh. On real partial pricing, source failure, stale revision or unavailable cache, expose accurate state, never fabricated completeness. Optional SQLite lock/corruption/unavailability must follow established safe degradation rather than crash Live or invent a total. Do not add per-card browser polling, per-tab aggregation or database writes on presentation-only ticks.
- **Future Sessions reuse, not a Sessions redesign:** make the derived aggregate/cache contract reusable by Sessions later, but **do not modify the Sessions-page UI** or bypass its existing canonical full-history report within this FR.
- **Prove the efficiency:** test/report a long-session first build versus one new prompt, no-op refresh, re-entry into Earlier, same-session concurrent cards and host restart. Instrument enough read/valuation/cache work to demonstrate that a no-op/redraw/history-membership change does **not** trigger a complete history revaluation, while changed request cost and pricing changes still produce the correct whole-session number. Exact cache schema, per-prompt contribution strategy and invalidation details are implementation decisions.

## Inspected baseline and previous FR boundaries

- **FR000542** once proposed complete session totals; **FR000545** explicitly removed them **and the expensive dedicated aggregate phase** for Watch. This **newer approved FR narrowly supersedes FR000545's removal for *Session CCost only***, contingent on genuinely incremental persisted caching. - **FR000570** (Mini Watch native icon) and **FR000571** (Mini Watch CTX tilde / daily CCost Today labels) remain separately queued. Do not change Mini Watch, its CTX estimate, daily headings or full Watch's global `CCost Today` label under this FR.

## Acceptance and verification

1. Active and Earlier prompt tables both have exactly the **ten headings in the requested order**, with `ECTX` immediately before `Δ Ctx`, **no `Context` column**, ECTX values faithfully representing per-prompt start context, and estimate explanation only in header help. N/A/unknown, numeric formatting, keyboard focus and responsive layout work.
2. Under each table is **one compact Session Context · Session CCost summary**. Both metrics are session-scoped; the context matches the latest valid continuation, and the cost covers **all** root-tree historical and current usage regardless of visible rows/Watch startup. No Session Total Duration.
3. Approaching warning: inline colored triangle, canonical parenthetical explanation **right after context value**, normal row text. Exceeded warning: inline triangle/explanation, **entire line warning-colored** (including Session CCost). No separate context-warning footer, loss of price-impact detail or stale/wrongly owned warnings. Compaction/threshold-crossing and recovery update the display coherently.
4. One session with thousands of prompts, late child costs, concurrent active prompts, older Earlier re-entry, resumed prompts, corrected/partial telemetry, missing prices and selected Credits/USD maintains the correct canonical full total with no double counting. Displayed totals equal the independent full-session report for equivalent revision/valuation/coverage.
5. Persisted incremental cache survives process restart and eligible reappearance. Unchanged history refresh and redraw avoid full revaluation; cache invalidation on source/catalog/algorithm change yields corrected totals, not stale ones. Cache failure is safe and states remain honest.
6. No regression to active-card visibility/cadence, Earlier selection/ordering, live updates, source/auth privacy, warning severity, responsive CSS/subgrid, existing account/daily summaries, Mini Watch, CLI Watch or Sessions page.
7. Extend focused deterministic Python cache/valuation/context and Watch-projection tests and JS/DOM/browser rendering tests, including approaching/exceeded colors, text placement, accessibility, narrow/wide/light/dark rendering and performance/no-op work counts. Update current Watch documentation (`docs/web-beta.md` and other affected current help); **do not rewrite historical completed FRs**.
