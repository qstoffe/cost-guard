# FR 000683 — Mini Watch: self-healing hover tooltips when pointer-exit events are lost

**Ready to Develop — owner-requested, 2026-11-12.** Priority **001020**. Main objective: no mouse-hover tooltip in Mini Watch (or any other shared Web help surface) should remain visible indefinitely after the pointer has left, **even if no `pointerleave`, document exit or window blur event is delivered**. Add an active-while-open, bounded *fail-safe*, not another event-only attempted fix.

## Owner observation / problem

Intermittently, a tooltip in the separate **Mini Watch Document Picture-in-Picture window** is still visible much later despite the mouse having left that window. The owner has noticed it after rapidly passing the pointer across Mini and into another window/app. There is no reliable on-demand reproduction. It is easy to mistake the abandoned tooltip for current UI, and it obscures a small Mini Watch.

A previous request already targeted *this same problem*: **FR000587**, completed on 2026-11-05. Its implementation replaced an `activeElement`-dependent hover lifetime with shared hover/focus/pinned origins and additional `pointerout`, `pointerleave`, `pointermove`, window `blur` and DOM-removal handling. Deterministic and headless actual Document PiP cases passed. **However, the real physical Windows pointer transition out of PiP/browser chrome/to another application was not tested** (explicit FR000587 verification exception). The current owner still encounters an occasional orphaned popup. The previous fix is useful but *insufficient in practice*; do not conclude success just because the same simulated exit handlers pass again.

### Code assessment on current `main`

- `src/web/assets/help.js::ContextHelp.controller(doc)` owns **one manual, text-only Popover per document**, including separate PiP. It distinguishes `origin === 'hover' | 'focus' | 'pinned'`. Mouse hover starts after **600ms**; a leaving trigger/panel starts a **150ms** grace timer.
- `leave()`, `exit()`, the document `pointerout`/`pointerleave` and outside `pointermove`, and window `blur` can close *only after some relevant event occurs*. **There is no independent revalidation timer while a hover tooltip is open.** If every exit event is lost (or opening is pending when the pointer silently leaves), the panel has no reason to close; `refresh()` continues to update/reposition the active panel rather than dismiss it.
- `src/web/assets/mini.js` uses the **same** `ContextHelp` controller in its own `win.document`; Mini's unrelated five-second UI freshness interval must **not** be repurposed as the only tooltip guardian. Fixing only `.mini-summary` would leave row/header/quota tooltips vulnerable.
- Existing `development/tests/integration/web_help.cjs` and `probe_help_lifecycle.cjs` exercise event-driven exits, including deliberate missing *trigger* leave with a delivered *document* exit. They do **not** establish recovery when **all** leave, outside-move and blur events are absent. The exact OS/browser trigger of the owner's intermittent incident is still unproven.

## Required behavior: lifecycle-owned hover watchdog

1. **Open-only watchdog.** When a tooltip is actually visible because of **pointer hover**, start **one small per-document check**, approximately once per second (`setTimeout` self-scheduling or equivalent). Each check must independently reconsider whether the pointer can still be over the active trigger's exact `pointerTarget` **or intentionally over the tooltip itself**. If not, dismiss the hover tooltip and clean up its ARIA/popover state. It must work even if there has been **no new pointer or focus event at all** since the tooltip opened.
2. **Do not rely exclusively on exit events.** Use current browser hover/hit-test state where supported (e.g. `matches(':hover')` on the actual trigger/panel, not the full enclosing button/card; recent trustworthy in-document pointer position + `elementFromPoint` can be additional evidence). Revalidate connectedness, document/visibility/window lifecycle and active target identity; preserve the existing 150ms trigger→panel transfer allowance. **A last-known mouse position is not perpetually valid evidence**: a pointer can leave PiP without another observable event.
3. **Guarantee a finite stale-hover escape hatch.** Some browsers can retain stale `:hover` after a cross-window move, and a webpage has no general OS-wide mouse-location API. A check that trusts an indefinitely stale CSS hover flag is *not* a complete fail-safe. If continued genuine pointer presence cannot be independently confirmed, terminate the hover-owned popup after a **bounded orphan/idle lease** rather than retaining it forever. Choose a measured, modest cap/grace that favors normal stationary reading; a new *actual* pointer interaction can rearm it, but a polling tick, stale `:hover`, timer reset, focus or Live redraw alone must not extend the lease. Explicitly document the unavoidable tradeoff where the browser does not provide external pointer coordinates. Do not add surprising global timeouts to deliberate keyboard/click-pinned help.
4. **No always-running timer.** Never create a permanent app-wide one-second poll. Stop/cancel exactly the owned watchdog immediately on `close()`, Escape, action click/dismiss, transition to focus or pinned ownership, active-target replacement, hidden/pagehide, Mini PiP close/reopen or document teardown. Only one watchdog can exist per live hover tooltip/document; no accumulating timers on repeated hover/refresh/Live updates. It must not perform HTTP requests, scan sessions or wake Python/host work.
5. **Protect the 600ms opening delay too.** If the pointer sweeps across a trigger and immediately leaves Mini while `pointerleave` is silently missed, the delayed open must **not** materialize an orphaned tooltip 600ms later. Revalidate target hover/ownership before opening; if browser state is inconclusive and it opens, the watchdog must still remove it promptly. A fast flyover must not create a permanently visible tooltip.
6. **Keep intentional interactions.** For a genuine stable pointer on the label or inside the help panel, normal hover help stays readable while trustworthy presence is observed; moving between label and panel retains the small grace. Intentional **keyboard-focus** help and **click/touch-pinned passive** help are separate owners, not automatically dismissed simply because no mouse is over them. Keep Escape/outside-click/blur behavior, source-aware refreshed help, focus and text selection, `aria-describedby` cleanup, and the existing one-Popover-per-document contract. If a hover popup is dismissed, it should not magically reopen due to a rerender or stale callbacks; a *new intentional* hover/focus action may reopen it.
7. **Shared ownership, Mini-first acceptance.** Prefer changing the **shared `ContextHelp` state machine** in `src/web/assets/help.js` so Mini PiP and ordinary Web/Full Watch inherit the same safety property. Apply any narrow CSS/document changes only if required. Do **not** introduce a second tooltip component, browser extension, OS mouse hook, extra Mini UI interval or rewrite of tooltip copy/layout.

## Acceptance tests that do not depend on reproducing the real bug

**This FR is explicitly a defensive lifecycle correction.** Do not make an exact naturally reproducing user incident a precondition for implementation or verification. Build deterministic missed-event tests to prove the fail-safe exists and has bounded behavior, then supplement with real-browser tests.

- **Missing every exit event:** Show a hover popup, silently move the simulated pointer away / change the test hit-test truth **without dispatching trigger `pointerleave`, `pointerout`, `pointermove`, document exit or window `blur`**. Assert it disappears due to the watchdog within a small bounded number of ~1-second checks; its `aria-describedby` is restored/removed, Popover hidden and timer count returns to zero. This is the key new regression; simply firing `pointerout(null)` is not adequate.
- **Stale hover signal:** Hold `:hover` falsely true with no further genuine pointer evidence. Demonstrate the bounded stale-lease escape hatch instead of a popup lasting forever. Conversely test a genuinely stationary/readable hover and an actual trigger→panel pointer transfer to avoid gratuitous one-second flicker. State the observable limitation rather than claiming exact OS cursor truth from mocked selectors.
- **Opening race:** Simulate a silent exit during the 600ms hover delay; no permanently orphaned popup may appear. Include rapid target A→B, re-entry, and timer cancellation, ensuring an old delayed tick cannot close a newly opened different target.
- **Focus and pin:** Keyboard focus without a mouse remains usable; an explicit passive touch/click pin can remain until its normal dismissal action; Escape and action activation stop hover/other owned timers without focus theft. Pointer-triggered focus must not accidentally convert a stale hover popup into permanent keyboard ownership. Repeated Live `ContextHelp.refresh` and active row changes must not reset an expired hover lease.
- **Lifecycle and cost:** Assert one active watchdog per hover popup, none while all help is closed and none for focus/pinned-only help. Exercise parent main document versus separate PiP, PiP close/reopen, pagehide, hidden document and removed trigger. Check no retained intervals/callbacks, no network/report work and no unexpected background cadence.
- **Real browser:** Extend the actual Chromium/Edge Document PiP and Full Watch help probe with **a deliberately suppressed/missed native exit path**, not just the already-passing synthetic `pointerout` fallback. If a safe physical Windows pointer test of PiP→browser chrome→another app is available, record its result separately; if not, state **UNVERIFIED** and do not pretend headless CDP is the same as physical OS event delivery. Normal real pointer hover, panel transfer, touch, keyboard, Classic/Web themes, zoom, viewport positioning and Mini tooltips should still pass.

## Implementation / documentation pointers

Start with `src/web/assets/help.js` (`controller`, `show`, `close`, `enter`, `leave`, `exit`); update `development/tests/integration/web_help.cjs` (virtual-clock and hover-state simulation), `development/tests/integration/probe_help_lifecycle.cjs` / `probe_web_help.cjs` plus relevant Mini browser coverage. Update `development/architecture/modules/web-help.md` and `development/journal/web/contextual-help.md` with the resulting lifecycle rule, actual verification and any browser limitation. Check `docs/web-beta.md` only where its user-facing help behavior needs updating.

**Non-goals:** new help content, more `?` icons, new Mini data cadence or report jobs, periodic work with no visible hovered tooltip, changing Python/Watch accounting, operating-system mouse hooks, or a promise to reproduce the intermittent real-world event before developing the safety mechanism.

**Done means:** a hover-origin tooltip in Mini Watch **cannot be orphaned indefinitely** merely because exit events fail to fire; an active-only ~1s watchdog **and** independently testable bounded stale-signal fallback actually enforce that property, existing intentional keyboard/pinned help and performance remain intact, and missing physical OS proof is honestly disclosed.
