# FR 000677 — Web secondary quotas: estimate Weekly and Monthly Capacity from usable period CCost

**Owner-approved Ready Feature Request, 2026-11-11.** Permanent identity **000677**; Ready queue priority **001100**, after the currently Ready FR000675 (001090). **Backlog publication only:** add this FR and advance `development/backlog/identity-state.json` highWatermark **676 → 677** in one direct-`main` commit. Do not implement product code, run product tests, modify releases/versions or rewrite unrelated backlog tasks during this publication.

## Owner report and desired result

In **Cost Guard Web → Accounts** (also the shared **Full Watch** subscription cards), a **Claude Pro** account's **secondary Weekly** quota displays about **7% used ($10.20 reference CCost)**, while both **Weekly Capacity** and **Monthly Capacity** show **?**. Hover/focus gives only `No reliable same-window reference CCost or source-confirmed full-window allowance.` The owner expects the same useful **guesstimate** behavior already supported for primary quotas, including secondary, tertiary and subsequent quota windows.

For illustration **only if $10.20 is a meaningful same-window reference Used amount and 7% is the exact native used fraction**, the raw full-week estimate is `$10.20 / 0.07 = ~$145.71`; its standardized **30-day equivalent** is `~$624.49`. The displayed 7% and USD amount may be rounded: use the **raw native fraction and raw Credits/Decimal cost**, not those UI strings. These are *reference CCost projections*, never actual provider dollars, an entitlement or a guaranteed spending limit. Apply the product's existing estimate rounding and `~` presentation.

**Outcome:** usable, properly scoped secondary-quota usage should produce a numeric estimated period Capacity and, when the recurring duration is known, the derived Monthly Capacity. Do not let a blanket completeness requirement turn an informative partial estimate into `?`; equally, do not manufacture a number from incompatible data.

## Source inspection: existing path and likely exclusion

- `src/accounts/claude_code.py::normalize_claude_usage()` creates an **account-scoped `seven_day` rolling quota with `duration_seconds=604800`**. A secondary quota is not intrinsically ineligible for a Capacity estimate.
- `src/analysis/period_ccost.py::quota_window()`, `src/reports/accounts.py::_period_scopes()`, `src/application/watch_accounts.py` and `src/application/projection.py::quota_record()` attach the relevant observed reference CCost to each native quota/window. Account attribution may be qualified estimated attribution, especially for Claude Agent → Claude Pro; completed FR000673/v81.24 already improved that route.
- `src/application/quota_ccost.py::quota_ccost_values()` can show **`ccost_used` from `cost.known_ccost` whenever some requests are priced**, yet its ratio Capacity requires **`cost.get("complete")`** as well as native fraction, freshness, active/reset window, matching scope, positive observed CCost and coherent native facts. Therefore a visible positive CCost and a native percentage can coexist with unknown Capacity. `monthly_values()` then necessarily returns unknown Monthly Capacity too.
- The current `development/tests/test_web_quota_ccost.py::test_unreliable_or_out_of_window_ratio_is_unknown_not_zero_or_negative` explicitly treats partially priced `ComparisonCost(100, 3, 2)` as unknown. This is a **confirmed code-level exclusion**, but **not yet proof** that it caused the owner's specific live card; missing full-period history, an attribution/window mismatch or another input can also explain `?`.
- `src/web/assets/account-cards.js` and `src/web/assets/render.js` render those shared rows and the generic unknown tooltip; they should consume the same server-owned reference result, not compute an alternative estimate in JavaScript.

## Required change

1. **Trace the actual blocker, then fix the estimate path.** Reproduce the reported shape: current active secondary Weekly with raw positive native-used fraction, positive parenthesized CCost, but unknown Weekly/Monthly Capacity. Inspect its normalized scope, exact reset/start, matching `period_ccost`, `known_ccost`, observed/priced request counts, source coverage, attribution and `capacity_basis`. Report the real reason(s); do not simply assume partial pricing is the only cause.
2. **Use qualified partial evidence for an explicitly approximate result.** Keep the existing complete-data ratio path. Where an active quota has a valid raw native fraction **greater than zero**, a **positive priced CCost subtotal actually tied to that same account/provider, quota scope and source-defined window**, and no contradiction or account ambiguity, permit a **provisional ratio guesstimate even if some in-window requests lack prices**. The existing `cost.complete` flag by itself must not automatically suppress a usable positive estimate. Make its partial coverage/provenance visible **concisely on the Capacity tooltip** (e.g. “Estimate from priced requests; unpriced usage may make this low”). Never describe the subtotal or extrapolated result as verified provider allowance. Reuse the existing estimated-attribution semantics for uniquely compatible Claude Pro requests; no silent allocation across multiple accounts.
3. **Do not disguise genuinely missing or mismatched evidence.** Keep `?` when no meaningful positive same-window CCost is available, the native used fraction is unknown/zero, period/reset evidence cannot establish the matching window, quota/source is stale or contradictory, or pricing/account/scope mismatch makes the numerator unsuitable. If multiple causes exist, fix an incorrect data join/history or attribution first. Avoid new arbitrary thresholds, provider-plan dollar constants, a new parallel estimator or blanket conservative checks.
4. **Make Monthly Capacity follow the corrected period estimate.** For a qualified nonmonthly recurring quota, calculate `raw period Capacity × 2,592,000 / verified duration_seconds` using **unrounded Decimal**, and show the existing **`~` 30-day theoretical equivalent**, not an actual monthly allowance. A genuine native monthly quota retains its single native-period row. If period Capacity is unavailable, keep Monthly unknown with an informative reason.
5. **Clear, source-specific unknown explanations.** Replace the one-size-fits-all capacity `?` tooltip with a brief actionable reason for the actual missing evidence (for example: no period cost, partially priced/no usable sample, unverified matching window, account attribution mismatch, inactive/resetting window). When a partial-but-usable estimate is shown, explain its lower-confidence origin once rather than hiding it or dumping technical metadata. Preserve the separate Used/Remaining and Capacity/Monthly tooltip responsibilities delivered by FR000663.
6. **Consistent account cards.** Apply the behavior to primary and every genuine secondary/later source quota on **Accounts** and **Full Watch** (same shared renderer), preserving the existing visible Capacity rows from FR000661, correct `~` marking, 5% estimate display tolerance, native progress/percent/reset, Credits↔USD, Used/Remaining setting, hover/focus/touch, Live updates and retained card identity. Do not accidentally reuse primary-window CCost for a secondary or aggregate independent restrictions.

## Acceptance / regression

- **Positive secondary weekly, fully priced:** synthetic 7% raw Used, 1,020 raw reference Credits ($10.20), valid 604,800-second window ⇒ raw Weekly Capacity `1020 / .07 = 14571.428… Credits` (≈$145.71) and raw Monthly `×30/7` (≈$624.49), with the existing display rounding/`~` and exact raw inputs in Capacity tooltips. Same for a comparable primary and an independent later quota, without cross-window leakage.
- **Partially priced but meaningful:** 3 matching observed requests, 2 priced, nonzero same-window subtotal, valid native fraction ⇒ show a **clearly qualified provisional estimate**, not `?` solely because `complete=false`; disclose partial basis. Separate controls with no priced requests, unknown/ambiguous account, missing history, wrong window, model-scoped quota lacking a reliable model ID, stale/inactive/resetting quota and native 0% Used remain honestly unknown as applicable. A genuinely verified native allowance remains exact, never ratio-inferred.
- **Raw vs rounded:** vary the native raw fraction slightly while the card still visibly reads `7%`; calculations must follow raw fraction and raw CCost, not visible `7` or rounded USD. Check source refresh/reset, partial→complete upgrade, USD/Credits and both Used/Remaining orientations. Unknown tooltip must identify the actual reason.
- **Regression ownership:** extend focused `development/tests/test_web_quota_ccost.py`, `development/tests/test_account_period_ccost.py` and appropriate shared Account/Full Watch DOM/browser fixture tests; verify independent primary/secondary identities and current Claude Agent subscription attribution after FR000673. Use synthetic/read-only evidence; no paid model calls are needed for this feature. Preserve existing source-native and CCost Today accounting.

**Not in scope:** changing Claude provider quotas/entitlements, actual billing, global cost/session pricing rules, new monthly subscriptions, unrelated cards or implementing FR000675. This FR is an estimate-eligibility and explanation correction, **not** a new restriction framework.

**Done means:** a secondary weekly quota with a useful matching positive CCost sample and native percent yields truthful `~` Weekly and standardized Monthly Capacity estimates, even with partial pricing when clearly marked; truly unsupported cases retain `?` with a specific reason.
