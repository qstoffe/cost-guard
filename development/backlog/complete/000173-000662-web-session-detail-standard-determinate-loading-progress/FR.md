# FR 000662 — Web Sessions: replace bouncing detail loader with centered, determinate report-style progress

**Owner-approved Ready Feature Request, 2026-11-09.** Permanent identity **000662**, Ready priority **000970**, after FR000661 (000960). The owner-promoted FR000651 (000001) remains the highest Ready priority. **FR-only publication:** add this file and advance `development/backlog/identity-state.json` highWatermark **661 → 662** in one docs-only `main` commit. No product code, tests or release modifications during FR publication.

## User problem and desired result

On **Cost Guard Web → Sessions → click/open one session**, the detail view currently displays **"Loading session…"** inside a conspicuous yellow/brown `warning` status box with a native indeterminate `<progress>` that animates/marquees/bounces back and forth. The owner observes visibly jumpy, broken-looking motion. Replace this one-off loader with the same clean **centered, determinate 0–100% report-loading UI** already used on **Models, Token Mix, AI Stats and Comparisons**, with the best possible **truthful, granular** progress and a short current-stage label.

The longer-term design preference is **one standardized loading visual language across all Web routes**. This FR implements that **specifically for single-session detail loading**, reusing existing shared components and CSS rather than independently redesigning every other route or changing unrelated progress logic.

## Verified current code and root of the visual issue

- `src/web/assets/session.js::SessionDetail.View.constructor()` creates `this.status = el('p', 'Loading session…', 'warning')` and sets `role="status"`. It appends it inside the detail page before the history table; `.warning` in `src/web/assets/app.css` applies warm warning text/background and a prominent border. Normal loading is **not** a warning.
- `SessionDetail.View.loading()` creates `el('progress')` and sets only `aria-label="Loading session"`; it **never assigns a `value`**, so the browser is instructed to render an **indeterminate/native marquee animation**. `freshness()` calls `loading()` while the first detail snapshot is absent and `sourceStatus()` can call it on subsequent loading polls, potentially reconstructing the element and restarting the native animation.
- The standard `src/web/assets/report-loading.js::ReportLoading.View` builds an ordinary **`<progress max="100" value="0">`**, numeric percent, short stage and polite status region. The `src/web/assets/app.css` `.report-loading` already centers this presentation with the right spacing, and explicitly disables progress animation. **Reuse that visual pattern and shared code wherever practical.**
- The session-detail API does not currently expose a universal percentage for *source readiness*. `session.js::load()` uses `POST /api/detail` actions **open → begin → chunk**. A successful `begin` has `data.total`, initial `data.result.view.prompt_blocks[0].rows`, `revision` and `state`; subsequent `chunk` replies supply additional rows and the same revision/total. Thus there is a **real, measurable per-session history transfer denominator**, but not necessarily a measured denominator for initial source acquisition/wait.
- `src/application/session_detail.py::SessionDetail.page()` intentionally returns `result: null` while pending/not yet acquired and otherwise returns source-qualified paginated history. The current live detail view may contain retained data on a later refresh. Do **not** invent a source-acquisition count, secretly rescan history or alter canonical acquisition to make the bar look busier.

## A. Presentation: one centered standard loader, no yellow warning

1. **On first opening a session without usable detail data**, display one `report-loading`-style panel **centered horizontally and vertically within the available detail content area**: a stationary-width standard determinate progress bar, legible **0–100%** text and a brief status such as `Opening session…`, `Waiting for session source…`, `Loading session history (X of Y)…`, `Preparing session…`. It should look like the Models loading view, not a special Session-themed warning/card.
2. **No indeterminate or marquee animation whatsoever** for this loading path: no native `<progress>` lacking `value`, bouncing highlight, CSS transform loop, or artificially elapsed-time animation. Each rendered loading bar must have explicit numeric `max=100`, bounded `value` and accessible numeric status/valuetext. Do not visually flash/restart the bar on successive loading polls.
3. Remove the use of `p.warning` (golden/yellow box, accent border/background) for **normal session loading**. Legitimate terminal **error/source-unavailable** warnings may keep appropriate warning/error presentation, with concise reason and existing retry/navigation affordance. Preserve the `Show all sessions` link and avoid duplicate global-toolbar loading/warning boxes.
4. Keep one **stable keyed progress DOM instance** throughout the first-load lifecycle; update values/text in place rather than destroying/recreating the element each `freshness()`/`sourceStatus()` call. Maintain a steady bar width, text alignment, accessible `role=status` / `aria-live` announcements of **stage changes** (not every integer increment), focus-safe lifecycle and Classic/Web light/dark styling.
5. **On successful first render**, show 100% **only after** complete valid history has been acquired and the user-visible rows are ready, then remove the loading panel naturally in favor of the real session detail. Do not introduce artificial delays so a fast-loading session visibly pauses just to show the bar. Keep existing scroll/focus/selection preservation where relevant.

## B. Honest, granular progress across real phases

**Progress must represent actual completed work, never a decorative estimate disguised as a measured percentage.**

1. **Initial admission and source readiness:** track the supported `open`, `begin`, session-source `loading`/`pending` and any meaningful source-side progress events if already available. Early stage labels explain what is genuinely happening, with a `0%` baseline or a small, *clearly phase-bounded* completed-admission contribution where warranted. **While the source is waiting with no measurable fraction, leave the value at the last verified point and update the stage**; no bouncing, arbitrary time-based fill, invented root count or automatic crawl. If implementing a shared phase-budget mapping (like `ReportLoading.observe`), treat percentages as **overall phase progress**, not a claim of a known number of pending upstream actions. Avoid jumping to 80% merely because a source request is queued.
2. **History pagination:** after a valid `begin` response, use its **actual total row count** and cumulative rows successfully returned from `begin` and each verified `chunk` to advance smoothly in real increments, including sessions with large histories. Example: if 50/200 rows are delivered, indicate the true completed fraction of the **history-transfer phase**, such as `Loading session history (50 of 200)…`. Do not display 25% of the *entire* task unless phase weights make that honest and explicit in the code. Use stable monotonic progression per coherent `revision`, avoid counting duplicated/retried chunks twice, and never reach 100% before valid final assembly.
3. **Rendering:** after final chunk, use a short genuine `Preparing session…`/render stage if rendering meaningful rows is still pending. If row construction/yielding can report actual completed row counts without redesigning the data model, expose these granular counts too; if not, a short stage and last measured percent are sufficient. Mark 100% on applied success, not on first server response.
4. **Freshness/polls:** a later 5-second poll of an already rendered session **must not erase the visible history or re-show the initial center loader**. Retain the previous usable data through background source acquisition, refresh and recoverable errors, with quiet appropriate freshness/error feedback. A coherent new revision can replace/update rows when complete, without reinitializing first-load progress. Only a genuine new route/opening with no usable data starts at 0.
5. **Lifecycle/cancellation:** delayed responses from an abandoned detail view/session must not update the newly selected session's bar. Preserve `generation`, attached-state and token/revision guards and safe chunk ownership; handle `detail_expired`, inconsistent history, source shutdown, authorization changes, unavailable source, empty/zero-row sessions and quick tab/Back navigation correctly. Never block other routes or create repeated API requests simply to animate the UI.

### Progress example (illustrative, not a requirement to fake exact phase percent)

```text
                    [██████████░░░░░░░░░░░░░░]  46%
                    Loading session history (86 of 220)…
```

An already observed `X/Y` denominator is real; the sample `46%` is an **illustrative total-stage-weighted percentage**, not a mandated formula. The implementer chooses and documents any bounded phase weights consistent with real work. On source waiting without counts, the stage text changes but the bar **does not falsely advance**. Initial zero-row content may complete immediately.

## C. Shared style, narrow accessibility contract and focused tests

**Likely ownership:** `src/web/assets/session.js::SessionDetail.View` (`loading`, `freshness`, `sourceStatus`, `load`, `update`); `src/web/assets/report-loading.js::ReportLoading.View` (prefer reuse of the shared visual controller without coupling session source ownership to finite report-job admission); and `src/web/assets/app.css` (reuse `.report-loading` styling, small session-only placement adjustments if needed). The `src/application/session_detail.py` paged source API already supplies reliable count/offset/revision; add only a tiny read-only progress field if an authoritative, useful source phase signal is demonstrably needed. No unrelated backend, Live/SSE, model costing or session pricing changes.

**Acceptance criteria:**

1. Clicking a session from Sessions catalog opens a **centered Model-style** progress display **without any yellow/brown warning box or animated/bouncing marquee**. DOM and computed styles confirm determinate `progress[max=100][value]` and shared standard sizing; the old valueless `progress` is absent from this route.
2. At first load, progress starts at **0%**, increases monotonically from true admission/pagination/render work to **100% on successful completion**, then hands off directly to session content. Unknown source-readiness waits are labeled clearly and **do not produce invented percent/time-based advancement**; 100% cannot appear on partial/inconsistent history.
3. A controlled 0-row, one-chunk and multi-chunk session (e.g. **220 actual rows**) demonstrates meaningful increment-by-increment progress with exact displayed `X of Y` transferred counts. Repeated `loading` polls do not recreate/reset the bar or restart animation. The status is readable, unobtrusive and screen-reader friendly.
4. Normal session refresh with retained data preserves the existing history, focus, scroll and context line instead of replacing it with the first-load loader. Network outage/recovery and initial terminal errors show truthful feedback and working return/retry behavior.
5. Test rapid session A→B navigation, leaving/back, hidden tab, source waiting/partial/recovered, `detail_expired`, changed revision, invalid chunks, empty session and genuine shutdown. No stale updates, stuck `aria-busy` or cross-session percent, duplicated source calls, infinite visual progress or unhandled errors.
6. Verify in a **real browser** at 360/768/1366/1920 widths and 100/125–150% zoom under Classic and Web light/dark, hover/focus/keyboard/touch and reduced-motion settings. Standard Models/Token Mix/AI Stats/Comparisons loaders remain visually and functionally unchanged; the Session detail path reuses the same style.
7. Update relevant session-detail JS DOM, API paging and browser progress tests (and only necessary docs). Preserve session data accuracy, paginated source verification, export, context help, user selection and the established 5-second polling cadence. Do not introduce paid inference or new source scans.

**Outcome:** a calm, standardized, genuinely informative session-loading experience consistent with the other Cost Guard Web report pages, and no more visually broken marquee.
