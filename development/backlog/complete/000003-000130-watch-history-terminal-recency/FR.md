# FR 0130 — Keep newly finished Watch prompts in history by terminal recency

## Observed problem and evidence

In **global Watch**, an older, long-running prompt may remain active while several prompts that started later finish. When the older prompt finally finishes or is aborted, Watch briefly shows its lime-green successful-completion marker (or the applicable terminal status) for roughly 30 seconds. After that recent-event window expires, the prompt can disappear altogether instead of entering the **bottom/newest position of the historical section**. There may already be enough more recently started prompts to fill the configured dashboard cap. The user suspects the observed termination may have been initiated by a plugin, but that cause and the presence/absence of a native terminal timestamp have **not been established**.

**Code-level evidence at authoring (v80.67):** `src/watch/tracker.py` uses `_sort_key` based on `_Observed.display_time_ms`, ordinarily the prompt's **start** (or a continuation/compaction placement boundary). `src/watch/session_retention.py::select_rows` applies this key to the global `watchDashboardMaxRows` selection **before** grouping historical and active sessions. Running and finite recently highlighted rows are temporarily protected. After their highlight expires, a long-running, recently finished prompt competes as an ordinary row using its old start position and can be evicted. Conversely, `WatchRowTracker._session_state` and `docs/watch-activity.md` already use the latest supported terminal end for a **historical session header/group order**. This mismatch is a plausible, concrete explanation for the disappearance **even if a correct terminal time was available**. Do not assume the plugin is the root cause without investigating the source evidence.

## Required behavior

- **Global Watch historical retention:** A terminal prompt/event that Watch observed should compete for the limited historical rows by its **reliable finish/terminal time**, not by when it began. A prompt started earlier but finished most recently must survive ahead of older completions when capacity is limited. The historical section remains chronological oldest-to-newest, so its newest qualifying session appears at the bottom. Use consistent temporal semantics for row-cap selection and historical session ordering; grouping must not hide a newly completed prompt simply because its original start was old.
- **Correct transition:** While running and while the existing finite success/abort/error highlight is in effect, preserve current active/recent ordering and soft-cap protection. When the highlight expires, the row should enter historical selection using terminal recency on that **same refresh**, without an intermediate disappearance, special extension of the green marker, forced pinning forever, or a new timer. A subsequent newer completion may evict it normally under the existing cap. Keep contiguous session blocks and established prompt/compaction order *within* each session; distinguish selection recency from row display sequence.
- **Terminal evidence and plugin paths:** Inspect V1/V2 normalization and Watch lifecycle for natural completion, explicit user stop/abort, failure/cancellation, and plugin-initiated stop/termination. Where a native, causally matched terminal timestamp exists, propagate its correct immutable value to the source-neutral prompt projection and use it. Do not misclassify abort/error as success, or lose an observed prompt when a V2 post-compaction projection stops including it. A session status change or plugin activity alone is not proof of a particular prompt's completion timestamp.
- **Missing end evidence:** If the source provides no trustworthy end, do not invent or persist a native finish time using elapsed duration, session metadata updates, inactivity, disconnect/reconnect, polling, or highlight expiry. Preserve the established honest end/start fallback for displayed historical timestamps. If a **confirmed running-to-terminal transition is actually observed by Watch**, a single immutable, explicitly Watch-local terminal-observation time may be used **only as a bounded retention/recency fallback**, not presented as a source-authenticated finish timestamp. Prefer authoritative terminal evidence if it later arrives. If the terminal transition itself is unproven, retain the deterministic existing fallback rather than manufacturing a completion. Document any such ranking/display distinction.
- **Scope/invariants:** Keep `watchDashboardMaxRows` as a **global soft prompt-row cap**, with running/recent protection; do not introduce a permanent session cache, separate history list, migration or persistence ledger. Keep startup `[Earlier]` baseline selection/one-shot eviction, session-specific Watch ordering, context/compaction chronology, report Duration semantics, run Token Mix/CCost, quotas, source read-only policy, terminal outcome labels and Watch geometry unchanged outside the necessary recency fix. Reuse existing normalized boundaries and tracker/retention ownership rather than teaching presentation or analysis raw plugin/provider fields.

## Ownership and implementation guidance

- **Session Source / normalization** owns any needed trustworthy terminal signal or correction for V1/V2/plugin-initiated termination. Audit the real supported event/part data before modifying it; do not create a provider-specific assumption inside core analysis.
- **Analysis/projection** owns the source-neutral terminal-time contract and remains the single authority for a true end, with unknowns represented honestly.
- **Watch tracker/retention** owns a history-specific selection key (and, only if needed, an observed-once local fallback) distinct from the active/recent display-position key. Apply it consistently before global cap selection and session grouping, while preserving per-session visible order and stable tie-breaking.
- **Documentation/presentation** should reflect actual timestamp semantics without representing a Watch observation as a native completion. Inspect the current implementation at execution time; these filenames identify responsibility, not mandatory edits.

## Focused deterministic regressions

1. Small cap: prompt A starts first and runs a long time; B, C and D start **after** A and finish **before** A. A then finishes successfully with an authoritative end newer than all of them. Assert the full recent-marker interval protects A, and after expiry A still appears in the historical section and is selected/ranked as the newest finished prompt/session, instead of disappearing.
2. Repeat for native manual abort, confirmed plugin-initiated terminal/abort event, and terminal error; preserve correct permanent `[ABORTED]`/`[ERROR]` outcomes and finite color/tool activity. Include a test proving no false success is inferred from a plugin or ordinary tool call.
3. Native terminal time supplied on a later snapshot/revision: initially unknown-end transition, then authoritative end arrives; historical recency updates once and stabilizes. Repeated polling, account-only redraw, title change, source resync and expiry must **not** renew a terminal timestamp or change order without new evidence.
4. Confirmed terminal transition with missing source end, no confirmed terminal transition, and a true connectivity gap. Verify conservative/explicit fallback behavior and no fabricated analysis/report end or Duration.
5. Interleaved prompts in the **same** session, compaction plus continued prompt identity, disappeared zero-call post-compaction row and equal timestamps. Preserve chronological internal prompt/compaction ordering, stable ties, correct session header, and global-cap selection from all eligible rows.
6. Startup `[Earlier]`, history eviction when genuinely newer completions exceed the cap, excess protected rows, `watchRecentEventSeconds=0`, session-scoped Watch and ordinary reports remain compatible. Use existing synthetic Watch/source fixtures; no personal session exports or real plugins/network are required.

## Acceptance criteria

1. A long-running prompt that finishes after newer-started prompts does not vanish on exiting the transient green/red highlight solely because of its old **start** timestamp; it occupies the newest appropriate historical position while it belongs to the global cap.
2. Completion, cancellation/abort and errors work alike for recency while retaining distinct terminal semantics; plugin-driven termination is investigated and covered by a verified synthetic path, not assumed to be the cause.
3. Reliable native ends are used when present; unavailable ends never become falsely authoritative or drift with Watch polls. Any Watch-local fallback is one-time, narrowly scoped to confirmed transitions and visibly documented.
4. Existing protected-row cap, active/recent start ordering, historical block grouping, internal prompt chronology, `[Earlier]`, costs/Duration and report invariants remain intact.
5. Relevant focused tests, environment-appropriate Quick/Full and package validation pass; update Watch behavior docs and the eventual implementation PR's `src/version.py`, README and `VERSION_HISTORY.md` according to then-current maintainer policy. **Do not assign an implementation version in this FR.**
