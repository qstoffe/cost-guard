# FR 000340 — First navigable Web Beta and static session reports

## Outcome and dependencies

After FR000300, deliver a usable first HTML interface rather than a mockup. Apply FR000200 before claiming parity for provisional running metrics. OS launchers can be developed independently; this UI must work from both the explicit development Web entry and the Beta launchers once available. Follow FR000290/PLAN.md. Visual details are intentionally delegated to the implementation agent and later owner feedback.

## Required behavior

- Create a coherent application shell with a clear Beta label, current source/status, navigation and browser Back/Forward/deep-link behavior. Proposed sections: Overview, Live, Sessions, Models, Accounts, Reports and Token Mix. Merge adjacent menu sections if that improves clarity, but retain reachable equivalents of all report modes. Not-yet-implemented areas are clearly unavailable, not empty success or fabricated sample data.
- Deliver the normal overview, session list and one selected session's static detailed report first. Use live API results from the shared application facade; no parsing CLI text, invented screenshot values, browser-to-OpenCode calls or separately implemented cost calculations. Keep all assets local and usable from source ZIP/clone without a user-side frontend build.
- Keep recognizable CLI concepts, column meanings, model/effort labels, warnings, pricing notices, account distinctions and CCost versus billing. Improve presentation using accessible HTML, readable spacing, sticky headers, appropriate light/dark contrast and responsive overflow. Pixel matching of terminal ASCII borders is neither required nor desirable.
- The session table uses the established eight columns: Prompt, CCost, Calls, Duration, ~Ictx, ~Ictx CCost, ~Extra CCost and I/C/W/O %. Preserve chronological prompt/compaction placement, linked child contribution, model transitions, error/abort/running evidence and totals. Session-ID links open the corresponding report; session names/prompts are escaped text. Do not expose hidden credentials or local filesystem paths as tooltips.
- Static is genuinely static: capture an explicit report result with its observation time. A prompt that was running is marked running **at that snapshot**, with FR000200's supported provisional metrics, not a live timer. An explicit Refresh obtains a new snapshot; neither source activity nor navigation events silently mutate a frozen report. Do not start global Watch just because a selected prompt is running.
- Keep report values and complete totals independent of visible row count. Session listing/detail can load bounded pages or virtualized portions, but every available row must be reachable and pagination must not reinterpret a session total as a page total. API cursors/results are revision-aware so inserts cannot silently skip or duplicate records. Do not import global Watch's row cap.
- Loading, source unavailable, account unavailable, partial data, no matching session and a genuinely empty session are distinct states. A reachable Web shell is not proof that data is healthy. Preserve the last known result with visible stale status when appropriate, not a spurious zero. Missing/archived session behavior must agree with report semantics, not blindly copy global Watch exclusions.
- Keep interaction state local to the view without persisting private prompt/history payloads in browser storage. URL navigation may identify the session but must never contain authentication/provider secrets. Keep keyboard navigation and text selection useful; transient refresh messages must not steal focus.

## Acceptance

Exercise real UI/API integration on synthetic fixtures for empty/long/running/completed/aborted/compacted sessions, unknown pricing, Unicode and hostile HTML-like text. Compare displayed meanings/totals to CLI for the same projection and clock. Test direct session links, browser refresh/back, narrow/wide layouts, missing source and deliberate snapshot refresh. Confirm that a frozen report and its duration do not change when new source events arrive. Verify normal CLI behavior without any web environment.

Provide a small working UI and a concise description of implementation-owned layout choices for owner testing. No approval of a perfect design is needed before delivery; no mockup or screenshot substitutes for a working route. Live acquisition arrives in FR000350/000360 and remaining report views in FR000370. Do not add editing of OpenCode, an account-login workflow, analytics, remote hosting or a new permanent test/release gate.
