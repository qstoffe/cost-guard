# FR 000559 — Fix recurring quota-stopped prompt intermittently reappearing as running in Web Watch

## Owner report and backlog decision

**Owner-approved executable Web Beta correctness bugfix, reported 2026-11-03.** Permanent identity **000559**; Ready priority **000080**, after FR000558 (000070). This is **separate** from the prompt-table and Token Mix presentation feature. It concerns the server-owned Running Prompts lifecycle, and its Web/CLI parity.

**Concrete observed symptom:** At **2026-11-03 18:29 Sweden local time (CET)** the owner could still see a Web Beta Watch prompt as running, showing approximately **22 hours 20 minutes** of age. Its start was **2026-11-02 at 20:09 CET**. The owner reports the model as **Claude Sonnet 5.5, Effort Low**. The prompt stopped because the account hit its **quota limit** and did **not finish normally**. **CLI Watch no longer lists it as running**, but Web Watch often does; the stale running card sometimes disappears and later comes back. Prompt/session/attempt IDs, the exact persisted terminal evidence, and installed Web host vs CLI revisions have **not** yet been supplied or verified. These times describe the user's observation, not a validated source event sequence or proof that the model was processing for 22 hours.

**Required outcome:** once authoritative source/canonical lifecycle evidence establishes that the relevant attempt is no longer active, Web Watch must not preserve, resurrect or indefinitely re-display it as Running. Web and CLI observing the *same* attempt and comparable fresh source revision should agree on active/terminal state. Preserve actual final usage and the supported end reason; do not fabricate success after quota exhaustion.

## Why this is a new report despite two completed FRs

- [FR000546](../../complete/000056-000546-web-watch-terminal-lifecycle-parity/FR.md), delivered v80.125, reconciled quota/interruption outcomes and retained authoritative terminal evidence between Web capture and CLI. Its completion did **not** reproduce the owner's exact historical quota incident.
- [FR000551](../../complete/000061-000551-web-watch-stopped-prompts-still-running/FR.md), delivered v80.129, fixed an additional four-worker capture **scheduler starvation** defect: changed early roots could repeatedly win slots and leave later retained Running cards without fresh terminal observations. Its regression cases covered quota stops without final usage, zero-usage interruptions and abandoned continuations. Again, its completion explicitly says the **owner's affected prompt/host and source were not verified**.
- The new **2026-11-02 → 2026-11-03** observed recurrence, including **disappearing and reappearing**, is new owner evidence. Do not reopen history or assume those earlier fixes were ineffective; equally, their historical completion does not justify declaring this new symptom solved. The running Web server might be an older build, or there may be another unhandled capture/retention/reconciliation/race condition. Determine which.

This FR is about **fixing or conclusively explaining that concrete mismatch**, rather than imposing a blind elapsed-time cutoff.

## Investigation and required behavior

1. **Verify which code is actually running.** Establish the WebHost-reported product version/revision (not merely current GitHub `main`), CLI version/revision, source type and actual canonical session/root/prompt/assistant-attempt identity if accessible via safe existing diagnostics. Compare the same source and similar observation time; test with a cold Web view and after a refresh/reconnect. Distinguish an outdated installed host, a browser retention artifact, insufficient source refresh and genuinely incorrect lifecycle analysis. Do not claim a current-code regression from a screenshot alone.
2. **Reconstruct the particular quota-stopped attempt.** Use read-only, sanitized, minimally scoped source snapshots or fixtures for the reported start, missing normal finish, failure/quota evidence and any subsequent assistant/tool events. Trace source normalization → causal completion/retirement → capture scheduling/generations → retention/accepted card state → immutable export → browser DOM. Identify *how* the Running label persists or **reappears**: e.g. no accepted fresh capture, an old running snapshot overwriting terminal state, mixing two attempts, misidentified continuation, or a stale browser/host. These are hypotheses, not diagnosed causes.
3. **Respect authoritative termination semantics.** On the first accepted complete authoritative evidence that an attempt ended, publish a nonrunning state and freeze running duration; do not include it in active/running totals, live tools or Mini Watch running metrics. A finite terminal highlight may remain under existing grace rules, without restarting on every refresh. Historical usage/CCost and Earlier Prompts must not be deleted merely to remove the Running badge.
4. **Prevent resurrection across lifecycle boundaries.** Cold startup after termination, an uninterrupted Web view, page reload, disconnect/reconnect, a session/catalog revision change, delayed or out-of-order worker results, retention fallback and another root's updates must not restore the *same* terminated attempt to Running. A genuinely new assistant attempt or resumed supported work must still be allowed to appear running under its correct identity; no cross-attempt termination or suppression.
5. **Avoid false positives.** An old start time, missing final usage, quiet tokens, another prompt starting, displayed quota reaching 100%, transient source outage or a row omitted from a partial snapshot is **not by itself** authoritative proof of termination. Preserve legitimate slow tools, child agents, background operations, in-flight steps and incomplete/unavailable source truth. Distinguish confirmed quota abort from an unproven/unknown end reason. Do not introduce an arbitrary age timeout, new quota-provider polling, or browser-only CSS/JS filtering to camouflage a server-state defect.
6. If the installed host is simply too old, verify that a current version with the **same canonical case** behaves correctly, record the supported version-specific explanation and what the owner needs to update. Do **not** claim a new bug fix without demonstrating a current-code defect. If current code reproduces the mismatch, repair the responsible owner rather than closing this as “already fixed by FR000546/551.”

## Acceptance and regression evidence

A speculative heuristic or just repeating old tests is not sufficient to claim a code fix.

It must show **Web active → terminal and never back to active for the same attempt** across repeated accepted updates, page reload/reconnect and earlier-history transitions; running duration/counters stop while known token/CCost history remains.
3. Cover multiple eligible roots competing for the existing **four capture slots**, catalog revision churn, stale generations, failed/partial captures, quota abort without priced final call, interrupted/abandoned continuation and a genuine later live attempt. Verify that fixes from FR000546 and FR000551 remain intact and avoid starving valid work.
4. Compare CLI Watch, Web Watch and Mini Watch's shared canonical active state for equivalent snapshots. Do not let a frontend-only disappearance count as success while server Running metrics remain wrong; do not label a quota-failed attempt `Completed` merely to hide it.
5. Execute relevant focused and normal product tests plus applicable existing read-only Web integration/probes, recording actual coverage, remaining uncertainty and any source access limits. No authorization is given to resume/abort real prompts, send model requests, change subscriptions, restart the user's shared OpenCode service or alter account quota state.
