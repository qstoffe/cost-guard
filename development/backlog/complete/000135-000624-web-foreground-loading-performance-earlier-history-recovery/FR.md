**Owner-approved Ready Feature Request / P0 reliability + P1 full-system mega-optimization + P2 reliable prewarming, 2026-11-07; owner scope escalation same day.** Permanent identity **000624**; Ready queue priority **000420** (the queue is currently otherwise empty). ## Why this is urgent — owner-observed symptoms

The recent change to start/warm all useful Web views in the background (FR000617, v80.197) delivered the desired *concurrent loading intent*, but the owner now perceives the **initial loading of essentially every page to be much slower**, especially:

1. **Models:** on a fresh Web launch or first visit, the model list takes far too long to finish. When Models is visible, its initial data should get the fastest safe service; inactive views should not compete for the same critical path.
2. **Full Watch → Earlier Sessions and Mini Watch → Earlier Sessions:** opening/expanding historical sessions takes an extremely long time.
3. **New, blocking functional regression:** Mini Watch now shows **“Loading…” followed by “Unable to verify latest sessions”**, rather than the actual latest earlier sessions. This is not merely a cosmetic progress issue. Full Watch and Mini consume the same server history; investigate both, not just the Mini notice.
4. **General responsiveness:** navigating to a page that was warming in the background should immediately promote its existing work and make it usable as rapidly as possible. Inactive tabs can take much longer to finish, provided their work continues opportunistically and does not steal capacity from the foreground.

The owner explicitly distinguishes **fast first usable load and foreground promotion** from periodic refresh: once a view is usable, its passive refresh can be deliberately gentler and slower to avoid sustained CPU/IO saturation. **Never “fix” speed by ceasing all background warming**; keep the intended all-pages-warm behavior, but enforce real foreground-first scheduling and source-efficient acquisition.

The two problems belong in **one FR with an early P0 correctness/availability gate and a substantial P1 measured performance phase**. Do not close it as a successful performance improvement if Earlier remains unavailable on a healthy, readable real source, or merely because a synthetic fixture passes.

## Owner escalation: this is a major performance recovery, not a limited tuning pass (2026-11-07)

**Superseding product acceptance intent:** The owner reports that the new background-loading design made cold/foreground loading **roughly 20× slower by observation, potentially much worse in places**, with multiple views sometimes never becoming usable. This ratio is a **user estimate, not a measured engineering result**. The owner did not request a trade of responsiveness for background work. The actual product objective is **(1) correct, reliably usable data, (2) first-load performance substantially *better than before FR000617*, and (3) all useful views warmed efficiently so switching to them is near-instant when their data has finished warming.** An implementation that merely recovers some fraction of the regression, passes a synthetic benchmark or makes background tasks run concurrently is **not accepted**.

### Owner clarification — no computation-duration fallback, and progressive honest loading (2026-11-07)

**Superseding acceptance clarification for the currently selected FR000624.** This is an update to the same task, not a new Ready selection, discard/restart of the worker's existing changes, or permission to reduce independently proven history correctness. The owner explicitly rejects any Web data-loading path that changes from loading to `unavailable` / `Unable to load` / `Unable to verify latest sessions` **solely because a computational or completeness deadline expired**. This rule applies across **all in-scope Web routes and their shared loading backends**, not only Mini/Full Watch: Models, Watch/Mini Earlier, Token Mix, AI Stats, Comparisons, Sessions, Accounts and prewarming/promotion.

**Separate elapsed processing time from real faults.** A normal, healthy, supported data source with a finite but expensive catalog, slow valid session, backlog or pricing/analysis workload is **not broken** simply because 5, 30, 90, 300 or any fixed number of seconds have elapsed. If valid computation/proof remains feasible, the app must keep the task pending and making bounded progress, retain already-verified useful information and eventually show the correct result. A computation or all-roots/history-certification deadline must not become a terminal UI failure, hard abort, invisible exception, expired state requiring manual Retry or a different time-named cop-out. A view may remain in meaningful loading/progressive state for arbitrarily long elapsed time (even days, in principle), and user-visible Stop/close/cancellation and real source identity changes still work correctly. **This is a lifecycle requirement, not permission to spin CPU, busy-poll, accumulate unbounded memory, hammer an upstream service or obscure a deadlock indefinitely.** Use resumable/periodic bounded work, fair scheduling, useful diagnostics, throttled progress/backoff and recovery; design away real stalls. If an existing internal watchdog must recover an actually wedged worker, it may restart/recover owned work **without declaring valid user data unavailable merely from the elapsed timer**. Avoid turning a recoverable timeout into infinite rapid retries.

**Allowed distinct failures:** Connection establishment, network/HTTP/provider quota calls, OpenCode API access, authentication, malformed/unsupported source schema and genuinely terminated services can have **bounded I/O timeouts and typed error/retry behavior**. A failed read can be retried/backed off; when independently established as a genuine source/service failure, show an accurate error with an appropriate recovery path. Do not camouflage an expensive but healthy read as a network failure, use a network request timeout as the global work-deadline, or convert a transient I/O timeout into a permanent proof failure on an otherwise healthy source. Missing authoritative evidence remains pending/unverified; it never turns into a fabricated result. The user distinguishes an actual fault from "this work took longer than we allowed".

**Systematic targeted cleanup inside this FR:** Trace source-level, scheduler/worker, application/job, API/HTTP/SSE and browser/UI loading paths that currently convert *elapsed processing/proof duration* into `unavailable`, `Unable`, `source_unavailable`, abort or manual Retry. Preserve intentional per-I/O request timeouts and cancellation for resource safety; classify each timeout by its actual purpose. No new general-purpose guard, timeout inventory database, universal time-budget validator or unrelated cleanup gate. Demonstrate the real state transitions through existing relevant test infrastructure.
