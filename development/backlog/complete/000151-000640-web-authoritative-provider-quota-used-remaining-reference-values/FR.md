# FR 000640 — Web Accounts / Watch / Mini Watch: provider-authoritative quota Used and Remaining amounts

**Owner-approved Ready Feature Request, 2026-11-09.** Permanent ID **000640**, temporary Ready priority **000810** (after existing Ready FR000639, priority 000800). This publication is **FR-only**: add the backlog document and advance the identity high-watermark from 639 to 640. No product implementation, tests, release/version, user settings or other backlog modifications now.

## User-observed problem and intended rule

In **Cost Guard Web** the account/subscription quota line shows a **Used or Remaining percentage** and a **parenthesized CCost amount** in the selected CCost unit (Credits or USD). Full **Watch** account cards, the **Accounts** account/quota presentation and the **Mini Watch** subscription lines must all agree.

For a subscription with **a real, trustworthy provider-reported finite quota/allowance that can be converted to the canonical CCost reference scale**, especially **GitHub Copilot's included monthly AI credits**, the number in parentheses must describe **that same provider's own quota Used or Remaining** — **not Cost Guard's independently observed OpenCode-session CCost**. Usage outside OpenCode can consume the provider allowance, so the locally observed cost may be lower, higher, differently attributed or not priceable at all.

- In **Used** mode, show the provider-reported **used allowance**, converted to the chosen CCost display unit.
- In **Remaining** mode, show the provider-reported **remaining allowance**, converted to the chosen unit.
- The **quota Capacity** amount and any **Remaining/day** or **Remaining/workday** values must use **the same provider-authoritative quota/capacity/remaining basis**.
- The provider's Used/Remaining percentage and progress bar already express the native quota: keep their meaning and pair them with the **matching converted native amount**, not an independently observed estimate.
- A **percentage-only** subscription (no provider-reported convertible finite allowance) may retain the established **observed-period-CCost / native-fraction ratio estimate** and its honest estimate/unknown conventions. Do not turn those plans into fictional provider-credit balances.

**Illustrative example, not an assertion about a real account or a plan price:** Copilot reports a finite **10,000 included AI-credit capacity**, **3,000 used**, **7,000 remaining**. With **Credits**, the paired parenthetical amounts are **(3 000)** in Used and **(7 000)** in Remaining, with **Capacity: 10 000**. With **USD**, the same unchanged provider values render **($30.00)** Used, **($70.00)** Remaining, and **Capacity: $100.00** (current reference CCost conversion **100 Credits = $1.00**). The quota percentages are **30% used** / **70% remaining**. The figures stay the same even if Cost Guard observed only 450 Credits of attributable OpenCode requests in that period. If the actual provider values are different, use the actual reported values, not these examples.

## Source-level findings in the current repository

1. **`src/application/quota_ccost.py::quota_ccost_values()`** currently assigns **`used` from `period_ccost.cost.known_ccost`**, i.e. observed same-window OpenCode CCost. For normalized **`github-copilot` / `github-copilot-enterprise`** account-scoped fixed monthly **AI credits**, it separately sets a **native** reference `capacity` from the provider `limit`, and **`remaining` from the provider remaining or limit − native used**. Thus **`ccost_used` and `ccost_remaining` can have incompatible provenance** within the same quota card; the existing help explicitly says their sum need not equal Capacity.
2. For `reference_ccost_capacity` with `basis="native"`, the current implementation sets `capacity` but does not always derive the matching **provider-based Used/Remaining**; this should be addressed for any **verified source-to-reference mapping**, not only hardcoded Copilot cases. A string resembling “credits” alone is **not** a valid mapping.
3. **`src/application/quota_ccost.py::quota_ccost_pace()`** (completed **FR000638**) already uses accepted `quota_ccost_values().remaining` to calculate Web CCost per-day/workday pace. It must automatically inherit the corrected, authoritative **remaining** basis and keep the same native calendar counts, rather than add a second incompatible calculation.
4. **`src/application/quota_display.py::quota_displays()`** owns normalized native Used/Remaining percentages and quota facts, independent of pricing. **`src/application/projection.py::quota_record()`** and **`src/application/watch_accounts.py::watch_quota()`** bind the quota and its own period projection; retain that identity/window coupling.
5. **`src/web/assets/account-cards.js::quotaTrack()`** renders `quota().quota_display[mode].percent` alongside `display(quota(), 'ccost_' + mode)`, and renders `ccost_capacity` and CCost pace. This component is shared by full Watch and Accounts' account cards. **`src/web/assets/mini.js::View.drawAccounts()`** independently selects the same `ccost_used` / `ccost_remaining` tokens for Mini Watch. The appropriate correction is **one source-of-truth server-side projection**, not two client-only conversions.
6. **`src/application/display.py::with_display()`** prepares `display_units.credits` and `display_units.usd`; **`src/numbers.py::ccost_amount()`** handles the existing canonical Credits-to-reference-USD conversion and rounding. Reuse it. The Web display preference must not mutate quota/source facts, mix units, or turn native quota credits into actual dollars billed.
7. Completed **FR000585** intentionally used observed CCost for parenthesized Used and provider native credits for Remaining. **This new owner request explicitly supersedes that part of FR000585 for source-verified convertible finite provider allowances only.** Preserve the older estimate contract for percentage-only quotas.

## Requirements

### A. Authoritative provider amounts for convertible finite allowances

1. **Select the basis by validated quota evidence, per quota window.** When the source reports actual used/remaining/limit for a finite included allowance and its relationship to canonical reference CCost Credits is verified (e.g. the existing **Copilot monthly account AI-credit** case, or an explicitly source-verified `reference_ccost_capacity` with a valid fraction/amount mapping), derive **provider-based reference Used, Remaining and Capacity from the same provider snapshot**. Do not substitute local OpenCode period `known_ccost` for either side. Keep each primary/secondary/model-specific quota distinct, with its own period, provider/account identity and reset.
2. For directly equivalent **Copilot AI credits**, a trustworthy source-reported `used` is the reference Used amount and source-reported `remaining` is Remaining; if one is omitted, a **coherent** known full limit and the other amount can supply its complement. If only a reliable remaining/used fraction plus a **verified convertible capacity** is reported, multiply by that capacity in raw Decimal precision. Prefer directly reported amounts over rounded UI percentages. Do not derive Used by subtracting an **observed OpenCode CCost** from provider Capacity.
3. For a **verified reference capacity of a different native unit**, only use the source's valid native amount-to-limit ratio (or accepted explicit mapping) to scale that verified reference capacity. Never assume raw **messages, tokens, requests, currency, arbitrary generic “credits”, Copilot API spend or paid overage** are CCost Credits just because they are finite or similarly named. The destination value must remain **reference CCost equivalent**, not a claim about dollars paid.
4. For a **true convertible source-proven allowance**, guarantee consistent semantics within the same fresh coherent window: **reference Used + reference Remaining = reference Capacity**, subject only to genuinely documented provider rounding/overage and final display rounding. The **percentage, amount, Capacity and pace** must not silently come from four unrelated bases. Do not force equality by clamping an actual overage or inventing a missing balance; preserve native overage/contradiction indicators.
5. Source states matter: a stale, expired, blocked, invalid, incoherent, unlimited or missing native amount must not be presented as a newly observed authoritative balance. Known **zero** is 0, not `?`; missing is not 0. Keep existing retained/unavailable behavior and distinct native quota/provenance diagnostics, avoiding false proof of an entitlement. Unknown/unsupported conversion must not silently fall back to OpenCode observation while still being presented as the provider's actual Used/Remaining; show an honest unknown or clearly separated estimate according to the existing applicable contract.

### B. Percentage-only subscriptions and independent OpenCode CCost

6. **Retain the existing percentage-only estimator** where supported: observed, sufficiently priced **same-window OpenCode CCost** represents Used; an eligible reliable native Used/Remaining fraction can estimate Capacity and Remaining. Keep **(guesstimate)**/tooltip/unknown handling where already appropriate. No inference of a real provider-credit limit, and no extrapolation at 0% Used with no known capacity.
7. **Do not change `CCost Today` or historical prompt/session costs.** Those remain observed, attributable reference costs from OpenCode. They may intentionally differ from a source-authoritative quota Used amount if usage occurred in other clients. Do not retroactively assign external provider usage to OpenCode sessions, billing, or per-prompt cost. In tooltips, clearly distinguish **“provider-reported quota Used/Remaining, converted to reference CCost units”** from **“OpenCode-observed period CCost estimate”** without adding long visible disclaimers.
8. The Web **Quota display: Used/Remaining** option changes **both** percentage direction and the accompanying numeric amount to that same direction. Web **CCost display: Credits/USD** only formats the same raw reference value. The two setting switches are independent and update promptly in full Watch, Accounts and an already open Mini Watch without source refetch or phantom budget changes.

### C. All account presentations and remaining pace

9. **Full Watch and Accounts:** for all applicable account cards, including primary and secondary quota sections, render **`X% used (<provider-based reference Used>)`** or **`Y% remaining (<provider-based reference Remaining>)`** as selected, and keep each card's **Capacity**, progress track, account name, native quota help and reset correct. Account cards should use the same shared projection/renderer and not show different values for the same quota.
10. **Mini Watch:** the compact account/subscription row must use exactly the same corrected source-prepared Used/Remaining CCost tokens and settings as full Watch; its primary quota percentage, parenthesized amount, progress bar and accessible **Capacity/Next reset** help must agree. No independent Mini-side multiplication, provider read or local-history cost re-estimation.
11. **Remaining/day and Remaining/workday** (when the quota has supported calendar pace) are derived from the **same provider-reported Remaining converted to reference Credits**, then divided by the existing native days/workdays calendar and formatted in the selected unit. Do not compute pace from Cost Guard's observed OpenCode spending or an incompatible ratio when provider-authoritative remaining is available. Preserve **0 workdays**, reset/expiry and omitted-when-unknown behavior from FR000638. Any other displayed remaining capacity/allowance number must follow the same source.
12. **Reference display units are not provider cash.** Use `ccost_amount`/prepared `display_units`, including the existing **100 Credits = $1.00** reference conversion and reasonable final formatting. Preserve full Decimal precision before conversion and day/workday division. Do not call live FX rates or suggest SEK, provider billing, Copilot subscription charges or additional spending.

## Verification / definition of done

- **Synthetic Copilot provider-vs-local mismatch:** provider reports 10,000 reference-equivalent monthly included Credits, 3,000 Used, 7,000 Remaining, while observed OpenCode period CCost is deliberately **450 Credits**. In **Credits** mode display **30% used (3 000)** / **70% remaining (7 000)** and **Capacity: 10 000**. In **USD** display **30% used ($30.00)** / **70% remaining ($70.00)** and **Capacity: $100.00**. Prove this exact matching presentation in full Watch, Accounts and Mini Watch, including a switch while all views are live. Do not change `CCost Today` (the separate local metric).
- **Native-fact variants:** one missing `used` but coherent `remaining+limit`; one missing `remaining` but coherent `used+limit`; credible source fraction and verified reference capacity; zero Used, zero Remaining, a valid partial quota, source refresh/reset and 0 remaining workdays. Confirm reference values are sourced from the native quota, not independent `period_ccost`.
- **Separation of two quotas:** primary Copilot monthly and a secondary quota, or two distinct account/provider quota windows, cannot inherit one another's `limit`, `used`, `remaining`, raw CCost or reset. Include both direct monthly Copilot units and `reference_ccost_capacity` mapping. Unknown or conflicting native facts must not be manufactured into equality.
- **Percentage-only control:** a rolling percentage quota with observed period CCost 100 Credits and a reliable 10% native Used fraction may still estimate **100 Used / 900 Remaining / 1,000 Capacity (guesstimate)**; in USD **$1.00 / $9.00 / $10.00** with appropriate estimation disclosure. Confirm the code does not falsely choose the provider-authoritative branch without a verified convertible allowance.
- **Unsupported native units and safety:** fixed quota expressed only in tokens/requests/messages/monetary billing with no supported reference conversion, exhausted/over-limit, unlimited, zero or absent limit, incomplete pricing, partial/stale/error/expired sources, contradictory fractions or amounts, rounding, large values and external-only usage. Preserve provider-native evidence in help/diagnostics and never display an unverified converted allowance as a fact.
- **Consistent surfaces/settings:** all full Watch/Accounts account-card primary/secondary rows and Mini primary row show equal appropriate tokens/progress for the same quota in both Used/Remaining × Credits/USD. Existing **CCost Today**, per-prompt CCost, rows, quota percentage, layout and existing Settings default/overrides remain correct. Unit changes do not fetch extra quota data.
- Extend focused Python regression coverage in **`development/tests/test_web_quota_ccost.py`**, **`test_web_quota_pace.py`**, **`test_web_watch_quota.py`**, and applicable quota normalization/projection tests. Extend shared account-card Watch/Accounts DOM fixtures and **`development/tests/integration/mini_watch.cjs`**, **`probe_quota_display.cjs`** or equivalent real browser PiP verification. Update **`docs/web-beta.md`**, **`docs/web-mini-watch.md`** and relevant account help descriptions during implementation, not during FR authoring.

## Scope / implementation boundary

Prefer a narrow correction in **`quota_ccost_values()`** and its source-verified mapping/projection so `ccost_used`, `ccost_remaining`, `ccost_capacity` and `ccost_pace` share one coherent basis and the existing `display_units` reach every Web renderer. Do not duplicate accounting in JavaScript, change CLI native quota semantics, invent provider APIs/allowance prices, fetch external usage outside permitted existing source paths, change history accounting or introduce new workers, storage, dependencies, banners or a new Settings option.
