# FR 000635 — Mini Watch: cohesive header, filled Earlier Sessions toggle, and Settings option-help wheel scrolling

**Owner-approved Ready Feature Request, 2026-11-08.** Permanent identity **000635**, Ready priority **000815** (immediately after related Web cleanup FR000634 at 000810, before FR000629 at 000820). **FR authoring only** now: create this standalone Ready FR and increment the identity high-watermark; do not change running product code, tests, release/version, active OpenCode/PiP windows or unrelated backlog in this publication.

## Owner-observed problems and exact desired UX

### A. Mini Watch header looks like three unrelated controls

In the separate **Mini Watch** Document Picture-in-Picture window, the top row contains **Cost Guard · Watch | Earlier Sessions | CCost Today <amount> · <N> prompts**. The owner reports that the middle Earlier Sessions control is squeezed awkwardly between the other two, its **vertical alignment and font** are inconsistent, and at small window sizes the header wraps/lands in unattractive places. The arrow preceding Earlier Sessions adds visual noise. The whole header looks as if assembled by three different designers.

**Desired:** a visually unified compact header: matching font family, calibrated text size, line-height, vertical centering, spacing, padding and semantic visual weight for all three pieces. It must look composed rather than merely "technically fitting" in a single row.

**Replace the chevron/arrow-style disclosure with a proper two-state toggle button** labelled **Earlier Sessions**, whose label *never changes*:
- **Collapsed (default on opening Mini Watch):** an unfilled/outlined or subtle button; Earlier Sessions table is hidden.
- **Expanded:** the **same button is clearly filled/selected** in a theme-compatible color; the Earlier Sessions table is shown below. Clicking again returns it to unfilled and hides the table.
- **No leading `›` / `⌄` chevron or replacement text**, no appended On/Off, no new status/progress copy. Make the selected fill itself communicate the state.
- Preserve mouse click, touch, Enter/Space, focus visibility, clear accessible `aria-pressed` as well as correct `aria-expanded` and `aria-controls`; maintain disclosure and history demand semantics.

### B. Settings option descriptions cannot be wheel-scrolled from the option

On **Web → Settings**, a supported Chrome/Edge customizable **Value** dropdown displays the hovered or focused option's long description in a scrollable panel beside the choices. Currently, when the pointer rests on an **option label/list item**, rotating the wheel does not scroll that option's long explanation. The owner can scroll only by moving the pointer *onto the description itself*, which on unselected options can cause the hovered option (and therefore its description) to disappear. This also makes the already selected option inconvenient.

**Desired:** when the picker is open and a description is visible/scrollable, **wheel scrolling anywhere over its associated choice/option should scroll that choice's description immediately**, without requiring the pointer to cross into the description area, without changing the highlighted option or committing a different setting. The selected and unselected options must behave consistently. The normal scrollbar and direct scrolling over the description must continue to work too.

## Confirmed code-based findings (visual incidents still require rendered reproduction)

1. `src/web/assets/mini.js::View` places `this.summary`, `this.earlierToggle` and `this.daily` as three siblings inside `.mini-header`. `src/web/assets/mini.css` defines `.mini-header` as `display:flex; justify-content:space-between; flex-wrap:wrap` with distinct `gap`. The title is a link-like button, Earlier is another button, and Today is a right-aligned paragraph.
2. Their sizes/styles are not unified: `.mini-summary` and `.mini-daily` use `font-size: .8rem` but `.mini-earlier-toggle` uses `.75rem`; the title has its own `align-self:flex-start` and padding; the toggle receives separate button padding/min-height. The `::before` pseudo-element switches `›` to `⌄`. Those differences and independent flex wrapping provide a credible structural explanation for the reported uneven baseline/spacing, but the owner's specific pixels have not been captured here.
3. `mini.js` already owns **nontrivial layout measurements**: `headerWidth()` measures inert header clones in both Earlier states, `OpeningMeasure.read()` requests a fitted PiP width with 8px reserve/gutter, and `DisclosureSize.toggle()` permits one bounded user-activated height-only native adjustment (with one-DIP width-rounding correction). Existing `fit-on-open` and `remember-last` modes depend on the real header. A cosmetic CSS tweak alone is insufficient if it breaks these constraints.
4. Settings uses **native customizable select**, not the shared floating `ContextHelp` tooltip, when available: `src/web/assets/settings.js::enhancedPicker()` and `View` build `select.settings-picker > option > .settings-choice-help`, with current option and independent descriptions. `src/web/assets/app.css` positions the help absolutely to the right (`left:46%`, bounded `max-height`, `overflow:auto`); `:hover/:focus` controls its visibility. A wheel event aimed at an option need not scroll an absolutely positioned sibling/descendant whose box is elsewhere. **This is the correct seam to investigate**, not a blanket wheel hack in `src/web/assets/help.js`.
5. Existing real Chromium coverage: `development/tests/integration/probe_mini_fit.cjs`, `probe_mini_width.cjs`, Mini disclosure/history-demand tests, and `probe_web_settings.cjs` check native picker hover and keyboard/zoom/touch behavior. The Settings probe currently verifies visible hover help but **does not assert wheel-driven scrolling from the hovered option**. Extend these rendered interaction tests.

## Required implementation — Mini Watch header

1. **Design the three header elements as a coherent system.** Use shared or deliberately coordinated font family, font size, weight, line-height, vertical alignment, controls' centerline, padding and gap. Cost Guard · Watch remains a clear link/return action, Earlier Sessions remains a button, and CCost Today remains a compact readout; no need to make them identical-looking objects, but they must **share one typographic rhythm** and no element may look arbitrarily higher/lower. Preserve actual CCost amount and prompt count without a new tooltip/partial technical label (FR000634).
2. **Actual pressed toggle:** use the existing `button` and change its appearance from subtle/outlined when collapsed to filled when expanded. Remove both chevron pseudo-elements, keep the exact stable visible text `Earlier Sessions`, and use selected/pressed colors with sufficient text contrast for Classic, Web light and Web dark. The fill should remain unmistakable after moving the pointer away, without relying on hover, color alone or an arrow. No extra toggle switch or new status label required.
3. **Correct state transitions:** synchronize `aria-pressed`, `aria-expanded`, `aria-controls`, `earlier.hidden` and `prompts.dataset.expanded` atomically after click/keyboard activation. New Mini windows start collapsed. Ordinary Live updates, source health changes, refreshed Earlier Sessions memberships and size/theme changes must **not reset the owner's choice**. Exactly one disclosure action per click/key press; no event duplication.
4. **Robust normal and narrow layout:** at a fitted width the three components should occupy one line with vertically aligned text/control centers and intentional left/center/right grouping. At narrow manually resized or OS-clamped widths, use a **deliberate compact reflow** (if absolutely necessary, a tidy secondary row with consistent horizontal alignment and spacing) rather than the current unpredictable independent flex wrap, off-center button, orphaned middle control, overlapping text or clipped CCost. Keep all three items visible and operable; no document horizontal overflow solely from the header, hidden labels or tiny hit targets. Prefer stable geometry: **expanding/collapsing should change fill and lower content, not move the three header texts horizontally**.
5. **Keep Mini's native PiP sizing contract.** Update `headerWidth()`, `OpeningMeasure.read()`, inert measurement copies and `DisclosureSize` assumptions to reflect the new no-arrow toggle and desired reflow. `Fit on open` must still reserve the real full Today text and focus/rounding margin in both pressed states; `Remember last size` remains browser-owned. Do not hardcode a new arbitrary wide window or force passive resize loops. Opening should fit when the physical screen permits; smaller native clamps must produce an intentional readable layout with normal scrolling. Earlier click may continue its existing *single bounded user-activated height-only adjustment*; no automatic width jump, resize oscillation, or passive resizing on fresh data.
6. **Polish interaction and aesthetics:** correct hover/focus/active/pressed contrast, readable small text, precise clickable hit areas, no awkward jumps between themes, zoom/fonts, high-contrast/reduced-motion where applicable, or interactive overlap with native PiP title bar. Maintain keyboard outline without clipping; no duplicate native `title` or unsolicited explanatory tooltips. Other Mini tables and quota cards are outside this visual redesign.
7. **No regressions to header purposes:** title still returns to the existing Cost Guard tab; Today's actual global cost/prompt count remains accurate and stable; Earlier expansion still requests/reuses its canonical shared history and displays the correct table. No additional EventSource, source reads, paid calls, OpenCode processes, background timers or altered history accounting.

## Required implementation — Settings customizable picker wheel behavior

1. **Precisely target the open Settings picker and active option.** When an `option` is visibly hovered (or is the current keyboard-focused option when appropriate) and its `.settings-choice-help` has vertical overflow, wheel input over the **option area** scrolls that *visible description* — even if the pointer never enters the description's painted box. The target includes all relevant choices, Default, the selected value and previously unselected choices. If there is no overflow, keep the native wheel behavior.
2. **Keep the correct explanation visible.** The hovered/focused option must remain the preview while its description scrolls. Wheel motion must not silently select another option, fire `change`, call Settings save, dismiss the popup, swap the help text, or jump focus. Preview is not commitment. Scrolling through a long description must be smooth enough to reach its bottom and reverse to the top; ordinary direct scrollbar dragging and wheel-over-description remain functional.
3. **Scope wheel handling carefully:** favor the native `::picker(select)`/option architecture and a small scoped `wheel` handler on the relevant Settings picker only if required. Normalize wheel delta units as needed, use a non-passive handler **only where actual description scrolling can be consumed**, avoid global `document`/window listeners, preventDefault only when appropriate, and allow natural surrounding picker/page scrolling at boundaries if it does not destroy the current preview. Avoid scroll trapping or double scrolling; no unbounded animation/timer and no third-party UI library for a minor interaction.
4. **Support both hovered and keyboard-focused previews** without stealing focus or changing normal native keyboard controls (Arrow keys, Home/End, Enter/Space commit, Escape cancel, typeahead, Tab). Keep `selectedcontent`, accessibility option names/descriptions, hidden description IDs, persistence on genuine selection, previous-value rollback after save failure, and touch behavior. Do not introduce a JS custom combobox unless native limitations have been demonstrated in an actual browser and an equally accessible targeted workaround is necessary.
5. **Browser capability fallback:** unsupported browsers already use native selects plus `Choice help` disclosure; preserve them. Apply wheel delegation **only when the enhanced picker and a visible scrollable description exist**. Do not add broken hover handlers to native OS option menus, mobile/touch layouts or the shared `ContextHelp` system. At narrow viewports where option descriptions are in-flow instead of a separate scroll pane, retain normal popup scrolling.
6. **Long and real content:** cover the particularly long `Mini Watch size → Fit on open` description and other settings, with at least one synthetic description much taller than the panel to prove substantial scrolling. No clipping/overflow outside the popup; no oscillating hovered option while scrolling or when an option is selected.
