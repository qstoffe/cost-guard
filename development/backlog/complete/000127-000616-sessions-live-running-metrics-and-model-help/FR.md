# FR 000616 — Sessions: live running-session metrics and contributing-model help

**Owner-approved Ready Feature Request, 2026-11-06.** Permanent identity **000616**; Ready queue priority **000340**, following current FR000615 (000330). This is **backlog publication only**, not implementation or release.

## Owner report and intended UX

On **Web Beta → Sessions** (`/#/sessions`; described verbally as the “Positions” page), the top/newest session may be actively executing a **running prompt** while its **Model, CCost, Prompts and Duration** columns show **Unavailable**. The owner wants the real session name immediately, a clearly visible **running** indicator beside that name, and each of those four metrics to be updated **live** as the prompt/session progresses. When a metric is genuinely still being acquired, show **`Loading…`** instead of prematurely presenting a terminal `Unavailable`. Once the source supports a value, replace its placeholder with the real observed/current number or model name; continue updating until completion.

The same table can display **`Multiple models`** in its **Model** column. Keep that concise cell text, but make it possible to **hover (or keyboard-focus/tap) the actual cell text to see which models contributed to the session**. The tooltip should show the distinct contributing models, not just repeat “Multiple models.” Use the existing shared help UX, not another visible table column, `?` button or browser-native `title` popup.

**Examples (synthetic, not observed private data):**

```text
Last activity      Session name                 Model            CCost      Prompts   Duration
2026-11-06 15:42   [RUNNING] Working on parser  Loading…         Loading…   1         Loading…
2026-11-06 15:47   [RUNNING] Working on parser  Multiple models  345?       3         8m 12s
2026-11-06 12:18   Finished work                Multiple models  892        6         24m 09s
```

Hover/focus `Multiple models`: **Models in this session: provider-a/model-one; provider-b/model-two** (illustrative). The examples are not a promise of precise real-time cost, fabricated zero, fixed durations or a changed currency convention. CCost should retain the existing configured Credits/USD display and partial-cost qualifiers.

## Source findings and likely causes

1. **A live catalog already exists**: `src/web/assets/sessions.js::View` fetches `/api/sessions` about **every five seconds** while attached/visible, and `src/application/session_catalog.py::SessionCatalog` admits bounded per-root summary work from the shared Live acquisition owner. This FR should **repair/extend that existing pipeline**, not introduce a new independent worker, SSE connection, paid model call or full-history rescan for each row.
2. `SessionsCatalog.rows()` already appends `[RUNNING]` to the **session name** when `value.running` is true, and recognizes `metric_state` with `pending / ready / retained / unavailable`. However `SessionCatalog.page()` currently exports `row["running"] = bool(row["running"] and current and not unavailable)`; a not-yet-indexed or temporarily unverified **known active** session can therefore lose its visible running indicator. Similarly `metric()` displays `Unavailable` for a missing summary when `metric_state` is terminal/unavailable, even though the owner's newer running session may still be awaiting source-backed metrics. **Reproduce the owner's exact state transition with sanitized fixture/evidence**; do not assume all real `Unavailable` cases are actually pending.
3. `SessionCatalog` receives full observed root membership, revision/activity metadata and `live_candidates` from the shared observer. A live *candidate* alone is **not proof of an actively executing prompt**. Derive the active/running indicator from trustworthy current source or existing canonical Watch/Live prompt evidence, and preserve freshness/time-bounded validity. Pending summary acquisition must not be silently equated with finished or failed execution.
4. `src/reports/session_summary.py::session_summary()` already bypasses cached per-root summaries for active work; `src/reports/service.py::_session_rows()` computes canonical per-root model, whole-session valuation, number of prompts, overlap-safe execution duration and running state. The catalog's current bounded index lane can progressively fill the live fields, but changes to row values and authoritativeness must be expressed correctly by the DTO and browser on each fresh observation. `src/application/session_catalog.py::_current()` uses recent successful validity for active roots; investigate whether slow/failed admissions, revision churn, stale summary and currently missing fields explain the placeholder/freeze behavior.
5. The canonical `SessionUsageRow` in `src/reports/models.py` currently stores `model` and the Boolean `multiple_models`, **not the actual set of contributing models**. `_session_rows()` already has `item.bundle.trace_entries` and the provider/model identity of contributors available while projecting the summary. `src/application/projection.py` allowlists only the current scalar fields to the Web response; that is why the `Multiple models` cell has no model list to show. Add a bounded, deterministic allowlisted **provider-qualified distinct model identity/name list**, derived from canonical contributors at the existing summary acquisition point. Never reconstruct this by parsing displayed strings or fetching raw session data from the browser.
6. `sessions.js::rows()` currently replaces all cell contents whenever `JSON.stringify(value)` changes, even for a small live metric delta. This can discard focused/hovered help targets and cause visible jumping. Retain keyed row, session link, focus, selection and any open passive contextual help while mutating only affected cell text/help where practicable; do not sacrifice live updates merely to preserve old DOM.

## Requirements — running-session display and live updates

1. **Immediate recognizable activity**: on `/#/sessions`, the current **session title remains a link** in the same existing Session name column, with a concise visible and accessible **[RUNNING]** (or equivalent established site convention) when an actively running prompt is affirmatively observed. A newly arrived session may show an in-progress marker **before all scalar history is indexed**, provided source-backed positive evidence exists. Never invent the marker from a mere recent timestamp, nonterminal catalog listing, old cached snapshot, missing data or the `live_candidates` set by itself.
2. **Loading is for actual pending work**: in **Model, CCost, Prompts and Duration**, show **Loading…** only when the desired per-field evidence is *pending and expected to become available*. If a field is already known, keep its real/qualified value visible while another field remains pending. Preserve honest `N/A`/`Unavailable`, `Partial`/`?`, `Retained` and source/error warnings when data is genuinely unsupported, no longer trustworthy, source-unavailable or definitively failed; never turn a permanent source failure into an endless fake loading state. If pending data has been retained from a valid previous observation, prefer showing that value with clearly qualified freshness over blanking it.
3. **Real-time observational updates**: while the Sessions view is active and its source healthy, reflect new supported **model selection / contributing models, whole-session CCost, prompt count and execution duration** through the existing bounded Live/catalog cadence, without requiring Refresh, navigation or reopening. Show actual known partial/provisional cost rather than treating a running, incompletely billed session as `0` or exact. When a new prompt begins, prompt count and model state update; when time/usage evidence advances, the appropriate display updates. Do not invent token/CCost increments or elapsed execution from the age of a root session or an idle gap. If a safe source-backed live clock estimate is used, qualify/reconcile it against the canonical interval model; otherwise show the last known measured duration until a new observation.
4. **Correct lifecycle transitions**: running → completed/failed/aborted, resumed later prompt, subagent/child activity, stale source, lost authorization and reconnect must update the marker and metrics truthfully. Don't freeze `[RUNNING]` after verified finish or erase verified running state solely because unrelated cost metadata is still pending; distinguish last-known retained state from fresh proof. Retain already known values after terminal completion and switch to final verified values once available. Do not alter canonical Watch vs Sessions definitions of running, duration, prompt counts or whole-session cost.
5. **Preserve catalog behavior and performance**: exactly six columns (`Last activity | Session name | Model | CCost | Prompts | Duration`), 50 rows/page, server-side global sort/tie-breaking, newest-first default, historic older-page epoch stability and document scrolling. Live row updates must not generate spurious reorders due to partial unsupported sort keys, introduce duplicate sessions, or break the existing global-sort “index incomplete” qualification. No new browser model valuation, extra one-request-per-row network polling, unbounded source scans, source writes, provider inference or tab-driven history ownership; reuse shared observed data and bounded per-root indexing. Preserve short polling/scheduling fairness with Watch, account and detail lanes.
6. **Stable, accessible UI**: mutate existing keyed row/cell/link nodes as practicable instead of replacing the whole row on each tick, preserve focus and selection, color contrast, quiet updates, smooth row geometry, existing responsive horizontal panning and screen-reader-friendly status without announcing every microchange. Tooltip targets must remain usable during live updates; keyboard navigation and pointer activation to the session detail keep working.

## Requirements — exact contributing models for `Multiple models`

7. **Model list from canonical evidence**: use **distinct provider-qualified model identifiers** from the actual physical/request contributors to this root session (including attributable child/subagent requests where they enter the canonical whole-session analysis). Prefer a readable display name plus provider/model identity where needed to disambiguate; deduplicate exact same model, keep a stable deterministic order, and include newly observed contributors as running evidence advances. Do not infer models from session title, pricing catalog candidates, available-but-unused models, or neighboring sessions.
8. **Shared value tooltip**: keep cell text exactly **`Multiple models`** when the existing multi-model rule holds. Attach shared `ContextHelp` to that **text itself** (not a `?` icon), with help such as **“Models used in this session”** followed by the real model list. Hover, keyboard focus and touch must reveal it; Escape/leave dismiss through the existing policy. Screen-reader access should expose the model identities. When there is exactly one known model, show that model normally; no unnecessary multi-model tooltip. A pending/incomplete contributor set must be labeled as **observed so far**, not falsely exhaustive; if a multi-model flag exists but list is not safely available, say so instead of inventing members.
9. **Minimal data contract and privacy**: extend the canonical session-row DTO / scalar index / allowlisted Web projection as needed to carry a small, bounded list of contributor model identities, not raw prompt text, session contents, tokens, secrets or exception strings. Revise any affected summary cache algorithm/version/schema validation so stale cached scalar payloads cannot become authoritative under a changed contract. Preserve existing model/CCost sort keys and per-session identity across source revisions. No new persisted user ledger or broadly exposed model catalog.

## Acceptance and verification at implementation time

1. **Fresh active session, cold scalar index**: with an independently verified running prompt and delayed summary hydration, the latest session **name + [RUNNING]** appear without a premature terminal `Unavailable` in healthy pending cells. Each of Model, CCost, Prompts and Duration becomes a real qualified value when its evidence arrives, without a reload. Test absent/unknown model, 0 observed requests, incomplete prices, null duration, and missing prompt boundary independently; not all missing fields mean the same thing.
2. **Live progression**: in an owned synthetic source, advance usage, execution, prompt count and model on successive authoritative observations, then finish and later start a new prompt. Verify observed values change in the Sessions table through the existing five-second-ish cadence; no fake cost/time increases during a true idle gap and no stale running marker after confirmed end. Verify source temporarily unavailable, explicit terminal failure, stale-retained data, source revalidation and recovered values behave truthfully.
3. **Multiple models tooltip**: a single known model displays normally; two distinct provider/model combinations show `Multiple models` and both actual identities in ContextHelp. Repeated requests of the same provider/model deduplicate; same model ID across two providers remains distinct; subagent models are included only when canonically attributed; partial contributors are qualified; changing models updates the tooltip correctly. Test keyboard focus, mouse hover, touch, Escape and no duplicate native/standalone help.
4. **Stable interaction during updates**: real rendered browser tests assert selected/focused session links remain connected, open model help stays usable across a live update, text selection and scroll are retained where possible, no flash/recreation of the entire 50-row table, and the newest-first row and pager update correctly on actual new arrivals. Check Classic/Web light/dark at 360/1366/1920 pixels with zoom/long localized model names; preserve one-line rows and horizontal scrolling only where necessary.
5. **Backend safety and sorting**: deterministic Python DTO/cache/index tests distinguish pending/ready/retained/unavailable and actual running, verify current-revision/provenance and cache invalidation, model list export allowlisting, no extra HTTP per metric, per-root bounded work, source failures and no regression in complete/partial sorting or older-page stable epochs.
6. Extend `development/tests/test_web_session_catalog.py`, existing `development/tests/integration/web_session.cjs` and `probe_web_sessions.cjs` or the focused Sessions browser probe; include a read-only real-source check only where authorized/feasible and record whether the exact owner incident was reproduced. Update `docs/web-beta.md` / the Sessions Web module description during **implementation**, not while publishing this FR. No new product gates or version bump in the authoring task.
