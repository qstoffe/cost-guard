# FR 000594 — Web Accounts: replace legacy report with the shared live Watch account cards

## Owner request and backlog decision

**Owner-approved executable Ready Feature Request, 2026-11-05.** Completely simplify the **Accounts** page in Cost Guard **Web Beta**. The existing account/subscription cards **at the bottom of Full Watch** are the desired design and behavior. **Replace the present Accounts report interface with those same cards and nothing else in the normal healthy view.** Accounts should now be a continuously refreshed display, just like the account section of Watch; the owner may request Accounts-specific card additions in later FRs, but none are needed here.

**Queue:** add as an independent Ready FR after current Ready FR000593. Coordinate with pending **FR000590**'s tooltip/card changes and prior **FR000585**'s quota/Capacity behavior. Use the **actual current Watch cards at implementation time** as the source of truth; do not reintroduce older completed designs. This is **backlog authoring only**. No application code, docs/tests or version/release change now.

## 1. Replace the entire old Accounts page presentation

- **Keep the existing `Accounts` navigation entry and `/#/accounts` route.** The route should render **only the shared Watch-style account-card grid** as its normal content, directly in the main document area.
- Remove Accounts-specific **report title/toolbar**, **Refresh snapshot**, **Cancel**, snapshot/frozen/observation text, **Reading this report**, **Presentation filter / Search displayed report tables**, report explanations, extra card/report wrapper layers and the old verbose **Accounts Overview / Observation details** style. No old report table, billing/report section, duplicate metrics or second copy of the same quota in an expansion panel.
- Do not remove **shared app navigation, authentication/source/host failure feedback** or the browser's accessibility support. Render a truthful concise empty/loading/error state if cards cannot yet be displayed; do not leave an empty white page or report a confirmed empty account list merely because an acquisition is pending.
- Do not change the Models, Sessions, Reports, Token Mix, Cost per Active Hour, CLI or native account Diagnostics layouts. Do not globally delete finite-report Refresh/Cancel controls: hide/retire them **for Accounts only**, as Watch already does.

## 2. The same Watch cards, not a second competing design

- Reuse the existing **Full Watch subscription cards** including the **same** actual account selection/order, one card per account, title, CCost Today, primary quota label/period and native percentage, parenthesized current-period CCost (Used/Remaining), **Capacity**, progress bar, reset/remaining-per-day/remaining-per-workday, secondary quotas and their separation, provider restrictions/exhaustion/stale/partial/error indicators. The actual card shown on Accounts must be visually and semantically equivalent to the corresponding Watch card with the **same observation**.
- Preserve the full Watch card's compact **subgrid alignment, sizes, max-width/physical-pixel scaling, responsive grid/wrapping, semantic colors, progress-bar fill, reset information, light/dark/Classic themes and screen reader labels**. The grid should behave naturally with one, several or many accounts and scroll with the page.
- **Share a single account-card renderer/view/component** between Watch and Accounts where practical; reuse/extract the code currently in `src/web/assets/watch.js::accounts()`, `quotaTrack()` and `quotaDetails()`, plus the same `watch-account-grid`/subscription styles. **Do not maintain separate copy-pasted code** which silently diverges in tooltips, spacing, warnings, price displays or future fixes. The user's “copy/paste” request means *identical resulting UI/functionality*, not duplicated product logic.
- Carry over the tooltip semantics **as they exist after FR000590** (no standalone `?` icons, hover on relevant labels/values, delayed pointer help, useful concise Capacity provenance with `(guesstimate)` where applicable) and any other merged updates. Do not introduce a new help framework or restore removed boilerplate.
- The existing **Settings → CCost display** (Credits/USD) and **Quota display** (Used/Remaining) must switch displayed numbers, progress bars, Capacity provenance and tooltip content **on an already-open Accounts page**, using the same server-prepared display tokens as Watch and with no new account refresh just for a preference change. Preserve provider-native vs estimated CCost provenance, no fabricated numbers or billing equivalence.

## 3. Share the existing process-lifetime account acquisition / Live feed

- **Accounts is a live consumer of the same application-level account observations that Watch uses**, not a new report or parallel quota refresh loop. The Web host already has one process-lifetime `LiveRuntime` and publishes `project_live(...).view.accounts` (see `src/application/live_projection.py::watch_accounts()`). The normal browser has a **single existing authenticated Live SSE consumer** in `src/web/assets/live.js` / `app.js` even when the Watch route is not selected. Reuse these paths.
- Account/provenance/price-history work is performed centrally at the existing cadence **whether a tab displays Watch, Accounts or another route**; switching **Watch → Accounts → Watch** must render the **latest retained common observation promptly**, not launch new provider/CLI/SQLite acquisition, start another Live driver, new SSE connection or wait for a fresh full report. If the user opens Accounts before any usable publication, show a quiet loading state and render automatically when available.
- **Do not start the old `kind: normal` finite report just because Accounts was opened**. The present `ReportRoutes.resolve('accounts')` maps to `normal` and `ReportView.render()` uses the static `overviewAccounts()` card family plus frozen snapshot/report prose; replace this Accounts-specific route/rendering integration without disrupting Models' normal-report cache/reuse or other report jobs.
- **Live account updates repaint the Accounts cards automatically**, including changes in native quota usage/reset, CCost Today, Capacity, primary/secondary quotas, source availability, account newly discovered/removed and configured display modes. A card's data should not be older than Watch's for the same host publication; account data need not wait for running-prompt cards, historical prompts or unrelated report completion.
- Avoid rebuilding/replacing all account DOM on **every** 1-second Live message when the account projection is unchanged. Prefer stable account-keyed reconciliation or a deterministic signature; preserve keyboard focus, open hover help, text selection, active tooltip, scroll and display units where possible. Do not hide a legitimate changed/missing account behind a stale signature or reuse the wrong account's data.
- **Retained data during transient outage remains displayed and honestly marked stale** with existing accurate account/source warning semantics. A source failure must not silently transform a previously observed set into “No configured accounts”; nor should a stale quota masquerade as current. Maintain the existing separate account failure/retry cadence, terminal auth/host behavior and honest unknown/partial/native values. No new polling or background work simply because a user enters Accounts.
- If Watch itself is not in the DOM or never opened in that browser tab, Accounts still renders all cards from the same shared publication. Browser tabs each have their own UI state but must not spawn independent server-side account workers. Startup/reconnect/replay respects the existing single-source/auth/instance boundaries.

## 4. Implementation scope and security boundaries

Likely owners to inspect after earlier FRs land:

- `src/web/assets/watch.js`: existing Watch-only card helpers and `WatchView.View.update()` currently draw `view.accounts`. Extract/reuse the card view instead of importing an entire Watch page with prompts/daily content.
- `src/web/assets/render.js`: old Accounts rendering branch `view.kind === 'normal' && section === 'accounts'` and `overviewAccounts()` should no longer be the actual Accounts route. Keep report-only consumers of those helpers where still needed.
- `src/web/assets/reports.js`: the Accounts route is currently backed by `kind: 'normal'`. Update its semantics so switching there doesn't schedule an extra finite report.
- `src/web/assets/app.js`, `live.js`, `app.css`, `index.html`: route-specific shell hiding, retained Live value routing, card DOM updates, styles/settings coordination and consistency when navigating.
- Existing `src/application/live_projection.py`, `src/application/watch_accounts.py`, `src/watch/` acquisition and account/status projection should normally remain authoritative and be **reused**, not forked. A small additive common DTO/style seam is allowed if necessary; no browser-side CCost/Capacity recomputation or sourcing raw private provider payloads.

Preserve read-only OpenCode access, private account/credential boundaries, existing per-account quota ownership and source/cache isolation, normal finite reports for unrelated pages, native account detail/Diagnostics access outside this intentionally simplified Accounts route, one authenticated host-bound event stream and existing job/resource limits. This FR does not propose new provider support or new data collection.

## Acceptance criteria

1. **Visual parity:** With an identical Live publication, account cards on `/#/accounts` match **Watch's bottom subscription cards** in fields, values, order, spacing, card widths, primary/secondary quota layout, bars, colors, labels and useful tooltips. Accounts shows **only those cards** in the healthy view, without report header, Snapshot/Refresh/Cancel/search, extra explanatory boxes, old observation disclosures or unrelated tables.
2. **Shared updates:** Open Watch, note the cards, navigate to Accounts, then back. Both pages reuse the **same latest server-observed values** immediately. No additional report jobs, source selection, provider polling, account history recomputation or extra SSE is started by the route transitions. Accounts updates without being on Watch.
3. **Live changes:** Account usage/Capacity/CCost Today/used-vs-remaining, primary/secondary/reset data and account membership changes render in Accounts automatically on the normal Live cadence. Background updates do not block on prompt history or require manual Refresh.
4. **Display settings:** Credits/USD, Used/Remaining, Default/explicit preferences and Classic/Web light/dark changes are reflected consistently on both routes and in open tooltip text; `(guesstimate)` provenance and provider-exact capacities match. No browser-side repricing or extra fetch triggered by these toggles.
5. **Correct state:** Genuine empty list vs initial pending vs known unavailable/partial/stale/recovering source/account, auth expiry and host shutdown are distinguished. Retained rows do not disappear or claim fresh; errors remain actionable but no lengthy boilerplate returns.
6. **Stable interaction:** Scrolling, focus, keyboard/touch/hover help, live update reconciliation, reduced motion, narrow/zoomed pages and multi-account card alignment behave correctly. Shared component changes cannot produce Watch-versus-Accounts drift.
7. **Verification:** Add or update focused JS/DOM and real browser tests for both routes, link navigation, initial Accounts launch without prior Watch DOM, long-lived account refresh, failed/retained state, secondary quotas, one/multiple/no accounts, unit/mode/theme changes and resource counters ensuring **one account-refresh owner**, not page-specific loops. Update current `docs/web-beta.md` and Web architecture/module guidance to describe Accounts as a live card consumer rather than a frozen normal report. No new unrelated permanent tests or paid model calls.

**Publication boundary:** approve/store this new Ready FR and increment the permanent identity watermark only; implement source, tests and release changes later under normal backlog execution.
