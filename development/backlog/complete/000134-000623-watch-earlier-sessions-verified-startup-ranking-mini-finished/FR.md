# FR 000623 — Bugfix: verify latest Earlier Sessions before publishing in Watch/Mini; rename Mini Activity to Finished

**Owner-approved Ready Feature Request / bugfix, 2026-11-07.** Permanent identity **000623**, Ready priority **000410**, after existing FR000622 (000400). **FR-only backlog authoring:** create this specification, advance the identity watermark, commit directly on main; do not implement code, tests or product documentation in the authoring transaction.

## Reproducible user-visible problem

On a fresh start of **Cost Guard Web Beta → Watch**, expanding **Earlier Sessions** can immediately show several **old** session cards from about an hour ago, presented as if they were the most recently finished sessions. **No new prompt or session runs.** Nevertheless, after roughly **one minute** the visible Earlier list suddenly swaps many of those entries out for **newer sessions that already existed all along**. The exact same replacement happens in the separate **Mini Watch → Earlier Sessions** table.

This is materially misleading: the user expects **the actual latest earlier sessions**, not merely the latest ones the app has gotten around to reading. The desired behavior is:

1. **Best case:** determine the correct most-recent eligible history **quickly**, and show it immediately once provable.
2. **If it cannot yet be proven:** show a neutral **`Loading earlier sessions…`** / verified progress or “verifying latest history” state, **not an apparently final list of older candidates** that will later be replaced solely because background hydration uncovered already-existing newer sessions.
3. **After verification:** present the actual correct newest list simultaneously to Full Watch and Mini, and keep it stable absent a genuine change of source/session facts.
4. **Minor naming polish in Mini:** change the Earlier Sessions first column header from **`Activity`** to **`Finished`**, matching Full Watch's existing historical prompt column. Retain the same supported local finish time and its full-date/time tooltip; this is a label change, not a redefinition of the timestamp.

The owner has reproduced the effect in the real app; our source inspection **establishes a causal mechanism capable of producing the symptom**, but we have not reproduced the exact private desktop timing/root sequence. The implementation should first create a failing test for the interleaving, then fix and verify it, rather than asserting unsupported source-specific causes.

## Confirmed source analysis: preliminary top-five incorrectly looks authoritative

### Server membership and admission

- `src/watch/observers.py::observe_catalog()` loads a catalog and `watch/coordinator.py::_selected_roots()` orders root metadata by `root_activity(...)` (with fallback `updated_at_ms`). These timestamps are useful **admission priorities**, but **not authoritative proof of the most recently completed prompt**: an old root may have later child activity, retained events, compactions or a finished prompt not indicated by root metadata. Other source/canonical tests already disallow metadata-only claims of actual events.
- `src/watch/web_coordinator.py` deliberately makes `_hydrate_startup()` and `_hydrate()` no-ops for global Watch. The new `src/watch/cards.py::WatchCards` / `src/watch/card_workers.py::CardWorkers` asynchronously captures roots in **bounded four-worker slices**, safely keeping the Live owner responsive. This is sound for resource management but means **not every known root has a verified capture at once**, especially with thousands of sessions or slow I/O.
- Every newly discovered root starts as `CardSession(..., latest_ms=None, finished_ms=0, state='loading')`. `WatchCards.accept()` fills `latest_ms` and `finished_ms` only after that root's canonical prompt capture is received; `src/reports/watch_capture.py::WatchCapture.history_row` chooses the latest supported finished prompt from the captured rows.
- **Precise suspected defect:** `WatchCards.historical_ids()` immediately chooses `sorted(eligible, key=(-finished_ms, session_id))[:5]` **among entries with `entry.latest_ms` already populated**, without checking whether newer, unprocessed candidate roots exist. Thus the first five completed older captures can populate Earlier as a *provisional* ranking. Minutes later, captures for roots that were already in the same initial catalog but had newer finished prompts promote them into the top five, replacing the earlier selections **without any real new activity**.
- `WatchCards.project()` returns `history_cards` from that provisional top five. `src/watch/web_coordinator.py::_build_projection()` already computes `history_pending = any(entry.latest_ms is None ...)` and exports `history_state='loading'` while unprocessed roots remain. **The source already exposes an incomplete-history signal, but does not enforce it at the authority/publishing boundary.** A separate `cards_state='observed'` for active prompts does not prove Earlier history is complete.

### Both UI surfaces expose the same incomplete history

- `src/web/assets/watch.js::View.update()` computes `historyLoading` but still loops over all supplied `view.history_cards` and renders them immediately. It only avoids the explicit empty-state message when loading. Thus its “Earlier Sessions” cards can look definitive despite `history_state='loading'`.
- `src/web/assets/mini.js::Observations.update()` consumes those **same shared Live history cards**, retaining some previously published data during partial refresh. `MiniWatch.View.drawHistory()` takes the latest three of the sorted five with `.slice(-3)` and still renders them while `view.history_state` is loading, instead of gating provisional membership. The two views are not racing different sources; they share the upstream uncertain selection. Fix authority **at the producer** and preserve coherent consumer handling, not two separate rankings in JS.
- For the small rename, `mini.js::View.table(parent, historical)` currently creates historical headings **`Activity | Session | CCost (Total) | Ctx`**, with `Activity` help describing *latest supported finish*. `watch.js::Card` already labels that same historical prompt clock **`Finished`**. Mini should therefore become **`Finished | Session | CCost (Total) | Ctx`**, including its heading mapping/ARIA docs and tests while keeping local date/offset help intact.

**Do not confuse this with genuine updates:** actual late-arriving source events, newly finished prompts, resumed activity, real corrections, root deletion/archive and price/source revalidation may correctly change the list. The regression is *discovering already-present newer sessions only after rendering an uncertified older top-k as the final newest list.*

## Requirements — correctness first, fast verified readiness second

1. **One authoritative history-readiness contract.** The shared Live server must expose a clear distinction between a **provisional top-k from already captured roots** and **globally verified newest eligible Earlier sessions** for its pinned source/catalog generation. An initial collection is ready **only when all potentially displacing candidates are accounted for** (either captured/verified or safely excluded with source-backed evidence). `history_state='loading'` and/or explicit coverage counts must govern whether `history_cards` is publishable as an authoritative list. Do not use elapsed time, first five captures, arbitrary last-updated cutoff, a flat 60-second timer, or first Live publication as proof.
2. **No provisional population shown as recent.** While the newest-five membership is not established, Full Watch's expanded Earlier section and Mini Watch's expanded Earlier table should show a compact, stable **`Loading earlier sessions…`** / **`Verifying latest sessions…`** with meaningful completed/eligible counters where grounded. They must **not render the current partial top five/top three as actual latest**. A full Watch page can show available running/recent prompts, subscriptions and Today normally while historical membership is being verified. If the user expands Earlier immediately, it should stay usable and accessible, not freeze/hide the entire Watch dashboard or block Mini window opening.
3. **Prefer fast correct winners.** Profile historical ranking/capture startup and prioritize the roots that have the best *safe* potential to occupy the top five. Investigate reusable bounded revision-keyed root summaries (e.g. last actual supported finish and active/grace eligibility) or existing derived evidence, with explicit source identity/revision and reliable temporal bounds, to prove a stable top-k **without serially rehydrating thousands of full prompt trees every startup** when possible. Current `root_activity`/`updated_at_ms` can guide priority, but **cannot alone certify an upper bound** on a root's latest finished prompt; roots with old metadata can contain recent causal activity. If no safe fast certificate exists, keep honest Loading until a bounded complete verification, rather than publish guesses. Reuse existing Live/captured evidence, source APIs and caches; do not build a second history scanner or store raw prompts/titles in a new global ledger.
4. **Correct candidate scope and ranking.** Preserve Full Watch's **five** newest eligible finished **distinct root sessions**, Mini's **newest up to three** of those (oldest-to-newest within Mini's subset), correct latest actual supported *finished prompt* for each, and existing deterministic timestamp/session-ID tie rules. Active/recent grace sessions are excluded **before** the history limit; when they legitimately finish after grace or resume running, the list updates coherently. Unknown-finish sessions should fill only genuinely unused slots, and missing/invalid timestamps or source-incomplete trees must not be treated as a recent completed prompt. Preserve archived/removed-root contracts and confirmed source capability; do not invent results from deleted/pruned data.
5. **Atomic verified publication and steady refresh.** Once an authoritative history population has been proved, publish its membership + representative prompt/finished times under one source identity/catalog revision/proof epoch to both clients. On subsequent ordinary Live ticks, do **not** withdraw/replace the verified list merely because one root is temporarily refreshing; preserve the last coherent version with truthful freshness/status until a new verified version or terminal invalidation. If a source revision/active status may change top-k, verify its effect before replacing the list; avoid a mixed version of old and new cards. Deliberate source switching, archive/removal and true new activity invalidate/recompute only where required. An expired old result cannot be rebranded as freshly verified simply because the UI polled.
6. **Truthful partial/failure states.** If capture of one root fails persistently, source is unauthorized/unavailable or there are impossible-to-exclude unfinished candidates, do **not** claim the correct latest five. Show a stable and meaningful *“Unable to verify latest sessions”* status (with typed source cause where possible) after the existing bounded recovery policy, or retain a clearly qualified previously verified set where safe. Avoid endless `Loading` for terminal issues, false **`No earlier sessions`**, silent omission of high-priority candidates or declaring success after only five captures. Never expose private session names/IDs in public diagnostics or claim an unverified partial subset is the definitive top-k.
7. **Preserve protected Live responsiveness.** Watch remains the highest-priority source owner; do not wait for history completion to publish active prompts, running status, daily CCost, account observations or Mini's other content. Bounded concurrency, source admission, cache revision checks and cancellation/host-shutdown semantics remain. Investigate the real cold-start bottleneck and measure elapsed time-to-first **verified** history. Optimize with proof rather than arbitrary extra threads/whole-archive CPU contention with Watch or the recently merged FR000617 dispatcher.
8. **Both frontends consume the same state.** Full Watch and Mini Watch must never independently select “latest” from different incomplete subsets. Render the shared verified state; gracefully handle re-entry after tab navigation, Mini opened while history pending, an already-open Mini when the proof completes, Mini disclosure expansion/collapse, reconnect and source-generation changes. No unwanted popup size changes from background publications; preserve Mini's existing height-only user-driven expansion, focus, scroll, selected unit/themes and normal four-column compact layout. Coordinate with pending FR000621's Mini tooltip/status polish without overriding those requests.
9. **Mini cosmetic rename only.** Change the first Earlier Sessions header from **Activity** to exactly **Finished**. Its value remains that **canonical representative prompt's supported local finish clock** (not session metadata updated time, browser-poll time or latest activity start). Keep existing missing `—` treatment, full local date/time/UTC-offset tooltip, keyboard focus/touch and accessible labels; adjust table/header help and any `Activity`-specific CSS/test selectors or docs. Running table's **Session | CCost (Total) | Duration | Ctx** remains untouched. Do not change Full Watch's already correct **Finished** heading.
