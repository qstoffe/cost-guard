# FR 000631 — Web Sessions: one-click session JSON export with native Save As

**Owner-approved Ready Feature Request, 2026-11-07.** Permanent identity **000631**; Ready priority **000540** (after FR000625 at 000520, before FR000628 at 000560). This publication is **backlog-only**: create the FR/update identity state and clarify existing FR000630's source context; no product implementation, test, version, runtime, CLI, or active OpenCode session change.

## User need and requested interaction

In **Cost Guard Web Beta → Sessions → an individual session detail**, the owner wants an **Export session** button, so they can save that specific session's OpenCode JSON export without finding a CLI executable or manually copying the session ID. This is especially valuable for OpenCode Toolkit LIVE tests: its isolated private CLI servers can create sessions in the shared OpenCode database that Cost Guard can display but which are **not accessible in the owner's ordinary OpenCode Desktop session list**.

On click, export **the selected full native session** (not merely the displayed Cost Guard summary, prompt rows, a Watch snapshot or the last N messages), and let the user choose the destination and filename in the browser when supported. The result must be a usable `.json` file matching the upstream native OpenCode export structure and independent of whether that session is currently active or finished.

Suggested UI: a modest **Export JSON** action beside the session-detail heading/ID, accessible on desktop/mobile, not on every prompt row. Default to **sanitized export**, matching the owner's recent `opencode session export <session-id> --sanitize` usage. The label/help should state that content is sanitized and may still warrant review before sharing. Do not silently offer raw data as though sanitized. An explicitly requested full/raw export may be considered separately but is **not required** by this FR.

## Verified feasibility and preferred architecture

The supported current OpenCode V2 CLI has `opencode session export <session-id> --sanitize`; its experimental HTTP source also provides `GET /api/experimental/session/{sessionID}/export` with `sanitize=true`. OpenCode Toolkit's guarded `Runtime.export` already consumes this endpoint for LIVE evidence; its source README confirms the private test servers share sessions with the ordinary installation. **Verify the running source's actual supported endpoint/shape** and sanitized parity before choosing a production transport: an experimental endpoint can change with OpenCode versions.

Cost Guard already has an authenticated, loopback-only Web Beta HTTP server (`src/web/http.py`), a selected OpenCode V2 source and same-origin/CSRF protections, and the individual-session view (`src/web/assets/session.js`). The server is in principle capable of performing a **read-only native export** without invoking an AI model or restarting OpenCode.

**Prefer source-native export through the already trusted local V2 transport**, using the source's existing credentials/instance rather than passing them to the browser. Avoid spawning a second OpenCode service, modifying active sessions or shell-executing a user-supplied command. If a CLI fallback is truly required for a supported version, execute a strict fixed executable/argument array without a shell, pin the known session ID and source/database context, set finite time/output limits, and verify native output JSON; no interactive picker, unbounded process or generic command endpoint.

**No disk staging/move is necessary when feasible.** The server can obtain a bounded export and deliver it as an authenticated `application/json` file response; the **browser** saves the bytes to the destination the user selects. A web server cannot directly move its own temp file to an arbitrary browser-selected local path. If bounded tempfile staging is warranted for large exports, scope it to an owned private directory with cleanup on success, error, cancel, host shutdown and expiry; never write the session content to the repository, shared temp area or persistent Cost Guard cache.

## Browser Save As behavior

- In browsers offering `window.showSaveFilePicker` (notably supported Edge/Chrome versions), request a native **Save As** picker directly from the **user's click** (transient activation can expire after asynchronous export), with a safe suggested `.json` filename and only user-chosen destination. Download/commit the content only after the export succeeds and validates. Cancellation is clean, with no completed-export claim or unnecessary source work.
- Provide a **standard authenticated browser download fallback** for browsers without the File System Access API. Use `Content-Disposition: attachment` and/or a safe same-origin Blob/object URL with `download`; the browser's own settings may save automatically to Downloads rather than showing a dialog. Do not promise a universal Save As picker or require additional browser extensions/dependencies. Revoke object URLs and release resources.
- Do not use browser localStorage, server saved-path preferences, `file://` writes, hard-coded Downloads paths or arbitrary destination path parameters. The user, not Cost Guard, chooses where the exported bytes are saved.

## Security, privacy and lifecycle limits

1. **Exact selection and identity:** accept only a currently selected, canonical source-qualified session identity already available to the authenticated host; validate a narrow `ses_...` ID grammar and resolve it under the same source instance. A stale detail/token, a source switch or deleted session should fail clearly, not export a different session. No user-controlled paths, raw URLs, subprocess arguments, source credentials or session dumps in errors/logs.
2. **Explicit user action:** authenticated same-origin access, CSRF-protected POST initiation if generating transferable content, bounded one-time download lease if using GET. Existing Host/Origin/Sec-Fetch/session/instance protections must not be weakened. Avoid putting secrets/download authorization tokens in a query string or Referer; prevent cross-site downloads, prefetch/autogenerated links and cookie-only cross-origin triggers.
3. **Privacy by default:** use *native* `sanitize=true` / `--sanitize` semantics, with a clear notice that sanitization is not a guarantee of public safety. No passing raw transcript to Cost Guard's normal analytics DTO, SSE, diagnostics or browser history. `Cache-Control: no-store`, `nosniff`, download-appropriate content type/disposition, safe ASCII filename, bounded memory/response body and no sensitive logs.
4. **Complete and honest:** preserve the upstream JSON structure (including native message types, lifecycle/outcome metadata where supplied); do not reconstruct from projected Cost Guard data, silently truncate, fabricate terminal state or mark success on incomplete source reads. Support a running session's *point-in-time* export and explain that it may change. Use bounded timeout/size and finite concurrency; oversized/unsupported/source-unavailable or interrupted exports produce clear errors without a corrupt partial-success file.
5. **Source support:** target the existing OpenCode V2 source first. If selected source/installed OpenCode version has no validated native export capability (including V1/older V2), show a useful **Export unavailable** state or error with a CLI alternative, not a broken button or an unsafe surprise fallback. Export must not depend on opening the session in Desktop or on the original private LIVE server still running.
6. **Host lifecycle:** do not block Watch/report refresh indefinitely or leave detached work on tab close, cancel, source generation change or Web shutdown. Release any buffers, temporary files and workers; no new dependency, external service or active model call.

## Acceptance and focused tests

- Open a real or synthetic **LIVE-style** session with a valid OpenCode native export but absent from ordinary Desktop's current project list; click **Export JSON** from that session detail; obtain a valid, complete *sanitized* JSON file for the **correct session**, matching native upstream export fields and content semantics.
- Check a completed session, a currently running/incomplete one, 0-assistant and nonzero-message cases, multi-page/large exports, Unicode characters and filenames, malformed/unsupported API responses, source restart/change, vanished ID and permission/authorization failure. Never mislabel native session `outcome=succeeded` as proof every later prompt completed.
- In Edge/Chrome, verify a user-click Save As picker on a real loopback host and that cancel produces no saved file. Test the ordinary download fallback on a browser without picker support and explain the browser-dependent save location. Preserve existing page navigation, history scrolling and UI focus on success/failure.
- HTTP/security tests: unauthenticated/cross-origin/cross-site/CSRF/bad ID/expired lease/host identity failures; response MIME/disposition/cache/size bounds, no path traversal or command injection, no raw transcript in diagnostics or storage, cleanup on cancel/timeout/host shutdown. An export must not start a new OpenCode process or modify selected source data.
- Record verified native interface/CLI version compatibility, bounded load/resource measurements, and limitations. Run relevant tests and existing package validation as normal implementation work; this authoring task runs no product tests.

**Non-goals:** importing sessions, deleting/archiving them, rendering a full transcript in the web page, rewriting the native OpenCode export format, automatic recurring exports, arbitrary filesystem access or making Toolkit LIVE sessions appear in OpenCode Desktop.
