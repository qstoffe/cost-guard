# FR 000520 — Cached console-free native Web Beta launcher and seamless startup

## Owner observation, goal and sequencing

After pulling the evolving Beta while FR000480 was being worked on (2026-10-27), the owner again observed a disruptive Windows desktop double-click experience: a transient console/PowerShell window remains open or appears to hang while the Web server, tray and browser seemingly become ready, and it may not close when expected. The owner would prefer a **one-click, polished app-like startup**: on an unchanged checkout the terminal should be absent or at most briefly flash, a managed tray icon and Web browser should open seamlessly, and the visible browser should own ongoing app/report loading progress. On a changed version a one-time local native-launcher build is acceptable if it gives visible, honest preparation status.

This is **new post-delivery owner feedback**, not proof that existing FR000420 failed all its automated tests. FR000420 intentionally delivered the visible-console/status fallback rather than a truly console-free launcher. FR000470 subsequently fixed a *different* reproduced source of unwanted windows: detached ReportJobs child consoles via the paired `pythonw.exe`. Keep those fixes; identify which window remains in a real double-click now.

**Sequence:** append after current Web page UX work FR000480–FR000510. Do not edit or pre-empt active FR000480 or rewrite completed FR000420/FR000470. This FR is an **optional Web Beta launch/runtime UX improvement**, not promotion/Legacy retirement or a general packaging mandate.

## Preferred design to evaluate and implement

1. **Reproduce and instrument the owner-facing launch.** On supported Windows, identify exactly which processes/windows own the transient console, PowerShell progress, detached `pythonw.exe` host, ReportJobs children, browser and native tray. Compare a cold/no-host launch, a warm host restart, repeat double-click, a slow/failed start, and a source update. Record process/window timeline and browser handoff time. Do not infer that browser paint or report readiness equals launcher completion. Confirm whether source-update shutdown or an error path can keep an existing console open. In particular audit `windows/Beta/Cost Guard Web.cmd` → `src/web/windows_launch.ps1` → `src/web/windows_launch.py` → `src/web/lifecycle.py` with the FR000470 `pythonw.exe` change in place.
2. **Favor a tiny, GUI-subsystem/native Windows launcher executable**, generated **locally from committed, auditable source** and stored in a protected user-local Cost Guard Web artifact area, not inside the checkout and not beside/deleting user data or analysis caches. A small OS-in-box C#/`Add-Type` helper or another genuinely no-install Windows-native solution is the initial feasibility candidate, as already allowed as a provisional option by FR000290's `PLAN.md`. The helper may orchestrate the existing managed Python Web/tray runtime; it need **not freeze/package the whole Python application**, duplicate its server, ship an interpreter, or rewrite the report-worker architecture. Evaluate the even simpler no-console script/interpreter handoff as a control; choose the simplest design that actually solves the owner-visible window problem with acceptable security/reliability/startup timings. If a locally compiled launcher offers no meaningful improvement, report evidence and choose the superior console-free no-build route rather than building an unnecessary exe.
3. **Cached rebuild-on-change.** The stable double-click entrypoint must detect an existing validated artifact. On unchanged relevant source/runtime/OS architecture/interpreter identity, reuse it without compiler work; delegate asynchronously and exit/close its own console immediately. On a mismatch/missing artifact, build/prepare once in a bounded, isolated temporary location, validate and atomically publish it with a bounded manifest/fingerprint. Include source inputs and build contract, OS/architecture and relevant interpreter/helper/tool versions in the key; **product version alone is insufficient**, and do not rebuild on unrelated documentation edits. Treat a changed checkout after `git pull` as a controlled update, not a network-based auto-updater. Do not execute a stale, partial or unverifiable cached binary, follow reparse/symlink redirections, or overwrite a possibly in-use executable.
4. **Honest first-build progress and errors.** On cache miss, show a clean, legible `Preparing Cost Guard Web…` native status/brief controlled console as needed, with real steps (finding already available compiler/interpreter, building, validating, launching). A **0–100% progress bar is welcome only if actual measurable build stages justify the percentages**; otherwise use a polished indeterminate progress indicator and current step/elapsed time, not fabricated precision. No unexplained blank black window for seconds. Bounded failed builds give actionable diagnostics and a safe usable fallback to the current supported launch method when possible, never a silent hang or destructive cache reset.
5. **Warm launch is genuinely smooth.** Double-clicking the normal Windows entry should not keep a console/PowerShell window alive while the host initializes, checks ownership, stops an old instance, opens a browser or loads accounts. A short initial flash is acceptable if platform launch mechanics require it, but the preferred solution has **no visible console on warm launches**. Launch detached and do not inherit a console/standard handles; show the tray icon as soon as the correct host has safely initialized, open the browser through the existing one-use authenticated flow, and present existing branded browser readiness/report progress. Avoid opening duplicate tabs/hosts on overlapping clicks and never show an incorrect ready indicator. No background daemon/service/autostart, automatic Git pull, browser pop-up loop or arbitrary OS permission change.
6. **Lifecycle/security must remain authoritative.** Preserve FR000310/FR000320/FR000380 instance ownership, checkout isolation, private lock/state, source-change shutdown, process-birth/identity checks, per-instance bootstrap/control token and loopback-only secure HTTP. A GUI wrapper must not leave orphan hosts, break tray Open/Exit, lose sanitized startup errors, let another checkout terminate this one, bypass preflight, or accidentally spawn consoles from ReportJobs (keep `pythonw.exe` or a verified replacement). Treat cache artifacts as executable code: private ownership/ACL, content integrity and safe paths/atomic publication. No claim of protection against arbitrary same-user malware. Ensure clean CLI/Watch and developer `--foreground` behavior is untouched.
7. **Respect the existing zero-install/offline contract.** Normal users must still be able to clone/pull/run with Python 3.11+ and OS-provided facilities, without PyInstaller/Nuitka/SDK/downloads, extra packages, a source-distributed exe or a separate installer. Do not silently add a build-tool prerequisite or download a compiler. If a native executable **cannot** be compiled using built-in supported tooling, do not quietly replace the Beta with a packaged Python binary: use a proven no-console handoff/fallback and state the limitation. A full frozen executable/bundled Python distribution would be a **different scope requiring explicit owner approval and cost/size/security/AV assessment**.
8. **macOS parity, without duplicating existing work.** The Mac Beta already locally compiles and caches a Finder `.app` using `/usr/bin/osacompile` with source/OS/interpreter fingerprinting in `src/web/macos_app.py`. Reuse/audit that mechanism and check whether Finder/Terminal startup remains intrusive. Do not require a second compiler, Windows-style `.exe`, downloadable bridge, unsigned distributed app or undocumented security bypass. State actual macOS native evidence/limitations, and if further changes are needed keep them platform-specific. The stable CLI remains separate on both platforms.

## Acceptance and evidence

- A real Windows Explorer double-click on an unchanged checkout shows **no persistent console window** while the detached server, tray and browser start. The launcher exits independently of slow source discovery, slow normal report and eventual browser paint; visible browser loading and server-failure recovery remain accurate. If any optional short flash is necessary, record why and its observed duration. No repeated shell/progress window that appears stuck after successful handoff.
- A cache hit performs zero build work; a cache miss or changed relevant source triggers exactly one controlled rebuild (including concurrent clicks), with honest visible progress, successful manifest verification and atomic swap to the correct executable. Tests include source/OS/Python version changes, corrupted/cache-tampered artifacts, symlink/reparse attacks, interrupted build and build/tool unavailable. No user cache/config/history deletion. Record cache size and actual warm/cold/build timelines on real hardware; prefer improvement evidence over arbitrary hardcoded universal timing targets.
- Tray Open/Exit, browser failure and retry, native tray/preflight failure, invalid configuration, stale/occupied-port instance, source-change detection, host identity, overlapping launch, multiple checkouts, long path/Unicode, ReportJobs and shutdown behave no worse than the current solution. Never weaken the private loopback auth/control boundary to make a window disappear.
- Run targeted Windows native/process lifecycle and real GUI/window-visibility smoke, plus the existing Full tests/package validator and, where applicable, the hosted Windows/macOS workflow delivered in FR000410. Separate simulated CI from physical GUI/Explorer verification. Update `docs/web-beta.md` with actual executable cache location, rebuild triggers, offline dependencies, repair/removal instructions **limited to owned executable artifacts**, failure modes and supported OS behavior.
- Report a clear implementation choice (tiny native cached helper vs verified no-build console-free mechanism), measured benefit, trade-offs and any unresolved owner-visual checks. Do not claim a complete packaged standalone Cost Guard executable if the helper still requires installed Python.

## Scope / related work

This FR authorizes a **bounded native Web Beta launch experience improvement** and local helper caching **if technically feasible under existing no-install constraints**, rather than presupposing that compiling the entire Python product solves the UX. Other page-parity FRs 000480–000510 retain their own scope and sequence. No product change takes place simply by publishing this specification.
