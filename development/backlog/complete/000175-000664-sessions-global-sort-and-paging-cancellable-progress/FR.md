# FR 000664 — Sessions: reliable global sorting and paged loading with truthful progress and Cancel

**Owner-approved Ready Feature Request, 2026-11-09.** Permanent identity **000664**, Ready priority **000990** following FR000663 (000980). **FR-only publication:** create this FR and advance `development/backlog/identity-state.json` highWatermark **663 → 664** together in a documentation-only commit on `main`. Do not change product code, tests, version/releases or completed backlog files in this publication.

## Owner observation and intended experience

The owner's **Cost Guard Web → Sessions** catalog contains **more than 3,000 sessions**. Sorting **Last activity** or **Session name** seems responsive. Clicking the other four advertised sortable headers — **Model, CCost, Prompts, Duration** — appears to do nothing, even after more than a minute, and gives **no visible progress or explanation**. The owner wants **all six headers genuinely sortable**, but slow global sorts and uncached page navigation should instead show the application's familiar centered **determinate 0–100% progress** and a clear **Cancel** control that returns to the previously usable view.

**Desired interaction:**

1. Click any header. If the new sort is already resolved/cached and the target 50-row page is ready, apply it **immediately**, without replacing the table or flashing an unnecessary loader. Same for quick Previous/Next navigation.
2. If a sort needs significant global index work, **replace/hide only the Sessions grid and pager for this pending navigation** with a centered, shared report-style progress bar, stage text, real percentage and **Cancel** below. A transparent explanation may say `Preparing Model sort (428 of 3,217 session summaries)…`.
3. On verified completion of that global ordering, present the **correct first page of 50 sessions in the requested sort**, with visible values ready as far as supported, then continue filling independent lower-priority fields normally. Once source-valid and sorting keys are ready, do not wait for all other pages' *display content* to be rendered or eagerly hydrate every entire session transcript solely because those pages exist.
4. Clicking Next/Previous to an uncached or insufficiently indexed page similarly shows the center loader. **Cancel** in this case immediately restores the **previous successful page**, not an unrelated default page.
5. **Cancel on a sort** immediately restores the **previous successfully applied sort, page, pager, focus and browser navigation state**. It should be clear from the Cancel button's own hover/focus/touch tooltip what will be restored for that particular operation.
6. If a sort/page cannot finish due to source outages or permanently missing evidence, **show an actionable bounded failure with Retry and Cancel**. Never silently sit in `pending_sort` forever with an old table and an apparently active new sort.

This is a Sessions catalog operation-level loading/cancellation UX, not a new global cancellation system for finite report jobs or session-detail loading. Coordinate with FR000658's shared pager visual rules and FR000662's centered Session-detail loader style; reuse the same shared Web progress design without changing either FR's independently scoped behavior.

## A. Actual code trace / reason this currently appears stuck

**Verified source at FR authoring (not a reproduced real-user timing measurement):**

- `src/web/assets/sessions.js::SessionsCatalog.View` advertises clickable sortable headers for `activity, name, model, ccost, prompts, duration`. Clicking sets a hash URL to `#/sessions?sort=...&direction=...`; `configure()` changes requested sort and generation.
- `src/application/session_catalog.py::SessionCatalog.page()` implements global ordering. It computes `indexed = sum(self._current(key) for key in self.roots)`, then `pending = sort not in ('activity', 'name') and indexed != len(self.roots)`. For a pending expensive sort, it **deliberately applies Activity instead of the requested metric** and returns `pending_sort=true`, `indexed`, `available`, `page_ready`, `sort=activity`.
- `src/web/assets/sessions.js::View.update()` explicitly **returns early** when `this.usable && data.pending_sort`, retaining the old display, and does not show a pending-sort notice, count or loader. That is a verified user-visible silence, **not proof that the worker stopped**.
- `SessionCatalog._targets()` selects all roots while a browsing lease requests Model/CCost/Prompts/Duration. The shared host-owned `SessionCatalog.tick()` indexes **up to four** roots per tick, with a **two-second slice bound**; `needed()` and `_eligible()` govern progress and retry intervals. With 3,000+ sources, cold/invalidated scalar summaries may legitimately take much longer than simple Activity/Name ordering. Roots with repeated failures, changing source revisions or unusable cache keys can also prevent `indexed==available`, so a terminally stuck pending state must be differentiated from normal slowness.
- `SessionCatalog.page()` already returns a coherent **50-row** page, total/epoch/sort/order and **indexed / available / page_ready** counts. Those values provide a natural starting point for real source-backed progress and first-page readiness **without** browser-owned per-session fetches.
- `src/web/assets/report-loading.js::ReportLoading.View` and shared `.report-loading` CSS render a central **numeric 0–100%** bar, percentage and stage without marquee animation. Reuse the stable visual controller/pattern rather than inventing a second progress design.
- The current URL/hash navigation and `SessionCatalog` leases/epochs maintain stable older-page membership, while visible interest influences indexing priority. Any new Cancel must preserve those correctness and ownership contracts. Existing index caches are valuable and should remain available after Cancel.

**Important distinction:** Nothing in this evidence proves every metric sort is intrinsically impossible. They are **supported** but globally gated. Do not remove their sorting affordance as a workaround. First reproduce and measure large-catalog behavior and improve/index or recover the actual blockers.

## B. Correct full-catalog sorting, with fast first-page publication

**Nonnegotiable correctness:** sorting Model, CCost, Prompts or Duration must be the **true deterministic global sort** across the pinned available root-session set, *not* a browser-side sort of whatever 50/150 rows happen to be visible, nor an Activity fallback silently relabeled as Model.

1. Preserve all six existing sort keys and their true semantics:
   - **Last activity:** actual root activity timestamp.
   - **Session name:** stable case-insensitive canonical title ordering.
   - **Model:** canonical model display/order, including `Multiple models` and correctly resolved model identities; distinguish genuinely unavailable model from not-yet-indexed.
   - **CCost:** unrounded **whole-session reference cost** with partial/unpriceable values last in either direction; not rendered USD/Credit text, not actual billed cost.
   - **Prompts:** canonical numeric root prompt count.
   - **Duration:** canonical execution duration in milliseconds, not formatted duration text.
   - Preserve deterministic session-ID ties, unknowns last in ascending/descending, distinct source revisions and currently supported contribution/usage facts.
2. **Global sort keys versus page bodies:** the first page of a globally sorted list cannot be known reliably while an arbitrary unindexed root may outrank the current candidates. Therefore resolve/reuse a **complete, revision-qualified scalar sort-key index for the relevant catalog membership** (or an equivalently proven upper-bound/top-k algorithm), then return/render only the **first 50 full display rows**. Do **not** promise a true top 50 from only 50 scanned sources. It is legitimate that global key validation for 3,000 sessions precedes first-page publication, but **not** that the browser eagerly fetches every other page's detailed rows, tooltips or transcripts.
3. Reuse valid existing `session_summary` and shared derived-cache evidence, source revisions, per-root scalar summary cache and indexed/terminal-known-missing facts. Where safe, optimize the expensive path to acquire **just the scalar sort keys** for all roots rather than full expensive row/render data; preserve identity/cost/duration integrity and the host's source/read/CPU/memory budgets. Prefer changing key readiness/index scheduling and reuse to adding yet another global report/worker.
4. If one root is **temporarily unindexed**, keep it pending. If a metric is **genuinely unsupported/unknown** based on completed source evidence, record it as a valid **sort-last unknown** once that is truly established. If terminal source failure means the global key's rank cannot be known, report a **terminally unavailable sort** with an honest reason and recoverable previous view, rather than claiming correct complete global ordering or never completing. Do not make one permanently unsupported root trap every metric sort forever.
5. Preserve **existing 50/page** navigation, one coherent source/epoch, ability to reverse sort, stable older-page memberships despite arrivals, page-1 freshness, properly correlated root updates and source invalidation. Previously pinned pages must not gain skipped or duplicated entries due to a new catalog revision. Do not degrade existing fast Activity/Name sorts.
6. **Performance proof:** instrument *index count/total, cache hits/misses, attempts and retries, applied vs requested sort, source-error reason and clock time*, using only sanitized counts/IDs. With a synthetic 3,000+ root catalog, prove that repeated/global sort with warm valid keys becomes fast without rehydrating every source; cold sort may be slow but must progress or terminate visibly.

## C. Loading UI: one consistent determinate bar, only when necessary

1. Use the existing shared `ReportLoading.View`-style visual (centered in the Sessions content region, same width, theme, font, spacing, `max=100`, numeric percentage and status label) while a **requested sort/page operation is pending**. It replaces the grid/pager only for a genuinely pending operation, not the entire app navigation or shared host status. Under the bar show a normal **Cancel** button, and a separate Retry when the operation is terminally failed.
2. **Do not flash the loader for cheap operations.** When the server returns an already sortable, fully ready matching snapshot or a pinned cached page immediately, keep the table and update in place without a loading-state layout swap. A small bounded admission delay/first-response check may avoid unnecessary spinner flashes, but must not falsely claim the new sort while the old rows remain.
3. **Truthful granular progress:** for global metric sort, use `indexed / available` (e.g. 428/3,217) plus any more specific authoritative count of *eligible missing keys remaining* and real revision/index phases, carefully distinguishing valid cached keys, observed unknowns, source failures and unavailable roots. A stable complete catalog can give **meaningful continuous 0–100% stage-weighted progress**; do not fabricate progress from elapsed seconds. For page loading on an established pinned sort, use the actual `page_ready` / 50 (last page may be smaller) and true page-delivery/apply milestones, not the whole 3,000 denominator again when unneeded.
4. **Phase labels examples** (adapt to source truth): `Checking cached sort keys…`, `Indexing CCost (428 of 3,217 sessions)…`, `Waiting for OpenCode source…`, `Preparing page 2 (18 of 50 sessions)…`, `Applying page…`. Show the exact requested column and page context as appropriate. On unknown source readiness, hold the measured percent and explain waiting, not a time-based animated estimate.
5. A progress attempt has a **unique operation generation**. It starts at 0 for a truly fresh pending operation, advances monotonically **within the current coherent source/index generation** and reaches **100 only when the correctly sorted, requested page has been validated and applied**. A catalog/source revision change requires an explicit controlled restart/rebase of progress and a truthful stage, not a silently decreasing denominator or an old result marked complete. When an attempt errors, it transitions to visible failure/retry; no permanent 90/99% hold.
6. Display **Cancel for every long-running sort and uncached page request**, placed directly beneath the loader with an accessible label/tooltip attached to the actual button (using the existing `ContextHelp` hover/focus/touch system). Tooltip wording must be **operation-specific**:
   - Changing sort: `Cancel this sort and return to the previous sorting and page.`
   - Next/Previous: `Cancel loading this page and return to the previous page.`
   No new modal/confirmation, no hidden gesture or indefinite pending cancellation.
7. **Short operations:** if a sort or page finishes before the loader would be visible, do not show the progress panel or a split-second Cancel. Commit the new correct snapshot directly. If user is already looking at cached fully qualified page membership, use it; no fake loading.
8. Provide concise polite screen-reader status (announce **stage transitions**, not each 1% change), a stable semantic `<progress max=100 value=...>`, keyboard-focusable Cancel, focus restoration after cancel/success, and responsive nonblocking layout under Classic/Web light/dark. Keep no marquee/bouncing animations.

## D. Cancel semantics: roll back the UI intent, not global shared source work

**Cancel is a per-user navigation rollback**, not permission to kill OpenCode, discard shared sessions, erase caches or stop the background indexer that Watch/Sessions/other tabs need.

1. Before starting a pending sort/page, retain the last successful **applied** snapshot: sort key, direction, actual current page offset, pinned epoch/revision, returned 50 row identities/values, existing scroll/focus/selection as practicable and browser hash destination. Do **not** treat a requested-but-not-applied sort or `pending_sort` Activity-fallback page as the previous successful state.
2. Pressing Cancel immediately restores the actual old table and pager, old sort indicators, old URL/hash/history semantics and the appropriate old page without needing to requery or re-index 3,000 sessions. Cancel after an unsuccessful Next returns to the **page the user came from**; Cancel after a header sort returns to the last fully applied sort **and original page**, not automatically page 1.
3. Retire/ignore old pending response generations; a delayed sort completion or page answer must **not** re-apply after Cancel, navigation away, second sort intent or a later successful operation. Manage request `AbortSignal` for local HTTP where supported and update **interest leases** so global expensive-sort prioritization can subside after Cancel, while **shared server work and its reusable cache entries remain safe**. Do not make Cancel block on pending server reads or call global cancel endpoints.
4. A completed prior cached page must be available for immediate return even after page requests fail. A stale/expired epoch is handled by the existing safe reacquire/rebase policy with an **explicit user-visible explanation**, never a fake restoration of wrong membership; the prior DOM snapshot can remain as retained data until validity is re-established.
5. Cancel button tooltip and keyboard/touch behavior are tested; Escape may optionally perform the same operation when focus is within the loader, but must not steal ordinary global Escape semantics or cancel unrelated tasks. No requirement for multiple simultaneous per-tab sorts; latest user intent wins.
6. On terminal source/auth failure, keep the prior good table and show a focused Retry/Cancel or error affordance. Avoid infinite 5-second silent retries and never disable all navigation indefinitely because one index root failed.

Selecting a metric initially pending never pretends the Activity order is the requested sort.

The URL, header arrows/`aria-sort`, highlighted row membership, keyboard focus, scroll, browser Back/Forward and active source-interest scope remain coherent; no canceled completion later replaces the restored view.
5. Source permanently unavailable, transient retryable error, model-reference/CCost validation failure, missing canonical key, expired epoch, revision churn, newly arrived sessions, canceled in-flight HTTP, host identity change and hidden-tab navigation produce **honest progress/wait/error/recovery**, never an unending silent `pending_sort` or forged unknown/zero sort keys.
6. Measured progress never runs ahead of the real work, goes backwards within one source generation, or reaches 100 for a merely cached Activity fallback. Counts/total come from actual index/page work; 0/empty and changed-root membership handled without NaN, arbitrary elapsed-time fill or phantom completed tasks.
7. Source work and cache remain shared/host-owned: no extra model calls, global backend termination, raw-content logging, full per-page transcript hydration, credential prompts or unbounded memory growth. Fairness to Watch, session detail, account and live lanes remains intact; canceled sort demand no longer indefinitely prioritizes every root.
8. DOM + **real browser** tests for busy-slow-progress, instant cached, cancel/fail/retry, 50/last-page, first/older-page navigation and 3,200-session membership in 360/800/1366/1920 widths at 100–150% zoom, Classic/Web light/dark, keyboard/hover/focus/touch. Extend `development/tests/test_web_session_catalog.py`, `development/tests/integration/probe_web_sessions.cjs`, `session_catalog_observations.py` and relevant session/pager route fixtures. Record sanitized before/after source-stage timing and PASS/FAIL honestly, without live model inference.

**Done means:** every advertised Sessions sort works correctly on a large catalog; long sorting/paging is visibly meaningful and cancelable; cheap cached navigation stays instant; the user can reliably return to the last good table rather than staring at an unchanged page for minutes.
