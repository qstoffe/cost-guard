# FR 000679 — Sessions: silently recover from expired catalog leases and refresh visible rows

**Owner-approved Ready Feature Request, 2026-11-11.** Permanent identity **000679**, Ready queue priority **001110** (currently the only Ready task). **FR-only publication:** add this file and atomically advance `development/backlog/identity-state.json` highWatermark **678 → 679** on `main`. Do **not** implement source code, run product tests, change product/release/version files, or edit unrelated backlog items in this publication.

## Owner-reported problem and desired UX

On **Cost Guard Web → Sessions** (`/#/sessions`), the populated sessions table displayed an amber banner:

> The previous catalog expired; showing the latest first page.

The banner gave no useful action or explanation, remained on screen, and disappeared only after the owner **manually refreshed the browser page**. A user should not need to know about internal catalog leases, epochs or retention limits, nor wonder whether to reload the whole website. This is a routine recoverable internal condition, not in itself a user-facing failure or proof that every displayed session metric is stale.

**Required outcome: Sessions automatically recovers and keeps the visible table useful, with no enduring `expired` warning and no manual Refresh/reload.** The preferred UX is *silent background revalidation*: show the last usable coherent page while the existing host-owned pipeline obtains a safe replacement; update changed visible rows/cells in place when fresh results are available. Do not make the page flash, hide the populated table, change unrelated rows or announce routine checking/loading.

The owner mentioned that a restrained temporary `Refreshing sessions…` hint could be acceptable if data truly cannot be presented usefully during a prolonged active refresh, but **prefers no refresh text at all in normal operation**. A status must describe actual work, disappear when resolved, and never become another sticky warning. This request does not authorize unsolicited freshness disclaimers.

## Existing contract, observed code defect and boundaries

- Completed **FR000634** already established Web-wide quiet refresh and explicitly required silent `catalog_expired` recovery in Sessions, including keeping usable rows visible and preserving URL/pagination/sort correctness. This FR is a focused repair/regression hardening of that existing behavior, **not** a replacement report-loader framework.
- In current `src/web/assets/sessions.js`, `View.load()` catches `catalog_expired` and reopens once, setting `recovering` while returning safely to the latest page when the prior epoch cannot be trusted. `View.update()` then sets `this.rebased = true` and unconditionally chooses `'The previous catalog expired; showing the latest first page.'` whenever `this.rebased` remains truthy. **The flag is not reset on subsequent successful updates**, which explains the persistent UI banner from the inspected code. Verify the real route lifecycle before calling any wider stale-cache issue fixed.
- `src/application/session_catalog.py`, the catalog HTTP interface and the host-owned Sessions interest/index worker already provide 50-row pages, lease/epoch validation and qualified background work. Lease expiry **does not imply** that the full historical catalog, all metric values or the underlying source have expired. Do not clear all analysis/cache or re-enumerate thousands of roots merely to dismiss a frontend notice.
- Existing global sorts sometimes require host-owned index keys beyond the visible 50 rows to guarantee correct ordering. Reuse that necessary shared work when required; **do not compromise globally correct sorting** just to enforce a literal 50-root-only backend rule. Avoid any new per-tab full-history scan or unbounded polling.

## Required behavior

1. **Remove the passive catalog-expired banner at its cause.** An automatically recovered lease/epoch must never leave `The previous catalog expired; showing the latest first page.`, a renamed equivalent, or a persistent hidden/live-region announcement above or below a populated Sessions table. Correctly retire/reset transient `recovering`/`rebased`/status state on successful page publication and ordinary subsequent polls. Do not merely hide the text with CSS or rely on navigating away or F5.
2. **Silent automatic revalidation of the currently displayed page.** When entering or revisiting Sessions, during ordinary five-second visible polling, or after a recoverable lease expiry, keep a valid last-known 50-row page and pager visible while the host refreshes/reconciles the needed page and visible metric values. Reuse qualified summaries and the existing interest/refresh cadence; update only values, rows and order actually changed by a coherent accepted response. Preserve keyboard focus, selection, scroll and table DOM where possible. No forced whole-page browser reload, table-wide empty/loading flash, global historical scan or extra spinner.
3. **Correctly handle invalidated page positions.** Reopen/re-anchor the same requested offset where the backend can prove it valid. Where the old membership/epoch cannot be proven, the existing safe fallback to the *latest first page* is acceptable: retain selected sort/direction, atomically synchronize new epoch/token, URL, pager count, rows and sort header. Do **not** silently mislabel old rows as page 1, show the wrong global order, or reuse data from a different source. Make the transition unobtrusive; never leave a stale position banner after it succeeds.
4. **Use status only when genuinely needed.** Before any usable page has loaded, a small initial `Loading sessions…` state is fine. For explicit user-initiated navigation that blocks on indexing, retain the existing truthful operation-specific progress/recovery controls. If a genuinely blocking prolonged source condition makes last-good content unusable, show one concise, non-alarming, *accurate* active-state message only while necessary and clear it on successful recovery. Routine lease renewal, stale-age checks, retained usable values and passive refresh must stay silent (including `role=status`/ARIA); a completed or failed operation must not be misrepresented as still `Refreshing…`.
5. **Real failures remain truthful and recoverable.** A lasting host, authorization, wrong-source or hard data failure must retain the existing appropriate actionable recovery surface; don't swallow it as success or spin forever. Safe retained rows may remain on screen with their internal provenance intact. Keep bounded automatic retry/backoff where applicable, lifecycle cancellation on navigation, source identity isolation, and no manual browser refresh requirement for the recoverable lease case.
6. **No unrelated behavior changes.** Preserve global sorting semantics, newest-session discovery, pagination (50/page), running indicators, per-field Loading/Unavailable correctness, CCost/CTX truth, session-detail links and host-owned read-only source boundaries. Do not change other reports, Mini Watch, backend cache semantics, user settings, pricing or releases simply to remove this notice.

The table remains usable; the banner is absent after recovery and **stays absent** without browser reload, including from visible DOM, accessibility status and any retained `rebased` state. Confirm the specific persistent-flag defect is fixed.
- **First and older pages:** repeat on page 1 and an older page, including changed membership/epoch, previously pinned sort, ascending/descending global metric sort and rapid navigate-away/back. Verify the backend-approved safe fallback, correct URL/epoch/token/pager/rows/header and no false page content or lingering status.
- **Quiet refresh:** healthy foreground polling with unchanged values makes no unnecessary table recreation, progress chatter or focus/scroll jump; changed visible session metrics and new newest sessions appear automatically. Retained usable rows stay visible during delayed background refresh, including foreground return after a hidden-tab interval. Expired lease alone does not trigger a broad source scan.
- **Initial and actual failure states:** first load remains intelligible, actual pending user sort still has truthful progress, transient expiry self-recovers, and terminal source/auth failures are not silently hidden or turned into permanent fake loading. Any exceptional active refresh status clears on completion or changes appropriately on failure.

Assert multiple post-recovery polls and accessibility status, not only the initial expiry. Run suitable real read-only Web/Sessions verification **during implementation**, reporting limits honestly.
