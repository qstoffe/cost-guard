# FR 000686 — Sessions detail: make loading percentage advance during source acquisition

**Ready to Develop — owner-requested 2026-11-12.** Permanent identity **000686**, Ready priority **001040**. A focused user-facing progress improvement for **Cost Guard Web → Sessions → open a single session**. Do not replace the progress bar, redesign Sessions catalog, or change unrelated historical report loading.

## Owner symptom and requested outcome

The centered loading presentation already looks good and its status text describes source work, but the **numeric progress remains at 0% for essentially the entire first load** and jumps to completion immediately before the session table appears. This occurs even for ordinary/early sessions that take roughly **2–10 seconds** to open. The owner wants the existing progress bar to **visibly advance through intermediate percentages while the session is actually being loaded**, not sit at zero until the end. Removing the bar is explicitly **not** the desired solution.

The goal is to communicate meaningful, forward-only loading work with a stable bar and useful stages, without a decorative clock animation that falsely pretends source progress.

## Verified causes in current code

1. `src/web/assets/session.js::SessionDetail.View` starts with `progress.percent = 0`; `sourceStatus()` receives pending `acquisition.phase`, `completed`, `attempts` and `progress_age_seconds`, but deliberately calls `loading(..., this.progress.percent, phase)`. Consequently **reading/verifying/analyzing/publishing may change the text while the bar always stays at 0%**.
2. `historyProgress(completed, total)` currently assigns **0–95% exclusively to browser transfer of already acquired, revision-pinned rich rows**, and `update()` marks **100% only after applying the complete DOM**. The first `/api/detail begin` cannot return a `total`/rows until the worker finishes acquiring, analyzing and publishing the source history.
3. `src/application/session_detail.py::SessionDetails.progress` stores only a cumulative `completed` work-unit counter plus a phase; `acquisition_status()` exposes these without a meaningful per-stage `total`. `src/watch/detail_capture.py::WorkMeter` counts heterogeneous real units (source operations, analysis/rows, serialized 64KiB chunks), **not one common denominator**. Dividing `completed` by an invented total would be invalid.
4. `src/reports/session_history.py::SessionHistory.acquire()` already reports real `reading`, `verifying`, `analyzing`, `publishing` phases and positive publishing row units; source adapters/analysis can report additional scalar work through `src/domain/progress.py::observe_work`. This is an integration point for useful progress before the first ready browser result.
5. Earlier **FR000662** intentionally introduced a determinate bar but reserved 0–95% for transfer and **left unknown source waits at 0**. **FR000674** fixed indefinite/poisoned source work with a supervised child, bounded retries and typed phases; it did **not** add a source percentage. **FR000673** improved pending polling/first-load measurements; its real delayed-source test explicitly observed **0% throughout pending acquisition**. This FR fixes that *remaining UX gap*, without reopening previously fixed liveness, source correctness or identity handling.
6. Current `development/tests/integration/web_session.cjs` explicitly asserts that 73 completed unknown-denominator source units remain at **0%**. `development/tests/fixtures/session_loading_browser.cjs`, `probe_web_sessions.cjs --detail-first-load` and `development/journal/web/session-loading.md` also codify the pre-acquisition zero behavior. Those tests are now **regressions of the desired UX** and must be updated, not used to veto the change.

## Required product behavior

### 1. A true whole-operation progress plan

Rebalance the single detail loader so there is **an explicit source-acquisition portion, a browser history-transfer portion, and an applied-render completion portion**.

A reasonable illustrative budget is:

- **0–70%: source acquisition/preparation.** Advance on actual start/phase milestones and, where available, measured per-phase completed/total source work: source selected/worker admitted, reading, revision verification, analysis, projection and source publication. Specific weights are implementation choices; they must be monotonic, meaningful, documented and consistent with real work. It is reasonable to mark a small **nonzero** percent when a real worker is admitted or a phase has actually started; that is a phase milestone, not claimed completion of a measured fraction.
- **70–95%: verified rich-row browser transfer.** Continue to use the real `completed/total` row fraction from validated `begin/chunk` replies, but remap it into the allocated transfer band. The accepted revision/row count and source identity remain authoritative. For a zero- or single-row session, this stage may complete almost instantly; that is fine because earlier source stages should already have shown progress.
- **95–100%: full table application.** The percent reaches **100 only once the final complete session DOM has actually been applied**. Avoid a falsely full bar while the table is still blank, and avoid an artificial fixed display delay after success.

These numerical bands are a **proposal, not an excuse to manufacture a percentage**. If another banding method better reflects the observed work and gives more informative intermediate updates, use it and document why. The key requirement is **real observable intermediate progress before `data.result` arrives**.

### 2. Surface meaningful server-side advancement before first ready result

- Prefer a compact, **source-owned and attempt-scoped progress contract** over mapping text or guessing a denominator in JavaScript. The existing `acquisition` object can be extended with bounded, safe **phase milestone/progress percent or per-phase measured `completed/total`** where the owning worker actually knows its total. Do not leak raw prompt/session contents, paths or credentials.
- Reuse `WorkMeter`, `observe_work`, the supervised detail capture and the existing immutable status API; **HTTP must not acquire history or start new source work** just to feed the bar.
- Distinguish discrete **phase-entry / phase-completed milestones** from actual within-phase fractions. Source operations with a natural known denominator (for example fetched message/part batches, already discovered rows or committed processed units) should advance within their phase where useful and cheap. Heterogeneous cumulative units without a denominator must not be mapped to a fabricated linear fraction.
- At minimum, a normal multi-phase **2–10-second session capture should show at least a few distinct, nonzero intermediate percentage values before the full result is available**, when those real phases and work units are emitted. Make the backend-to-browser status propagation frequent enough to paint them, using the already established roughly **500ms visible pending polling** or safe existing publication hints. Do not force additional source reads, report jobs, full-history passes or paid model calls.
- For a genuinely **opaque, non-progressing individual source operation** with no valid intermediate denominator, do not claim that 25%, 50%, 75% of that operation finished merely because a wall clock elapsed. Keep a truthful stage and the last proven watermark, or use a clear pending/waiting substate while honoring the current liveness watchdog. Explicitly document this limitation; it does not justify leaving **all ordinary multi-phase loads** at 0.
- No cosmetic `setInterval`/CSS interpolation that advances percent on elapsed time alone, fake source counts, arbitrary cap that creeps toward 99 while blocked, or invented completion from number of status polls. The user wants an informative progress bar, not a placebo.

### 3. Preserve existing recovery and UI guarantees

- Keep `ReportLoading.View`, its centered determinate bar, compact stage label, percent and accessible status. **One stable progress node** across polling and real work; no bouncing marquee, warning-colored normal loading, UI flashing or extra buttons.
- Percent is **monotonic within a coherent attempt** and never regresses due to changed phase, delayed poll, interleaved status, repeated work counts or browser rerender. If source retry/revision churn occurs, retain the last proven watermark where truthful and communicate the retry/wait separately; never use a previous attempt's speculative progress as proof for a new source. Reset appropriately on a genuinely new session/lease/generation, and reject late results.
- Normal fast success, large/archived/running sessions, 0/1/many rows, multi-chunk transfer, source reconnect, delayed source start, revision churn, separate active detail workers and cached same-revision refresh remain correct. Existing automatic status/retry and user **Retry session loading** semantics remain unchanged; failure must not look like 100% success.
- **Previously displayed, verified history** must stay on screen during quiet refresh, retained outages and normal navigation; no reappearance of first-load progress or focus/scroll/selection loss on warm revisit. Navigation away/Back, hidden tabs, host identity changes and abandoned loads must not modify a newer detail's progress.
- Keep progress lightweight for fast sessions: no minimum-loading animation time or intentional sleep to make progress visible, no extra toolbars or duplicated ReportLoading elements. If several phases complete between browser paints, allow jumping past them honestly; intermediate states must be observable on representative 2–10-second real work, **not artificially staged after completion**.

## Mandatory verification / acceptance

1. **Reported symptom (ordinary short session):** a supported cold detail that takes roughly 2–10 seconds and emits measurable reading/verification/analysis/publication work produces a visible ordered sequence **0 → several distinct nonzero intermediate percentages → 100**. At least one nonzero percent is displayed **while `result:null` and before the first ready `begin`**. Stage label matches the phase. It must not be only `0 → 95 → 100` after the result lands.
2. **Actual HTTP + browser evidence:** run the existing authenticated `Sessions → click session` flow through shipped JS and backend source worker, recording timestamps, `acquisition` phase/work/percent and rendered bar value in a representative source-shaped 2–10-second fixture. Ensure at least one genuine browser paint contains an intermediate nonzero value during acquisition. Use the existing `detail-delayed` fixture and/or a bounded read-only real-installation capture without modifying shared OpenCode. Document exactly what was actually observed, not just a mocked `sourceStatus`.
3. **Known and unknown work:** test source phase transitions, arbitrary positive heterogeneous units with no total, real `completed/total` fractions when known, first and final work, delayed poll, repeated phase, source restart/retry and stalled/poisoned child. Unknown-unit counts must not be mislabeled as a percentage; actual phase milestones can advance. No ticking solely from virtual clock progression.
4. **Transfer/render:** assert the new documented source/transfer/render budget, precise validated fractions for 0, 1, 25, 50, 220 and 1001 rows, exact revision/offset/row identity checks, late/out-of-order responses, 100 only after applied DOM. An incomplete/malformed chunk never finishes; honest terminal errors keep last-good history or a useful failure message.
5. **Lifecycle/accessibility:** stable DOM, single `<progress>`, correct `max=100`/`value`/`aria-valuetext`, stage-only polite announcements, 360/768/1366/1920 widths, themes and zoom/reduced motion. No scroll/focus theft, duplicate polling or extra HTTP/source workload; hidden tabs and navigation cleanup remain.
6. **Performance:** compare source work/child counts, HTTP status calls, cold and warm timings and first nonzero progress latency against baseline. Do not increase source hydration or serialize otherwise-parallel work purely for display; no new slow startup regression. Document when an atomic source operation remains unverifiable.

## Implementation pointers and non-goals

Likely owning areas: `src/web/assets/session.js::SessionDetail.View.sourceStatus/historyProgress/loading/update`, `src/application/session_detail.py::SessionDetails.progress/acquisition_status`, `src/watch/detail_capture.py::WorkMeter`, `src/web/detail_worker.py`, `src/reports/session_history.py` / `src/domain/progress.py` as warranted, plus `development/tests/integration/web_session.cjs`, `development/tests/fixtures/session_loading_browser.cjs`, `probe_web_sessions.cjs`, `development/tests/test_session_detail_liveness.py` and `development/journal/web/session-loading.md`. Preserve existing ownership boundaries and do not rewrite unrelated `report-loading.js` or change Token Mix/AI Stats/Models/Comparisons progress.

**Non-goals:** replacing the bar with a spinner, redesigning all report progress, synthetic percent-by-time, a new user setting, another worker, different provider/pricing/usage calculations, paid inference, raw private logs or any write to the shared OpenCode source.

**Done means:** opening a normal session shows **visible, source-driven progress percentages while the backend is still acquiring it**, followed by measured transfer and 100 only when the page is ready; the bar no longer sits uselessly at 0 for virtually the entire normal 2–10-second wait, without lying about opaque work or regressing correctness and performance.
