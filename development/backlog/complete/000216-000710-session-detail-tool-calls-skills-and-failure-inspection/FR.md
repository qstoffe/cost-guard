# FR 000710 — Session detail: expand all Tool Calls, Skills and failed call details

**Owner-approved Ready to Develop — 2026-11-14.** Permanent identity **000710**, Ready priority **000018**, following FR000709 (000017). **FR-only publication:** add this standalone request and advance the backlog permanent-ID high-water mark in a documentation-only commit. Do not implement product code, change running sessions, execute tools or paid models, change release/version files, migrate backlogs or modify unrelated FR statuses while authoring.

## Owner request and missing feature

When a user clicks a session in **Cost Guard Web → Sessions** and opens its **individual Session Detail** page, the page currently shows the prompt/history table and usage statistics but **not the Tool Calls and Skills expandable sections familiar from Full Web Watch**. The owner wants to examine all tool activity and used custom skills at leisure, including past/completed sessions.

**Desired experience:** On the selected session detail page, add **two familiar, initially collapsed, independent top-level sections: Tool Calls and Skills**, like the expandable activity sections under a running prompt card on Watch. Expand Tool Calls to see the **whole session's recorded tool-call totals, types and failures/cancellations**. If failures are present, expand the red failed-tool group and then each failed physical call to inspect **which actual invocation failed and its supported outcome/reason and safe details**. Expand Skills to see the session's confirmed custom skills and their supported failure indicators. The owner should not need to catch a prompt while Running in Watch to review this information later.

Keep the view oriented around **the selected full session**, not only the most recent prompt or the last displayed Watch card. Preserve the current Sessions table, prompt-history rows, session export action and cost/context displays.

## Binding functional behavior

1. **Two top-level expandable sections.** Place clearly labeled **Tool Calls** and **Skills** disclosure sections immediately following or adjacent to the complete Session Detail prompt-history table and totals, visually matching Full Watch's existing activity hierarchy, indentation, summary text, colors and native keyboard/touch disclosure behavior. Each panel starts collapsed on first selection. If a category has no verified activity, provide a consistent quiet empty/zero state or omit that unused panel as appropriate; never make an empty category look like work occurred. There is no need for a third top-level Running panel for an already completed session.
2. **Full-session scope.** Include **all source-observed physical tool calls across the selected root session's complete prompt history**, including older user prompts, applicable compaction/tool work and correctly linked subagent/nested-descendant calls within their actual causal windows. Counts must not be limited to the last active prompt, first history page, latest 5 Watch sessions, last terminal grace card or the current visible table viewport. Count one physical tool call once despite duplicate snapshots, repeated parts/IDs, retry observation or root/child attribution. Do not borrow work from unrelated sessions or another root.
3. **Tool Calls summary and expanded breakdown.** Reuse Watch's recognized tool-name groups, physical total, failure/cancellation count and red outcome groups. Make clear that **model Calls** in the session's existing table means model requests, not tool invocations. The tool group breakdown must account for the same session scope as the summary and include all supported historical completed, failed and cancelled calls, not silently suppress older tool types.
4. **Inspect individual failed calls.** Each supported red failed outcome group (for example, **4 × read failed**) should itself expand to a separate entry for **each distinct source-supported physical failure**, and each failure entry opens to its own details. Provide its actual tool kind, owning prompt/agent identification when source-qualified, original invocation information (for example, safe file path, grep pattern or shell command/workdir and relevant arguments), **recorded final status/outcome** and the **actual safe, source-supported failure reason/category** when available. Identical tool names/inputs on different calls remain distinct and inspectable; never invent reasons from a tool name, error count or time. If the recorded safe reason is unavailable, explicitly say so instead of claiming success or showing a fabricated error.
5. **Failure versus cancellation.** Keep genuine errors, user cancellations and interrupted calls distinguishable. Cancellations appear in the appropriate red/terminal aggregate with their factual status and may be inspected with the same safe per-call pattern where supported, but must not be reported as failed errors without evidence. Aggregate counts always reflect all qualifying calls, even if some individual details are unavailable.
6. **Skills summary and breakdown.** The Skills disclosure lists confirmed **custom skill IDs/names** used during the selected session with the same supported ordering/count and per-skill failure markers as Watch. Count unique skills consistently with Watch's definition; if multiple prompts load the same skill, avoid duplicate distinct-skill counts while preserving reliable usage/failure information. Do not infer that a skill was used solely because a bundled/built-in tool, unrelated script, instruction text or configuration mentioned its name. If the source cannot prove a specific skill, maintain an honest partial/unknown state rather than fabricate attribution.
7. **Full history and scalability without silent truncation.** A long-running session can have hundreds or thousands of tool calls. Preserve **complete aggregate counts** without a Watch-sized last-N or 10-failure cap silently masquerading as all history. Use bounded, user-controlled paging/incremental disclosure for lengthy per-call records, deterministic order and explicit **Load more** / remaining-count affordances where necessary. Every recorded, safely presentable individual failure in the selected scope should eventually be reachable, not only the first ten. For calls genuinely missing historical proof or safely displayable detail, give a truthful unavailable/omitted count; never fetch private history or fabricate details to fill gaps.
8. **Static and live sessions.** A finished historical session yields a stable reviewable outcome. When the opened session is still running, refresh genuine new activity into the correct groups without collapsing the user's already-open sections or swapping content from a new scope. Terminal updates preserve final counts and the right error/cancellation status. Opening, changing or returning to another session must not retain the previous session's private invocation contents or incorrectly carry open states into unrelated sessions. Allow content updates without rerendering entire disclosure trees.
9. **No unsafe raw output.** Match or strengthen Full Watch's existing **source allowlist, redaction, size limits and supported fixed failure-reason policy**. The owner wants to inspect what failed and what its outcome was, **not** arbitrary raw stdout/stderr, full file contents, unreviewed exception messages/stack traces, environment variables, secrets, credentials, tokens, headers or complete prompts. Only surface a bounded, meaningful result/status/error category proven safe by the source. Do not introduce a new unfiltered transcript view or new data exfiltration channel. No read-on-expand native command execution or privileged source mutation.
10. **Respect pinned detail revision and source lifecycle.** Build a coherent tool/skills snapshot for the **same source revision and selected root session** as the detail's displayed prompt history; do not mix old counts with a newly refreshed prompt table, double-count child contributions, run an extra unrestricted full-history scan each UI poll, or convert a partial snapshot into false complete counts. Preserve existing read-only, cancellable, bounded source acquisition, source identity/generation checks and current session detail loading/progress behavior. Keep the page usable even for very long histories.
11. **Visual parity and accessibility.** Use Full Watch's Tool Calls / Skills disclosure presentation including red outcomes and nesting, modest logical indentation, visible expanded arrow, screen-reader labels, native details/summary, keyboard focus and touch support, readable long paths/commands and theme/mobile/zoom behavior. Prefer reusing shared presenter components rather than copying a separate implementation that drifts from Watch. Maintain stable DOM identity/open state under updates according to **FR000709**.

## Concrete existing code and architecture to inspect

- **src/web/assets/session.js** currently creates Session Detail with a context line and ten-column prompt-history table, and performs 5-second live polling plus revision-pinned chunk loading. It does not construct Tool Calls or Skills disclosure panels. Add the two sections without changing the existing table or export interaction.
- **src/web/assets/watch.js** already contains the native disclosure hierarchy and the Tool Calls → red failed outcome group → physical failed invocation inspection, along with Skills, focus/selection handling and themed styling. Share or extract applicable presentation logic rather than diverging; pending **FR000709** must fix Watch's refresh/caret instability before this page relies on it, or be integrated so the fix applies consistently.
- **src/watch/tools.py::observe_tools()** already derives tool totals, outcomes, verified custom skills and source-bound physical failures from a hydrated canonical snapshot. **src/watch/invocation.py** owns allowlisted, bounded, redacted invocation text and safe failure reasons. **src/analysis/child_links.py** owns verified recursive child scope. These are promising reusable semantics, not automatic proof that the current session-detail API already exposes the required historical data.
- **src/application/projection.py::block()/prompt()** currently exports session and prompt report metrics, without this activity breakdown. **src/application/session_detail.py::SessionDetails.page()** serves revision-aware snapshot and 25-row begin/chunk history (50-row compatibility pages); integrate the new session-wide activity DTO or coherent, revision-pinned detail endpoint with these constraints instead of a browser-side count from visible rows. **src/reports/session_history.py** and **src/reports/service.py** own history acquisition and source-qualified projections.
- **src/application/live_projection.py** has Watch-specific tool/outcome/failed-invocation serialization. Reuse the same source semantics and safe formatter where possible while retaining the more complete historical Session Detail scope.
- **Completed FR000701** delivered Watch's nested physical failed-call details and matching redaction; pending **FR000709** repairs refresh/DOM stability. **FR000708** addresses prompts kept running by active child sessions; its lifecycle state must not cause these session-wide tool/skill counts to disappear. Keep these separate responsibilities compatible.

These file leads are based on static repository inspection, **not** an observed running implementation of this requested feature.

## Acceptance and regression coverage

1. **One finished session, multiple prompts.** Fixture with at least three prompts and different historical tool calls; opening Sessions → a specific session shows exactly two appropriate independent top-level disclosure sections. Tool Calls summary and opened groups cover **every prompt**, not just the most recent; model Calls column remains unchanged. Skills lists the session's actual confirmed custom skill IDs.
2. **Failed-call drilldown.** Four physical read calls fail in different prompts (two with identical names and paths); expand Tool Calls → **4 × read failed** → each actual failed call. Each has a stable separate identity, correct owning prompt where known, sanitized recorded invocation and supported outcome/reason. One lacks a safe reason and explicitly reads **Failure reason unavailable**. Include mixed successful/cancelled/failure counts and a red outcome breakdown.
3. **Recursive and duplicate attribution.** Root invokes a subagent with nested descendants, repeated physical call parts, reused session sources and a compaction. Totals include properly owned child tool work exactly once; count categories and skills consistently; exclude unrelated roots. Session totals reconcile with canonical per-prompt activity without adding up duplicated physical records.
4. **Long archived history.** Hundreds of tools and more individual failures than Watch's display limit: aggregate always shows complete evidenced counts and all source-safe failures can be inspected through bounded paging/load-more; no arbitrary first-10-only results claimed as complete. Loading and navigation remain responsive and bounded, with truthful unavailable/omitted proof for incomplete history.
5. **Live refresh stability.** Open a running session detail and expand Tool Calls, a failure group and one physical failure; then simulate source updates adding tools, changed failure reasons, child activity and terminal transitions. Keep stable group nodes, expanded state, selection, scroll and focus through same-scope refresh; security-invalidated details are cleared. Switching sessions clears previous private data. No flickering caret or forced collapses from the old FR000709 issue.
6. **Consistent source/DTO snapshots.** Verify initial loading, pinned chunk revision, out-of-order/stale response, source retry, source-generation change, archived/frozen view, partial missing source and reconnect. Don't present a full-session activity total computed from only the first displayed page, and don't mix two different revision counts. End-of-history evidence, not absence in a partial page, decides whether counts are complete.
7. **Privacy and non-regression.** Use synthetic source fixtures and safe redaction tests with credential-bearing commands, hostile output, failed error objects, paths and secrets. Never show arbitrary native tool output, tokens or user files; maintain exact aggregate counts. Preserve existing Watch appearance/behavior, Sessions table, Export Sanitized JSON, loading bar, versions, cost accounting and source-read budgets.
8. **Verification:** add focused Python canonical activity/projection tests and rendered browser session-detail integration tests for nested details, counts, model request/tool-call distinction, keyboard/touch, light/dark/narrow layouts and long histories. Reuse Watch outcome/invocation tests where sensible. Report what actually ran; no paid inference or live user-session mutation needed.

**Deliverable:** Session Detail becomes a complete, calm place to review a session's **Tool Calls** and **Skills**, with Watch-style nested expandable **failed physical tool calls** and safe result/reason inspection, covering the selected session's actual recorded history rather than only its most recent running prompt.
