# FR 000627 — Quiet partial CCost indicators in Mini Watch and Watch daily summaries

**Owner-approved Ready Feature Request, 2026-11-07.** Permanent identity **000627**; deliberately low Ready queue priority **000720**, after FR000624 (000420), FR000625 (000520) and FR000626 (000620). This is **FR-only backlog publication**, not an instruction to change the running product now. The earlier FR000624 loading/performance work may improve completeness but is **not** a prerequisite or proven fix for the UI behavior below.

## Owner-observed problem

In the upper-right **Mini Watch** header, `CCost Today` sometimes shows a leading **`?` on its numeric amount** and the separate text **`Partial pricing / token data`** beneath it. These terse technical caveats look like small persistent warnings even when the user can use the product normally. The owner explicitly wants **both removed from the ordinary visible daily summary**, without replacing them with `≥`, `~`, another warning badge, or a help/question icon. The general UX principle is to keep routine incomplete pricing/token evidence out of prominent UI chrome; genuine inability to provide a useful value or an actionable service failure remains distinguishable.

## Verified implementation context

- `src/web/assets/mini.js::drawDaily()` builds `CCost Today <amount> · <N> prompts` and appends `Partial pricing / token data` if `!value.total.complete`, `!value.mix.cost_complete`, or at least one observed token-mix category total is null.
- The leading `?` is separately produced by shared server-side display formatting: `src/application/display.py` uses `src/numbers.py::ccost_amount(..., unresolved=True)` for incomplete `known_ccost`. It should **not** be globally changed merely to fix the daily header, since other scopes intentionally retain their own partial-value conventions.
- `src/web/assets/watch.js::daily()` shows the corresponding full Watch daily amount and adds `Partial CCost pricing` and `Prompt count incomplete` notices; this FR deliberately aligns **only that daily summary** with the quieter Mini presentation. Earlier completed FR000620 preserved those daily warnings, and this request **supersedes that presentation decision for CCost Today only**.
- `ComparisonCost.complete` means all *observed* requests were priced. Incomplete price/token evidence does **not** establish whether the missing amount is negligible or large. Do not assume an error percentage, silently repair source records, or claim that the known priced subtotal is the proven all-activity total.
- FR000624 addresses Web loading/correctness and may reduce temporarily missing data; it does not guarantee complete model pricing or source token evidence. FR000625 changes a Web default display unit, not the daily completeness policy.

## Required behavior

1. **Mini Watch:** When a positive known priced daily CCost subtotal is available, show it as the normal plain CCost amount in the current Web display unit, with the existing prompt count. The visible day line and its immediately subordinate note must contain **no leading partial `?`, `Partial pricing / token data`, similar partial-completeness banner, or replacement decoration**. This must hold on initial publication, ordinary Live refresh, retained verified observations and Credits/USD unit changes.
2. **Full Watch, same global day:** Apply the same quiet policy **only to its CCost Today amount and nearby passive partial pricing/prompt-completeness notices**. Preserve its ordinary definition/help for reference CCost and today's prompt count; do not add an extra help icon, popup or warning in place of the removed UI text. This is not a request to hide actionable failure information elsewhere on Watch.
3. **Retain honest unavailable/zero semantics:** A verified acquired day with no recorded requests remains **0**. Observed usage with *zero priceable requests* remains **N/A**, not invented 0. Before data arrive use the existing Loading/placeholder state; when acquisition or service is genuinely unavailable, show the existing clear unavailable/recovery state. Keep legitimate source/authentication/service errors and long-unavailable update health notices; these are **not** the routine partial-pricing warning being removed.
4. **Do not alter accounting or completeness:** Preserve exact underlying `known_ccost`, `observed_requests`, `priced_requests`, `complete`, `mix.cost_complete`, token category evidence, `prompt_count_complete`, source/age/health state and canonical day/timezone. The displayed partial amount is the **known priced subtotal**, not a newly proven full amount. Where existing sanitized diagnostics/logging captures missing evidence, keep it available without log spam or private prompt data. No extra UI alert is required for the routine partial state.
5. **Strict scope:** Do not globally remove `?` from prompt/session CCost, other reports, Token Mix, quotas, accounts, CLI or help explaining those distinct scopes. Do not affect pricing sources, source loading/distribution, FR000624's worker, refresh/scheduler, CCost/unit conversion, actual billing or model usage. A narrow server-prepared daily display token or similarly contained solution is preferable to brittle client-side string stripping.
6. **Documentation:** During implementation, update `docs/web-mini-watch.md` and any current Watch/CCost descriptions that explicitly promise a visible daily partial marker. Describe succinctly that a plain daily amount can be a known-priced subtotal when source prices or tokens are missing; avoid a recurring banner or new icon.

## Focused acceptance

Show ordinary plain daily CCost and the acquired prompt count **without `?` or routine partial warnings** in both Credits and USD; backing completeness flags stay false as appropriate.
- Distinguish valid zero usage (**0**) from observed-but-wholly-unpriced usage (**N/A**) and absent/failed source (**Loading/Unavailable**). Do not fabricate success or conceal a genuine service failure.
- Confirm that unrelated prompt/session/Token Mix partial markers and diagnostics retain their current meaning, plus stable Live updates and the existing Mini first-row layout.
