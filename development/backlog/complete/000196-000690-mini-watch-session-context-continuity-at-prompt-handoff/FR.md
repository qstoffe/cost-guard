# FR 000690 — Keep the last known session Ctx visible across rapid prompt handoffs in Mini Watch and other session-level context views

**Ready to Develop — owner-requested 2026-11-12.** Permanent identity **000690**, Ready queue priority **001030**. This is a recurring owner-visible regression after completed **FR000666** (v81.16, 2026-11-10). **Primary owner: Mini Watch (Document Picture-in-Picture).** Audit and repair the equivalent same-session **next-context** presentation in Full Watch and any other existing session-level Ctx views where it drops a still-valid value solely because a new prompt started. Not a redesign of context accounting or prompt-local Ictx/Delta.

**FR publication only:** no product code, tests, installed OpenCode source, paid inference, cache changes or releases in the documentation commit.

## 1. User observation — direct, rapid handoff

A running session's Mini Watch **Ctx** column displays a perfectly usable next-incoming-context estimate, for example **`230k`**. The prompt then finishes or is stopped, and the user starts a new prompt **almost immediately / within the existing approximately 30-second completed-prompt highlight window** in the **same session**.

Mini correctly recognizes the new prompt and colors it yellow as Running. But **the same session's Ctx cell briefly flips from `230k` to `N/A` for a few seconds**, only later showing a numeric context again after the new prompt's analysis/source updates arrive. The owner explicitly requested earlier that this must never happen merely because the prompt changes.

**Mandatory owner-visible sequence:**

```text
Same root session S                       Mini Ctx
Previous prompt running, valid estimate   230k
Previous prompt finishes/is stopped       230k
New prompt enters Running, not ready      230k   (not N/A)
Several early/partial/queued Live ticks    230k   (not N/A)
New prompt obtains a qualified estimate   235k   (immediate replacement)
Another healthy update or quiet refresh   235k
```

The previous number is deliberately the **last known same-session estimate**, not a claim that the new request has already measured exactly 230k. The Ctx tooltip/focus text can distinguish that while needed. **Do not wait for the new prompt to generate its first token before retaining the old displayed estimate.** The 30 seconds are an observed reproduction window, **not** a desired expiration timer or a permission to invent idle work.

The same principle applies if the previous prompt ended with an interrupt/Stop action but its earlier **valid, displayed session estimate** remains meaningful: the end/abort flag alone is **not proof that the session lost its context**. A real context reset/move/compaction or provably incompatible epoch/model may be, and must be handled separately.

## 2. Why FR000666 can still fail — verified code paths, not a verified private-machine trace

**Read FR000666's original FR, completion and `development/journal/web/mini-watch.md#same-session-ctx-handoff-fr000666` before editing.** FR000666 implemented a narrow happy-path proof, tested `172k → 172k → 175k` in synthetic source/real headless PiP, but its read-only installation check observed **zero actual new-prompt handoffs**. It explicitly did **not reproduce the owner's real incident**; the current report shows the previously untested transition is still broken.

A. **The browser has a one-frame-destructive gate.** In `src/web/assets/mini.js::View.drawSessions`, a per-session `row.lastContext` is preserved **only** if all these conditions hold:

- current row is running, not execution-unverified, with null current `watch_next_context_tokens`;
- the server supplied `card.context_handoff`;
- the browser still has a `row.lastContext` whose **exact predecessor prompt ID and raw token number** match `context_handoff.previous_id/previous_tokens`.

Otherwise `row.lastContext` is **set to a fresh numeric current value or to `null`**. Thus a *single* early frame with no handoff clears the valid last-known session number. **Even if the correct handoff is finally published one or two SSE ticks later, its required old value has already been destroyed.** The existing fixture `development/tests/fixtures/mini_context.cjs` actually asserts that a temporarily missing handoff makes the card show `N/A` and permanently invalidates retention; that assertion is wrong for a **pending** transition.

B. **The producer intentionally suppresses handoff during otherwise normal temporary uncertainty.** `src/reports/watch_capture.py::mini_context_handoffs` only yields `(current.prompt_id, (previous.prompt_id, previous_tokens))` when many strict conditions hold: current prompt in progress, no root-model request yet, exact `pre_prompt_entry`, active/compatible history, no known model/provider change or compaction, no aborted/error prior prompt, and a supported predecessor **present in the bounded captured rows**. The `capture_rows` function suppresses these handoffs when `fresh.complete` is false or the capture is retained.

`src/watch/cards.py::WatchCards._card` **further withholds** `context_handoff` unless the card is `observed`, not retained, and its current capture generation is fully verified. `src/application/live_projection.py` forwards only this exact handoff. The first view of a fresh new prompt can legitimately be queued/partial/retained/unverified while source acquisition catches up; **the absence of this optional permission is not affirmative proof of a context reset**.

C. **Mini's card observation retention is keyed by `[session_id, focal_id]`** (`src/web/assets/mini.js::Observations.update`). A newly started prompt has a different `focal_id`, so the preceding card's row facts are **not automatically carried into the new card**; the rendered row itself is keyed by the session ID. This adds a gap across the handoff if the new capture has no context and no `context_handoff`.

D. **A separate history-proof identifier is used as a Ctx retention reset key.** `MiniWatch.Controller.update` currently clears every `row.lastContext` when JSON `[host instance, view.source_label, view.history_scope]` changes. `history_scope` belongs to the independent **Earlier/history** publication (`src/watch/history_publication.py::HistoryPublication.scope`, generated per owner lifetime), not a proven context-epoch boundary for the displayed session. Verify whether a coordinator/history transition can clear a healthy active session's last Ctx. Reset on **actual host/source/session/context epoch invalidation**, not a change in unrelated history bookkeeping. This is a plausible secondary defect, **not proven to explain the owner's precise moment**.

E. **Multiple views have different semantics.** Mini's current active value is `item.live_context.watch_next_context_tokens`; historical representative uses `card.session_summary.context`. Full Watch's footer `src/web/assets/watch.js::drawContext` currently does `N/A` when the session-summary context is absent, while its prompt table intentionally shows **Ictx** (first-request input) and **Δ Ctx** (prompt-specific delta), which are not interchangeable with the Mini next-session Ctx. `src/reports/session_summary.py::context_fields` produces a session-level continuation Ctx for the Sessions catalog. **Audit the same-session next-context displays**, not every unrelated null numeric column.

F. **Missing vs invalid is not encoded strongly enough.** Source-prepared `None` or missing optional `context_handoff` may mean an early, not-yet-processed new prompt, a partial/retried capture, the previous valid metric not in a six-row slice, a new unbound model, or **actual invalidation**. One generic `N/A` and one optional positive handoff cannot safely distinguish these cases. **Do not fix this with a longer arbitrary 30-second timer or brittle string comparison.**

The code findings prove a plausible deterministic regression path. A causal replay of the owner's **real** 2026-11-12 transition has not been performed in this FR-authoring environment; implementers must not falsely claim it has.

## 3. Binding product rule — session-level last-good Ctx wins during a pending handoff

1. **Persistent within a live session, not per prompt:** If the source and display have a valid numerical next-session-Ctx estimate for root session **S**, save the last accepted **raw tokens plus formatted view value and provenance** under a **source-qualified canonical session ID / context-epoch identity**. Keep it during completion, recent-success grace, immediate manual Stop, new-prompt selection and running setup. It must **not** depend on the exact old `focal_id`, the previous DOM row still being mounted, or receiving `context_handoff` in every intermediate publication.
2. **Pending is not invalidation:** Until a **new valid current Ctx** arrives, showing the last known value is mandatory if there is no **positive, authoritative incompatibility proof**. This includes fresh user prompt with unbound model, first pre-request milliseconds, waiting for source/analysis, retained/partial data, late/dropped SSE, asynchronous Watch card generation verification, source/period refresh and a provisional missing estimate after an earlier valid number. **A missing handoff field, empty current `live_context`, `null` token, new prompt ID or mere `N/A` projection cannot erase previous valid state.**
3. **Update immediately:** The first source-qualified numeric Ctx for the newer prompt/session replaces the carried value **as soon as published**, even if the formatted value remains the same; provenance/help switches from previous-session-estimate to current. Preserve the canonical prepared token formatting (e.g. `230k`, no extra tilde). Do not derive a new estimate from the number's text, add an arbitrary debounce/delay, or trigger an additional expensive read.
4. **Positive invalidation only:** An actual explicit compaction/reset/rewind/context epoch change, source host/instance/generation change, session removal/reassignment or proven incompatible request/model/context boundary must clear/replace an old value according to canonical semantics. A **not-yet-known new model** is *pending*, not incompatible. A previous prompt's success/aborted/error status alone is not evidence of invalidation if its last numeric context was valid at the observation time. A first-ever session without any valid number may use the existing honest missing/pending value. **Never copy another session's tokens** to hide a missing value.
5. **Fresh Mini launch:** If the PiP window did **not** see the prior prompt itself but the same-source **authoritative current session context/cached last known value** is available, it should be able to start from that legitimate session-level estimate rather than demanding that a row in this particular PiP document displayed the predecessor. Do not confuse a historical prompt's local `Ictx` with a verified current-session continuation Ctx. If no legitimate prior value exists, do not fabricate one.
6. **Session summary compatibility:** The current session's `card.session_summary.context` may already contain a numerical value when the focal new prompt's `item.live_context` is temporarily null. Review whether a **verified same-session context summary** can serve as an immediate fallback to avoid duplication and make the answer visible even on the first frame. Reject stale, unrelated or incompatible summaries. A summary that is also temporarily null is not itself invalidation.
7. **Tooltips and colors:** While carrying an older value, Mini's Ctx help should say briefly **`Previous same-session Ctx; current prompt updating`** or equivalent. Tooltip **Δ Ctx** remains the *new prompt's* own delta (may be N/A while genuinely unknown); do not borrow the prior prompt's delta, effort, warnings, tool counts, cost or input-token metrics. Running row remains yellow and updates immediately. Clear or recompute context-dependent price warnings when the new model is not yet established; never silently present a previous model's warning as new-model proof.
8. **No endless freezing:** Carry a previous number **only while the current update lacks a new supported value and no affirmative invalidation exists**. A valid new measured/estimated number, confirmed incompatible epoch, or source owner replacement must transition immediately. Do not hide a genuine known context reset, claim the retained number is a fresh current request measurement, or allow yesterday's/another session's data to survive an actual source switch.

### Implementation ownership preference

Favor a **single source-owned, session-qualified last-valid-context / handoff-state contract** in the existing Watch capture, session guidance or compact Live projection over fragile prompt-ID-coupled DOM memory. A narrow Mini UI cache is acceptable as a supplementary presentation fallback only when it is keyed to **source instance + canonical root + actual context epoch** and has an explicit invalidation signal. Reuse `src/analysis/context.py::ContextEpochs`, `src/reports/watch_context.py::card_context` and the existing source-derived provenance rather than inventing browser-side heuristics, recomputing Ctx from a text label, inventing context via wall clock or persisting user contexts in browser storage.

**Design requirement:** distinguish at least `pending/unknown-yet`, `ready-current` and `explicitly-invalidated` in a maintainable way. If introducing an allowlisted DTO state or generation, preserve source/pricing layer boundaries and keep payload small. A one-off fallback expression in `mini.js` that still clears memory on one missing handoff does **not** satisfy this FR.

## 4. Other Web surfaces — audit matching semantics without scope creep

- **Mini Watch** is mandatory: active/yellow, recently completed/green, older retained and newly resumed same-session Ctx, including reopening PiP. The numeric value is next *session* context, not prompt Ictx.
- **Full Watch**: check `watch.js::drawContext` on the existing active/recent session's **Context:** summary/footer; if it has the same `value → N/A → next value` problem at new prompt start, fix it by using the same source-qualified last-good session context contract. Do not backfill per-prompt **Ictx** or **Δ Ctx** with a session-level number, since those legitimately can be undefined pending a request.
- **Sessions catalog Ctx** and any other existing session-scoped next-context display: audit for the same temporary clearing when a prompt is added, and fix the same issue if observed using the shared context observation/provenance. Do not relax actual cross-epoch validity, rewrite historical prompt facts, change global Sessions sorting or merge history from two roots.
- **Existing Watch metrics not in scope:** CCost, Total CCost, duration, token mix, running/terminal labels, tool activity, quota, model, warnings unrelated to Ctx, CLI report/accounting, and general cache retention policy should keep their established semantics and refresh costs.

## 5. Mandatory failures and regression evidence

1. **RED baseline reproduction of the owner scenario:** using source-shaped V2 history and the production normalization/analysis/Watch capture/Live/SSE renderer, model a completed (or user-stopped) prompt with observed **230,000 tokens**, a **new prompt started within 1–30 seconds**, and at least **two intermediary publications** for its new focal ID: first with no usable current Ctx and **without `context_handoff`**, second with a valid handoff or continued pending, then one with source-qualified **235,000**. Prove the current implementation shows `230k → N/A → ...` and the fix shows **`230k → 230k → 230k → 235k`**. Do **not** inject an always-perfect handoff from the start as old FR000666's fixtures did; that would miss the bug again.
2. **Explicit one-frame loss oracle:** currently `mini.js` sets `row.lastContext=null` when current raw tokens are null and `handoff` is absent. Assert that **absent permission is pending**, that session last-good survives, and a later otherwise-valid handoff/fresh result does not require it to have survived on a continuously mounted prompt row. Update old fixture expectations `show([pending without handoff]) ⇒ N/A` and similar source-shaped tests: missing eligibility must **not** stand in for explicit invalidation. Test a true separate invalidation marker as the negative control.
3. **Previous prompt statuses:** complete/success, recent terminal-highlight overlap, **manually stopped/aborted after a valid prior Ctx**, prompt tool-call continuation, rapid repeated prompts A→B→C, multiple running prompts in one root, child/subagent work and source-verified same-number updates. No unwanted 30-second timeout that expires the number while the new request has yet to yield a new metric.
4. **Temporary uncertainty matrix:** first new-prompt SSE with partial/retrying/retained capture, verification-generation gap, old+new card coexistence, new focal key, missing latest `pre_prompt_entry` in the bounded capture rows, unknown model, app reconnect, background history progress/epoch and quiet Mini's 5-second presentation timer. These **must not cause a momentary N/A** if the same root's previous valid Ctx remains usable.
5. **True invalidation controls:** context reset/compaction/rewind, actual incompatible known provider/model, source generation/host swap, session move with incompatible context, distinct root session S2, removed session, stale snapshot/replayed older SSE, no earlier value, a genuinely empty session, newly resumed historical session where the old value is no longer current. They **must not resurrect** a previous invalid Ctx, leak S's 230k into S2 or use a historical prompt-context estimate as a current continuation without support.
6. **Fresh Mini / source owner:** show legitimate carry-forward for a PiP opened just after new prompt start using already available validated session summary/history, not only a previously rendered row. Also test deliberate Mini close/reopen and new source identity; reload must not create an invented value.
7. **Full Watch + Sessions audit:** record which existing session-level Ctx surfaces are affected. For each affected surface, assert the same source-owned pending→fresh continuity. If Full Watch's footer or catalog does **not** exhibit the problem, prove why and document `NO CHANGE`; do not make unrelated prompt-specific Ictx/Δ fields falsely non-null.
8. **End-to-end PiP:** run an actual hidden supported Chromium/Edge Document PiP with the shipped source-shaped session/capture→Live publication→PiP DOM, correct `230k` display while the current prompt turns yellow and its own raw token field is **still null**. Inspect row text, role/accessible help, bounded layout, focus, hover/touch and whether last-good survives 5-second rerenders without flicker. Include both 0.5s and 5s gaps, not just an artificially synchronized perfect handoff; also test source reconnect/changed history state and a real equal-number replacement.
9. **Read-only real-installation check:** where available, inspect one of the owner's rapidly changing OpenCode V2 sessions and collect only **sanitized** [session/source hash, prior number, new prompt timestamp, actual `context_handoff` presence/absence, selected source/model context state, published Ctx and render] without raw prompts, session IDs, credentials or user paths. No paid AI request is required to implement/test this FR; if the exact live transition is unobserved, explicitly mark it `NOT VERIFIED`, not a real-world PASS.
10. **Performance/regression:** reuse the existing Live watch source worker, snapshots/observed session summary and event cadence; no extra full-history load, new source watcher, per-cell HTTP, paid provider request, command execution or extra foreground interval. Preserve DOM row identity, PiP geometry, source/host authentication, per-session cardinality and browser privacy. Update focused Python and browser contract tests and documentation to prevent a future reversion to "null means invalidate".

**Prior FR comparison:** FR000666 correctly avoided *cross-session* or *proven incompatible-epoch* stale data, but its exact-predecessor-only positive permission and destructive no-handoff reset created an avoidable user-facing hole. **This FR supersedes that eligibility gate only for transient missing new-prompt evidence; it does NOT authorize presenting demonstrably wrong context after a confirmed boundary.**

**Non-goals:** change context math or billing; turn a previous prompt's **Ictx/Δ Ctx** into the new prompt's own value; hide proven model/epoch invalidation; persist context values outside existing source-qualified Live memory; add a 30-second grace timer to mask a bad data model; force a new OpenCode refresh on every prompt or hover; alter unrelated running-window markers or Mini design.

**Done means:** A session which has already shown a valid Ctx **never flickers to N/A solely when a new prompt begins**, even when the first Live publications are missing handoff, partial, or arrive out of order. It keeps the last known **same-session** value until a new source-qualified number or an actual explicit invalidation arrives. Mini Watch is fixed first, and equivalent Full Watch/session-level displays are checked and corrected where necessary.
