# FR 000614 — AI Stats: resumable long-history analysis, shorter-period priority and benchmarked speedups

**Owner-approved Ready Feature Request, 2026-11-06.** Permanent identity **000614**; Ready queue priority **000320**, after current FR000613 (000310) and after the shared-loading FR000609 (000270). **Backlog publication only**: write this specification and advance the identity watermark. Do not implement the product, run its gates, change versions/releases or move unrelated work while authoring.

## User report and intended experience

On the owner's own large AI history, **AI Stats → 30 days** ran for the full **120-second report-job limit** and then stopped with an error equivalent to **“Report reached its 120-second limit …”**. This is not acceptable for a report the user explicitly wants to load: a large but healthy local history should not be abandoned simply because a fixed wall-clock threshold was crossed.

The user wants the page to **continue making observable progress for as long as legitimate work takes** — even extremely long analyses — rather than fail at two minutes. A visible, meaningful **0–100% progress bar** and work description should explain how far acquisition has come, and what remains where quantifiable. In addition, while a **30-day** analysis is underway, switching to **7 days** (or Today) must **prioritize finishing that narrower range promptly**, without waiting for the full broad scan and without throwing away already completed useful work. Prefer to organize initial broad work **recent-to-older / shorter periods first** so shorter results naturally become ready before larger ones. The user also asks for a serious performance investigation, optimizations where demonstrated by evidence, and repeatable built-in development benchmarks.

**Product goal:** “Long-running” is not synonymous with an unkillable runaway process. Remove the **arbitrary 120-second *logical report* expiry for AI Stats** while retaining bounded individual work, cancellation, resource/fairness limits, diagnostics and genuine failure reporting. A connected user should see forward progress and eventually coherent results, not a timeout loop or an eternally spinning stalled task.

## Code evidence and current limitations (not proof of the owner's precise root cause)

1. `src/web/jobs.py::ReportJobs` uses **`deadline=120`** for each spawned report process. In `tick()`, `time.monotonic() - started > self._deadline` sets **`failed/report_timeout`** and terminates that child; `src/web/assets/app.js::failure()` renders the quoted 120-second error. This is the proven mechanism of that error, **not** proof of which source operation was slow for this particular incident. `MAX_PENDING=4`, a serialized active finite report process, `MAX_RESULT_BYTES=8 MiB` and ownership/cancel semantics currently protect host responsiveness and privacy.
2. `src/reports/ai_stats.py::build_ai_stats()` lists the source catalog, resolves root revisions, reads a compact revision-/algorithm-/pricing-keyed cache, then handles cache misses in **64-root batches** with `service.prepare_roots(..., detail=True, progress_scope='date')`, `service._analyze(..., detail=True)` and per-batch cache writes. These saved stable-root entries can help a *new* attempt, but there is **no first-class pause/resume/progress checkpoint for one logical AI Stats request** spanning multiple bounded process executions. Volatile/changed roots must be revalidated.
3. **Existing observed benchmark, not a guarantee:** `development/journal/web/ai-stats.md` records one cold 30-day V2 run at **84.692 s**, **2,698 roots**, **54,056 analyzed requests**, **43 prepare batches**, **44 catalog fetches / 2,156 pages**, and **42.297 s child CPU**. A previous smaller batching design exceeded 120 seconds; subsequent warm runs took only seconds. That record explicitly identifies catalog-bracket amplification and cache reuse as performance factors. The owner's newer 120-second failure is consistent with a larger/busier workload but **must be instrumented rather than attributed to an unverified single bottleneck**.
4. `src/web/assets/app.js::selectStats()` mutates one AI Stats `state.period` / `state.request`, while `acquire()` immediately refuses additional work when `state.loading` is true. The already-started broad request can therefore remain the work owner after the user selects a narrower scope, with no immediate reprioritization. `src/web/jobs.py` also serializes running reports and ranks historical report kinds as lower priority than other finite reports. Merely changing button labels cannot deliver 7-day-first responsiveness.
5. The current `src/analysis/ai_stats.py::windows()` supports **Today, 7 days, 30 days, This month, All time** with correctly scoped interval clipping, selected-local calendar/DST, event-time cost and overlap-safe durations. A 30-day build currently returns multiple contained periods in one result; **the completed narrower result may legitimately be published before its parent scope**, but not before the roots/coverage needed to prove it have been checked. Active roots with older metadata may still affect recent windows.
6. **FR000609** already owns the standardized centered determinate progress UI and safe temporary-startup waiting/retry. This FR must reuse/extend that shared component for AI Stats' **long-lived, incremental** scope states and progress, not fork a competing bar. **FR000612** owns honest `Loading` vs `Unavailable/Partial/No data` metric reasons; this FR must feed it reliable scope completion/coverage, not show incomplete calculations as final.

## Requirements — complete large scans without a global two-minute abandonment

1. **Logical AI Stats acquisition is resumable.** An otherwise valid large AI Stats report must not terminally fail merely because the *sum* of its work exceeds 120 seconds. Design **bounded, cooperative work slices/checkpoints**, or an equivalent demonstrably safe approach, so individual child workers/operations still have watchdogs, explicit limits, cancellation, resource ownership, and actual liveness evidence while the **logical** job can continue across multiple finite slices. Keep the existing 120-second contract for **other report kinds** unless separately approved; do not simply change a global deadline to infinity or run an unbounded process. Per-chunk timeout/stall, source errors and retry exhaustion remain actionable failures.
2. **Resume without restarting.** Checkpoint committed progress at safe, source-aware boundaries and reuse valid existing **revision-/pricing-/algorithm-keyed compact evidence**. An interruption, recoverable per-slice timeout or user switch to a different period should not restart the full archive scan at root 1 or discard finished stable-root analysis. Avoid duplicate physical-request counts, mixing different source revisions/catalogs, or returning stale/prior-valued results as current. Recheck changed/active roots and catalog validity before claiming a completed period. Stale/corrupt/private cache must fail soft into correct reacquisition, never fabricated coverage. No raw prompts, session text, attachment content or secrets in checkpoints or client progress.
3. **True terminal distinction.** A slow but progressing task stays **Queued / Loading / Waiting / Resuming** as appropriate. Missing source, authentication/instance identity failure, unrecoverable corruption, repeatedly stalled I/O, explicit user cancellation, host shutdown, actual bounded resource exhaustion or unresolvable revision churn must end in an **honest, specific, recoverable/error state** where appropriate. Do not endlessly spin or automatically retry permanent faults, hide failed attempts as “still working,” suppress cancellation or leak orphan workers. No successful `100%` for a partial/failed run.
4. **Visible-route/resource policy.** Honor the application's authenticated local source, single-host lifecycle, finite job queue, host/Watch priority, cancel/stop semantics, and read-only service ownership. A **navigational switch within AI Stats** should preserve reusable progress; leaving the route or hiding the browser should not launch an uncontrolled private history scan. Pause/deprioritize safe incremental work when inactive if appropriate, and resume on return without losing valid completed slices. Clearly define how page reload/host restart uses durable *derived* checkpoints, and avoid an always-on background daemon or other unapproved scheduler.

## Requirements — recent periods first, immediate priority switching

5. **Prioritize overlapping windows correctly.** For a new 30-day/This month/All time request, order the expensive candidate work to make **Today**, then **7 days**, then the wider requested period available as soon as **their independent coverage is provably sufficient**. A source catalog/revision baseline may need to be collected first; prioritize newest qualifying roots without misclassifying long-running/old-root sessions whose activity affects recent dates, or assuming root start/update time is a complete event-time filter. Do not mark Today or 7 days complete merely because the first calendar-week batches happened to finish. The first result may be a narrower *coherent* completed period while other periods remain Loading.
6. **User selection preempts presentation and work priority.** If the user clicks **7 days** while **30 days** is acquiring, show 7-day-specific progress immediately and schedule its missing work **ahead of the remaining broader backlog**. Prefer reusing already-covered roots and completing the narrower result promptly; if a nonpreemptible active chunk must finish first, keep it small and explain the brief wait. Avoid needless duplicate worker/process creation, four-slot queue saturation, source scans or losing valid 30-day progress. When the user switches back, the broader computation **resumes from its saved state**, rather than beginning again. Repeat for Today, This month, All time and rapid toggles.
7. **Truthful period results and retained displays.** A result for a shorter scope can appear while the wider scope continues, but each reported metric must satisfy its existing canonical completeness/partial constraints. Do not promote provisional aggregate duration, highest-cost session, best-day record, cost ratios or matched-run fact to a final champion before full relevant evidence and revisions are checked. Preserve the ten core cards, conditional matched-input fact, selected period, focus, scroll, and previously successful coherent values on quiet refresh. Prevent late 30-day payloads from overwriting the selected 7-day result, reset-to-zero animations, duplicate content or status flicker.
8. **Progress and time remaining.** Use **FR000609's shared 0–100% central progress control** for the *currently selected period*, with descriptive real stages and completed/total counters (e.g. roots or verified batches). Progress may stay at a truthful value while a slow opaque step runs; it may jump for fast stages. Reset/rebase the indicator **only when scope identity changes**, and preserve monotonicity for one attempt, ignoring old sequences. If total work grows after catalog discovery, explain revision of the denominator without representing a fake exact percentage. **Optionally show a measured remaining-time estimate only after sufficient actual throughput evidence**; otherwise show “Calculating remaining work” / actual completed counts, not a fabricated ETA. Distinguish waiting on a shared slot from historical analysis. 100% only after coherent successful completion of that selected period.

## Requirements — optimize with measurement, not speculative parallelism

9. **Instrument the actual slow stages, safely.** On controlled synthetic and eligible read-only real installations, measure separately source catalog/revision queries, repeated before/after catalog checks, snapshot I/O, cache read/write/hit/miss, per-root analysis CPU, projection, serialization/IPC and queue wait. Record stage wall-clock, root/request counts, catalog page/request counts, cache hits/misses, memory peak where feasible and whether source activity changed. Avoid raw personal prompt/session data and private identifiers in public FRs or benchmark artifacts. The owner's specific timeout is not yet reproduced or diagnosed beyond the fixed deadline.
10. **Fix the measured bottlenecks.** Investigate safe catalog-bracket amortization, persistent/reusable revision snapshots, cache eligibility, dedup of repeated work, analysis batching, and avoiding rehydration/repricing of stable roots. Test bounded I/O parallelism **only when actual measurements show benefit**: V2 already supports at most **four concurrent source reads** for selected batch operations, with revision checks and source normalization constraints. Do not assume more threads/processes always improve latency, exceed upstream concurrency limits, change canonical pricing or introduce mutable shared source/cache races. Optimize the cold path while preserving warm refresh performance.
11. **Include reproducible development benchmarks and regression gates.** Extend `development/tests/integration/probe_ai_stats.py` or add focused owned performance fixtures to compare **before vs after** on equivalent histories: small/large; cold, warm and partly changed; 7 days, 30 days, All time; many archived roots, active roots and source mutation. Capture at least the existing approximately **2,700 roots / 54,000 requests**-scale case and a **deliberately slower-than-120-second** deterministic scenario without making routine tests literally idle for two minutes. Report actual timings, cache reuse, source I/O, CPU and reproducible environment; distinguish synthetic latency models from real installations. Require evidence of improved work or eliminated redundant I/O and **no material regression** in small/warm workloads or the unrelated Watch/Models/Comparisons responsiveness, rather than asserting an unmeasured universal percentage speedup.

## Acceptance criteria / verification during implementation

1. **Cold large 30 days >120 seconds:** deliberately force enough bounded slow source work that the overall logical analysis lasts beyond 120 seconds. UI remains active with real progress and phase/count feedback; worker slices continue/resume; report eventually completes correctly without `report_timeout` at the *logical* level, an endless retry storm or silent truncation. Verify source/catalog identity and per-slice limits.
2. **30 days → 7 days → Today → 30 days:** while wide acquisition has substantial work left, selecting 7 days (and Today) **advances their needed work first** and presents independently valid results without waiting for the entire 30-day scan. Returning to 30 days resumes from already completed roots. Use real counters to prove shorter-scope latency/work priority, not just a spinner/label change. Test rapid changes, changed active roots and multiple tabs.
3. **Full accuracy and freshness:** compare final totals, durations, overlap, local calendar/DST, top sessions/dates, costs, per-period matched fact, partial/unavailable and dedup with the pre-existing canonical calculations over a fixed consistent source. Test source-revision churn, late arrivals, incomplete/archived trees, lost/corrupt checkpoint, catalog/pricing change, background result races, resume after reload/host restart and no stale/partial claimed as full.
4. **Safety/termination:** validate cancellation during a stuck chunk and between chunks; host shutdown, browser navigation/hide, queue priority, source missing/auth failure, hard per-operation/per-slice timeout, persistent no-progress stall, 8 MiB single-result bound and bounded memory. No orphan child, leaked thread, oversubscribed HTTP connection, endlessly retrying permanent error or Watch starvation. Other report types retain original deadlines.
5. **Progress UX:** shared determinate bar remains visually stable, monotonic per scope, no fake time-based advance; stage + counts visible; percentage/ETA qualified when denominators are unknown; 100% only after a complete successful selected-scope result, with separate warning for usable partial source coverage. Preserve keyboard/focus, theme, navigation, quiet refresh and FR000612 metric statuses.
6. **Profiled performance:** run reproducible cold/warm/changed benchmarks with clear source revisions, timings, operation counts, cache figures, process/CPU/memory and any claimed speedups. Include the historical baseline (84.692 s/2,698 roots/44 catalog calls) as a *contextual past observation only*, not as a repeatable identical fixture or promised target. Target actual bottlenecks and explain any intentional trade-offs. Update focused Python/Node/Web probes and `docs/web-beta.md` / AI Stats knowledge **when implementing**, not during FR publication.
