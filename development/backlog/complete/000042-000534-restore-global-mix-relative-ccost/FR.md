# FR 000534 — Restore one global latest-100-prompt mix for model-list Relative CCost

## Owner decision and reason

FR000521 introduced model-first, then same-publisher, then global fallback token-mix weighting for **Relative CCost** in the model comparison. That was useful for estimating each model's historically observed workload, but it also makes the model *price comparison* depend on which kinds of jobs the owner happened to assign to each model. Models used mainly for specialized tasks can therefore rank differently even if their published token-category prices would compare differently under the same workload.

For the model list, the owner prefers the earlier **single global token mix from the latest up to 100 eligible completed prompts across all models**. Price *every* displayed model and context tier with that same I/C/W/O distribution. This intentionally compares reference prices against one common workload profile, not separate predictions of what a particular model's assigned tasks cost.

This is a **narrow reversal of FR000521's Relative CCost model-list weighting only**. FR000521's other delivered features—especially historical **Token Mix by publisher**, alongside Token Mix by model—must remain. Do not edit or reuse FR000527; implement this FR **after** its separate absolute-token-column work.

## Required behavior

1. **One shared comparison mix.** For CLI Normal's main model table, `--all-models` and the corresponding Web Beta Overview/Models comparison lists, use the existing *global* Relative CCost sample: latest up to 100 **distinct eligible completed, non-aborted, reference-priceable user prompts** from available history, independent of which model or publisher processed them. A tool-loop with many requests remains one sampled prompt. Include only eligible, uniquely attributed physical requests and their pooled known Input/Cached input/Cache write/Output token volumes (reasoning included in Output); keep canonical priceability, attribution and missing-telemetry rules. Normalize the pooled category tokens once using exact fractions. Do **not** use each model's own mix, a publisher mix, a model/publisher prompt-count blend or a fallback per model when calculating displayed Relative CCost.

2. **Same valuation basis for every model.** Apply those **identical unrounded global fractions** to the published I/C/W/O reference rates of *every* comparable model and each published context-price tier, including models with no prior usage. Keep the existing cheapest positive comparable base-tier price as the single 1.0x denominator; preserve raw-Decimal sorting/tie-breaking, one-decimal ratio display, promotion and release-date behavior, availability filtering vs full catalog, threshold boundaries, unknown rates and actual vs reference cost separation. A model's observed usage should not independently change its relative rank when global mix and catalog prices are fixed.

3. **Existing empty/small-sample behavior.** If only 1–99 eligible global prompts exist, use their actual pooled mix; never fabricate 100 observations. If none exist, Relative CCost stays blank and the existing **hidden 2/96/1/1 sorting-only** fallback remains non-observable. Do not silently substitute the dashboard's different Token Mix % sample: that usage metric may include running or interrupted prompts and remains separate.

4. **Consistent dependent comparisons.** Context-tier / Next Ictx price-threshold multipliers documented as ratios of the model-table Relative CCost levels must use the **same global comparison mix**, with their existing refresh/caching, unknown and no-sample semantics. Do not allow the model list to use global mix while a warning purporting to match that list still uses FR000521's model-specific mix. Do not change context estimation, unrelated warning triggers or actual request CCost.

5. **Explain the revised meaning everywhere.** Update the CLI's Relative CCost definition, `--all-models` explanations, Web Overview/Models headings/help/tooltips/accessibility text, `README.md`, `docs/usage-and-cost.md` and relevant tests/goldens. Describe the latest **up to 100 completed priceable prompts globally** and one shared mix for every model. Remove misleading user-facing claims that the displayed model-list ratios depend on model/publisher evidence, effective blends, model-specific 100-prompt samples or 100 statistical weight slots. Be clear that this is a common **token-category workload price comparison**, *not* a controlled same-task capability/throughput benchmark, actual billing, or a forecast of a model's specialized future jobs. Show truthful actual global sample size.

6. **Preserve unrelated FR000521 and FR000527 functionality.** Keep the historical Token Mix **by model and by verified publisher**, publisher attribution/identity, separate per-publisher raw-token category shares and original-request/tier CCost totals, distinct prompt/call counts, partial/unknown classifications and the explicit Web deep-history scan with progress/cancel. Retain publisher labels in model lists. FR000527's absolute **Tokens per model** addition stays intact. Do not remove or repurpose historical model/publisher evidence or common analysis infrastructure merely to undo one Relative CCost selection policy; remove unnecessary deep comparison-sample acquisition from ordinary model-list rendering only where safely unneeded, and do not introduce new history I/O, API calls or background processing. Preserve FR000526/FR000528 display-unit behavior.

7. **Shared implementation.** Keep comparison calculations in canonical Python analysis/reports and pass one consistent projection to CLI and Web; JavaScript must not reprice models or produce its own sampling policy. Prefer reuse of existing global `latest_prompts` / `_relative_usage` / `normalized_average_token_mix` paths, rather than a second sampler. Avoid product changes outside this targeted reversal and its directly dependent descriptions/tests.

## Acceptance / regression

- With deliberately **different model and publisher mixes** (e.g. one model mostly cached-input and another mostly output), every model's price and rank uses the **same pooled latest-global-100 I/C/W/O mix**, not its own historical pattern or the publisher's. Two models with the same exact published tier prices compare equally regardless of whether either model has been used. A model's older 100 own prompts outside the latest 100 global prompts do not change its comparison independently.
- Fixtures cover 0, 1, 99, 100 and >100 eligible global prompts; aborted/running/unpriceable/incomplete requests; several model requests per prompt, subagents, model-switch and duplicate physical requests; unavailable/deleted history, alias/unknown publisher, zero vs missing rates, tier boundaries and untried models. Exact raw tier prices, common denominator, sorting and threshold warning ratios reconcile. No-data ratios remain blank with only the hidden ordering fallback.
- CLI Normal and `--all-models`, Web Overview and Models, and warning text/ratios agree on the same frozen source, catalog and global sample. User-facing explanations no longer describe model-/publisher-weighted model-list ratios. Dashboard Token Mix % retains its separate sample, unchanged.
- Historical model **and publisher** Token Mix outputs remain identical to before this FR (apart from independent already approved FRs), including prompt/call counts, percentages, CCost, partial markers and explicit Web capture. FR000527's absolute token totals and Web/CLI parity are not regressed. Ordinary report latency/history acquisition should not worsen due to sampling work that is no longer needed for model-list pricing.

FR000527 remains untouched and continues to own its own requirements. This FR publication changes only the backlog, not product code or release metadata.
