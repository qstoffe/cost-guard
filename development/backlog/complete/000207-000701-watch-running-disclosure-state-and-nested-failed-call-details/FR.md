# FR 000701 — Watch: stop spontaneous Running disclosure collapse; indent expanded activity; inspect individual failed tool calls

**Owner-approved Ready to Develop — 2026-11-13.** Permanent identity **000701**, queue priority **000009**, immediately after FR000700 (000008). **FR-only documentation publication:** create this specification and advance the backlog identity watermark in one documentation-only commit. Do not implement product code, change source/runtime data, run tests or paid inference, create implementation workers, or change version/release metadata while authoring.

## User-observed incident and combined feature request

In **Cost Guard Web → Full Watch**, below the **Running Prompts** table, the owner expands a yellow **Running: <tool> <duration>** disclosure to inspect a long-running invocation, e.g. a shell command. **Sometimes the disclosure spontaneously collapses a few seconds later**, despite the same Running tool still being present. Reopening shows apparently the **same command and original continuously advancing elapsed time** (perhaps already 3 minutes), *not* a fresh invocation timer. The owner does **not** claim the cause is proven. A real finished tool disappearing, or a newly started tool replacing it, is normal and may legitimately clear the old detail. A forced collapse of a **still-running identical physical invocation** is unwanted.

Two modest UI enhancements belong in the same Watch FR:

1. **Indent the entire *expanded content*** of each **Tool Calls**, **Skills** and **Running** disclosure (foreground and background tool/job sections); make the visual hierarchy follow the disclosure arrow rather than leaving child lines flush with the parent.
2. **Add another individually expandable level beneath the existing red failed tool-call rows** inside **Tool Calls**. Example: `2 × read failed` should expand to **two different failed physical read calls**. Each call's additional nested detail should show the **actual file/path or command and supported input arguments** that call used, plus a concise, source-supported failure reason when safely available. This must work even if the two failed calls have identical tool names and identical inputs; they are still separate physical calls. The second expansion level must be indented more than the first.

This task is **Full Web Watch / Running Prompts activity only**. It is not a request to change model prompts, CCost, actual command execution, historical session accounting or Mini Watch's compact layout.

## Repository findings (static review; not a replay of the owner's incident)

**Strong specific candidate for the spontaneous collapse:**

- In `src/web/assets/watch.js::drawInvocation()`, the state key is currently computed as `JSON.stringify([detail?.identity, detail?.revision, reason])`, and whenever that key changes **the implementation unconditionally executes `target.node.open = false`**.
- In `src/watch/invocation.py::invocation()`, `identity` is based on source/provenance, owning session and the physical call ID/part ID; **`revision` also hashes `part.updated_at_ms`, copied/redacted text and qualification**. So an update/correction to the same physical running call can change its revision without ending or restarting it. The Running elapsed time is independently derived from the original part start in `src/watch/tools.py::observe_tools()`. This gives a concrete plausible mechanism for **same command + steadily increasing timer + suddenly collapsed disclosure**.
- The same revision-triggered closure applies to `target.jobs`' individual running invocation disclosures in **multi-invocation foreground/background** mode. `drawInvocations()` also switches structure between single and multi paths, removes/reinserts compatibility nodes and reuses children by identity; check that these transitions do not implicitly collapse surviving calls or lose the user's open state.
- This source design was deliberate in **completed FR000632/FR000648**: old details close on identity/revision changes for privacy/staleness. The owner now asks to **refine that specific behavior**: **preserve disclosure openness across a revision of the *same proven current call* while updating its contents safely**, without ever retaining stale sensitive input after the source becomes unverified. The old rendered-browser test `development/tests/integration/probe_watch_invocation.cjs` explicitly asserts `corrected = !target.node.open` after a same-identity revised command; update that acceptance intentionally, not by bypassing tests.
- Existing `src/web/assets/watch.js::drawDisclosure()` holds Tool Calls/Skills as native `<details>` and replaces expanded `<div>` rows when aggregated lines change. Unlike Running's code, it does not intentionally reset the parent `open` flag, but **expanded child row elements are not keyed per physical failed call**; the new nested controls will need stable identities during Live updates.

**Why failed-call detail is currently missing:**

- `src/watch/tools.py::observe_tools()` obtains per-prompt canonical physical `NormalizedPart` tool calls using `_prompt_messages()` and `_physical_tools()` (session/callID or partID coalescing). It classifies an individual structured error/cancellation and builds **only aggregated** `tool_outcomes: ToolOutcome(tool_name, outcome, count)`. Failed calls remain part of normal `tool_counts`; the red counts are subsets, not extra calls.
- `src/watch/models.py::ToolObservation` and `src/application/live_projection.py::card_row()` currently export those **aggregate tool/outcome/count** tuples to the browser. `src/web/assets/watch.js::Card.drawActivity()` creates plain red text rows like `2 × read failed` with **no per-call identities or source arguments**, so the client cannot truthfully reconstruct an individual failed invocation from this DTO.
- **An existing safe extraction path already exists for running calls**: `src/watch/tool_contracts.py::tool_input()` reads actual normalized `state.input` / legacy `input`; `src/watch/invocation.py::_format(), invocation(), invocation_redaction` enforce bounded allowlisted command/path/options with redaction and qualifiers. The failed-call feature should reuse this privacy protection and exact physical join **at observation/projection time**, including real `read` path / shell command / grep pattern where available. The browser must **not infer commands from name, elapsed time, arbitrary output or other calls**.
- **Existing tests** include `development/tests/test_watch_tool_activity.py`, `test_watch_invocation.py`, `development/tests/fixtures/watch_tool_outcomes.cjs`, `development/tests/integration/probe_watch_invocation.cjs` and `probe_watch_tool_outcomes.cjs`. These prove various previous contracts, but not the owner's particular spontaneous-collapse scenario or individual failed invocation detail.
- Current `src/web/assets/app.css` sets `.watch-activity` colors/margins and `.watch-invocation` wrapping but contains **no deliberate nested-content indentation rule**. The new CSS should explicitly establish a hierarchy without shifting the summary headings or damaging mobile widths.

## A. Bugfix: keep a running invocation expanded for its proven physical lifetime

1. **User choice owns open state:** once a user expands a **particular real running tool invocation** (or parent Running group), ordinary Live timer ticks, same physical call's source revisions, text updates, corrected qualifications, status polling, SSE render and harmless DOM updates **must not automatically collapse it**. Manual collapse persists too; do not repeatedly force open on every refresh. If the user explicitly closes it, later updates of that same call remain closed.
2. **Physical identity, not label/command/revision/time:** distinguish call continuity using stable, source/provenance-qualified **call identity** (and owning session/prompt plus foreground/background mode where relevant). **Do not** use matching command text, input arguments, tool kind or elapsed duration as identity. Two sequential shell calls with exactly identical input are **different invocations** and must not inherit the previous call's disclosure state or details. Concurrent same-kind/same-command calls must also remain separately identifiable.
3. **Revision updates are content updates, not termination:** for a verified same-identity invocation, replace only changed input/qualification text, keep its existing `<details>` and `open` state, and refresh safely. Respect selected text and keyboard focus without freezing potentially important source corrections indefinitely; if selection must defer noncritical updates, apply when interaction releases. Make clear which updates truly remove authoritative identity/verification and therefore **must** clear source details.
4. **Genuine end/switch/invalidation:** a source-confirmed completed/failed/cancelled call may disappear immediately even while its detail is expanded — explicitly acceptable. A genuinely different invocation, newer prompt/focal ID, root/provenance/source generation change, revoked link, failed authoritative verification, or expiration must **not** keep a former command visible under a new Running label. Preserve existing privacy and stale-source safeguards. A short temporary gap in evidence must not be “repaired” by guessing the old command belongs to a new call.
5. **Multiple running jobs:** when two or more foreground tools or background shell jobs are running, preserve **each surviving child's** open/closed state as other siblings are added, corrected or finished, and keep the parent group stable where meaningful. A 1→2→1 transition may change layout, but must not collapse/erase still-active unchanged invocations simply because `drawInvocations()` changes rendering mode. Foreground and background are separate identity namespaces. Preserve initial privacy boundary: newly encountered call details are not accidentally exposed just because an unrelated earlier call was expanded.
6. **Timer coherence:** the elapsed `Running: <tool> 3m...` duration continues from actual source start for the same call; a truly new call's duration follows its own start. Timer does not control the disclosure. Do not add a workaround involving forced re-expansion, browser timeout hacks or UI-side assumptions about tool execution.
7. **Scope/performance:** keep current bounded acquisition and canonical Live card membership, source-read budgets, current running command redaction and command recovery from FR000688, and only update keyed DOM needed for a still-valid call. No new tool execution, source mutation or extra polling to preserve an `open` attribute.

## B. UI feature: indent all expanded Watch activity content

Keep the existing concise single-line summaries and their disclosure arrows at the current left alignment. When expanded, **indent the whole descendant content block consistently**:

~~~text
▼ Tool Calls: 6 tool calls · 2 failed
    3 × read
    2 × shell
    ▼ 2 × read failed
        ▼ Failed call 1 — read
            filePath: src/example-a.py
            Reason: File not found
        ▶ Failed call 2 — read
    1 × shell cancelled

▼ Skills: 2 skills
    my-skill
    other-skill

▼ Running: shell 3m12s
    command:
    python build.py --check
    cwd: project
~~~

- **Depth 0:** Tool Calls / Skills / Running summary rows. **Depth 1:** their entire expanded contents, including all tool counts, skill rows, failed/cancelled groups, running command + qualification, and nested running-job summaries where present. **Depth 2:** each failed call under its red `N × tool failed` group. **Depth 3** (if separate nested command pane is needed): the source-backed command/arguments/error detail opened for that one failed call. Make the hierarchy visually unmistakable but modest in width.
- Preserve running yellow and failure/cancellation red highlighting; normal activity remains its existing color, command detail remains readable monospace/selectable. Use semantic native `details/summary` and existing text-safe construction; no decorative detached arrow, over-wide gutter, nested scrollbar trap or unnecessary new hover/popover.
- Make indentation robust for narrow phone-size Web, long paths/commands, responsive layout, Classic/Web light/Web dark themes, zoom, keyboard focus, touch and assistive-tech navigation. Use inline-start logical spacing so RTL/multilingual layout doesn't need browser hardcoding. Avoid double indenting an existing multi-job level.

## C. UI/data feature: expand each actually failed physical tool call

1. **Aggregate stays the first level:** retain existing red rows under Tool Calls, e.g. `2 × read failed`, and the existing combined compact `N failed / cancelled` summary. A failed/cancelled physical call still counts in the ordinary `read`/other tool total; expanding does not alter any counts, classifications, Skills totals, CCost or session status.
2. **The red failed group is now expandable if there are evidenced members.** Inside it list **every separate physical failed call supported by the observation** as a separate, keyboard/touch-accessible disclosure: `Failed call 1 — read`, `Failed call 2 — read`. Opening one reveals its own bounded, sanitized **actual recorded invocation**: file path for `read`, pattern/path for `grep`, original command/workdir/selected flags for `shell`, or applicable allowlisted fields for other tools. Stable ordering based on original physical-call start/order and stable identity, **not** tool names/identical arguments; duplicate calls must both appear.
3. **Reason where trustworthy:** show a short source-backed reason/status/error category when safely available (e.g. confirmed missing file or permission denial); **do not** dump untrusted native `state.output`, stack traces, environment/credentials, full file contents or arbitrary error payloads. If no safe exact failure explanation was recorded, show the invocation plus `Failure reason unavailable` rather than inventing a reason. Distinguish **failed** from **cancelled**, not conflating interrupted calls with errors. Cancellation may retain its current group text; if expandable cancellation detail is provided for symmetry, it must use the same evidence/privacy rules.
4. **Privacy boundary is mandatory:** extend `src/watch/invocation.py` or a narrowly shared redaction/formatted-input helper as needed, **reusing the existing allowlist and `invocation_redaction`**. Source-captured input may be sensitive; redact/withhold precisely, cap text and number of exported records, and explain omitted fields conservatively. Never expose raw command output, authentication headers/tokens, environment mappings, prompt bodies, user files, large nested objects, private account identities or full session histories. No new on-hover/read-on-open native fetch; data must be a bounded allowlisted part of the existing Live publication.
5. **Bounded large failure populations:** a tool can fail dozens or hundreds of times. Render a bounded reasonable number of individual details per group (e.g. first 10–20 or another justified limit), preserving deterministic source order and a clear `+N additional failed calls not shown` note. The **aggregate count must always include all proven failures**; no false claim that hidden calls were absent. If only some call identities/inputs are recoverable, indicate the unknown count, without inventing names/arguments. Bounded omission of display details is not data-loss in counts.
6. **Stable nested state across Live updates:** expanding Tool Calls → `2 × read failed` → `Failed call 2` must not snap closed when another tool count increments, other failures arrive, the same failed call obtains a corrected safe reason, a Running timer advances or Live publishes an unchanged list. Key outcome groups and individual child disclosures by their actual identity, maintaining focus, text selection and scroll. When a physical call is removed/corrected to success or the prompt is no longer eligible to show its activity, remove/close only relevant no-longer-valid detail; don't show ghost failures.
7. **Terminal retention:** respect the existing brief completed/error/aborted prompt activity retention semantics: if the latest prompt transitions to a terminal highlight with its proven failed tool calls, they can remain inspectable while that activity card is legitimately retained, then disappear with it. Do not open earlier sessions' unrelated/old tool trees or extend the terminal grace just to support details.

## Required diagnosis and acceptance tests

**First establish causality**, preferably with a synthetic source-shaped reproduction rather than inferring everything from the owner report. The same running physical call must survive a sequence of authoritative observations with the **same identity and original start**, a changed **revision** due to `updated_at_ms`, corrected/redacted input or qualification, and a timer that continues increasing. Show the old code closes its disclosure, then demonstrate the fix preserves its chosen state. This should cover single foreground, background and multi-job contexts. If real installed evidence is permitted, a bounded **read-only** observation can supplement it; do not claim the owner's intermittent exact case was reproduced unless it actually was.

**Behavior matrix:**

- Same physical running call, only clock advances: open stays open; user-closed stays closed.
- Same physical call and same elapsed origin but revision/input/qualification changes: updated safe text, disclosure stays in user's chosen state. Test with and without current keyboard focus/selection.
- New call with **exactly the same tool kind and command/arguments**: new physical identity, prior detail not reused, no inherited expanded state, genuine new duration. Two concurrent identical commands remain separate.
- Call ends (completed/failed/cancelled) or source ownership becomes unverified: old running content immediately cleared; no stale code/secret exposure. New prompt, source generation/epoch, disconnected/retained evidence, failed acquisition and later verified resumption are bounded and truthful.
- Parallel tools/jobs, 1→2→1, reordering, sibling completion and revision changes: surviving per-call disclosure state stays stable, obsolete members removed, bounded jobs/provenance valid.
- Tool Calls / Skills / foreground Running / background Running all display **indented entire expanded content** at the correct depth. Failed subgroup and its separately expanded calls show another obvious indentation level without clipping at 360px.
- `2 × read failed` with different files: two unique failures and their **correct separate paths**; same paths on two distinct callIDs still two entries. A failed shell with a safe command shows command/workdir; a failed call with no safe input says details unavailable. Literal malicious HTML appears as text, never DOM; fake `error` in plain output is not an observed failure.
- Failed+cancelled mixed, same tool name, copied callID revisions, an authoritative correction from error→completed, directly evidenced skill script failure, nested subagent tools in the owning prompt scope, partial and missing evidence, bounded large groups and no double-counting: all summary/outcome totals stay exact.
- Rendered browser checks: native details with pointer, Enter/Space, touch, Escape where applicable, selected command text, focus and scroll retention under repeated Live publications, narrow/desktop/zoom and each theme. Verify individual failed-call details are source-owned, privacy-filtered and have no on-open network/side effects; no persistent per-call ledger.

**Non-goals:** no new OpenCode tool command execution, no raw native output/error dumping, no source mutation, no expanded Mini/CLI UI, no new model calls, no CCost or subagent accounting change, no unbounded session acquisition or ad-hoc browser state cache, no automatic forced-open disclosure after user closes it.
