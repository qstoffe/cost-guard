# FR 000579 — Mini Watch: make Web theme visually consistent with Web Beta

## Owner request and backlog decision

**Owner-approved executable feature request, 2026-11-04.** Permanent identity **000579**; Ready priority **000190**, after FR000578 (000180). This is a targeted **Cost Guard Web Beta → Mini Watch** presentation/theme improvement. This FR is for backlog authoring only; do not implement it while creating the request.

Under **Settings → Web settings → Theme**, choosing **Web** makes the main Web Beta interface use the intended Web appearance, but the owner observes that **Mini Watch remains predominantly dark / Classic-looking**, although some elements change. Mini should feel like a compact extension of the selected Web theme rather than a mostly Classic-looking second window.

**Preserve today's Classic/default dark Mini Watch exactly as it is.** Only the appearance when the effective Theme is **Web** needs design work. The product's shipped default is currently **Classic**; this request does not change that default, introduce another theme choice, or reinterpret FR000576's Default-versus-explicit setting inheritance.

## Desired outcome

1. **Web mode = coherent Web-styled Mini:** When the main Web Beta uses effective Theme **Web**, Mini Watch should use a deliberately styled, cohesive **Web presentation**. In particular its **page/window content background** must not keep the current Classic-looking dark appearance when the main Web is in light appearance. Use Web's color system, surface separation, borders, typography/contrast and restrained visual accents rather than Classic's charcoal background and CLI-inspired palette.
2. **Respect Web light AND dark:** Web currently follows the system light/dark preference. The Mini Web presentation must match the **effective appearance of the owning Web page**, not blindly force light or dark and not fall back to Classic colors in Web dark mode. Thus: main Web light → Mini Web light; main Web dark → Mini Web dark, with the *Web* palette, not Classic. If PiP and owner document resolve media queries or CSS variables differently, reconcile the effective palette/appearance reliably without changing Web's documented system-theme semantics.
3. **Style the whole Mini, not just a few accents:** Review the content canvas/background; header/return action, Earlier Sessions disclosure and CCost Today; running and Earlier Sessions tables (headers, rows, separators and sticky headers); session state colors; subscription names/percentages and quota progress bars; empty/loading/unavailable states; focus/hover affordances, accessible popover/help surfaces, warnings and scrollbar readability. All should use the appropriate Web theme semantic roles with adequate text and focus contrast. Do **not** turn Mini into a large full-Web dashboard: keep its existing compact, lightweight presentation.
4. **Classic regression boundary:** Effective **Classic** (including **Default (Classic)**) must retain its **existing dark Mini appearance, colors, dimensions, status semantics and compact design**. No visual restyle of Classic is requested, and no new Classic-versus-Web toggle inside Mini.
5. **Live inheritance:** Mini should pick up the effective selected theme **on opening** and **when the Web Settings theme changes while Mini is already open**, without requiring closing/reopening PiP, restarting the server, a report refresh, an additional live data stream or browser-local preference storage. Switching Web → Classic → Web must restore the corresponding appearances, including background and overlays, not just text accents.

## Implementation investigation

The current Mini is a separate Document Picture-in-Picture document. It loads shared `src/web/assets/app.css` plus `src/web/assets/mini.css`; `src/web/assets/mini.js` currently mirrors the owner's `document.documentElement.dataset.theme` during rendering. The shared CSS contains Web light/dark variable sets under `prefers-color-scheme` and a separate forced-dark `[data-theme="classic"]` palette. **These source facts do not explain or disprove the reported runtime mismatch by themselves.**

Before designing the fix, reproduce the user's actual symptom with **Web/light** selected in a supported desktop browser: inspect both documents' effective `data-theme`, `prefers-color-scheme`, computed background/text/surface tokens and applied Mini CSS; compare Web dark and Classic. Determine whether the issue is PiP's isolated document/media query behavior, theme propagation timing, a Mini-specific surface/layout choice, or a combination. Fix the owner-visible discrepancy rather than assuming that copying a theme attribute guarantees visual consistency. Avoid brittle duplicated hardcoded palettes if existing semantic tokens can be reused; scoped Mini Web-only overrides are acceptable when genuinely needed.

The browser owns native PiP frame/chrome and its controls; only style the **app-controlled document/content**. Do not promise to recolor browser-native controls.

## Compatibility and acceptance

1. With **Theme = Web**, system **light** appearance, and a light-looking main Web page, an open Mini Watch has a visibly Web-consistent **light content background** and coordinated surfaces, tables, headers, text, separators, controls, tooltips and quota bars. It no longer appears predominantly Classic-dark.
2. With **Theme = Web** and system **dark**, both main Web and Mini use the corresponding **Web dark** design with readable contrast, not Classic styling. OS/browser appearance changes while Mini remains open are reflected coherently where the browser supports live updates.
3. With **Theme = Classic** or current **Default (Classic)**, verify the **pre-change dark Mini presentation remains unchanged** (including opening and dynamic theme switching). Existing explicit settings retain their saved meaning; a future shipped default is resolved by the existing settings contract, not hardcoded here.
4. Changing Theme in an already-open Mini transitions both directions promptly and completely; a fresh Mini opens in the effective theme without a flash of incorrect dark/Classic styling that persists into interaction. Main Web remains visually correct and unaffected by Mini-specific adjustments.
5. Verify at the existing compact **560×250 DIP** standard opening and at manually narrowed/resized windows: no added overflow, lost table headings, clipped costs, contrast regressions or broken Earlier Sessions disclosure/sticky table/independent quota scroll. Preserve keyboard focus and readable popovers in both themes.
6. Preserve all metrics, CCost pricing/currency, prompt/session history and status semantics, alerts, quota Used/Remaining orientation, accessibility, single shared live/SSE owner, source acquisition, security/CSP, navigation and native PiP lifecycle. Coordinate with **FR000578** so its combined Session / Total CCost first-column layout is themed correctly without undoing its pipe alignment.
7. Use targeted DOM/browser visual/computed-style checks for **Classic**, **Web light**, **Web dark**, already-open theme switching and normal/narrow Mini. Update `docs/web-mini-watch.md` and relevant Web-theme docs after implementation to describe the actual supported appearance, and distinguish native browser chrome from application content.

**Out of scope:** changing shipped default Theme from Classic, recoloring the main Web application as a broader redesign, adding theme settings, forcing Web light against system dark preference, changing full Watch/CLI, window geometry or placement, and implementing the feature in this FR-authoring session.
