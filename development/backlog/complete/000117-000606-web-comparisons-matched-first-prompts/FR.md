# FR 000606 — Web Comparisons: repeat first-prompt runs, cost and duration

**Owner-approved Ready Feature Request, 2026-11-06.** Permanent identity **000606**, Ready queue priority **000240**, after the current last Ready item FR000605 (000230) and after AI Stats FR000599 (000210). This is **backlog authoring only**: do not implement the product, modify FR000599, change tests/docs/source, or bump release/version during publication.

## Goal and why

Restore a modern Web equivalent of Cost Guard's removed legacy CLI **same-prompt comparisons**. Compare **independent top-level sessions whose first actual user input is exactly the same**, from the start of that first prompt through its final completed response, including causally attributed tool and child-agent work. Unlike the current Models **Relative CCost** (one synthetic pooled token mix, not matched tasks), these are **observed individual runs**. The main use is to see both cross-model differences and natural variance among **repeated executions by the very same model/effort**. Do not collapse three repetitions of the same model into one averaged row.

Legacy clues, not live implementation: `matchedModelComparisons.enabled` is an accepted no-op in `src/config.py` and `config/default-config.jsonc`; `samePromptComparison` legacy colors survive. The original terminal tables were removed in v78; recreate the behavior using current source-neutral analysis rather than restoring old CLI display code.

## 1. New Web page and layout

- Add a main Web navigation item **Comparisons** and dedicated browser route **/#/comparisons**. Keep Models, Watch, Sessions, Accounts, Token Mix, planned AI Stats and Settings intact; no Mini Watch or CLI redesign.
- Show **up to ten comparison groups per page**, each **unframed and unindented**, directly in normal document flow: a concise heading, a Watch-style table of individual runs, a small strip of useful comparison fun facts **under that table**, then a restrained divider/spacing before the next group. **Do not put all ten groups in a visible boxed parent panel, nested accordion, giant card, or tabbed container.** Groups remain visible without expansion.
- The heading uses a human-readable **session title from the group's most-recently-active member** (the first row by group recency), plus a compact first-prompt preview and the count of matched sessions. This is a display label, **not** the match key. If the title is missing, use an honest generic prompt/session label; handle extremely long/private-looking input safely with truncation/escaping and accessible full text where appropriate. No prompt/hash identifier in navigation URLs.
- Use the same coherent **Web Watch table language**: headings, row density, alignment, numeric styles, semantic colors, small help on text/value targets, responsive focus/keyboard support, horizontal overflow on narrow screens, accessible table headers and links. Tailor columns to this page; do not clone Watch's running-only layout.
- At the bottom show **Previous / Next pagination** for ten **comparison groups**, not ten individual runs. Show useful page/total information if known. An individual group can contain *any number of distinct session runs*; do not silently truncate repeated runs. Keep row rendering efficient for large groups.
- Group order is **descending by the newest supported session activity timestamp among its member sessions**, not by the oldest member's first prompt, group creation, alphabetic title or fastest run. Within a group list individual session runs newest-activity-first, with deterministic tie-breaking. If a new session repeats an old prompt or a grouped session gains real new activity, its group moves upward, including back onto page 1. Reconcile paging after a refreshed order without duplicate/skipped groups or falsely stable page counts.
- Only display a group when **at least two distinct root sessions** share the verified same first input. A single session containing repeated prompts is not a match. Show a friendly genuine no-matches state when a complete scan found none; distinguish loading/partial/unavailable rather than claiming none.

## 2. Exact match identity and comparison boundaries

- Identify the **first real user prompt** of each top-level/root session from the source-normalized message/part stream. Exclude synthetic continuations, compaction summaries, background notifications, tool-only messages and child-agent sessions as independent candidates. Use a deterministic, versioned **exact input fingerprint** made from the **complete original first user message's ordered semantic input parts**, not from session title, model/effort, a 120-character preview, normalized whitespace, a reused prompt/message ID or a truncated first-prompt display token.
- **Exact really means exact**: case, whitespace and part ordering must not be flattened into near matches. Identical text with genuinely different attachments is *not* an exact match. File name/MIME/path/URL alone cannot prove identical attachment content. Where binary/file/content evidence is unavailable or identity cannot be verified, do not present the pair as a proven exact match; safely exclude or clearly classify it outside exact comparisons. Never read arbitrary referenced filesystem paths, fetch attachment URLs or store raw private payloads merely to manufacture a match.
- The **model, provider, effort/variant, runtime, date, output and tools used** are *not* part of the input match key: they are the measured or explanatory differences. Allow three or more rows with identical provider+model+effort; no merging, deduplication or averaging of separate root sessions.
- The measured work is **only the first prompt's causal execution**, including any attributed calls, tools, linked subagents, background continuations and their costs, until the supported **final response/terminal boundary** for that prompt. Do **not** take whole-session CCost/duration, later prompts, later context, idle session age, or only time-to-first-token. Use canonical prompt attribution, unique physical request valuation, terminal evidence and qualified elapsed duration. A model switch/effort change *during* that first prompt must be represented honestly (e.g. mixed marker/help), not falsely reported as one model's solo work.
- Only complete, reliably bounded first-prompt runs participate in fastest/slowest or cost-ratio conclusions. Unfinished, failed/aborted, unknown-end or partially priced runs may be displayed **with explicit status, unavailable/partial marks and appropriate help**, but not silently treated as successful comparable timings/costs. No division by zero, guessed finish, fabricated precision or misleading zero=free.
- Matching user input alone **does not prove identical execution context**: repository state, files, system instructions, available tools, environment and remote model service may differ across days. The page compares *observed runs sharing exactly the first user input*; never claim controlled scientific benchmarks, comparable answer quality or that one model is intrinsically superior.

## 3. Run table columns and Watch-like explanations

Suggested visible column order (use readable compact labels): **Session | Started | Model | Effort | CCost | Duration | Context | Token Mix | Calls**.

- **Session:** one row per individual root session, with its existing human-readable session name as a link to the canonical Web Sessions detail `/#/sessions/<session-id>`. A row for each repeat, including same-model repeats. No artificial "A/B average" row replacing the actual runs.
- **Started:** actual configured-local date/time when its *first* prompt started (24h), not session's later last-activity clock; hover/focus gives precise first-prompt start and, when supported, final completion and offset. **Duration** is the execution interval from first prompt start to final finished answer including caused work, not session lifetime. Group ordering independently uses **latest session activity** as specified above.
- **Model** and **Effort:** first prompt's actual selected/main provider-qualified model and effort where supported. Reveal real mixed-model/variant work and unavailable effort instead of inventing a single attribution. Details can show provider and other genuinely contributing models.
- **CCost:** canonical **first-prompt reference cost** (current Credits/USD preference), including linked subagents, tool-initiated model calls and complete attributable work, **not full-session cost or actual bill**. Reuse Watch's cost breakdown/help presentation where useful: main vs linked-subagent/child cost, I + E, contributing provider/model/effort groups and completeness/estimate status **only when backed by current canonical evidence**. Never count duplicated calls twice or hide unknown prices behind a confident sum. Keep amounts stable and right-aligned; do not launch backend scans on mouse hover.
- **Context:** approximate **context remaining/next valid incoming-context estimate immediately after this first prompt completed**, scoped historically to that prompt, **not** current/final context after later session prompts. Display the short heading exactly **Context**, and explain estimate, units/meaning, historical validity and unknown state in a tooltip. Do not borrow a future prompt's current context to fill a missing historical value.
- **Token Mix:** existing first-prompt I/C/W/O token-category percentages (incoming/cache-read/cache-write/output), across its **attributed** model requests, with a compact `I/C/W/O` value. The tooltip explains fractions and supports the underlying token totals/completeness; percentages are usage composition, **not** CCost distribution. Keep shared accounting/missing-data rules.
- **Calls:** count canonical attributable physical model requests for the first prompt, with meaningful hover/focus information about linked child/subagent/tool work or errors where evidence exists. Do not expose private logs or misleading tool-call totals.
- Use the same shared `ContextHelp` hover/focus/touch semantics as Watch: concise, specific column-header explanations and **richer per-value help for cost/Context/Token Mix/Calls/model provenance**. No blanket identical tooltip on every cell, browser-native title duplication, extra always-visible paragraphs or revaluation in JS. Unknown/partial data must remain truthful without hovering.

## 4. Per-comparison fun facts immediately below each table

Show a **small, quiet inline strip** with the most informative values supported by this group, e.g.:

- **Largest time gap:** fastest vs slowest qualifying first-prompt runs, difference and ratio (e.g. 3.6×), with recognizable model/session labels or linked source rows.
- **Largest CCost gap:** cheapest vs most expensive **fully priceable** first-prompt runs, difference and ratio, using unrounded values for arithmetic.
- **Same-model variation:** if at least two matched runs share the same provider/model/effort, show their observed minimum/maximum duration and/or CCost spread, including the repetition count. Do not require different models for this metric.

Use a few unobtrusive stat snippets, not a large bordered dashboard or distracting banners. Omit or mark an unsupported metric instead of inventing comparisons; clarify sample sizes and mixed-model/incomplete cases through local help. These are per-group observations, not a global model leaderboard or answer-quality score.

## 5. Loading, automatic freshness, history and performance

- A first visit to Comparisons automatically starts an **explicitly finite, read-only, cancellable** history match/analysis acquisition with honest progress and states. Scan **all available recorded root history**, including eligible archived sessions, so a repeat of an old prompt can join that historical group; do not silently constrain it to the last 30 days or the first 100 sampled prompts. Deleted/unavailable history cannot be recovered. Source/catalog revisions and missing segments must be handled without inventing complete coverage.
- Match detection may be expensive, so reuse **existing source-neutral analyzed root bundles, source revisions, valuation, derived caches and bounded acquisition/batch facilities** where sound; build a compact safe **revision-aware match index** if appropriate. Persist only minimal private scoped fingerprints/derived stats, not raw prompt text, untrusted attachment bodies or unrestricted payloads. Avoid O(N²) comparisons by indexing fingerprints, and avoid rehydrating every old stable session on each refresh. Correctly invalidate affected groups on changed source/tree/pricing/identity rules, including repeated first prompts arriving late and later activity changing group recency.
- **While Comparisons is the active *visible* browser route**, aim for **approximately one low-priority cache-first freshness check every five minutes**. Coalesce work with any already running acquisition; apply coherent refreshed ordering/stats without flicker, focus loss or a storm of duplicate cross-tab jobs. This is not a five-minute unconditional full-history scan.
- **When the route is inactive, hidden, or the host is offline, do not start periodic Comparisons refresh work.** A single already-started finite request may finish/cancel under established job lifecycle; leaving the page must not keep an unseen polling loop alive. Re-entering should reuse a genuinely fresh retained result and check stale/changed evidence according to current Web behavior, never treat a mere page visit as successful observation. Protect normal Watch/live, account/price requests and native session-detail responsiveness from the expensive scan.
- Preserve secure local Web session/CSRF/source boundaries, cancellation, native V1/V2 evidence parity, bounded memory, accessibility and existing route navigation/Back/Forward behavior. No model inference, provider paid calls, code execution, OpenCode writes or new network dependencies.
