# FR 000674 — Sessions: fix indefinitely stuck “Waiting for session source” at 0%

**Owner-approved priority Web reliability bugfix, 2026-11-10.** Permanent identity **000674**, Ready priority **001065** (ahead of minor Ready FR000672 and mixed-scope FR000673 because some Sessions detail pages become unusable). **FR-only publication:** create this new FR and atomically advance `development/backlog/identity-state.json` highWatermark **673 → 674** on `main`. Do not implement product code, run tests, change versions/releases or alter existing backlog files in this publication.

## Problem: persistent reproducible-to-owner usability failure, not merely an unattractive loader

In **Cost Guard Web v81.21**, selecting **some Sessions** opens the standard centered progress bar, which **remains at 0% with the text “Waiting for session source…” indefinitely** (rather than loading a session detail). The owner confirms the problem *still occurs* after the delivered progress redesign. No session table, meaningful progress, explanation or recovery appears for those sessions. Other sessions may load.

**Expected:** An eligible selected session starts loading promptly; the UI shows true source-backed work phases and progress when measurable, and a qualified, complete session detail eventually renders. **No selected session may sit indefinitely in an undiagnosed 0% state.** If source acquisition cannot complete, expose a meaningful typed failed/waiting/retry state with a cause and a safe recovery path instead of leaving a passive eternal bar. Genuine slow but advancing work must not be interrupted merely by a simplistic wall-clock timeout.

**Keep this distinct from the earlier FRs:**

- **Completed FR000662** (v81.12) introduced the centered determinate bar with real **0–95% during browser history transfer**, 100% only after DOM application. Its own completion record expressly says: **“No source API, acquisition, export, pricing, other report-loader behavior or polling change.”** It intentionally leaves unknown pre-publication source waits at 0%, which cannot fix indefinite source acquisition.
- **FR000673 is currently still READY, not completed in v81.21.** Its part B asks for better *initial pending state information and 5-second polling responsiveness*; part A covers unrelated Claude Pro subscription CCost. **This new FR000674 is a distinct, higher-priority correctness/liveness investigation of session-specific waits that never terminate.** Implementers should coordinate: reuse any improvements in FR000673(B), do not copy conflicting controllers, and do not conflate closure of the Claude attribution half with proof that indefinitely stuck Sessions are fixed. FR000673(B)'s shorter pending polling alone is not sufficient acceptance for FR000674.
- The owner has not supplied an affected session ID or a sanitized trace. The exact hang cause is **not yet confirmed**. The failure report, version and screen behavior above are owner observations; candidate code seams below are source inspection, not proof of the specific failed session.

## Relevant code as shipped in v81.21

1. `src/web/assets/session.js::SessionDetail.View.poll()` polls a visible route **every 5000ms**; `load()` performs `/api/detail open → begin`. A response with `result: null` is treated as `Waiting for session source…`; `loading()` keeps a 0% value until a revision-qualified result and browser chunk count appear. There is **no per-session source acquisition watchdog** in that frontend pending loop.
2. `src/application/session_detail.py::SessionDetails.open()` creates a lease and an entry `state="loading", result=None, due=0`. `page(..., begin=True)` returns `{state,pending,result:None}` until validated content is available; **no backend phase, last attempt/error, queued/in-flight/failed status, measurable root/row work or progress revision** is returned. `SessionDetails.tick()` picks active leased sessions and attempts `SessionHistory.acquire()`, normally scheduling another try after 5 seconds. It catches `SourceError` and `PricingUnavailableError` but has no source-status detail in this API. Investigate whether an entry is never admitted, repeatedly fails/churns, or spends unbounded time in source hydration/analysis.
3. `src/watch/web_coordinator.py::WebWatchCoordinator.tick_details()` owns a **single worker** (`detail_pool max_workers=1`); while `detail_job` is unfinished, **no next capture is submitted**. It calls `_detail_capture`, which invokes `details.tick()` through an isolated read service. Examine single-worker starvation, a blocked read, unexpected future exceptions, retry policy and whether the route's requested session is ever selected. The HTML/browser/HTTP layer must not turn into a second source-acquisition owner.
4. `src/reports/session_history.py::SessionHistory.acquire()` must obtain the actual root, revision, source snapshot, analysis and complete session result before the first `begin` returns visible rows. Sessions with **large histories, running/churning revisions, incomplete/partial data, archived roots, plugin/tool events or deep subagents** may have different acquisition profiles. Avoid assuming every missing result is the same "waiting for source" reason.
5. Existing FR000662 tests established real chunk counts and render correctness **after source capture**; they did not establish a bounded outcome for every cold/unstable/unavailable root. The 5-second browser poll can delay observation of success, but **faster polling cannot by itself repair missing/blocked source progress**.

## Required engineering changes

### 1. Find and reproduce the true liveness problem

- Trace a stalled detail request **end to end**: session selection, source instance/generation/revision, lease/token and last touch, `open`, `begin` repeated status, `SessionDetails` candidate eligibility/due order, worker job lifetime, `SessionHistory.acquire` stages, source read/retry outcome, validated publication and browser consumption. Identify **the actual branch where the selected session stops making forward progress**, including cases where a worker is busy with another session or continually re-reading changing material.
- Add **bounded, privacy-safe diagnostics**: state/phase, monotonic attempt/change ages, progress counts when supported, typed failure reason and retry counts; session identity may be a correlation token or locally hashed opaque ID, not public raw IDs, paths or transcripts. Do not log prompt text, credentials or raw source responses. Establish cause by evidence, do not simply reclassify every 0% as a network issue.
- Reproduce **a truly indefinite/persistently pending session**, not only one normal 5-second wait. Build controlled V1/V2 read-only fixture cases with an older/archived root, a large prompt/subagent tree, live writes/revision churn, intermittent source failures, a permanently blocked/stalled read, competing detail leases and a vanished/missing root. Include a normal fast/warm control. If real installation is available, permit read-only bounded verification of session detail with no model inference or shared-service stop; document limits without leaking private history.

### 2. A finite outcome for failure, continued work for healthy acquisition

- **No infinite silent pending state.** Distinguish `queued`, `reading`, `verifying`, `analyzing`, `publishing`, `waiting/retrying`, `failed` and `ready` where actually observable. Track forward progress per request/source generation so repeated identical `loading` responses are not mistaken for health.
- Provide **bounded, source-appropriate liveness/failure handling** for genuinely blocked or repeatedly unsuccessful acquisition. Preserve existing source I/O deadlines and cancellation; add local retry/backoff, admitted-work detection, no-forward-progress safeguards or work-lease recovery **only where evidence justifies them**. Do not choose an arbitrary short total wall-clock cutoff for a huge *advancing* session. A hard failure must be typed, user-visible and actionable; never pretend it acquired an empty session.
- **Do not let one poisoned/slow session monopolize the single detail lane indefinitely** or break Full Watch, Sessions catalog, quota acquisition, other session details or normal source shutdown. Use the established bounded ownership model, isolate/cancel/retire stuck work safely if supported and ensure stale/late worker outcomes cannot overwrite a newer attempt. Avoid an unbounded thread/process per clicked session and don't kill existing OpenCode/Claude service or user sessions.
- If the source is temporarily unavailable, show a distinct truthful waiting/recovery state and give **Retry** / other applicable action when retries are exhausted; permit return to Sessions at all times. Define what Retry does (fresh eligible attempt/lease) without corrupting a previously valid snapshot. Missing, archived, source-changed or permanently unreadable cases must report an accurate outcome and not stay 0% forever.

### 3. Source-backed progress rather than a frozen generic phrase

- During source work, show the real phase and **measured work units** when the existing source boundary can supply them (verified request/row/page counts, catalog or snapshot work, analyzed blocks, etc.). Do not use generic server clock ticks, source hints or `completed_at` timestamps as invented fractions. If the operation is initially opaque, the bar can truthfully remain 0% **temporarily**, but the **current phase and last verified progress/attempt** must be intelligible; a permanent opaque wait with no error is not acceptable.
- Keep FR000662's coherent **0–95% browser transfer / 100% after DOM application** while making room for any new proven acquisition phase (adjust overall phase budgeting explicitly if needed, never make progress falsely reach 95% before data exists). Use a stable DOM bar, no marquee or fake percent, accessible status text and no excessive flicker.
- Reduce unnecessary delayed completion from the existing visible **5-second polling loop** using a source-ready event/wake or bounded short pending status reads; normal/hidden/success cadence remains responsible and HTTP requests read only detached immutable state. Avoid repeated unbounded reads while awaiting a blocked source.
- On a transient failure followed by a corrected/available source, resume safely from valid snapshots/caches where possible. No duplicated rows, incorrect stale-model/price totals, wrong request/session/epoch, invalid progress 100% or unauthorized data.

## Mandatory regression and acceptance

1. **Owner symptom:** a cold eligible session that previously remains `Waiting for session source… 0%` for repeated visible polls must now (a) finish with correct table and genuine staged progress, or (b) reach a **specific actionable failure/retry state** when no source-backed forward progress is possible. Repeated identical uninformative 0% for an indefinite interval is an explicit test failure.
2. **Worker liveness:** one deliberately blocked or failing root, with another healthy root enqueued, cannot starve every other detail forever; the healthy root must eventually become usable under bounded resources. Repeat with rapid route swaps/Cancel/Retry and late old-worker completions; no wrong session shown, no orphaned workers.
3. **Long legitimate capture:** 1000+/10000+ prompt trees, slow but measurable hydration, active revision churn with useful prior verified data, V1 polling/V2 reads and multiple subagents. Never interrupt healthy real progress merely because elapsed time is long; do not display fabricated percent. Preserve data correctness, partial/retained semantics and accounted token/cost totals.
4. **Errors and recovery:** cover source missing/deleted/archived, unavailable credentials/registration, revision race, repeated transport failures, partial source, terminal unsupported data and host stop/reconnect. Each must show appropriate waiting/error/recovery without permanent `state=loading` and without affecting the host's other pages.
5. **Browser:** actual authenticated WebHost, `/#/sessions/<session_id>`, 360/1366px Classic/Web light/dark, 100–150% zoom, Back/Forward/focus/aria and progress geometry. Verify ready→DOM latency is not artificially extended by 5000ms polling; navigation away retires work and hidden tab work remains bounded. Tests must assert **actual time/state transitions and source read counts**, not just the presence of a prettier progress bar.
6. Extend `development/tests/test_web_session_detail.py`, `development/tests/test_web_live.py`, `development/tests/integration/probe_web_sessions.cjs`, `src/watch/web_coordinator.py`-related tests and the owned fixtures/probes as needed. **Run the full relevant suites and browser-based acceptance at implementation time**; record before/after causality, real versus synthetic evidence, resource costs and limitations in `development/journal/web/session-loading.md` and `docs/web-beta.md`. Do not close as fixed without a test covering the **indefinitely pending** case.

## Coordination and scope

- New FR000674 **owns persistent session-detail loading liveness/correctness**. Existing Ready **FR000673(B)** remains relevant for general initial-loading latency and stage feedback; reuse rather than duplicate its changes, but its completion must not be used as evidence that an indefinite stall is solved. **FR000673(A)**, Claude Pro CCost, is independent and its special authorization for paid Claude Agent model prompts **does not apply to this FR**.
- Keep edits local to session-detail source acquisition/status/progress and minimal UI/host wiring. Preserve source/permission limits, immutable revision-pinned chunks, row/cost calculations, native OpenCode behavior and cancellation/cleanup. No paid inference, account-login changes, source mutation, arbitrary transcript collection, new background daemon or unbounded scan.

**End state:** Cost Guard Web v81.21's indefinitely stuck session-detail symptom is causally explained and fixed: selected sessions either produce source-backed progress and a correct page or give a finite, truthful, recoverable error, rather than remaining forever at `Waiting for session source… 0%`.
