# Claude Code account and reference identity contract

## Summary

v78.25 discovers the CLI-owned Claude account independently of experimental quota collection. OpenCode owns selectable models; pricing owns exact/verified reference identities; shared report/Watch projections need no Claude-specific branches. No Claude credentials are read/copied and current login is not historical account/billing evidence.

## Account and transport

- `accounts/claude_code.py` uses `claude auth status --json` to normalize current login, backend, plan and a hashed source/account identity. First-party `claude.ai` proves subscription semantics; API/external backends do not inherit a Pro plan. Registration alone proves neither login nor plan.
- `accounts/claude_transport.py` invokes only the optional installed official CLI, resolved from PATH. It uses the published Agent SDK's `initialize` and experimental `get_usage` control requests over stream-json. The latter is equivalent to `Query.usage_EXPERIMENTAL_MAY_CHANGE_DO_NOT_RELY_ON_THIS_API_YET({skipBehaviors:true})`, with `skip_behaviors: true` on the wire. It sends no user messages or model prompts. No JS runtime or third-party Python package is needed.
- This is an unstable SDK/CLI control contract, not a guaranteed API. A successful matching control response detects support; explicit unknown-request errors mean unsupported capability. Changed shapes, transport errors and timeout fail softly. Account discovery does not depend on quotas. The helper disables hooks, MCP, Chrome and persistence, uses empty setting sources, closes pipes and reaps its private process after collection. It never stops OpenCode.
- `accountInfo.organization` is an organization **name**, whereas auth status supplies both `orgId` and `orgName`. Match email/name for quota provenance; retain the distinct organization ID for account identity. Do not equate the two fields or expose them in reports/diagnostics.
- Native percentages and timezone-qualified ISO reset times normalize inside the Account Provider. Missing/malformed windows remain partial/unknown; supported model-family and OAuth-app windows keep model/surface scope, without invented request-model IDs. No quota-to-dollar extrapolation or extra-usage billing inference occurs.
- `anthropicQuota.enabled` gates both API and Claude discovery; `authJsonPath` remains API-inventory-only. The shared provider-neutral scheduler owns Watch's 30-second healthy cadence, 20-second attempt deadline and bounded 5/10/20-second transient recovery. Freshness includes acquisition/publication/rendering, not upstream propagation; see [the budget](../../../docs/account-support.md#watch-freshness-budget). Five-minute stale retention is never extended on resume. No helper runs per redraw/source event. Durable auth/capability failure clears stale quotas but preserves the account row. Explicit zero utilization/null reset means `window_active=False`, complete rather than partial.

## Model identities

`sources/model_availability.py` accepts opaque enabled selectable `id` values, including `[1m]`, and rejects controls/bidi/whitespace/malformed contracts. The working registered API never needs model CLI fallback. Empty/disabled-only responses are authoritative; actual failures retain the explicit full-pricing-catalog warning.

`pricing/identities.py` owns reviewed aliases, not generic date/suffix stripping. Haiku 4.5's pinned `20251001` ID maps to its documented base alias. A bounded set of documented Claude versions recognizes `[1m]` as context capacity. Exact catalog variants win before alias resolution; ambiguous matches return unknown. Existing input-token thresholds select long-context rates, not the suffix by itself. Availability/reference valuation never replaces actual billing. Unsupported Fast/other variants still have no guessed price.

## Evidence and limits

### Quota freshness investigation — 2026-10-19 (v80.58)

**Finding:** Cost Guard has no ten-minute Claude quota cache. A fresh CLI response is not proof of fresh Anthropic data. The reported ten-minute 15%→1% jump is consistent with delayed source data, but its exact cause remains unproven. No diagnostics attachment was available with this specification; its times/values are user-reported, not independently inspected ZIP evidence. There was no simultaneous authorized web observation or ten-minute reproduction in this investigation.

Confirmed source trace:

- Every `read_claude_usage()` starts a private CLI process, sends `initialize` then `get_usage` with `skip_behaviors`, parses that request's matching response and closes the helper. No prior response, CLI session or transcript is reused by Cost Guard. Each provider acquisition consumes the pending *auth discovery* at most once, then calls its usage reader again; `_last` retains account identity for discovery failures, not successful quota responses.
- Provenance requires the CLI-initialized account to match discovery email/organization name and first-party backend. Normalization computes remaining as `1 - utilization/100` using Decimal; resets must have a timezone and become UTC milliseconds. The independent Diagnostics report constructs fresh providers and `AccountAcquisition`; it does not acquire from Watch's evidence file or mailbox. Watch acquisition timestamps come from worker completion, not cached projection/publication.
- The scheduler already treats unchanged success as a new observation, without retrying or marking it stale. Credentials/identity changes, late-result rejection, failures, bounded retries and five-minute hard expiry remain independent of value history. Concurrent Watch histories are never combined: the atomic evidence file contains one complete latest writer, now explicitly identified by a random run ID; it is not a record of every running Watch.

Official-source evidence (retrieved 2026-10-19):

1. [Claude `/usage` documentation](https://code.claude.com/docs/en/costs#using-the-usage-command) explicitly describes a machine-local last-known usage snapshot, up to **60 minutes** old, shown when fetching plan limits fails (often rate limiting); behavior is documented from CLI v2.1.208. This confirms CLI-owned persistence can outlive a single process, not a specific ten-minute TTL or proof that `get_usage` used that fallback during the reported incident.
2. The official [Agent SDK 0.3.303 package](https://www.npmjs.com/package/@anthropic-ai/claude-agent-sdk/v/0.3.303), `sdk.mjs`, forwards `usage_EXPERIMENTAL_MAY_CHANGE_DO_NOT_RELY_ON_THIS_API_YET({skipBehaviors:true})` directly to the same `get_usage`/`skip_behaviors` control request; changing SDK wrappers is not an independent data source. `sdk.d.ts` still marks it experimental. Its `SDKControlGetUsageResponse.rate_limits.model_scoped` comment explicitly allows an answer served from cached data; no upstream observation timestamp, age or force-refresh parameter is declared. `skip_behaviors` skips a seven-day transcript scan, not a quota-cache bypass.
3. [SDK changelog](https://github.com/anthropics/claude-agent-sdk-typescript/blob/main/CHANGELOG.md) v0.3.273 introduced structured `SDKUsageReport` on headless `/usage`; v0.3.277 specifies its rows come only from a live server reply and are absent on fetch failure. The [TypeScript reference](https://code.claude.com/docs/en/agent-sdk/typescript#sdkusagereport) and 0.3.303 types describe the same plan-usage endpoint, not an independent backend or an upstream propagation guarantee. It is still experimental, plan/scope-gated, and submitting `/usage` adds command/turn handling and its usage-behavior work rather than the existing metadata-only skip. This is better explicit cache/failure provenance for that command, but not established as a safer, cheaper or fresher replacement for this integration.

**Decision:** Keep the existing metadata-only transport and 30-second cadence. Do not add `/usage` as a duplicate polling/fallback path, upgrade/install the user's CLI, probe private endpoints, read CLI snapshot/auth files, scrape the browser or infer quota consumption. No verified supported method in these sources guarantees a fresher subscription value without those tradeoffs. CLI fallback and backend propagation are plausible delay locations; neither is isolated as the incident's root cause. Even a live server response leaves **upstream freshness unknown** without provider timestamp evidence.

Verification: two independent metadata-only acquisitions against installed Claude CLI **2.1.289** succeeded, each exposing normalized five-hour/weekly windows with **0.700s / 0.669s** provider acquisition (total **0.722s / 0.690s**). They had distinct run IDs and no Watch-publication timestamp. No user/model messages were sent and no raw response/account identity was retained. This establishes current acquisition and isolation, not real-time web parity, a backend update SLA or elimination of the reported delay.

The subsequent real Diagnostics acquisition succeeded alongside OpenAI/Copilot and included the independent history in its UTF-8 ZIP. Its Claude reset timestamps differed from the earlier probe by **24ms** with unchanged percentages. Therefore `value_changed`/change age compare remaining percentages; `reset_changed` separately records exact reset metadata differences without inventing a heuristic cache TTL or repeatedly resetting the percentage-change clock.

A finite **33-second account-only Watch** probe then captured two successful observations per Claude window, **30.083s** between request starts, **0** retries/failures/timeouts, and **0.119s** final completion-to-publication delay. Both percentages stayed unchanged, successful retrieval/publication times advanced, and no first-baseline value-change time was invented. A synthetic worst-case **64 × 64** history exported in **0.803ms** and atomically sanitized/wrote **706,884 bytes** in **13.862ms** before the additive reset-change flag; export happens at the existing five-second evidence cadence/on diagnostics demand, not each 100ms scheduler turn. These are dated workstation measurements, not universal performance guarantees.

`accounts/quota_observations.py` now retains the bounded normalized history in the existing Diagnostics evidence path. [Freshness semantics](../../../docs/account-support.md#watch-freshness-budget) define success vs change age, reset/identity boundaries and first-observation uncertainty. Synthetic regressions capture 21 successful unchanged 30-second polls followed directly by 15%→1%, independent acquisitions, failure/timeout/recovery, bounded/private state and existing retry/stale behavior. The normal Watch display gains no freshness clutter.

Synthetic tests cover parser/control safety, dated/context/explicit-rate identity, tier boundaries, method absence, changed format, timeout/private-helper cleanup, auth failure, missing/scoped windows, account swaps, discovery failure/logout, report/Watch visibility and shared cadence/stale expiry. Neighboring OpenAI/Copilot/API accounts coexist without attribution changes.

Read-only workstation evidence on 2026-10-04 used installed official Agent SDK **0.3.289** types/method and Claude CLI control behavior. The metadata-only probe observed **zero model usage**, Pro, five-hour/weekly utilization and ISO resets, then closed its process. The current OpenCode list had **42 models**, **14 Claude IDs**, **eight `[1m]` IDs**; parsing/filtering succeeded without model CLI fallback. Twelve Claude selectable IDs had reference prices; `claude-opus-4-7` and `claude-opus-4-6[1m]` lacked prices in the current catalog and stayed omitted. Live report/Watch showed Claude Pro/windows; process-local timeout/capability simulations retained stale/account semantics and normal redraw made no quota call. Event-stream hints were disabled for this bounded authoritative-snapshot check; it is not a new SSE/restart/sleep claim.

The user's older external diagnostics/probe paths were absent locally. They were not reconstructed or packaged. Fixtures contain synthetic data only. Live Pro success does not establish every plan/backend/SDK version; unsupported installations must continue to show unavailable quotas safely.
